01

今日命题

会议室预订请求超时，Agent 的 belief 仍同时包含‘已订但回执丢失’和‘请求未提交’。它可以重刷旧页面、按操作 ID 查权威结果、再发一次请求、问用户是否还要订，或交人工。每种动作花费不同，也揭示不同信息；其中有些甚至会产生新副作用。不确定时的下一步不是“再想久一点”，而是选择能改变决策的观察，同时尊重不可越过的授权和提交门。

昨天的 1/2 把 event log、durable memory 与当前 world-state belief 分开，说明动作先产生多种可能，新观察再按来源可靠性校正；工具超时保留 unknown，未校准概率不等于事实。今天完成 Agent World State & Partial Observability 2/2：主动感知、信息价值、停止与升级、澄清/重试/补偿的不同语义，以及如何在风险分层的会话轨迹中验收。不会再推昨天的 Bayes filter，也不重复 9 月工具重试专题的 dedup ledger 实现。

02

从 belief 更新走到选择观察

在普通 agent loop 中，tool result 常像被动送来的下一条消息。部分可观测环境要求 Agent 主动决定看哪里、问谁、查哪个 API，以及何时不再观察。查询不是免费：占用延迟、调用配额、token、隐私预算；刷新页面可能依旧读到缓存，问用户则不能揭示后台事务是否已提交。主动感知的关键是：一个观察是否能区分当前会影响行动的分支，而不是它能返回多少文本。

昨天的状态例子里，若 book 请求可能已提交，最有辨别力的通常是按稳定 operation ID 查询远端终态（前提是 API 支持、调用者获权且结果有明确一致性语义）。另一次 UI 截图只证明当时页面显示什么；即使文字更长，也未必缩小不确定集合。对目标意图不清则相反：后端查询无法回答‘用户要订哪间房’，应向用户澄清并把确认绑定对象、时间和会话。状态未知与意图未知需要不同传感器。

POMDP 形式化让观察动作进入策略；经典论文讨论在部分可观测环境中规划与行动。它不规定某个日历工具的权威来源。ReAct 展示模型交替产生动作与观察的轨迹，但若每次观察都由模型随意挑、又没有权限/成本/终态门，轨迹仍可能在错误状态上越走越远。外层 runtime 要把可用查询、观察质量、风险与截止时间写成合同。

03

机制：查询、澄清、提交与停止的分流

1. 先列出未决问题与可用观察

从 belief 和 typed control state 生成两个清单：未决状态（请求是否提交、房间是否仍空闲）与未决意图（用户究竟要哪个房间/时段）。再列只读观察动作：按 operation ID 查询、查资源当前版本、读回业务对象、查看 UI、向用户澄清。为每项写明数据来源、权限、延迟、费用、缓存/一致性边界和可能返回 unknown。一个查询可能对某分支完全无辨别力；不要因它‘容易调用’就反复调用。

2. 优先查会改变决策的权威证据

若远端可按原 operation ID 返回已提交 outcome，先查它；如果只返回‘请求已接收’，那不是终态。若同时存在资源竞争，查询房间当前版本也有价值，但‘房间已占用’不证明占用者就是本次请求。需要关联 owner、slot、transaction ID 与稳定 key。观察结果要更新 belief 和未决 action ledger，不能只把一段自然语言塞回 prompt。缓存 UI、旧截图或模型自述不应覆盖权威业务结果。

3. 区分澄清、重试与补偿

澄清解决用户意图或参数缺失；它不能替远端确认事务。重试是同一个逻辑操作的新传输 attempt，必须依赖效果拥有方支持幂等/状态查询，或确定原请求未 dispatch；具体 dedup 合同已在 9 月工具专题讲过，这里不重建。补偿是已确认副作用后的新业务操作，需自己的授权、前提与失败处理，不能把‘用户改口’或‘模型觉得应撤回’自动映射为逆向工具。三者在 state machine 中应有不同 action type 和审计字段。

4. 设停止条件，不无限轮询

为每类任务设 deadline、最大只读查询次数、权限边界和能够接受的未知程度。查询连续返回 pending 时，延迟增加不保证信息增加；可按合同等待回调或在期限到达后交人工。低风险只读任务可明确答‘目前无法确认’；高风险状态未知时不得宣称成功、重发新业务操作或执行依赖该状态的下一动作。安全门是硬约束，不能因为概率达到 0.99 就变成有权限。

5. 执行前再次检查当前前提

查到‘尚未预订’不等于现在仍可订。若决定发送新的 booking action，先确认用户目标未变、房间时段当前可用、会话主体获权、旧 operation 不会迟到提交，并尽可能用条件写与稳定幂等键。请求与效果拥有方的事务边界若不支持这些保证，就把残余风险显式交给用户或人工。一个只读 status lookup 的成功不能让外层 broker 省掉执行前授权。

6. 在对照轨迹中验收策略

固定同一真实隐藏状态，分别让 API 正常回执、回执丢失、查询缓存、竞争者抢占、status 永远 pending、用户改口。比较立即猜测、固定轮询与主动查询策略：是否选到首个真正区分分支的观察，是否重复副作用，是否错报成功，是否正确停机或接管，最终任务是否达成，以及延迟与成本。评测需记录每个 observation 的 available_at 和权限，不能把离线事后状态偷偷提供给在线策略。

04

必要数学：信息价值是决策损失的下降

设 belief 为 b，允许的行动集合为 A，状态为 s，行动 a 在状态 s 的损失为 L(a,s)。不再查询时的最小预期损失写成 R(b)=min_{a∈A}Σ_s b(s)L(a,s)。R 是 Bayes risk，不是模型主观‘不确定度’；A 必须先经权限过滤，越权动作不能靠低预测损失混入。对订房任务，错误宣布成功、错误宣布失败、暂停交人工各有不同损失；业务负责人需要明确定义，而非让 LLM 临场编造。

候选只读查询 q 有成本 C(q)，可能返回观察 o 并把 belief 更新为 b_{q,o}。它的决策价值可写成 VOI(q)=R(b)−[C(q)+Σ_o P(o|b,q)R(b_{q,o})]。P(o|b,q) 是在当前 belief 下查询 q 得到 o 的预测分布；中括号是查询成本加查询后仍需承担的最小预期损失。VOI>0 才说明该查询在模型假设下值得做；它不是数据量或 entropy 降幅本身。一个高信息却不会改变任何行动的查询，可能没有业务价值。查询权限、隐私和 deadline 仍是硬约束。

教学例子：超时后对‘已提交’的估计为 0.4，对‘未提交’为 0.6；若不查，最便宜的合规处理是交人工，代价定为 8。假设按 operation ID 的权威查询成本为 2，且总能区分两种终态，仅针对‘旧请求是否提交’这一步，查询后剩余判定损失为 0（后续新预订成本另计），则 VOI=8−(2+0)=6。这组概率与成本纯属说明；现实查询可能只返回 pending、受权限限制，或在延迟后才一致，届时剩余损失大于零。不能因为公式算出正值就跳过工具合同和安全门。

05

对 Agent 架构与验收的影响

runtime 应把‘观察计划’作为受控对象：query type、目标 entity、operation ID、可用身份、预期区分的状态、最大等待、成本上限和停机条件。模型可以提议查询或澄清问题，broker 校验权限、速率、敏感数据范围和是否真的属于只读。查询返回后记录来源、版本、observed_at/available_at 和终态语义，再更新 belief。这样即使模型很会解释，也无法把‘请求已接收’口头升级为‘已预订’。

对 effectful 操作，三条恢复路径必须显式：确认未 dispatch 后可在原授权下发起；已提交则核验并准确回复，若需撤销另走补偿授权；无法判断则暂停并保留 operation ID 供人工或异步回调。不能把用户的澄清答案当远端状态，也不能把远端状态查询当用户意图确认。一个任务可能需要两种不同的观察，且顺序要尊重因果与权限。

上线指标应包括 query 选择的辨别力、无效查询率、未知状态停机正确率、错报成功/失败、重复副作用、人工接管率、权威 verified outcome、p95/p99 终态延迟及每个完成任务成本。对风险较高的动作，安全门单列，不能让总体 success 或平均成本抵消。对照实验要固定隐藏环境与权限，只改变观测策略；否则无法知道提升来自更聪明的查询，还是更容易的样本。评测 trace 应能复现每个决策当时可见的结果，而非事后补全的世界。

06

取舍与失败模式

  • 多查总比少查好：同一缓存反复返回 pending 不缩小 belief，却持续增加延迟与费用。
  • 信息增益最高就先查：若答案不改变可允许行动，entropy 下降也不等于决策价值。
  • 问用户能确认远端提交：用户知道意图，不一定知道事务；分开澄清与状态查询。
  • 超时后立即新建操作：旧请求可能已提交；仅在原请求状态可核对或未 dispatch 有证据时按合同处理。
  • 补偿就是重试的反面：补偿是新的副作用，需新授权、前提和结果核验。
  • 概率足够高即可越权：预测只能在已允许动作中排序，不能扩展 credential scope。
  • 停机就是失败：在未知高风险状态下明确暂停并保留证据，可能优于错报成功或重复执行。

更强的观察能力并非零代价：权限、隐私、延迟、配额和模型上下文都有限。简单工作流可用确定性 status lookup 与固定 stop rule；复杂环境才值得估计 VOI。公式不可靠时，应退回保守的状态机与人工接管，不要用精密数字包装未校准猜测。

07

可复用的技术判断

  • 主动感知问的是‘哪次观察会改变当前行动’，不是‘哪个工具返回更多文字’。
  • 未知世界状态与未知用户意图要用不同查询；澄清不能代替事务回执。
  • VOI 只在校准假设与已授权行动集合内有意义，安全门不参与概率交易。
  • 重试、补偿、暂停和接管是不同状态转移；超时不得自动生成新副作用。
  • 以对照轨迹同时验收辨别力、正确停机、verified outcome、尾延迟与成本。

Agent World State & Partial Observability · Part 2 of 2

When an Agent Is Uncertain, What Should It Check—and When Must It Stop?

Choose the next observation by its decision value, while keeping clarification, retry, compensation, and human handoff at distinct commit boundaries.

2026-11-0220 min readActive sensing / Value of information / Belief state / Uncertain outcomes / Decision policy / Handoff
01

Today's proposition

A room-booking request times out. The agent's belief still contains both 'committed but response lost' and 'never committed.' It could refresh a stale page, query the authoritative result by operation ID, send the request again, ask whether the user still wants the booking, or hand the case to a person. Each choice costs something, reveals different information, and some create new effects. Under uncertainty, the next step is not merely to think longer. It is to choose an observation that can change the decision while respecting non-negotiable authority and commitment gates.

Part 1 separated event log, durable memory, and live world-state belief. Actions branch possible states; observations correct them according to source reliability. Timeout preserves unknown, and an uncalibrated probability is not a fact. This final part covers active sensing, information value, stop and escalation rules, the different meanings of clarification, retry, and compensation, and risk-tiered trajectory evaluation. We do not repeat yesterday's Bayesian filter or the September runtime lesson's dedup-ledger implementation.

02

From belief update to choosing an observation

In a simple agent loop, a tool result looks like the next message arriving passively. A partially observed environment requires a decision about where to look, whom to ask, which API to query, and when to stop observing. Queries are not free: they consume latency, quotas, tokens, and privacy budget. Refreshing a page can return the same cache, while asking a user cannot reveal whether a backend transaction committed. Active sensing asks whether an observation distinguishes branches that change the action, not how much text it returns.

In yesterday's booking example, if commitment is unknown, the most discriminating observation is often a lookup by stable operation ID at the effect owner—if that API exists, the caller is authorized, and its consistency semantics are known. Another screenshot proves only what a page displayed then; even a longer response may not narrow the possible states. If the uncertainty is about the user's intent, the situation reverses. A backend query cannot tell which room the user meant. Clarify with the user and bind the answer to room, time, and session. Unknown world state and unknown intent require different sensors.

The POMDP formalism makes observation actions part of a policy; its classic treatment studies planning and acting under partial observation. It does not specify the authoritative source for a calendar product. ReAct demonstrates trajectories with interleaved model actions and observations. Without authority, cost, and outcome gates, however, free-form selection of observations can still propagate a mistaken state. The outer runtime should contract available queries, observation quality, risk, and deadlines.

03

Mechanism: route queries, clarification, commitment, and stopping

1. Enumerate unresolved questions and available observations

From the belief and typed control state, list unresolved world state (did the request commit, is the room still free?) separately from unresolved user intent (which room and time?). Then list read-only observation actions: lookup by operation ID, fetch the current resource version, read the business object, inspect UI, or ask the user. For each, record source, authority, latency, cost, cache or consistency limits, and possible unknown outcomes. A query may distinguish none of the relevant branches. Do not repeat it merely because it is easy to call.

2. Prefer authoritative evidence that can change a decision

If the effect owner can return a committed outcome by the original operation ID, query it first. A response saying only 'request received' is not a terminal result. With competing bookings, a query for the room's current version can help, but 'occupied' does not prove that our request owns it. Correlate owner, slot, transaction ID, and stable key. Update both the belief and pending-action ledger from a result; do not only append a natural-language paragraph to the prompt. A cached UI, old screenshot, or model narration must not overwrite authoritative business state.

3. Separate clarification, retry, and compensation

Clarification resolves missing user intent or parameters. It does not confirm a remote transaction. Retry is another transmission attempt for the same logical operation and depends on effect-owner idempotency or status lookup, or proof that the original request never dispatched. The September runtime lesson covered the dedup contract; we do not rebuild it here. Compensation is a new business operation after a confirmed effect, with its own authority, preconditions, and failure handling. A user's changed mind or a model's wish to undo something must not automatically invoke a reverse tool. These belong to distinct action types and audit fields in the state machine.

4. Stop rather than poll forever

For each task class, set a deadline, maximum read-only queries, authority boundary, and acceptable uncertainty. Repeated pending responses add latency without necessarily adding information. Wait for a callback when the contract permits, or hand off at the deadline. A low-risk read-only task can say 'I cannot verify it yet.' A high-risk unknown outcome must not be narrated as success, retried as a fresh business operation, or used as the premise for a dependent action. Safety gates are hard constraints; a probability of 0.99 does not grant permission.

5. Recheck current preconditions before execution

'Not booked' from a status lookup does not prove the room is still free now. Before deciding on a new booking action, verify that the user's objective has not changed, the room and slot are currently available, the session principal is authorized, and the old operation cannot later commit. Use conditional writes and a stable idempotency key where the effect owner supports them. If the API cannot provide those guarantees, surface residual risk and hand off as appropriate. A successful read-only lookup never lets the broker skip pre-execution authority.

6. Evaluate against matched trajectories

Hold the same true hidden state fixed while varying normal receipt, lost receipt, cached query, competing booking, indefinitely pending status, and a user correction. Compare immediate guessing, fixed polling, and active-query policies. Did the agent choose the first truly discriminating observation? Did it duplicate an effect, falsely announce success, stop or hand off correctly, achieve the task, and stay within latency and cost bounds? Every observation in the test needs available_at and authority. Offline hindsight must not be smuggled into an online policy.

04

Essential mathematics: information value reduces decision loss

Let b be the belief, A the permitted action set, s a possible state, and L(a,s) the loss from action a in state s. Without another query, the minimum expected loss is R(b)=min_{a∈A}Σ_s b(s)L(a,s). R is Bayes risk, not the model's informal sense of uncertainty. A must first be filtered by authority; an unauthorized action cannot enter because its predicted loss looks small. In the room task, falsely announcing success, falsely announcing failure, and pausing for a human carry different losses. The business owner must specify them instead of asking the LLM to invent them during execution.

A candidate read-only query q has cost C(q), may return observation o, and updates belief to b_{q,o}. Its decision value is VOI(q)=R(b)−[C(q)+Σ_o P(o|b,q)R(b_{q,o})]. P(o|b,q) is the predictive distribution of query outcomes under current belief. The bracket is query cost plus the minimum expected loss that remains afterward. Positive VOI means the query is worth taking under the model assumptions. It is not simply bytes returned or entropy reduced: a highly informative answer that never changes an action can have little business value. Query authority, privacy, and deadline remain hard constraints.

In an illustrative example, a timeout leaves probability 0.4 on committed and 0.6 on not committed. Without a query, suppose the least costly compliant response is human handoff at cost 8. An authoritative operation-ID lookup costs 2 and, in this teaching case, always distinguishes the two terminal states, leaving zero loss for deciding whether the old request committed; any later booking cost is outside this example. Thus VOI=8−(2+0)=6. The probabilities and costs are invented for explanation. A real lookup might return only pending, require permission, or become consistent later, leaving nonzero residual loss. A positive formula result never waives the tool contract or safety gate.

05

Implications for agent architecture and acceptance

The runtime should make an observation plan a controlled object: query type, target entity, operation ID, principal, states it is expected to distinguish, maximum wait, cost cap, and stop condition. The model may propose a query or clarification question. A broker checks authority, rate limits, sensitive-data scope, and whether it is genuinely read-only. On return, store provenance, version, observed_at and available_at, and terminal-state semantics before updating belief. A fluent model cannot narrate 'request accepted' into 'room booked.'

For effectful operations, three recovery paths need explicit representation. If non-dispatch is proven, a new attempt may be initiated under the original authorization. If commitment is confirmed, verify and report it accurately; reversal, if needed, is a separately authorized compensation. If the outcome cannot be established, pause and retain the operation ID for human or asynchronous callback. The user's clarification answer is not remote status, and remote status lookup is not user-intent confirmation. A task may need both observations, ordered by causality and authority.

Production metrics should include query discriminative value, useless-query rate, correct stopping under unknown status, false success and failure claims, duplicate effects, handoff rate, authoritative verified outcomes, p95 and p99 terminal latency, and cost per completed task. Keep safety gates separate for high-risk actions; aggregate success or mean cost cannot offset them. In matched evaluation, hold hidden environment and permissions fixed while varying only the observation policy. Otherwise improvement might come from easier samples rather than smarter queries. A trace must replay what was visible at each decision, not a world completed in hindsight.

06

Trade-offs and failure modes

  • More queries are always better: repeated pending from one cache does not narrow belief, but keeps adding latency and cost.
  • Always query for maximum information gain: reducing entropy has little decision value if no permitted action changes.
  • Ask the user to confirm remote commitment: the user knows intent, not necessarily transaction status. Separate clarification from state lookup.
  • Start a new operation after timeout: the old request may have committed. Follow the contract only after status reconciliation or evidence of non-dispatch.
  • Compensation is the inverse of retry: compensation is a new effect with new authority, preconditions, and outcome checks.
  • High probability permits an unauthorized action: prediction ranks only actions already allowed; it does not expand credential scope.
  • Stopping is failure: explicit pause with evidence under high-risk unknown status can be better than false success or duplicate execution.

Better observation is not free: permissions, privacy, latency, quotas, and context are finite. A simple workflow may use a deterministic status lookup and fixed stop rule. A complex environment may justify VOI estimation. When the model behind the formula is unreliable, fall back to a conservative state machine and human handoff rather than wrap an uncalibrated guess in precise numbers.

07

Reusable technical judgments

  • Active sensing asks which observation changes the decision, not which tool returns more text.
  • Unknown world state and unknown user intent need different queries. Clarification does not replace a transaction receipt.
  • VOI matters only under calibrated assumptions and an authorized action set. Safety gates are not traded probabilistically.
  • Retry, compensation, pause, and handoff are distinct transitions. Timeout must not automatically create a new effect.
  • Matched trajectories should measure discrimination, correct stopping, verified outcomes, tail latency, and cost together.
08

Primary sources and evidence tiers

  • Kaelbling, Littman & Cassandra, Planning and Acting in Partially Observable Stochastic Domains — the original treatment of belief policies under partial observation; business losses and query options here are engineering models.
  • ReAct — the authors study interleaved language-model reasoning, action, and observation; it does not guarantee query authorization or terminal results.
  • DreamerV3 — the authors report a latent world model for diverse decisions, not a license to fill a missing business receipt with prediction.
  • RFC 9110 If-Match — the conditional-request specification can guard version preconditions for a concrete resource; it does not replace cross-resource transactions or idempotency contracts.

09

Series synthesis and the next path

This series is complete: Part 1 separated hidden world, actions, observations, and belief. Actions predict multiple states; observations correct by source reliability. Event log, durable memory, typed control state, and model summary have distinct roles, and timeout preserves unknown. Part 2 chooses active queries over possible states by whether they reduce expected loss for permitted actions. It separates user clarification, remote status lookup, retry of one logical operation, compensation for a committed effect, and stopping or handoff. The full loop is observation and version → belief branching → costly discriminating query → correction or clarification → authority and current preconditions → tool commitment → authoritative terminal state.

Continuing limitation: transition and observation models drift, and a new business API may not expose lookup by operation ID. Uncalibrated VOI is only a design intuition and cannot soften a safety gate. Completing the series does not certify a production deployment.
