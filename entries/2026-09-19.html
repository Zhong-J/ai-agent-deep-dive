Agent Runtime 内核 · 第 4/4 篇

一个跑三天的 Agent，凭什么还能安全地继续？

把 durable timers、signals、审批、workflow versioning、supervision 与 terminal verification 组合成可运营的长运行 control plane。

2026-09-19约 20 分钟Durable execution / Control plane / Workflow versioning / Human approval / Terminal verification
01

今日命题

一个持续三天的 Agent 不是一段运行三天的进程。进程会重启，worker 会滚动升级，凭据会过期，审批可能晚两小时到达，外部系统还会先成功再丢失回执。真正长寿的是一条可重放的 execution record：稳定 workflow identity、持久事件历史、等待条件、未决副作用、策略版本与可验证终态。

长运行 Agent 因而需要 data plane 与 control plane 分离。data plane 执行模型推理和工具调用；control plane 决定何时调度、等待什么、谁能发 signal、哪个代码版本解释旧历史、失败由谁监督，以及何时有足够证据宣布完成。把这些职责留给 prompt，会让 crash recovery、授权与升级语义随模型输出漂移。

核心判断：durability 不是“保存聊天”，而是让每个外部输入和调度决定在崩溃后得到同一解释；completion 也不是“模型说完成”，而是 terminal verifier 对预先声明的 postconditions 产出带 provenance 的证据。
02

把前三篇装进一个 control plane

1/4 把 tool call 拆成 command、attempt、result 与 outcome_unknown；2/4 用 structured concurrency 约束 child tasks、deadline、cancellation 和 backpressure；3/4 用稳定 idempotency key、checkpoint、reconciliation 与 compensation 处理副作用的不确定结果。今天给这些机制一个跨天存在的管理层。

workflowId/runId 是最外层 identity；operationId、callId、attemptId 位于其内。event history 记录 transition 的原因，snapshot 只是恢复加速缓存。timer、signal 和 approval 都追加为带 identity、时间与 schema version 的事件。worker 可以消失，因为新 worker 能从 history 恢复；但 replay 时不能重新读 wall clock、重新调用模型或重做副作用。

03

机制：三条闭环，而不是一条超长 loop

1. 事件溯源 record

command 先通过 admission：验证 tenant、principal、workflow schema、policy version 与唯一 commandId，再 append history。reducer 以 state+event 计算新 state 和待发 commands。snapshot 可缓存第 N 个 event 的状态，但丢失它只能降低速度，不能改变结果。影响控制流的模型输出也保存 model/version、prompt digest 与 response digest。

2. Durable timer

记录 TimerScheduled(timerId, fireAt) 后释放 worker。timer service 到点追加 TimerFired，重复 fire 由 timerId 去重。其语义通常是“不早于 fireAt 被处理”，不是精确时刻执行；拥塞会造成 lateness。业务 deadline、提醒 timer 和授权 expiry 要分开，取消也写事件，不能依赖内存 timeout handle。

3. Signal 与 correlation

callback 规范化为 signal：workflowId、signalId、type、schemaVersion、issuer、payload digest、receivedAt。control plane 认证 issuer、按 signalId 去重，再检查当前 wait set 是否接受该 type。早到 signal 可缓冲；晚到或指向已取消 workflow 的 signal 只能审计，不能复活 execution。用自然语言正文匹配任务会把 correlation 错误变成授权漏洞。

4. Human approval

审批请求冻结 intent digest：工具、目标、关键参数、风险、policy version、有效期和允许变更。approval event 绑定 approver identity、decision、digest 与 timestamp。若金额、收件人、代码 diff 或权限范围 material change，旧 approval 失效；超时走 escalation/reject/pause，绝不能默认批准。

5. Replay 与 versioning

history 包含旧代码作出的选择。新 worker 若对同一 history 走不同分支就产生 non-determinism。安全方案有：旧 execution pin 到旧 build；在 history 写 version marker，replay 永远读取同一 marker；或 continue-as-new，将显式压缩 state 转入新 run/schema。event upcaster 只能确定性转换 schema，不能改写历史事实。

6. Lease 与 supervision

worker poll task 后获得有限 lease，heartbeat 报告进度和 checkpoint。lease timeout 只表示 owner 失联，不证明 effect 没发生；接管仍遵守上一篇的 idempotency/fencing/reconciliation。supervisor 监控 state age、last progress、timer lateness、budget、open approvals 与 unresolved effects，并按 typed failure 选择 restart child、pause、escalate、compensate 或 fail。

7. Terminal verification

模型提交 completion_candidate 后不直接成功。control plane 运行预声明 verifier：查询目标系统、执行测试、检查 artifact digest、policy 与未决 calls。evidence bundle 含 verifier/version、observedAt、source identity、query/test、结果与 hash。所有 required postconditions 为 true 且没有 outcome_unknown 才追加 WorkflowCompleted，否则 bounded repair 或人工。

8. Runbook

每个异常状态映射 owner、诊断查询、安全动作与禁止动作。waiting_approval 检查 expiry/digest，禁止自批；timer_late 检查 capacity，禁止批量重建 timer；effect_unknown 先 reconcile，禁止新 key；non_deterministic 恢复兼容 worker，禁止删 history。redrive 记录 operator、reason 与原 identity。

reduce(state, event):
  next = deterministicTransition(state, event)
  persist(next.commands, expectedVersion=state.version)

onCompletionCandidate(run):
  evidence = verify(run.postconditions, externalSources)
  if evidence.allRequired and run.unknownEffects == 0:
    append(WorkflowCompleted(evidence.digest))
  else:
    append(RepairOrManualReview(evidence.failures))
04

必要数学：安全余量、积压与收敛

Timer lateness 与 lease

timer 计划时间为 tf，实际处理时间为 tp，则 ℓ=max(0,tp−tf)。应监控 ℓ 的 p95/p99；若 approval expiry 是硬边界，必须比较 event time 与 expiry，不能因晚处理让过期授权生效。

lease 时长 L 至少容纳 heartbeat 间隔 h、最大延迟 d 与时钟误差 ε：L>h+d+2ε 可减少误接管。但它不是安全证明；暂停的旧 worker 仍可能复活，所以 effect 还需 fencing token 或稳定 idempotency key。

积压收敛

runnable 到达率 λ，可持续完成率 μ，backlog 为 B。只有 μ>λ 才收敛，理想排空时间 T≈B/(μ−λ)。B=18,000、μ=120/s、λ=100/s 时约需 900 秒，不是 150 秒。timer 同时到期会抬高 λ；jitter、分区与 admission control 是容量安全机制。

完成谓词

required postconditions 为 V₁…Vₙ、未知副作用数为 U，则 C=(V₁∧…∧Vₙ)∧(U=0)。这不是概率乘法，而是逻辑门：任一 false/unknown 都不能成功。运维 SLO 可测 P(Tterminal≤D)，即 deadline D 内进入 succeeded、failed 或明确 manual-review 终态的比例，比 worker uptime 更接近收敛性。

05

对 Agent 系统的影响

等待成为一等动作

Agent 可声明等待 callback、审批或明早 09:00，释放计算，在 signal/timer 后从 durable state 恢复。模型只接收压缩 current state 与新 event，不必回灌三天 transcript；完整 history 留给 replay、审计和证据。

认知判断与控制判断分离

LLM 负责规划、解释模糊输入和提出 repair；runtime 拥有 identity、authorization、deadline、replay、retry 与 terminal gate。模型可建议重跑，却不能绕过 unresolved effect 或 retry budget；可总结审批理由，却不能生成 approval event。模型升级因此不会改写故障语义。

可观测性必须复原状态，而不只是统计请求

trace span 应携带 workflowId、runId、operationId、callId 与 attemptId，metric 则按 state、wait reason、tool class 和 failure class 聚合；高基数 identity 留在 logs/traces，不直接做 metric label。核心面板同时展示 open executions 的年龄分布、timer lateness、approval age、unknown effects、repair 次数与 terminal convergence SLO。这样 on-call 才能从聚合异常下钻到事件历史，并判断是容量不足、外部依赖停滞、审批无人负责，还是 verifier 发现真实后置条件未满足。

成本与产品语义

event、snapshot、timer index、visibility query 与 verifier 增加存储/I/O，兼容 worker 和 schema migration 增加工程成本，却避免长占 worker、重复推理与人工追查。状态页应显示 waiting reason、last progress、owner、certainty 和安全下一步；把一切写成“Agent 正在思考”会掩盖系统停滞。

06

设计取舍与失败模式

  • History 增长：每次 heartbeat 都入 event 会拖慢 replay；用粗粒度 checkpoint、payload 外置、retention 和 continue-as-new，但不能删未决 effect。
  • 版本分叉：维护旧/新 worker 有成本，强制迁移又可能无法解释旧 history；compatible builds + marker 通常更安全。
  • Signal race：callback 可能早到、重复、乱序或晚到；先持久化去重再消费，“无 waiter 就丢弃”会永久卡住。
  • Approval TOCTOU：dispatch 前重新比较 intent digest；expiry、revocation 或 policy changed 都要重评。
  • Poison execution：确定性 bug 会在同 event/version 反复 crash；停止 restart，路由兼容 build 或人工修复。
  • Verifier 自证：执行 Agent 自称通过仍是同源 assertion；高风险条件应查目标 API、独立 test runner 或只读观察面。
  • 恢复风暴：region 恢复后 expired leases、timers、retries 同时 runnable；分区、rate limit、priority、jitter 保护 effect owner。
  • 平台差异：Temporal、Durable Functions、Step Functions 的 history、timeout、delivery、versioning contract 不同，不能移植保证。
07

可复用的技术判断

  • 长运行 Agent 的 durable unit 是可重放 execution record，不是常驻进程或完整 transcript。
  • timer、signal、approval 都是带 identity、schema、policy、provenance 的事件；approval 绑定 material intent digest。
  • pin build、version marker、continue-as-new 分别处理旧 history 的执行兼容、分支兼容与代际切换。
  • supervisor 管理 progress、lateness、budget、unresolved effect；lease expiry 不等于 effect 未发生。
  • 成功是独立 verifier 对 postconditions 的合取证明，并要求 unknown effects 为零；runbook 定义未收敛时谁做什么、禁止什么。

Agent Runtime Internals · Part 4 of 4

How Can a Three-Day Agent Resume Safely?

Compose durable timers, signals, approvals, workflow versioning, supervision, and terminal verification into an operable long-running control plane.

2026-09-1920 min readDurable execution / Control plane / Workflow versioning / Human approval / Terminal verification
01

Today's proposition

A three-day agent is not a process that remains alive for three days. Processes restart, workers roll forward, credentials expire, approvals arrive late, and an external system may commit while its acknowledgement disappears. What survives is a replayable execution record: stable workflow identity, durable event history, wait conditions, unresolved effects, policy versions, and a verifiable terminal state.

Long-running agents therefore separate a data plane from a control plane. The data plane runs model inference and tool calls. The control plane decides when work is schedulable, what it awaits, who may signal it, which code version interprets old history, who supervises failure, and when enough evidence exists to declare completion. Leaving those duties to a prompt makes recovery, authorization, and upgrades drift with model output.

Core judgment: durability is not saving a chat. Every external input and scheduling decision must retain the same interpretation after a crash. Completion is not the model saying “done”; a terminal verifier must produce provenance-bearing evidence for predeclared postconditions.
02

Place the first three parts inside one control plane

Part 1 decomposed a tool call into command, attempt, result, and outcome unknown. Part 2 used structured concurrency to bound children, deadlines, cancellation, and backpressure. Part 3 handled uncertain effects through stable idempotency keys, checkpoints, reconciliation, and compensation. Today gives these mechanisms a management layer that survives across days.

Workflow and run IDs are outer identities; operation, call, and attempt IDs live within them. Event history records why state transitioned; a snapshot is only a recovery accelerator. Timers, signals, and approvals append events carrying identity, time, and schema version. A worker may disappear because a replacement reconstructs state from history, but replay must not reread wall clock, recall the model, or repeat effects.

03

Mechanism: three closed loops, not one enormous loop

1. Event-sourced record

Every command passes admission before append: validate tenant, principal, workflow schema, policy version, and unique command ID. A reducer takes state plus one event and computes next state and commands. A snapshot may cache state at event N, but losing it may only slow recovery; it cannot change the result. Model output affecting control flow is also recorded with model/version, prompt digest, and response digest.

2. Durable timers

After recording TimerScheduled(timerId, fireAt), release the worker. At due time the timer service appends TimerFired, deduplicated by timer ID. Its usual meaning is “not processed before fireAt,” not exact execution then; congestion adds lateness. Separate business deadlines, reminder timers, and authority expiry. Record cancellation instead of trusting an in-memory timeout handle.

3. Signals and correlation

Normalize callbacks into signals carrying workflow ID, signal ID, type, schema version, issuer, payload digest, and receive time. Authenticate the issuer, deduplicate by signal ID, then test whether the wait set accepts the type. Buffer an early signal. A late signal or one targeting a cancelled workflow becomes an auditable rejection; it cannot resurrect execution. Routing from natural-language body text turns correlation error into an authorization vulnerability.

4. Human approval

An approval request freezes an intent digest: tool, target, material arguments, risk, policy version, expiry, and permitted variation. The approval event binds approver identity, decision, digest, and timestamp. Material change to amount, recipient, code diff, or permission scope invalidates the old decision. Expiry follows escalation, rejection, or pause—never implicit approval.

5. Replay and versioning

History contains decisions made by old code. A new worker taking another branch over the same history creates nondeterminism. Safe strategies include pinning old executions to an old build; recording a version marker that replay reads consistently; or continuing as new, carrying explicit compacted state into a new run and schema. An event upcaster performs only deterministic, tested schema transformation and never rewrites historical facts.

6. Leases and supervision

A polling worker receives a finite lease; heartbeats report progress and recoverable checkpoints. Lease timeout says the owner disappeared, not that an effect did not happen. Takeover still follows Part 3's idempotency, fencing, and reconciliation. A supervisor watches state age, last progress, timer lateness, budgets, open approvals, and unresolved effects. Typed failure determines restart child, pause, escalate, compensate, or fail.

7. Terminal verification

A model's completion_candidate does not directly become success. The control plane runs predeclared verifiers: query target systems, execute tests, inspect artifact digests, policy, and unresolved calls. An evidence bundle records verifier/version, observation time, source identity, query or test, result, and hash. Only all required postconditions being true with no unknown effect permits WorkflowCompleted; otherwise bounded repair or human review follows.

8. Runbooks

Every abnormal state maps to an owner, diagnostic query, safe action, and forbidden action. For waiting approval, inspect expiry and digest; never self-approve. For timer late, inspect capacity; never recreate timers in bulk. For effect unknown, reconcile first; never mint a new key. For nondeterminism, restore a compatible worker; never delete history. Redrive records operator, reason, and original identity.

04

Essential mathematics: safety margins, backlog, and convergence

Timer lateness and leases

For scheduled time tf and actual processing time tp, lateness is ℓ=max(0,tp−tf). Monitor p95 and p99 of ℓ. If approval expiry is hard, compare event time with expiry; delayed processing cannot revive authority.

Lease length L should accommodate heartbeat interval h, maximum delay d, and clock uncertainty ε: L>h+d+2ε reduces false takeover. It is not a safety proof. A paused worker may revive, so effects still need fencing or stable idempotency.

Backlog convergence

Let runnable arrivals be λ, sustainable service rate μ, and backlog B. It converges only if μ>λ, with ideal drain time T≈B/(μ−λ). For B=18,000, μ=120/s, λ=100/s, that is 900 seconds, not 150. Cohorts of timers raise λ together; jitter, partitioning, and admission control are capacity-safety mechanisms.

Completion predicate

For required postconditions V₁…Vₙ and unknown-effect count U, define C=(V₁∧…∧Vₙ)∧(U=0). This is a logical gate, not probability multiplication: one false or unknown blocks success. An operational SLO can measure P(Tterminal≤D), the fraction reaching succeeded, failed, or explicit manual review by deadline D. It captures convergence better than worker uptime.

05

Implications for agent systems

Waiting becomes a first-class action

An agent can wait for a callback, approval, or 09:00 tomorrow, release compute, and resume from durable state after a signal or timer. The model receives compact current state plus the new event rather than three days of transcript. Full history remains for replay, audit, and evidence.

Separate cognitive from control judgment

The LLM plans, interprets ambiguity, and proposes repair. The runtime owns identity, authorization, deadlines, replay, retry, and the terminal gate. A model may suggest rerunning but cannot bypass an unresolved effect or retry budget; it may summarize approval rationale but cannot create the approval event. Model upgrades therefore do not rewrite failure semantics.

Observability must reconstruct state, not merely count requests

A trace span carries workflow, run, operation, call, and attempt identities. Metrics aggregate by state, wait reason, tool class, and failure class, while high-cardinality identities stay in logs and traces rather than metric labels. A useful control-plane dashboard combines the age distribution of open executions, timer lateness, approval age, unknown effects, repair count, and the terminal-convergence SLO. An on-call engineer can then descend from an aggregate anomaly into event history and distinguish insufficient capacity, a stalled dependency, ownerless approval, or a verifier correctly finding that a real postcondition remains false. Request success rate alone cannot make those distinctions.

Cost and product semantics

Events, snapshots, timer indexes, visibility queries, and verifiers add storage and I/O; compatible workers and migrations add engineering cost. They avoid holding workers, repeating inference, and manually reconstructing outcomes. Status should expose wait reason, last progress, owner, certainty, and the next safe action. Saying “agent is thinking” for every state hides systemic stalls.

06

Trade-offs and failure modes

  • History growth: eventing every heartbeat slows replay. Use coarse checkpoints, external payloads, retention, and continue-as-new without deleting unresolved effects.
  • Version forks: old and new workers cost money, while forced migration may make old history uninterpretable. Compatible builds plus markers are usually safer.
  • Signal races: callbacks arrive early, duplicated, reordered, or late. Persist and deduplicate before consumption; dropping when no waiter exists can stall forever.
  • Approval TOCTOU: compare the intent digest again before dispatch. Expiry, revocation, or policy change requires reevaluation.
  • Poison execution: a deterministic bug crashes repeatedly at the same event/version. Stop restart and route to a compatible build or repair.
  • Self-verification: the executing agent claiming success is a same-source assertion. High-risk conditions query target APIs, independent tests, or read-only observation.
  • Recovery storms: expired leases, timers, and retries become runnable together after recovery. Partitioning, limits, priority, and jitter protect effect owners.
  • Platform differences: Temporal, Durable Functions, and Step Functions differ in history, timeout, delivery, and versioning contracts; guarantees do not transplant.
07

Reusable technical judgments

  • The durable unit is a replayable execution record, not a resident process or full transcript.
  • Timers, signals, and approvals are events with identity, schema, policy, and provenance; approval binds a material-intent digest.
  • Build pinning, version markers, and continue-as-new address execution compatibility, branch compatibility, and generational transition.
  • Supervisors manage progress, lateness, budgets, and unresolved effects. Lease expiry never proves an effect did not happen.
  • Success is an independent verifier's conjunctive proof of postconditions with zero unknown effects. Runbooks define who acts and what is forbidden.
