“订好会议室”不是一个工具调用：子目标怎样成为可控能力？

从 option 的启动条件、内部策略和终止规则出发，区分子目标、skill 包、工具动作与可恢复执行单元。

2026-11-05约 20 分钟Hierarchical planning / Options / Temporal abstraction / Semi-MDP / Subgoals / Termination
01

今日命题

Agent 的计划写着‘确认会议室→通知团队’。但‘确认会议室’不是日历 API 里一个原子按钮：它可能要查询空档、尝试预订、处理竞争冲突、等待回执、核验房间与时间，失败时再选备选房。若父 Agent 把子目标当一次 tool call，孩子说‘我完成了’就推进到通知，旧房间可能根本没订成。层级规划的价值不是把待办列表缩进，而是给一段跨多步的行为明确启动、内部控制和终止语义。

昨天结束 model-based planning：rollout 是想象分支，broker 只执行获授权第一步，真实观察后重定根；有限搜索不能剪掉高损失路径。今天开始 Hierarchical Agent Control Internals 1/2，问一个新问题：规划器能否把‘确认会议室’当成一个可复用的高层动作，而不隐藏其中的权限、未知结果和取消边界？Options 的经典形式给出三个核心部件；工程 runtime 还要给它加结果、预算与副作用合同。下一篇处理多个 option 如何组合、并行或中断，并以终态证明层级确实帮到了 Agent。

02

把高层动作与 skill、tool、workflow 分开

你已熟悉 tool 是可调用边界，skill 是承载指令、代码或资源的能力包，workflow 可把长期执行持久化。它们和层级规划里的 option 不同：option 是一个在特定状态可启动、内部按策略选择低层动作、达到终止条件才返回的时间扩展动作。一个 skill 包可能提供实现 option 的模板，但安装 skill 不自动产生可核验的终止条件；一个 workflow 可以执行 option，却还需自己的 durable timer、审批与恢复语义。不能因为名字都叫‘能力’就视作同一抽象。

昨天的 plan graph 需要在 root 比较‘先确认房间’还是‘先问用户’，若每次都展开查询、预订、冲突恢复、核验四五步，搜索树会膨胀。把这段行为封成高层动作，parent 在较粗粒度上比较路径；child 仍要根据最新 observation 调整内部步骤。这种 temporal abstraction 减少 parent 必须即时考虑的低层组合，但代价是内部细节可能被隐藏。parent 应收到 typed outcome 和关键证据，而非只有一行‘成功’。

Options 论文在 MDP/semi-MDP 中形式化这种延长动作；Option-Critic 研究怎样学习内部策略与停止规则；MAXQ 研究值函数的层级分解。它们的实验环境不是业务权限系统。SayCan 作者把语言指令与机器人 affordance/skill 选择结合，说明高层语言与低层可执行性需要连接；但机器人 skill 的成功分数不能直接映射成邮件、支付或会议室预订的授权。

03

机制：为子目标建立 option 合同

1. 定义 initiation set，不靠一句‘可以开始’

‘确认会议室’只在房间/时段明确、当前会话有查询和预订权限、旧预订操作没有未知副作用时启动。传统 option 的 initiation set I 列可启动状态；业务 Agent 看不见完整状态，于是 runtime 对 belief、权威资源版本和 typed control state 设 guard。若前提缺失，返回 not_started 或需要澄清，不能先调用预订再说‘权限不够’。启动判断与模型对任务成功的语言自信分离。

2. 内部 policy 在每次观察后可改路线

Option 的 policy π 不是固定脚本：查到房间 R 被占，可以试授权的备选房；收到 pending 可等回调或按 operation ID 查状态；用户中途改时间则失效原 intent。每个内部 step 仍经过工具 schema、权限、幂等与资源预算。parent 只看到高层动作并不意味着 child 获得更大 credential；capability 只可按具体子任务收窄，不能把 parent 的全部权限复制过去。

3. 停止信号与成功结果分开

理论中的 β 决定 option 在某状态是否终止，通常不说明为何终止。业务实现至少区分 succeeded_verified、failed、cancelled、outcome_unknown 和 expired。成功要附房间 ID、时段、权威 booking ID 与核验时间；取消只表示停止继续发新命令，不保证已提交预订被撤回。终止若仅由模型说‘搞定’触发，parent 会将未知或失败误读成成功，并继续发通知。

4. Parent 接收一份可组合的结果

结果对象包含 optionId/version、intent digest、输入参数、终态枚举、输出 artifact IDs、未决 effect IDs、源 observation IDs、实际耗时与消耗预算。parent 只在 succeeded_verified 且与原 intent 参数匹配时进入‘通知团队’；failed 可选替代 option，unknown 则先 reconcile 或交人工。若 child 返回‘预订房间 A 失败但 B 成功’，parent 仍需确认 B 是否符合用户约束，不能把任何成功房间当目标完成。

5. 处理内部更新与被中断的工作

Option 可持续数分钟，期间会议室、政策或用户目标变化。每次有外部副作用前重新检查与该动作相关的 guard；若 parent 取消或 deadline 到期，child 停止新 dispatch，登记在途工具；在期限内等权威状态，仍未知则返回 outcome_unknown 并保留追查责任，而不是遗弃请求。长运行任务的 durable timers/leases 已在 Agent Runtime 系列讲过，这里关心的是层级边界：child 停止后 parent 得到真实 terminal status，而非孤儿回调晚到时静默改写计划。

6. 区分抽象复用与过度封装

好的 option 把一个稳定子目标封成可测试单元，内部允许多步观察与恢复，向上暴露最小充分结果。过大的 option 如‘把整个项目搞定’启动前提含糊、终止难核验，等于把原 Agent 问题藏进一个黑盒。过小的 option 若只包装单次 read API，则没有时间抽象收益。应按可复用的中间后置条件切分，而不是按 prompt 段落或供应商工具数量切分。

04

必要数学：时间扩展动作与可变时长

经典 option 可写作 o=(I_o,π_o,β_o)：I_o 是允许启动的状态集合，π_o 是 option 内选择低层动作的策略，β_o 是在状态下终止的规则或概率。这里的 o 不是一次 API call；从启动到停止可跨多个低层步骤。β_o(s)=1 仅表示在 s 停止，不表示成功；业务的 succeeded_verified 仍由独立后置条件判断。在部分可观测 Agent 中，I_o 的真实状态未必可直接读到，实际应用常用 belief 与外层 guard 作保守近似，不能声称直接满足经典 MDP 假设。

若 option 持续随机的 τ 个低层步骤，其价值可用 semi-MDP 直觉写成 Q(s,o)=E[Σ_{k=0}^{τ−1}γ^k r_{t+k}+γ^τ V(s_{t+τ}) | s,o]。s 是启动时状态，r_{t+k} 是第 k 步的收益或负成本，γ∈[0,1] 折扣远期，V 是 option 停止后从新状态继续的估计价值，E 对内部策略与环境的不确定性取期望。τ 可因冲突、等待或回执未知而变化；parent 不能把‘一个 option’当固定一次工具耗时。业务系统若没有可信 reward model，可先用显式成本、成功后置条件和风险门替代漂亮但虚假的 Q 值。

工程上需要更严格的完成条件。设 required postconditions 为 P₁…Pₙ，未决副作用数为 U，则可写 success(o)=(P₁∧…∧Pₙ)∧(U=0)。Pᵢ 是经权威来源核实的条件，例如正确房间、时段和 booking ID；U=0 表示没有仍未知的工具效果。这个逻辑与式不是概率评分，任一条件 unknown 时不应返回 succeeded_verified。它说明 option 的终止 β 与业务完成 success 是两套不同语义，避免 parent 把‘停止运行’误作‘目标已达成’。

05

对 Agent 架构的影响

planner 的动作目录可有不同层级：primitive tool、option 和需审批的高风险操作。Option registry 不只是名字/描述，还应有版本、参数 schema、initiation guard、可调用子工具白名单、最长执行/成本、终止枚举、成功后置条件、取消处理与 source refs。模型可以提出‘启动确认会议室 option’，但 registry 和 broker 编译并验证合同；同名 skill 文档不构成执行权限。若 option 版本升级改变终止语义，旧的 parent plan 要固定版本或迁移，不能在恢复时悄悄换定义。

日志与指标要按 parent/option/primitive 三层关联：option 实际时长 τ、内部 calls、失败恢复次数、unknown 终态、父任务是否错误推进，以及中间成功对最终 verified outcome 的贡献。只测子 option 在模拟器里“完成”会漏掉 parent 参数错绑、权限扩大和后续动作依赖失效。将 child 的 typed outcome 转成 parent belief 更新时保留证据和未决 effects；不能把 child summary 当权威状态覆盖。

这个抽象还能改善规划成本：parent 不必反复展开稳定子流程，但要保留在关键节点下钻的能力。若‘确认房间’在某租户失败率高或权限流程特殊，可要求 parent 在选择前展开其风险/耗时摘要，或切到人工。因而 option 是带可见边界的压缩，不是把复杂性永久藏掉。下一篇会检验多 option 组合时终止、取消与下游副作用的传播。

06

取舍与失败模式

  • 子目标就是一行 prompt：没有启动、内部策略、终止和权威结果合同，parent 无法安全复用。
  • option 停止就算成功：β 可能因失败、取消或过期触发；终态枚举与后置条件另验。
  • skill 包就是 option：包是分发/指令单位，option 是运行时的时间扩展控制合同。
  • parent 授权自动继承给 child：权限应按子任务收窄；高层抽象不能扩大 capability。
  • 取消能撤回所有内部工具：已提交副作用需核对或补偿，晚到结果仍要关联原 option。
  • 越大越能复用：巨型 option 的启动条件和完成判据可能不可检查；按中间后置条件拆分。
  • 越小越可控：只给单次 API 换名字没有减少规划深度，却增加包装开销。

层级抽象把 parent 的搜索空间压缩，却要求 child 提供可核查的边界。与其追求“自动学出所有技能”，不如先在高复用、成功判据明确的任务上建立少量 option，并在真实环境里测启动拒绝、未知终态、耗时尾部和父子组合正确性。

07

可复用的技术判断

  • option 是带启动集合、内部策略与终止规则的时间扩展动作，不等于一个 tool call。
  • 理论 β 只决定停止，业务成功仍需 typed outcome、权威后置条件和 U=0。
  • parent 可用高层动作降低搜索复杂度，但 child 仍按每步观察、授权和预算执行。
  • skill 包、option 与 durable workflow 可组合但职责不同，不能因名称相同而混用权限。
  • 按可验证的中间后置条件切分；过大隐藏错误，过小没有抽象收益。
08

‘Book the Room’ Is Not One Tool Call. How Does a Subgoal Become a Controlled Capability?

Use an option's initiation set, internal policy, and termination rule to separate subgoals, skill packages, tool actions, and recoverable execution units.

2026-11-0520 min readHierarchical planning / Options / Temporal abstraction / Semi-MDP / Subgoals / Termination
01

Today's proposition

An agent plan reads 'confirm a room → notify the team.' But confirming a room is not one atomic calendar-API button. It may require checking availability, attempting a booking, handling a race, waiting for a receipt, verifying room and time, and selecting a fallback after failure. If the parent treats the subgoal as one tool call and advances when the child says 'done,' it may notify everyone about a room never booked. Hierarchical planning is more than indenting a task list: a temporally extended behavior needs explicit initiation, internal control, and termination semantics.

Yesterday completed model-based planning: a rollout is an imagined branch; the broker executes only an authorized first action and re-roots on real observation; finite search must retain severe paths. Hierarchical Agent Control Internals begins with a different question. Can a planner treat 'confirm the room' as a reusable high-level action without concealing permission, unknown outcomes, or cancellation? The classic options framework supplies three components; an engineering runtime adds result, budget, and side-effect contracts. Part 2 will compose, parallelize, and interrupt multiple options and test whether the hierarchy improves verified outcomes.

02

Separate high-level action from skill, tool, and workflow

You already know that a tool is a callable boundary, a skill can package instructions, code, and resources, and a workflow may durably run across time. None is automatically the option of hierarchical planning. An option is a temporally extended action that can start only in certain states, chooses lower-level actions through an internal policy, and returns when its termination condition holds. A skill package may help implement an option, but installing it does not create a verifiable completion predicate. A workflow may execute an option while retaining its own durable timers, approval, and recovery semantics. Calling all three a 'capability' does not make them the same abstraction.

Yesterday's plan graph must compare root choices such as 'confirm the room' and 'ask the user first.' Expanding availability lookup, booking, race recovery, and verification every time makes search wider. Packaging the behavior as a high-level action lets the parent compare coarser paths, while the child can still react to fresh observations internally. Temporal abstraction reduces the low-level combinations the parent considers at once, but it can hide details. The parent needs a typed outcome and decisive evidence, not a single line saying 'success.'

The options paper formalizes extended actions in MDPs and semi-MDPs. Option-Critic studies learned internal policies and termination, while MAXQ studies hierarchical value decomposition. Their experimental settings are not business permission systems. SayCan connects language instructions with robot affordances and skill choice, showing why high-level language needs a bridge to executable ability. A robot-skill success score does not transfer directly into authority for email, payment, or room booking.

03

Mechanism: give a subgoal an option contract

1. Define an initiation set, not a verbal 'go ahead'

'Confirm the room' may start only when room and time are known, the session permits availability lookup and booking, and no older booking operation has an unresolved effect. A classical option's initiation set I lists eligible states. A business agent does not observe full state, so the runtime guards on belief, authoritative resource version, and typed control state. Missing prerequisites return not_started or need_clarification; it must not try booking and only afterward discover missing authority. Initiation is separate from the model's verbal confidence about task success.

2. Let the internal policy react after each observation

The option policy π is not necessarily a rigid script. If room R is taken, it may try an authorized alternative. Pending status may lead to a callback wait or lookup by operation ID. A user changing the time invalidates the old intent. Every internal step still passes tool schema, authority, idempotency, and resource budget. The parent seeing one high-level action does not give the child larger credentials. Capabilities should be narrowed to the subtask, not copied wholesale from the parent.

3. Separate termination from successful outcome

In option theory β decides whether an option terminates in a state; it need not say why. A business implementation needs at least succeeded_verified, failed, cancelled, outcome_unknown, and expired. Success carries room ID, slot, authoritative booking ID, and verification time. Cancellation stops new commands; it does not guarantee a committed booking was reversed. If the model's 'done' alone triggers termination, the parent can mistake unknown or failure for success and notify the team.

4. Return a result the parent can compose

A result object contains option ID and version, intent digest, input parameters, terminal enum, output artifact IDs, unresolved effect IDs, source observation IDs, duration, and spent budget. The parent enters 'notify team' only on succeeded_verified matching the original intent parameters. Failed can lead to another option; unknown requires reconciliation or human handoff. If the child reports 'room A failed but B succeeded,' the parent still checks whether B satisfies the user's constraints. Any successful room is not necessarily the requested outcome.

5. Handle updates and interrupted work inside the boundary

An option can last minutes while rooms, policy, or user goal change. Recheck relevant guards before each external effect. When the parent cancels or a deadline expires, the child stops new dispatches and records in-flight tools. It waits for authoritative status only within a deadline; if still unknown it returns outcome_unknown with reconciliation ownership rather than orphaning requests. Durable timers and leases were covered in the earlier Agent Runtime series. The new concern is the hierarchical boundary: the parent receives a truthful terminal status when the child stops; a late orphan callback must not silently rewrite the plan.

6. Balance abstraction reuse against overpackaging

A good option packages one stable subgoal as a testable unit, permits multi-step observation and recovery, and exposes a minimally sufficient result upward. An oversized option such as 'finish the entire project' has vague prerequisites and unverifiable termination. It merely hides the original agent problem in a black box. A tiny option that wraps one read API gains no temporal abstraction. Split around reusable intermediate postconditions, not prompt paragraphs or the number of vendor tools.

04

Essential mathematics: temporally extended actions

A classical option is o=(I_o,π_o,β_o). I_o is the set of states where it may start, π_o the policy choosing lower-level actions within it, and β_o its rule or probability of termination in a state. o is not one API call; it can span many low-level steps. β_o(s)=1 means stop at s, not succeed. A separate business postcondition decides succeeded_verified. In a partially observed agent the true state needed by I_o may not be readable. An implementation often uses belief and outer guards as a conservative approximation; it should not claim to satisfy the classical fully observed MDP assumptions directly.

If an option lasts a random τ lower-level steps, a semi-MDP value intuition is Q(s,o)=E[Σ_{k=0}^{τ−1}γ^k r_{t+k}+γ^τ V(s_{t+τ}) | s,o]. s is the start state; r_{t+k} is reward or negative cost at internal step k; γ∈[0,1] discounts distant outcomes; V estimates value after the option ends in its new state; and E averages over uncertainty in its policy and environment. τ varies with competition, waiting, and uncertain receipts. A parent cannot price 'one option' as one fixed tool call. If a business system lacks a trustworthy reward model, explicit costs, verified postconditions, and risk gates are safer than a precise-looking but fictional Q value.

Engineering needs a stricter completion condition. Let required postconditions be P₁…Pₙ and unresolved side effects count U. Write success(o)=(P₁∧…∧Pₙ)∧(U=0). Each Pᵢ is verified by an authoritative source, such as correct room, time, and booking ID. U=0 means no tool effect remains unknown. This conjunction is not a probability score. If any condition is unknown, the result must not be succeeded_verified. Option termination β and business success are distinct semantics; the parent must not mistake 'stopped running' for 'goal achieved.'

05

Implications for agent architecture

A planner's action catalog may contain primitive tools, options, and approval-gated high-risk operations. An option registry needs more than a name and description: version, parameter schema, initiation guard, child-tool allowlist, duration and cost cap, terminal enum, success postconditions, cancellation handling, and source references. The model can propose 'start confirm-room option,' but the registry and broker compile and validate the contract. A skill document with the same name is not execution permission. If an upgrade changes termination semantics, an old parent plan should pin a version or migrate explicitly, not silently use the new meaning on resume.

Link logs and metrics across parent, option, and primitive layers: actual duration τ, internal calls, recovery attempts, unknown terminals, whether the parent advanced incorrectly, and whether intermediate success contributed to the final verified outcome. Testing the child option only for simulated 'completion' misses parent parameter misbinding, expanded authority, and invalid downstream dependencies. When a typed child result updates parent belief, retain evidence and unresolved effects. A child summary cannot overwrite authoritative state.

The abstraction can reduce planning cost: a parent need not repeatedly expand a stable subflow, but it should be able to inspect critical internal branches. If 'confirm room' fails often in one tenant or has unusual approval, expose a risk and duration summary before selection or route to a person. An option is a compression with visible boundaries, not a way to hide complexity permanently. Part 2 will test termination, cancellation, and downstream effects when several options compose.

06

Trade-offs and failure modes

  • A subgoal is one prompt line: without initiation, internal policy, termination, and authoritative outcome, a parent cannot reuse it safely.
  • Option stopped means success: β can fire on failure, cancellation, or expiry. Terminal enum and postconditions are separate.
  • A skill package is an option: a package distributes instructions and assets; an option is a runtime contract for extended control.
  • Child inherits every parent permission: narrow authority to the subtask. Abstraction must not enlarge capability.
  • Cancellation undoes internal tools: committed effects require reconciliation or compensation, and late results remain linked to the option.
  • Bigger always means more reuse: a giant option may have uncheckable initiation and completion. Split by intermediate postconditions.
  • Smaller always means more control: renaming one API call does not shorten planning and adds wrapper overhead.

Hierarchy compresses the parent's search space while requiring the child to expose a verifiable boundary. Rather than aim to 'learn every skill automatically,' begin with a small set of high-reuse tasks that have explicit success predicates. Test initiation rejection, unknown terminals, duration tails, and correctness of parent–child composition in the real environment.

07

Reusable technical judgments

  • An option is a temporally extended action with initiation, internal policy, and termination—not one tool call.
  • Theoretical β decides stopping; business success still needs typed outcome, authoritative postconditions, and U=0.
  • A parent can shorten search with high-level actions, while a child still observes, authorizes, and budgets each step.
  • Skill package, option, and durable workflow can compose, but have distinct responsibilities and permissions.
  • Split at verifiable intermediate postconditions. Too large hides failures; too small yields no abstraction benefit.
08

Primary sources and evidence tiers

  • Sutton, Precup & Singh, Between MDPs and Semi-MDPs — the original options and temporal-abstraction paper; business guards and authority are our extensions.
  • MAXQ Value Function Decomposition — the author studies hierarchical tasks and value decomposition, not an enterprise workflow specification.
  • The Option-Critic Architecture — the authors study learning internal policies and termination; results belong to their experimental settings.
  • Do As I Can, Not As I Say / SayCan — the authors report connecting language to robot skills and affordances; it does not grant business-tool authority.
  • FeUdal Networks — the authors study manager–worker structure at distinct timescales; we do not claim direct deployment on calendar tasks.

Links and titles were checked on 2026-11-05. Typed outcomes, narrowed permissions, the U=0 completion gate, and cancellation contracts are editorial engineering designs. The papers do not jointly define an agent option API.

09

Established and next starting point

Established today: building on sourced belief and one authorized real action from model-based planning, a high-level option packages a reusable multi-step subgoal with I, π, and β rather than persisting an imagined plan. A business runtime adds initiation guards, child-tool authority, budgets, cancellation, and typed results. β means stop; success requires authoritative postconditions and no unresolved effect. A skill package supplies material and a workflow supplies durable execution; neither automatically equals an option.

Still unresolved: how do several option results compose into the parent's next step? When a child fails or is cancelled, how do siblings, approvals, and downstream tools stop or recover? Does hierarchy really reduce search cost, or does hiding internals increase terminal mistakes?
