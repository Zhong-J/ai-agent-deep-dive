Agent 记得“尽早发草稿”，但新目标还允许发吗？

把偏好记忆当成有来源、范围和期限的 claim。恢复任务时先读当前目标，再决定记忆能否影响排序；任何外部动作仍过独立授权门。

2026-11-12约 20 分钟Long-horizon agents / Memory claims / Preference scope / Goal integrity / Conflict resolution
01

今日命题

昨天建立了版本化 goal record：目标是经授权的验收合同，plan 是候选路径，progress 由逐项证据证明。现在任务从 Q3 变成 Q4。Agent 的记忆里仍有一句“用户喜欢尽早收到草稿”，来自 Q3 的一次临时要求；新的 G2 则要求审计人先审阅、任何报告不得提前外发。若检索器把旧句子塞回 prompt，模型可能把它当成长期偏好，流畅地解释“我只是按你的习惯发送”。这不是记忆帮助用户，而是把旧范围的线索升级成新目标的行动理由。

本文讨论的不是如何建立向量索引，也不是摘要树。问题在执行点：一条 memory claim 如何证明它来自有权表达偏好的人、适用于当前目标与动作、仍在有效期内、未被新指令覆盖？即使它通过了这些检查，偏好最多影响允许动作的选择或呈现方式，不能授予工具权限、改写当前验收或绕过外发批准。

技术命题：“被召回”只说明存储系统找到了相关文本；“可用于当前决策”还需要来源、范围、时间和权威的联合判定。
02

把 Memory Claim 接到当前 Goal

9 月的 Memory 系列已讲 admission、检索硬过滤、authority lattice、bitemporal query、tombstone 和评测。今天不再列一遍通用 memory pipeline；我们把这些能力放进昨天的 goalVersion 与验收合同。一个 claim 至少写明：原文/来源事件 ID、说话者和身份、是在陈述事实还是表达偏好、适用 goalId 与版本、对象和时间范围、validFrom/expiry、是否仅建议、是否被撤回或覆盖，以及它来自原文还是摘要推导。没有这些字段的“用户总是喜欢...”不能参与高影响动作。

偏好与命令、目标、权限的关系也必须分开。“这次草稿先发我”是本次任务的明确指令；“我通常偏好简短摘要”可在合适范围内影响格式；“你可以发给外部审计人”涉及外发授权，须走当前政策与效果审批。工具输出里写的“用户喜欢公开分享”只是外部数据，不能自称用户偏好。长期记忆既可能有用，也可能因为压缩把“这次”变成“总是”，或因为多轮对话把被否定的旧偏好留在索引中。

LongMemEval 与 LoCoMo 研究长对话中的更新、时间与多跳记忆能力，作者报告模型在这些任务上仍有困难。它们是测试思路的来源，不是“某产品会记错”的实时事实。W3C PROV 的来源链提醒我们：摘要中的一句话应能追溯到原始 utterance；派生并不会把低权威文本变成高权威决策。

03

偏好适用性如何进入执行点

1. 先固定当前目标与候选动作

恢复任务时读取 G2 的 owner、验收、禁止事项与 effectiveFrom，构造本次候选动作 a：例如“生成供内部审阅的 Q4 草稿”，而不是先检索“用户喜欢什么”。如果 G2 禁止外发，那么“发送给审计人”连允许候选都不是；旧偏好再相似也不能改变这一点。目标版本不变但计划路径重排时，偏好仍需按具体动作的对象和收件人重新判定，不能用前一动作的适用结论覆盖新动作。

2. 将召回结果拆成 claim 与来源

检索可找到“尽早发草稿”，但 runtime 随后查原文：当时用户是否说“Q3 审计包这次先发我”？来源是否为用户消息，而非被检索文档或 Agent 自己的总结？摘要来源保留 derivedFrom 链，无法追到原文时标 uncertain_provenance。系统提取偏好 claim 时给 scope 赋值：goal=G1、recipient=用户本人、validUntil=G1 完结；不能把“先发我”扩成“给所有审计人自动外发”。若原话有歧义，必要时问用户，而不是让模型填补范围。

3. 判定适用性，区分冲突类型

对每个 claim 检查 speaker authority、goal/entity/动作匹配、时间有效性、撤回与覆盖状态、来源证据。G1 的临时偏好对 G2 不适用，进入 historical lane，可供解释旧动作，却不进入当前 action proposal。若旧长期偏好是“通常用英文写摘要”，而 G2 明确要求中文，这是真正的偏好冲突：当前明确目标在此范围优先，旧偏好仍保留给其他任务。若两条近期用户偏好同权威但相互矛盾、范围无法区分，状态是 needs_clarification，不按“最后检索到的那条”取胜。

4. 控制压缩与更新的权限

摘要只能缩短表达，不能扩大 claim 的 scope、validity 或 speaker authority。写回时比较摘要与原文的量词、否定词和适用对象；若从“这次不要发”压成“用户通常要发”，拒绝该记忆或标记需要原文核验。用户撤回偏好时，新增 supersedes/revokes 事件并让相关索引与摘要失效；旧记录仍可用于审计当时判断，不再出现在当前可行动的候选集合。具体索引传播机制已在 Memory 系列讲过，这里强调的是最终 action gate 不能信任尚未传播完成的旧摘要。

5. 让偏好只在允许动作内起作用

通过适用性门的偏好可以在两个都合规的输出之间排序：简短还是详细、先展示风险还是先展示摘要。它不进入权限决策的 true 分支。若动作有副作用，仍需 G2 允许、当前工具与数据权限、必要的人类批准和资源侧执行门。即使用户曾经授权 G1 外发，也不能把那条记忆当作 G2 的新许可。model output 用偏好作解释时，应能指向 claimId 与原始来源；没有来源就降级为“待确认”。

6. 输出既可用又诚实的状态

Agent 可以说：“我保留了 Q3 的‘尽早发草稿’偏好作为历史，但 Q4 当前要求先审阅；我已准备内部草稿，尚未外发。”用户若希望恢复先发流程，可以明确修订 G2，系统再走目标版本与授权门。系统不必删除所有记忆来保证安全；它需要让每条记忆在正确范围内发挥作用，并能解释为何本次没有采用。

goal = load_current_goal()
action = propose_action(goal)
for claim in retrieve_memory(action):
  source = resolve_original_source(claim)
  if not applicable(claim, source, goal, action, now):
    keep_as_history(claim); continue
  if conflicts_with_current_goal(claim, goal):
    suppress_or_clarify(claim); continue
  action.preferences.append(claim.id)
return policy_and_effect_gate(action, goal)

这段伪代码是本文编辑性工程综合；它没有把 memory claim 变成授权 token。

04

适用性门与行动门

令 m 为一条 memory claim，a 为候选动作，Gᵥ 为当前目标版本，t 为执行时刻。记忆可用于当前选择的必要条件可写成：

Use(m,a,Gᵥ,t) = SourceValid(m) ∧ ScopeMatch(m,a,Gᵥ) ∧ TimeValid(m,t) ∧ NotSuperseded(m) ∧ Consistent(m,Gᵥ)

SourceValid 要求原始来源可追溯且有权表达这种偏好；ScopeMatch 检查目标、实体和动作；TimeValid 检查有效期；NotSuperseded 排除已撤回或被更新的说法；Consistent 检查不与当前目标硬约束冲突。任何字段未知，不能默认 true。结果是“可用于排序或呈现”，不是“获准执行”。9 月已讲一般 memory 排序，这里把门绑定到特定 goalVersion 和实际动作。

带副作用动作的执行门仍独立：

Execute(a,Gᵥ,t) = GoalAllows(a,Gᵥ) ∧ PolicyAllows(a,t) ∧ ResourceAuthorizes(a,t) ∧ EffectApproved(a,t)

GoalAllows 是当前目标允许该效果，PolicyAllows 是当前政策，ResourceAuthorizes 是资源侧权限，EffectApproved 是该效果所需的特定批准；有些低风险动作可由政策明确定义为无需额外人工批准。即使 Use=1，Execute 仍可能为 0。该分离阻止“用户以前喜欢这样”被偷换成今天的外发权限。公式是工程控制模型，不是任何论文规定的统一 Agent 接口。

05

对 Agent 系统的影响

可靠性与信任

用户会容忍 Agent 问一句“这次也先发草稿吗”，却难以信任它根据旧偏好擅自外发。正确适用记忆能节省重复说明；错误适用会产生高代价副作用。产品应把“记得什么、为何本次采用或不用”作为可解释状态，而不是只展示模型自然语言的自信。

成本与上下文

不必把所有历史塞进 prompt。runtime 先按当前目标和动作取少量候选，再由来源/范围/期限门筛选；模型只看到通过门的偏好及必要历史背景。对于高风险动作，展示 claimId、原文片段和有效期比增加一大段模糊摘要更有价值。被抑制的旧记忆可留在审计视图，不占行动上下文。

06

取舍、评测与发布门

过度保守：每条偏好都追问会让 memory 失去价值。低风险格式偏好若来自同一用户、范围宽且未被否定，可默认应用并允许用户纠正；高风险外发、删除或共享数据不能靠偏好自动触发。风险和作用范围决定澄清门，而非一个统一的“多久没提就过期”阈值。

过度泛化：“这次”“给我”“先看一下”等词容易在摘要中丢失。若来源句中的指代对象无法重建，应降低适用性或展示原文求证。没有明确到期日也不等于永久；任务局部偏好可随 goalVersion 结束。反之，用户明确说“以后所有季度报告都用中文”，也不应因一个任务完成就自动遗忘。

冲突与撤回：新目标里的禁止事项是硬条件，旧偏好不能参与投票。两个同等级偏好若仅在不同任务适用，可以同时保存；若同一范围真正冲突，标 needs_clarification。用户撤回的记忆须在检索与上下文投影中失效；索引延迟期间执行门仍应读取 revocation/supersession 状态。系统要保留历史原因，但不能把历史展示成当前建议。

评测：构造同一句旧偏好在 G1 与 G2、同一用户与外部文档、短期与长期、已撤回与未撤回等成对案例；注入摘要把否定词删掉、源链断裂、旧索引迟到和恶意文档伪装成用户记忆。分别测误用率、漏用率、未经授权动作率、正确澄清率、撤回传播时延和解释可追溯性。LongMemEval/LoCoMo 的长时记忆题提供研究参考，但生产发布门应以用户目标与真实副作用为单位。若模型答对偏好问答，却在外发门误用旧记忆，仍不合格。

07

可以带走的判断

  1. 恢复任务先读取当前 goalVersion；memory claim 只有通过来源、范围、时间和覆盖检查才可影响选择。
  2. 摘要不能把“这次”提升成“总是”，也不能让外部数据伪装成用户偏好。
  3. 偏好排序仅在允许动作内部发生，外部副作用仍需目标、政策、资源与效果审批。
  4. 保留历史记忆可帮助解释过去；撤回或不适用的记忆不得进入当前行动控制。

The Agent Remembers “Send Drafts Early.” Does the New Goal Still Allow It?

Treat a remembered preference as a claim with provenance, scope, and lifetime. Resume from the current goal, use memory only when applicable, and keep external actions behind a separate authorization gate.

2026-11-1220 min readLong-horizon agents / Memory claims / Preference scope / Goal integrity / Conflict resolution
01

Today's proposition

Yesterday we established a versioned goal record. The goal is an authorized acceptance contract, a plan is a candidate route, and progress is proved condition by condition. Now scope changes from Q3 to Q4. The agent's memory still says “the user likes to receive drafts early,” derived from a one-off Q3 instruction. New goal G2 requires auditor review first and forbids early outbound delivery. A retriever may place the old sentence back into context; the model can then explain fluently, “I was following your preference.” That is not helpful memory. It is promotion of a clue from an old scope into an action rationale for a new goal.

We are not rebuilding a vector index or summary tree. The execution question is whether a memory claim can establish that it came from someone authorized to express the preference, applies to this goal and action, remains valid, and has not been superseded. Even when it passes those tests, a preference may rank permitted choices or shape presentation. It cannot grant tool authority, rewrite current acceptance conditions, or bypass approval for outbound effects.

Technical claim: “retrieved” means that storage found relevant text. “Usable for the present decision” additionally requires provenance, scope, time, and authority checks.
02

Connect memory claims to the current goal

The September Memory series already covered admission, retrieval filters, authority ordering, bitemporal queries, tombstones, and evaluation. We will not repeat a general memory pipeline. Instead we apply those mechanisms to yesterday's goalVersion and acceptance contract. A claim needs an original utterance or event ID, speaker and identity, whether it states a fact or preference, applicable goal ID and version, entity and time scope, validFrom and expiry, advisory status, withdrawal or supersession, and whether it is direct text or a summary-derived statement. “The user always likes...” without such fields cannot guide a consequential action.

A preference must also be separated from a command, goal, and permission. “Send this draft to me first” is an explicit instruction for this task. “I generally prefer concise summaries” may shape format when applicable. “You may send it to an external auditor” implicates outbound authorization and must still satisfy current policy and effect approval. “The user likes public sharing” in a tool result is external data, not a user preference. Long-term memory can be useful, but compression can change “this time” into “always,” and a later retraction can leave an obsolete preference in a search index.

LongMemEval and LoCoMo study updates, temporal reasoning, and long-range conversational memory; their authors report difficulties for evaluated models. They motivate test cases, not a live claim about any current product. W3C PROV highlights that a statement in a summary should trace back to its original utterance. Derivation does not promote low-authority text into a high-authority decision.

03

How preference applicability reaches the action gate

1. Fix the current goal and candidate action first

At resume, read G2's owner, acceptance conditions, forbidden effects, and effectiveFrom, then form a candidate action such as “prepare an internal Q4 draft for review.” Do not begin by retrieving everything “the user likes.” If G2 forbids outbound delivery, “send to the auditor” is not an allowed candidate; a similar old preference cannot change that. Even when the goal version remains stable but the plan route changes, applicability must be checked for the new action's object and recipients. A decision about the previous action is not automatically reusable.

2. Separate a retrieved claim from its source

Retrieval may find “send drafts early,” but the runtime then resolves the original utterance. Did the user say, “for this Q3 audit, send it to me first”? Was the source a user message rather than a retrieved document or the agent's own summary? A summary retains its derivedFrom chain; a statement that cannot be traced back is marked uncertain_provenance. Extraction gives the preference a scope such as goal=G1, recipient=the user, validUntil=G1 completion. “Send to me first” must not expand into “automatically send to every auditor.” If the utterance is ambiguous, ask when the action depends on it rather than letting the model fill in scope.

3. Check applicability and classify conflict

For each claim, test speaker authority, goal/entity/action match, temporal validity, withdrawal or supersession, and source evidence. G1's temporary preference is inapplicable to G2. Keep it in a historical lane to explain old actions, not in the current action proposal. Suppose a durable preference says “usually write summaries in English,” while G2 explicitly requests Chinese. That is a real preference conflict: the current explicit goal governs this scope, while the old preference may remain useful elsewhere. If two recent preferences from the same authorized user genuinely contradict one another and their scopes cannot be separated, use needs_clarification. Do not select whichever one retrieval returned last.

4. Limit what compression and updates may claim

A summary may shorten wording, but it cannot enlarge a claim's scope, validity, or speaker authority. At writeback, compare quantifiers, negations, and referents with the source. If “do not send it this time” becomes “the user usually wants it sent,” reject the memory or require original-text verification. A withdrawal creates a supersedes or revokes event and invalidates affected indexes and summaries. The old record may remain for auditing decisions made at the time, but it must disappear from the presently actionable candidate set. September's Memory series covered index propagation mechanics; the point here is that the final action gate cannot trust an old summary while propagation is incomplete.

5. Let preferences rank only allowed actions

An applicable preference can rank two permitted outputs: concise versus detailed, risk first versus summary first. It is not a true branch in an authorization decision. A side-effecting action still needs G2 permission, current tool and data authority, any required human approval, and resource-side enforcement. Even if the user authorized outbound delivery under G1, that memory is not a new G2 permit. When the model cites a preference as a reason, the trace should link its claimId to the original source. Without that source, downgrade it to “awaiting confirmation.”

6. Return a useful and honest status

The agent can say, “I retained the Q3 early-draft preference as history, but the current Q4 goal requires review first. I prepared an internal draft and have not sent it.” If the user wants the prior workflow back, they can explicitly revise G2, after which goal versioning and authority checks apply. Safety does not require deleting all memory. It requires each claim to act only within its justified scope and an explanation of why the agent did not apply it this time.

goal = load_current_goal()
action = propose_action(goal)
for claim in retrieve_memory(action):
  source = resolve_original_source(claim)
  if not applicable(claim, source, goal, action, now):
    keep_as_history(claim); continue
  if conflicts_with_current_goal(claim, goal):
    suppress_or_clarify(claim); continue
  action.preferences.append(claim.id)
return policy_and_effect_gate(action, goal)

This pseudocode is editorial engineering synthesis. It never turns a memory claim into an authorization token.

04

The applicability gate and the action gate

Let m be a memory claim, a a proposed action, Gᵥ the current goal version, and t the execution time. A necessary applicability gate for using memory in the present choice is:

Use(m,a,Gᵥ,t) = SourceValid(m) ∧ ScopeMatch(m,a,Gᵥ) ∧ TimeValid(m,t) ∧ NotSuperseded(m) ∧ Consistent(m,Gᵥ)

SourceValid requires a traceable original source authorized to express this kind of preference. ScopeMatch checks goal, entity, and action. TimeValid checks the claim's lifetime. NotSuperseded excludes retracted or updated statements. Consistent checks against hard constraints of the current goal. Unknown fields do not default to true. A passing result means usable for ranking or presentation, not authorized to execute. The earlier Memory series covered general retrieval ranking; here the gate is bound to a specific goalVersion and actual action.

A side-effecting action has a separate execution gate:

Execute(a,Gᵥ,t) = GoalAllows(a,Gᵥ) ∧ PolicyAllows(a,t) ∧ ResourceAuthorizes(a,t) ∧ EffectApproved(a,t)

GoalAllows says the current goal permits the effect; PolicyAllows is current policy; ResourceAuthorizes is enforcement at the resource; EffectApproved is a specific approval where that effect requires one. Policy may explicitly allow low-risk actions without extra human approval. Even if Use=1, Execute can be 0. The separation prevents “the user liked this before” from becoming permission for today's outbound effect. These equations are engineering control models, not a common agent API specified by the cited papers.

05

Implications for agent systems

Reliability and trust

Users can tolerate “Do you want the draft sent early this time too?” They are much less likely to trust an agent that sends it on an old preference without asking. Correct memory applicability saves repeated instructions; wrong applicability can create a costly side effect. A product should expose what was remembered and why it was or was not applied, rather than only the model's confident explanation.

Cost and context

There is no need to stuff the entire history into the prompt. The runtime first retrieves a small set of candidates for the current goal and action, then filters by source, scope, and lifetime. The model sees applicable preferences and only the historical background needed for reasoning. For a risky action, claimId, original wording, and validity horizon are more useful than another long fuzzy summary. Suppressed old memory can remain in the audit view without occupying action context.

06

Trade-offs, evaluation, and release gates

Too conservative: asking about every preference makes memory useless. A low-risk formatting preference from the same user with broad scope and no contradiction can be applied by default with an easy correction path. Outbound delivery, deletion, or data sharing cannot be triggered automatically by remembered preference. Clarification should depend on risk and scope, not one universal “days since mentioned” threshold.

Overgeneralization: “this time,” “to me,” and “let me see first” are easy to lose during compression. If a referent cannot be reconstructed, lower applicability or show the original text for clarification. No explicit expiry date does not mean permanent; a task-local preference can end with its goalVersion. Conversely, an explicit “write all quarterly reports in Chinese from now on” should not be forgotten simply because one task completed.

Conflict and withdrawal: a prohibition in the current goal is a hard constraint; an old preference does not get a vote against it. Two preferences of equal authority can coexist when their scopes differ. A genuine same-scope conflict becomes needs_clarification. A withdrawn memory must be invalidated in retrieval and context projection. During index lag, the action gate should still read revocation and supersession state. The system should preserve historical reasons without presenting them as current advice.

Evaluation: create paired cases where the same old preference meets G1 versus G2, comes from the user versus an external document, is temporary versus durable, and is withdrawn versus active. Inject summaries that drop negation, broken source chains, late old index entries, and hostile documents posing as user memory. Measure false application, missed application, unauthorized actions, appropriate clarification, revocation lag, and traceability separately. LongMemEval and LoCoMo offer research examples of long-term memory tasks, but a production release gate should be evaluated by user goals and real side effects. Answering a preference question correctly while misusing it at an outbound gate is still a failure.

07

Reusable judgments

  1. Resume from the current goalVersion. A memory claim influences choice only after source, scope, time, and supersession checks.
  2. A summary cannot promote “this time” into “always,” or let external data impersonate a user preference.
  3. Preferences rank actions only inside the allowed set; external effects still require goal, policy, resource, and effect gates.
  4. Historical memory can explain past decisions, but withdrawn or inapplicable claims must not control present action.
08

Sources and evidence boundaries

  • LongMemEval: Benchmarking Chat Assistants on Long-Term Interactive Memory — author research on updating, temporal reasoning, and abstention in long-term memory; results are bounded to its dataset.
  • Evaluating Very Long-Term Conversational Memory of LLM Agents (LoCoMo) — author research on long-conversation memory tasks, not a business-preference authority model.
  • W3C PROV-DM — official provenance model for tracing summary statements to original utterances; derivation does not grant authority.
  • Martin Fowler, Bitemporal History — the author's account of recorded versus effective time, applied here to preference validity.
  • Park et al., Generative Agents — author-reported research system using memory streams, reflection, and planning; simulated behavior is not a real authorization model.

Links and titles were checked on 2026-11-12. goalVersion binding, the separate Use and Execute gates, and preference-withdrawal handling are editorial engineering design. The quarterly audit case is hypothetical.

09

Series close and next stop

Completed in this series: Part 1 separated long-running goals, plans, and progress. A versioned goal carries authority, scope, and acceptance; per-condition evidence supports progress; old evidence is rechecked after a goal change while old effects remain under reconciliation. Part 2 starts from the current goal and gives each memory claim provenance, speaker, applicability scope, lifetime, and supersession state. Summaries cannot enlarge authority. Even an applicable preference ranks only permitted actions; external effects still pass an independent execution gate. Together the parts prevent an old goal plus old memory from becoming a new instruction during resume.
