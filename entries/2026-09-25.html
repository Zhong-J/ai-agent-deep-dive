Tool schema 如何决定 Agent 能做什么？

从 JSON Schema 到语义契约、capability 设计、两阶段 validation、错误 taxonomy 与副作用边界。

2026-09-25约 20 分钟Tool schema / JSON Schema / Capability design / Validation / Tool contracts
01

今日命题

给 LLM 一个 tool，不只是告诉它“有个函数可以调用”。tool name、description、parameter schema 和 result/error shape 共同定义模型可生成的动作语言。若 schema 允许任意 filesystem path、SQL 或 HTTP URL，模型动作空间接近通用解释器；若只允许 resourceId、批准过的 operation enum 和有界参数，许多危险动作在生成层面就不可表达。

但 schema-valid 不等于安全或正确。JSON Schema 能证明 amount 是正数、currency 属于枚举，却不能证明账户属于当前 tenant、余额足够、审批仍有效、请求可安全重试或 effect 尚未发生。这些属于语义契约和 runtime policy。工具系统至少有三层：模型可见语法、runtime 验证的语义与授权、effect owner 真正执行的业务边界。

核心判断：tool schema 是 Agent action space 的编译接口，不是 API 文档的自动复制。好的 schema 让合法意图容易表达、危险歧义无法表达；好的 contract 再保证同一结构在权限、时间、重试和结果上具有稳定语义。
02

承接 Runtime 与 Memory：command 必须可判定

Agent Runtime 已区分 typed command、callId、attemptId 与 lifecycle；Memory 系列又要求 authority、scope、valid time 和 provenance 显式化。tool schema 是两条线的连接点：模型提出的自然语言意图必须在 dispatch 前编译成可验证 command。runtime 将 principal、tenant、approval、deadline 与 idempotency key 作为可信 execution context 注入，而不是允许模型填写。

例如 send_email(to, body) 把 recipient resolution、sender identity、sensitivity、模板、附件和确认策略藏在自由文本里。更强的 contract 可以是 send_approved_notification(notificationDraftId, recipientGroupId, approvalId)：模型选择已存在 capability，runtime 解析真实地址并重新验证 approval。它牺牲通用性，换来更小动作空间和更强审计。

tool 与底层 API 因此不必一一对应。一个模型工具可编排多个内部 API；一个底层 endpoint 也可暴露成多个按风险分层的 capabilities。设计目标不是减少 wrapper，而是把模型负责的认知选择与系统负责的确定性控制切开。

03

机制：从 schema 到一次可安全执行的 call

1. 从 decision 建 action vocabulary

先列 workflow 必须做的业务动作，而不是把 service Swagger 全量暴露。每个 tool 对应可审计 capability：query、draft、validate、commit、revoke 分开；read/write 分开；preview/commit 分开；高风险 action 先生成 draft 或 plan。

2. Name/description 是检索接口

模型通常先根据 name/description 选 tool，再生成 arguments。名称使用稳定动词+对象，description 明确何时使用、何时不用、前置条件和副作用。多个近义工具若只以团队缩写区分，selection error 在参数 validation 前已经发生。

3. 用 schema 缩小语法空间

优先 enum、oneOf/discriminator、bounded number、format、pattern、min/max items 与 additionalProperties:false。用 resource ID 代替任意 URL/path，用 structured filter 代替 SQL，用 ISO timestamp+timezone policy 代替含糊自然语言。optional 字段区分 absent、null 与 empty；默认值由 runtime 填，不能让模型猜。

4. 可信 context 不进入模型参数

tenantId、principalId、roles、credential、approval scope、traceId、deadline、idempotency key 由 runtime/session 注入。若 schema 暴露 tenantId，prompt injection 可诱导模型跨租户；即使 authorization 最终拒绝，也扩大攻击面和日志噪声。

5. 两阶段 validation

第一阶段做 schema validation：类型、必填、枚举、长度、未知字段。第二阶段做 semantic validation：resource 是否存在且属于 tenant、状态是否允许 transition、approval 是否覆盖当前 args、policy 是否允许 purpose、乐观版本是否仍匹配。错误码分开，模型才能修复参数而不反复挑战权限。

6. Normalize 后再 fingerprint

时区、大小写、空白、ID alias 和默认值先规范化，再生成 canonical command 与 request hash。相同业务意图获得同一 fingerprint；amount 或 recipient 变化必须产生不同 hash。schema/tool version 进入 fingerprint，防止升级后同 key 表示不同语义。

7. Dispatch contract

adapter 映射到 effect owner，传递 deadline、cancellation、idempotency/fencing context。runtime 不把 HTTP 200 自动当业务成功，而解码 accepted/completed/rejected/pending/outcome_unknown union。异步 operation 返回 operationId 和 query capability，而不是让模型轮询自由文本。

8. Error taxonomy

至少分 validation_error、authorization_denied、precondition_failed、rate_limited、transient_unavailable、outcome_unknown、business_rejected 与 internal_contract_error。每类声明 retryable、user-actionable、safe-to-rephrase、requires-reconciliation。不要只返回 “Something went wrong”，也不要把 stack trace 交模型。

9. Result schema 与 provenance

结果只返回下一决策所需字段，包括 resource/version、status、observedAt、source、warnings 与 nextActions。避免庞大 backend object 挤占 context，也不能省略版本导致 stale update。tool output 仍是 untrusted data；返回文本不能借 tool 身份获得 system instruction authority。

10. Contract evolution

breaking change 创建新 tool/schema version；旧 execution pin 旧语义。增加 optional 字段也影响模型选择和 token cost。部署前用 recorded calls 做 compatibility replay，检查 old args、new validator、result decoder 和 retry policy。撤销 tool 时返回 typed unavailable/deprecated，不得静默复用名称指向新 effect。

11. 分层评测 contract

tool eval 不能只统计最终 task success。先用只有 name/description 的样本测 selection confusion；再固定正确 tool 测 arguments exactness、schema validity 与 repair turns；随后用资源状态和 policy fixtures 测 semantic reject/allow；最后用 fake effect owner 测 idempotency、timeout、typed result 和 replay。mutant tests 故意交换两个近义 description、放宽 additionalProperties 或删掉 version 字段，验证评测能否捕获 contract regression。

12. Dispatch 前重验 capability

catalog 中可见不代表执行时仍获授权。selection 与 dispatch 之间可能发生 role revocation、approval expiry、resource version change 或 tool disable。runtime 在最后边界以当前 policy 和 normalized args 重验；approval digest 必须覆盖 material fields。这个 TOCTOU gate 失败时返回 typed precondition/authorization error，不能让模型“解释一下”后绕过。

04

必要数学：动作空间与错误放大

组合空间

若 schema 字段 i 有 nᵢ 个可选值，粗略动作组合数 |A|≈∏nᵢ。三个 free-form strings 实际近似无界；operation 5 个 enum、授权 resource 20 个、mode 2 个时约 200 种。估算忽略依赖约束，却说明 enum/oneOf 不只是 validation，也是搜索空间压缩。

流水线成功率

工具选择正确率 pₛ、syntactic validity pᵥ、semantic validity pₘ、execution success pₑ、result interpretation pᵣ，简化端到端 P≈pₛpᵥpₘpₑpᵣ。各层 0.95 时约 0.774。structured output 只提高 pᵥ，不能替代 selection、semantic validation 或 result handling。

Contract utility

可比较 U=TaskSuccess−λ·Risk−μ·Latency−ν·TokenCost。更细 schema 可能提高 success、降低 risk，却增加 description tokens 和选择负担。过多微工具也会降低 pₛ。目标不是字段越多越好，而是在风险约束下最大化任务效用。

05

对 Agent 系统的影响

能力：capability-oriented tools 把 backend 组合成模型可可靠选择的业务动作。Agent 不需理解 OAuth、tenant routing 或 transaction internals，却能在受控范围完成任务。

可靠性：typed results/error taxonomy 让 retry、reconciliation、human escalation 由 runtime 决定，不靠模型猜 error string。schema version 与 fingerprint 把 tool evolution 纳入 durable execution。

安全：最强控制不是 prompt 说“不要做 X”，而是 schema 无法表达 X、runtime 不注入 capability、effect owner 再验证 principal/policy。三层 defense 避免单点。

成本：更窄工具增加 adapter 和 contract tests，但减少无效调用、重试与 context noise。指标分 selection error、schema invalid、semantic reject、authorization deny、effect failure、outcome unknown、result decode；总 tool success 无法定位设计问题。

06

设计取舍与失败模式

  • Swagger 直出：大量 endpoint/字段使选择困难且暴露内部控制；先设计业务 capability。
  • 万能 execute：自由 SQL/shell/URL 动作空间无界；仅在强 sandbox 和人工边界使用。
  • 过度微工具：几十个近义函数降低 selection；按认知决策而非每个 endpoint 切分。
  • schema-valid 幻觉：resourceId 类型正确但不存在或越权；semantic/policy validation 必须存在。
  • 默认值歧义：缺省 recipient/mode 可能危险；高风险字段 required，默认由可信 runtime 决定。
  • 错误全重试：authorization/business reject 被当 transient；typed taxonomy 与唯一 retry owner。
  • 结果过大：backend payload 挤 context 并携 injection；裁剪、分页、引用 artifact。
  • 静默版本漂移：同名改语义使 replay/idempotency 失效；显式 version 与 compatibility replay。
07

可复用的技术判断

  • tool schema 定义模型可表达的动作语法；tool contract 定义权限、状态、重试和结果语义。
  • 不要复制 backend API；按业务 capability 切分 read/draft/validate/commit。
  • tenant、principal、credential、approval、deadline、idempotency 由 runtime 注入。
  • schema validation 与 semantic/policy validation 分层；error/result 使用 typed union。
  • tool evolution 需要 version、canonical fingerprint、recorded-call replay 与旧 execution 兼容。
08

Tools and Extensibility Internals · Part 1 of 4

How Does a Tool Schema Define What an Agent Can Do?

From JSON Schema to semantic contracts, capability design, two-stage validation, error taxonomies, and side-effect boundaries.

2026-09-2520 min readTool schema / JSON Schema / Capability design / Validation / Tool contracts
01

Today's proposition

Giving an LLM a tool is not merely telling it that a function exists. Tool name, description, parameter schema, and result or error shape jointly define the action language the model can generate. A schema allowing arbitrary filesystem paths, SQL, or HTTP URLs approaches a general interpreter. A schema limited to resource IDs, approved operation enums, and bounded parameters makes many dangerous actions inexpressible at generation time.

Yet schema-valid does not mean safe or correct. JSON Schema can prove that amount is positive and currency belongs to an enum. It cannot prove that an account belongs to the current tenant, funds are available, approval remains valid, retry is safe, or the effect has not already happened. Those properties belong to semantic contracts and runtime policy. A tool system therefore has at least three layers: model-visible syntax, runtime-validated semantics and authorization, and the business boundary where an effect owner executes.

Core judgment: a tool schema is the compilation interface for an agent's action space, not an automatic copy of API documentation. A good schema makes valid intent easy to express and dangerous ambiguity impossible to express. A good contract then gives the structure stable meaning across permission, time, retry, and result handling.
02

From runtime and memory to decidable commands

Agent Runtime distinguished typed commands, call IDs, attempt IDs, and lifecycle. The Memory series made authority, scope, valid time, and provenance explicit. A tool schema connects the two: natural-language intent must compile into a verifiable command before dispatch. Runtime injects trusted execution context such as principal, tenant, approval, deadline, and idempotency key rather than allowing the model to fill them.

A tool named send_email(to, body) hides recipient resolution, sender identity, sensitivity, template, attachments, and confirmation policy inside free text. A stronger contract might be send_approved_notification(notificationDraftId, recipientGroupId, approvalId). The model selects an existing capability; runtime resolves actual addresses and revalidates approval. Generality decreases, but action space and audit become tractable.

Tools therefore need not map one-to-one to backend APIs. One model tool may orchestrate several internal APIs; one backend endpoint may be exposed as multiple capabilities by risk tier. The objective is not fewer wrappers. It is separating cognitive choice assigned to the model from deterministic control assigned to the system.

03

Mechanism: from schema to a safely executable call

1. Derive an action vocabulary from decisions

List business actions required by the workflow rather than exposing an entire service Swagger document. Each tool represents an auditable capability. Query, draft, validate, commit, and revoke are modeled separately. Reads and writes remain distinct; preview and commit remain distinct; high-risk actions first create a draft or plan.

2. Names and descriptions form a retrieval interface

The model often selects a tool from name and description before generating arguments. Use stable verb-object names. Descriptions state when to use the tool, when not to use it, prerequisites, and side effects. Near-duplicate tools distinguished only by team acronyms cause selection failure before argument validation can help.

3. Shrink syntax with schema

Prefer enums, oneOf with discriminators, bounded numbers, formats, patterns, item bounds, and additionalProperties false. Use resource IDs instead of arbitrary URLs or paths, structured filters instead of SQL, and ISO timestamps with timezone policy instead of ambiguous language. Optional fields distinguish absent, null, and empty. Runtime supplies defaults; the model does not guess them.

4. Keep trusted context out of model arguments

Tenant ID, principal ID, roles, credentials, approval scope, trace ID, deadline, and idempotency key are injected by runtime or session. If tenant ID appears in the schema, prompt injection can ask the model to cross tenants. Authorization may reject it eventually, but exposure still expands attack surface and log noise.

5. Validate in two stages

Schema validation covers types, required fields, enums, lengths, and unknown properties. Semantic validation checks whether a resource exists and belongs to the tenant, state permits the transition, approval covers the exact arguments, policy permits the purpose, and optimistic version still matches. Separate error codes let the model repair malformed arguments without repeatedly challenging authorization.

6. Normalize before fingerprinting

Normalize timezone, case, whitespace, ID aliases, and defaults before creating a canonical command and request hash. The same business intent should produce the same fingerprint; changing amount or recipient must change it. Schema and tool versions enter the fingerprint so an upgrade cannot give one key a new meaning.

7. Define dispatch semantics

An adapter maps the command to the effect owner and carries deadline, cancellation, idempotency, and fencing context. Runtime does not equate HTTP 200 with business success. It decodes a result union such as accepted, completed, rejected, pending, or outcome unknown. An asynchronous operation returns an operation ID and query capability rather than asking the model to poll free-form text.

8. Define an error taxonomy

Distinguish validation error, authorization denied, precondition failed, rate limited, transient unavailable, outcome unknown, business rejected, and internal contract error. Each class declares whether it is retryable, user-actionable, safe to rephrase, or requires reconciliation. Do not return only “something went wrong,” and do not send raw stack traces to the model.

9. Shape results and provenance

Return only fields needed for the next decision, including resource and version, status, observed time, source, warnings, and next actions. Avoid flooding context with backend objects, but do not omit versions needed to prevent stale updates. Tool output remains untrusted data inside a content boundary; returned text does not gain system authority merely because it came from a tool.

10. Evolve contracts deliberately

A breaking change creates a new tool or schema version, while old executions remain pinned to old semantics. Even optional fields can affect model choice and token cost. Before deployment, replay recorded calls through the new validator, decoder, and retry policy. A revoked tool returns a typed unavailable or deprecated result instead of silently reusing its name for a different effect.

11. Evaluate the contract by layer

Tool evaluation cannot report final task success alone. First test selection confusion using only names and descriptions. Then hold the correct tool fixed and measure argument exactness, schema validity, and repair turns. Next use resource-state and policy fixtures to test semantic allow and reject. Finally use a fake effect owner to exercise idempotency, timeout, typed results, and replay. Mutant tests deliberately swap two similar descriptions, relax additionalProperties, or remove a version field to prove that evaluation detects contract regression.

12. Revalidate capability at dispatch

Visibility in a catalog does not prove authorization still exists at execution time. Between selection and dispatch, a role may be revoked, approval may expire, a resource version may change, or the tool may be disabled. Runtime revalidates current policy against normalized arguments at the final boundary, and the approval digest covers every material field. A time-of-check to time-of-use failure returns a typed precondition or authorization error; the model cannot explain its way around it.

04

Essential mathematics: action space and error amplification

Combinatorial action space

If schema field i has nᵢ possible values, a rough action count is |A|≈∏nᵢ. Three free-form strings are effectively unbounded. Restricting operation to five enums, resource to twenty authorized IDs, and mode to two values yields about two hundred combinations. The estimate ignores dependent constraints, but shows that enum and oneOf compress search, not merely validate output.

Pipeline success

Let correct tool selection be pₛ, syntactically valid arguments pᵥ, semantic validity pₘ, execution success pₑ, and correct result interpretation pᵣ. A simplified end-to-end rate is P≈pₛpᵥpₘpₑpᵣ. Five layers at 0.95 yield about 0.774. Structured output improves pᵥ only; it does not replace selection, semantic validation, or result handling.

Contract utility

Compare designs using U=TaskSuccess−λ·Risk−μ·Latency−ν·TokenCost. A finer schema may improve success and reduce risk while increasing description tokens and selection burden. Too many micro-tools can lower pₛ. The objective is not maximal field count but maximal task utility subject to risk constraints.

05

Implications for agent systems

Capability: capability-oriented tools package backend complexity into business actions the model can select reliably. The agent need not understand OAuth, tenant routing, or transaction internals, yet completes work inside a controlled boundary.

Reliability: typed results and error taxonomies let runtime decide retries, reconciliation, and human escalation rather than asking a model to interpret strings. Schema versions and fingerprints integrate tool evolution with durable execution.

Security: the strongest control is not a prompt saying “do not do X.” The schema cannot express X, runtime does not inject the capability, and the effect owner revalidates principal and policy. Three layers prevent a single point of failure.

Cost: narrower tools require more adapters and contract tests, but reduce invalid calls, retries, and context noise. Metrics separate selection error, schema invalid, semantic rejection, authorization denial, effect failure, outcome unknown, and result decoding. One overall tool-success rate cannot diagnose design.

06

Trade-offs and failure modes

  • Raw Swagger export: too many endpoints and fields make selection difficult and expose internal controls. Design business capabilities first.
  • Universal execute: arbitrary SQL, shell, or URLs create an unbounded action space. Use only inside strong sandboxes and human boundaries.
  • Too many micro-tools: dozens of near-synonyms reduce selection. Split by cognitive decision, not every endpoint.
  • Schema-valid hallucination: a resource ID has the correct type but does not exist or is unauthorized. Semantic and policy validation remain mandatory.
  • Ambiguous defaults: default recipient or mode may be dangerous. Require high-risk fields; trusted runtime supplies defaults.
  • Retry every error: authorization and business rejection are treated as transient. Use typed taxonomy and one retry owner.
  • Oversized results: backend payloads consume context and carry injection. Trim, paginate, and reference artifacts.
  • Silent version drift: changing semantics under one name breaks replay and idempotency. Use explicit versions and compatibility replay.
07

Reusable technical judgments

  • A tool schema defines the syntax of model-expressible actions; the contract defines permission, state, retry, and result semantics.
  • Do not copy backend APIs. Split read, draft, validate, and commit by business capability.
  • Runtime injects tenant, principal, credentials, approval, deadline, and idempotency.
  • Separate schema validation from semantic and policy validation. Use typed unions for errors and results.
  • Tool evolution needs versions, canonical fingerprints, recorded-call replay, and compatibility for old executions.

09

What is established and where we continue

Established today: schemas shrink action syntax, semantic and policy contracts determine whether calls are permitted, and adapters or effect owners define business meaning. Runtime injects trusted identity, approval, and idempotency. Typed errors and results support recovery and audit.

Still unresolved: when tools come from dynamic servers, MCP registries, skills, or plugins, how are they discovered, filtered, namespaced, authorized, and cached? How does a host resist malicious descriptions, schema drift, and capability confusion?
