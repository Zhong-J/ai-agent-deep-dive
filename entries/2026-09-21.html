Context 与 Memory 系统 · 第 1/4 篇

把所有历史塞进 prompt，为什么不等于“有记忆”？

拆开 context window、event log、working state、retrieval index 与 durable memory，并跟踪一次 context assembly 的完整读写路径。

2026-09-21约 20 分钟Context engineering / Working state / Retrieval / Durable memory / Provenance
01

今日命题

LLM 每次生成只直接读取本次请求中的 token，以及推理期间由这些 token 建出的 KV cache。它不会在下一次请求里自动“想起”上一次调用；Agent 看起来有连续性，是 runtime 把先前事件、状态与检索结果重新序列化进下一次输入。context window 因而是当前计算的有限工作面，不是持久数据库，也不是模型内部新增了一段可寻址记忆。

把 transcript 原样追加似乎最诚实，却混合了事实、过期计划、工具噪声、失败尝试、恶意内容与重复结论。容量再大也不能解决来源冲突、时间有效性和任务相关性；长输入还增加 prefill 成本，并可能让关键证据在位置与语义干扰中更难被使用。

核心判断：可靠 memory 不是“保存更多”，而是把 event log、working state、retrieval index 与 durable records 分开管理，再由 context assembler 按任务、权限、时效与 token budget 生成一个带 provenance 的临时视图。
02

History 可重放，不代表应该全喂给模型

上一系列把 durable event history 定义为 control plane 的事实账本：为了 replay 与审计，它应完整且不可随意改写。但模型 context 的目标不同——用有限 token 支持下一次决策。把事实账本等同于 prompt，会把 durability 的正确性要求误移植成输入策略。

一次部署可能产生 8,000 条 heartbeat、三次失败日志、旧审批和最终成功回执。replay 需要全部顺序；下一步判断只需当前目标、已选 commit、最新审批范围、部署结果与相关异常。working state 是事件归约出的“现在”；retrieval 是按问题选出的候选证据；durable memory 是跨任务复用、经过写入策略的记录。它们生命周期和信任等级不同。

因此 context engineering 不是 prompt 文案优化，而是编译过程：从任务和状态生成信息需求，查询多个存储，执行安全过滤，分配稀缺 token，并把不同 trust domains 序列化成模型可读、却不混淆 authority 的输入。

03

机制：一次 context assembly 的读写路径

1. 四类对象

Transcript/event log 记录发生过什么，服务 audit、replay、debug，不承诺每条都相关。Working state 是 reducer 产出的结构化当前态：goal、plan version、open calls、constraints、accepted results。Durable record 可跨 execution 读取，必须有 subject、source、valid time、confidence、ACL 与 supersedes。Retrieval index 是找候选的派生结构；embedding 命中不是事实认证。

2. 编译 requirements

assembler 不应只拿最后一条消息做向量搜索。它先生成 typed requirement：待决策问题、必须引用的 authoritative state、历史先例、时间范围、tenant/subject、允许数据域与 token budget。退款邮件需要当前退款状态与联系方式，不应因语义相似召回另一客户模板。

3. 多路召回与硬过滤

候选可来自 structured query、BM25、dense embedding、graph edge 与 recent-event window。合并后先按 ACL、tenant、subject、validFrom/validTo、record status、source class、schema compatibility 过滤；这些是 correctness gate，reranker 不能覆盖。superseded 记录默认不作 active fact，但可解释变化。

4. 排序、冲突与去重

按 relevance、authority、freshness、specificity、novelty 排序；重复 chunk 归并到同一 source。冲突的高权威记录不能只选 top-1，应同时暴露差异、时间与 provenance。cross-encoder 或 LLM reranker 只产生 selection score，不产生事实。

5. 保留 invariant 再分配 token

policy、当前 goal、hard constraints、open side effects 与 authoritative state 属于 reserved region；examples、conversation、retrieved evidence 在剩余预算竞争。每块标来源、时间、可信类型、是否为 instruction。外部文档放在 data boundary，避免“忽略前文”升级为 control instruction。

6. 稳定序列化

模板分开 instruction、current state、evidence、conversation 与 output contract。证据使用 immutable recordId/version，便于 trace。长 artifact 只放 task-specific slice 与可回查 pointer；summary 指向源并声明覆盖范围，不能冒充原文。

7. 写回 admission

模型输出首先是 proposal。tool result 进入 event log；memory candidate 经过 schema、PII/secret、source attribution、conflict、dedup 检查，才 create、update、supersede、reject 或留在本次 execution。用户明确偏好可入库；模型猜“用户可能讨厌表格”不能无标记升格为事实。

8. 每步重组

每个 transition 后重新计算需求与预算，而非永久累积 prompt。相同 state、policy、index snapshot 与 budget 应产生可解释的同一候选集合，即使模型采样仍会变化。

9. Assembly 自身也要可观测

每次调用保存 context manifest：assembler/policy version、query、index snapshot、候选 recordId、硬过滤原因、rank score、分区 token 数、最终引用与截断项。manifest 不必复制敏感正文，但要能在授权环境重建选择过程。错误答案才能被分类为 retrieval miss、filter bug、ranking error、serialization loss 或 model-use failure，而不是反复盲调 top-k。

10. 一个冲突实例

profile 说“默认用个人邮箱”，两小时前工单说“本项目只用公司邮箱”，CRM 又显示公司邮箱刚被撤销。正确 assembler 不能凭最高 cosine score 选一个：project instruction 更具体，但 revoked 状态阻塞执行，结果应是请求新地址或人工确认。memory 系统的价值不是只召回句子，而是保留 scope、authority、time 与 contradiction，使 Agent 能安全 abstain。

04

必要数学：token 预算与检索价值

容量约束

总 context 为 W tokens，预留输出 O，固定 policy P，working state S，则其余预算 B=W−O−P−S。若 B≤0，必须压缩 state 表达、换模型或拒绝任务；截断 policy 或未决副作用不是合法优化。输入增加还扩大 prefill 与 KV cache 成本，“容得下”不等于延迟可接受。

受约束选择

候选 i 的 token 成本 cᵢ、决策价值 uᵢ、选择变量 xᵢ∈{0,1}，理想目标为 max Σuᵢxᵢ，subject to Σcᵢxᵢ≤B。uᵢ 综合 relevance、authority、freshness、conflict coverage，而非 cosine similarity。权威约束虽不相似也可高价值；重复 chunk 边际价值近零。实践用分区配额、贪心与 rerank 近似。

检索指标拆分

需要的证据为 G、召回为 R，Recall=|G∩R|/|G|；最终入 context 为 K，Precision=|G∩K|/|K|。两者都不证明模型正确使用证据，还要测 citation correctness、temporal correctness、conflict detection 与 task success。

05

对 Agent 系统的影响

能力来自 state abstraction

长任务靠把“发生过什么”归约成“现在必须知道什么”，不是靠无限 transcript。typed state 支持换模型、压缩、worker handoff 与 recovery，recordId 保留回查路径。

可靠性来自 provenance 与时态

“预算是 10 万”没有 subject、currency、source、valid time 与 supersedes 就不可安全使用。schema 应表示 unknown、conflicting、expired，并区分 stored evidence 与 model inference。

安全边界进入 retrieval

权限过滤发生在候选交给模型之前；要求模型不泄露已检索越权内容太晚。外部文本是 data 与潜在 prompt injection，instruction 只能来自 trusted control region。

成本与可观测性

成本还包括 embedding、index、reranking、migration、冲突合并、加密与删除传播。trace 应记录候选、过滤原因、token 分配和引用，才能离线 replay 失败，而不是只调 top-k。

Latency 与 cache 行为改变架构选择

稳定、较短的 policy/state prefix 更容易复用 provider 或 runtime 的 prefix/KV cache；每步把整个 transcript 重新排序、插入动态摘要会降低 cache 命中，并让 prefill latency 随历史增长。assembler 因而应保持固定分区顺序，把高变化 evidence 放在明确区域，并记录实际 input tokens、cached tokens 与 time-to-first-token。缓存只改善计算，不改变 evidence freshness；命中旧 prefix 也不能绕过重新授权和时态过滤。

Context contract 也需要版本

assembler template、record schema、ranking features 与 token quota 的变化会改变 Agent 行为，即使模型版本不变。execution trace 应保存 contextSchemaVersion 和 assemblerVersion；离线 replay 要能用旧版本重建当时输入，再与候选新版本做 counterfactual comparison。否则一次上线后的质量变化会被误归因于模型，团队无法判断是检索、过滤、排序还是序列化发生漂移。

06

设计取舍与失败模式

  • 完整 transcript：易实现、审计多，但成本增长且旧指令污染；适合短 session，不是长期 memory architecture。
  • 只存摘要：便宜但固化遗漏；summary 应版本化、可回源、区分 confirmed facts、open questions 与 discarded detail。
  • 向量库即 memory：语义强，但 identifier、否定、数字、时间、权限需 hybrid retrieval 与 metadata filter。
  • recency 偏置：最新不等于最权威；freshness 与 authority 分开。
  • 自我污染：模型猜测写回后又被当证据；derived record 标注 inference、保留 source、提高 admission threshold。
  • 删除不完整：主记录删除但 embedding/cache/snapshot 仍在；删除是跨派生存储的 tombstone/propagation protocol。
  • top-1 隐藏冲突：高风险字段需 conflict set、authority rule 或人工 resolution。
  • 评测错位：hit rate 忽略错误使用、越权和过期；要用时间切片、对抗冲突和遗忘任务做 end-to-end eval。
07

可复用的技术判断

  • context window 是一次推理的有限工作面；连续性由 runtime 重建。
  • event log、working state、durable record、retrieval index 的目标与信任等级不同。
  • 先做权限/时态硬过滤，再做相关性排序和 token 分配。
  • memory 写入是带 provenance、冲突与 supersession 的 admission decision。
  • 评测覆盖 retrieval、selection、正确使用、时间有效性与删除传播，最终看任务质量。

Context and Memory Systems · Part 1 of 4

Why Is Putting All History in the Prompt Not Memory?

Separate the context window, event log, working state, retrieval index, and durable memory, then trace a complete context-assembly path.

2026-09-2120 min readContext engineering / Working state / Retrieval / Durable memory / Provenance
01

Today's proposition

On every generation, an LLM directly reads only the tokens in that request and the KV cache produced from them during inference. It does not automatically recall a previous call. An agent appears continuous because the runtime serializes earlier events, state, and retrieved records into the next input. The context window is therefore a finite workspace for the current computation, not a persistent database or newly addressable memory inside the model.

Appending the full transcript seems maximally faithful, but it mixes facts with obsolete plans, tool noise, failed attempts, hostile content, and repeated conclusions. More capacity does not resolve conflicts, temporal validity, or task relevance. Longer input also raises prefill cost and can make decisive evidence harder to use amid positional and semantic interference.

Core judgment: reliable memory is not “save more.” Manage the event log, working state, retrieval index, and durable records separately. At each step, a context assembler creates a provenance-bearing temporary view constrained by task, authorization, freshness, and token budget.
02

Replayable history is not model context

The previous series defined durable event history as the control plane's fact ledger. It remains complete and resistant to casual rewriting for replay and audit. Model context has another objective: support the next decision using finite tokens. Equating the fact ledger with the prompt mistakenly turns a durability requirement into an input-selection policy.

A deployment may accumulate 8,000 heartbeat events, three failed logs, an obsolete approval, and a final success callback. Replay needs their order. The next decision may need only the current goal, selected commit, latest approval scope, deployment result, and relevant anomaly. Working state is the present reduced from events. Retrieval selects candidate evidence for a question. Durable memory contains cross-task records admitted by a write policy. Their lifetimes and trust levels differ.

Context engineering is therefore not prompt-copy editing. It is compilation: derive information requirements from task and state, query multiple stores, enforce security filters, allocate scarce tokens, and serialize different trust domains without confusing data with authority.

03

Mechanism: one context-assembly read/write path

1. Define four object types

The transcript or event log records what happened for audit, replay, and debugging; not every event is relevant. Working state is the structured present produced by reducers: goal, plan version, open calls, constraints, and accepted results. A durable record is readable across executions and needs subject, source, valid time, confidence, ACL, and supersession links. A retrieval index is a derivative optimized for candidate discovery. An embedding match does not authenticate a fact.

2. Compile requirements

The assembler should not vector-search only the latest message. It derives a typed requirement: pending decision, mandatory authoritative state, useful historical analogies, time range, tenant and subject, permitted domains, and token budget. A refund-email step needs current refund status and contact details; semantic similarity must not inject another customer's old template.

3. Retrieve broadly, then hard-filter

Candidates may come from structured queries, BM25, dense embeddings, graph edges, and a recent-event window. Before reranking, enforce ACL, tenant, subject, valid-from and valid-to, record status, source class, and schema compatibility. These are correctness gates; a reranker cannot override them. Superseded records normally leave active facts but remain historical evidence for questions about change.

4. Rank, expose conflict, and deduplicate

Rank by task relevance, authority, freshness, specificity, and novelty. Merge duplicate chunks under one source. If authoritative records conflict, do not hide disagreement by choosing top-1; expose both with timestamps and provenance. A cross-encoder or LLM reranker produces a selection score, not a new authenticated fact.

5. Reserve invariants before allocating tokens

Policy, current goal, hard constraints, open effects, and authoritative state occupy a reserved region. Examples, conversation history, and retrieved evidence compete for the remainder. Label every block with source, time, trust type, and whether it is instruction. External documents stay inside a data boundary, so “ignore previous instructions” cannot become control authority.

6. Serialize stably

A template separates instruction, current state, evidence, conversation, and output contract. Evidence uses immutable record IDs and versions for tracing. A long artifact contributes a task-specific slice plus a dereferenceable pointer. A summary links to its source and declares scope; it cannot impersonate the original.

7. Write-back passes admission

Model output is initially a proposal. Tool results enter the event log. A memory candidate passes schema validation, PII and secret checks, source attribution, conflict detection, and deduplication. Policy then creates, updates, supersedes, rejects, or keeps it execution-local. An explicit preference may become durable; a model guess that the user dislikes tables must not silently become fact.

8. Reassemble at every step

After each transition, recompute requirements and budget rather than growing a permanent prompt. Given the same state, policy, index snapshot, and budget, the candidate set should be explainable and repeatable even when final model sampling varies.

9. Make assembly itself observable

Persist a context manifest for every call: assembler and policy versions, query, index snapshot, candidate record IDs, hard-filter reasons, ranking scores, per-partition token allocation, final citations, and truncated items. It need not duplicate sensitive text, but an authorized environment must reconstruct selection. A wrong answer can then be classified as retrieval miss, filtering defect, ranking error, serialization loss, or model-use failure. Without this boundary, teams repeatedly tune top-k and prompt wording without locating the failing subsystem.

10. A conflict example

Suppose a profile says “use personal email by default,” a ticket two hours ago says “this project must use corporate email,” and the CRM says the corporate address was just revoked. A correct assembler cannot pick one by highest cosine score. The project instruction is more specific, but revocation blocks execution, so the result must request a valid corporate address or human confirmation. Memory is valuable not merely because it recalls a sentence, but because it preserves scope, authority, time, and contradiction so the agent can abstain safely.

This example also separates retrieval from decision. All three records may be correctly retrieved; failure can still occur if serialization removes timestamps, if ranking hides the revocation, or if the model treats a default preference as stronger than project policy. The manifest makes those boundaries testable and lets evaluators compare the assembled evidence with the final action.

04

Essential mathematics: token budgets and retrieval value

Capacity constraint

Let total context be W tokens, reserved output O, fixed policy P, and working state S. The remaining budget is B=W−O−P−S. If B≤0, reduce state representation, choose a larger-window model, or reject the task. Truncating policy or unresolved effects is invalid. More input also expands prefill and KV-cache cost, so fitting does not imply acceptable latency.

Constrained selection

For candidate i, token cost is cᵢ, decision utility uᵢ, and selection xᵢ∈{0,1}. The idealized objective is maximize Σuᵢxᵢ subject to Σcᵢxᵢ≤B. Utility combines relevance, authority, freshness, and conflict coverage; it is not cosine similarity. An authoritative constraint can be valuable despite low similarity, while duplicate chunks add nearly zero marginal value. Partition quotas, greedy selection, and reranking approximate the optimization.

Separate retrieval metrics

Let G be evidence actually required and R the retrieved set. Recall=|G∩R|/|G|. Let K be final context; Precision=|G∩K|/|K|. Neither proves correct evidence use. Also test citation correctness, temporal correctness, conflict detection, and task success.

05

Implications for agent systems

Capability comes from state abstraction

Long tasks continue by reducing “what happened” into “what must be known now,” not through an infinite transcript. Typed state enables model switching, compression, worker handoff, and recovery, while record IDs preserve drill-back.

Reliability comes from provenance and time

“The budget is 100,000” is unsafe without subject, currency, source, valid time, and supersession. Schemas represent unknown, conflicting, and expired, and distinguish stored evidence from model inference.

The security boundary enters retrieval

Authorization filters candidates before the model. Asking a model not to disclose unauthorized content after retrieval is too late. External text is data and possible prompt injection; instructions come only from a trusted control region.

Cost and observability

Costs include embeddings, indexes, reranking, migrations, conflict merging, encryption, and deletion propagation. Traces record candidates, filter reasons, token allocation, and citations so failures can be replayed offline instead of blindly tuning top-k.

Latency and cache behavior change the architecture

A stable, relatively short policy-and-state prefix is easier for a provider or runtime to reuse through prefix or KV caching. Reordering the entire transcript or inserting a changing summary at every step reduces cache hits and lets prefill latency grow with history. The assembler should keep partitions in stable order, place volatile evidence in an explicit region, and record actual input tokens, cached tokens, and time to first token. Caching improves computation only; it does not establish evidence freshness. A cached prefix cannot bypass renewed authorization and temporal filtering.

The context contract also needs a version

Changes to assembler templates, record schemas, ranking features, and token quotas alter agent behavior even when the model version remains constant. Execution traces should retain a context schema version and assembler version. Offline replay must reconstruct the historical input with the old version, then compare it with a candidate version counterfactually. Otherwise a quality change after deployment is misattributed to the model, and the team cannot tell whether retrieval, filtering, ranking, or serialization drifted. Versioning also permits staged rollout by task class and fast rollback without rewriting durable records.

06

Trade-offs and failure modes

  • Full transcript: easy and auditable, but cost grows and obsolete instructions contaminate decisions; it suits short sessions, not long-term memory architecture.
  • Summary only: cheap, but omissions become durable. Version summaries, link sources, and separate confirmed facts, open questions, and discarded detail.
  • Vector database as memory: strong semantic recall, but identifiers, negation, numbers, time, and authorization need hybrid retrieval and metadata filters.
  • Recency bias: newest is not most authoritative. Score freshness and authority separately.
  • Self-contamination: model guesses written back return as evidence. Mark derived records as inference, retain sources, and raise admission thresholds.
  • Incomplete deletion: primary records disappear while embeddings, caches, or snapshots remain. Deletion is a tombstone and propagation protocol.
  • Top-1 hides conflict: high-risk fields need conflict sets, authority rules, or human resolution.
  • Misaligned evaluation: hit rate misses misuse, unauthorized recall, and expiry. Use temporal splits, adversarial conflicts, and tasks requiring forgetting.
07

Reusable technical judgments

  • Context is finite workspace for one inference; runtime reconstruction creates continuity.
  • Event logs, working state, durable records, and retrieval indexes have different goals and trust levels.
  • Apply authorization and temporal gates before relevance ranking and token allocation.
  • Memory write-back is a provenance-, conflict-, and supersession-aware admission decision.
  • Evaluate retrieval, selection, correct use, temporal validity, and deletion propagation, ending with task quality.

09

What is established and where we continue

Established today: context is a temporary token view. The runtime separately maintains the event log, typed working state, retrieval index, and durable records. Starting from task requirements, the assembler applies authorization and temporal filters, ranking, conflict exposure, and token allocation. Model output enters memory only through admission.

Still unresolved: how can long history be compressed without losing open constraints? When should a system use rolling summaries, hierarchical summaries, or state abstraction? How can faulty summaries be traced, recomputed, and migrated?
