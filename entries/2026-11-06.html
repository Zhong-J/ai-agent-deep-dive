多个 Option 如何组合而不放大错误？

从单个子目标的 typed outcome，走到依赖图、中断传播、动态重分解和层级发布门。关键是让抽象减少搜索，而不抹去证据、权限与未决副作用。

01

今日命题

昨天定义了单个 option：启动集合 I、内部策略 π、终止规则 β；业务 runtime 还要给它 guard、最小权限、预算、取消和 typed outcome。今天的问题是：当 parent 把“安排一次客户会议”拆成核对日历、查权限、预订房间、通知参会人等多个 option 时，怎样避免一个子节点的“完成”误导整个任务？层级控制的价值，是把可复用的多步子目标视为高层动作，降低 parent 每一步都重新搜索底层工具的成本。但被抽象遮住的内部状态，恰恰可能包含延迟写入、过期证据或权限变化。组合需要可执行的合同，而不只是计划图上的漂亮方框。

本文提出一个工程约束：parent 仅能消费带类型、来源和版本的子结果；依赖门根据这些结果决定下游是否可启动；每次重规划都生成新 plan version，旧结果不能悄悄推进新图；任何在途副作用都必须被归属和核对。这里的 DAG、版本栅栏和发布门是编辑性工程综合，并非 option、MAXQ 或 ReAct 论文共同定义的标准 API。

核心判断：组合成功不是所有子节点都返回 green，而是目标仍有效、必要后置条件已由权威来源核验、权限在执行点仍成立，并且未决副作用已有明确处置。
02

从单个 Option 到控制图

把昨天的 typed result 想成一种带证明材料的边，而不是一句自然语言总结。一个“查到可用会议室”的结果至少包含房间与时段、数据版本、观察时间、来源 ID 和过期条件；“已预订”的结果还要包含 booking ID、权威读取状态和在途 effect ID。parent 只看到摘要也能做决策，因为摘要保留了决定下一步所需的最小充分信息。

这与 MAXQ 的分解思想相连：高层任务通过子任务组织，值函数能分解为当前子任务与其完成后的价值。但业务任务的成功条件不等于一个标量回报。预订先成功、通知后失败，不能通过正负奖励相加就解释清楚。对外沟通时要知道房间是否仍保留、消息是否可能已发出、是否能安全重试。层级结构帮助分配决策责任；结果合同承担事实与副作用责任。

与 ReAct 的观察后调整也相连：新观察可以改变下一步，但“重新思考”不能撤销已提交的动作。计划是可替换的推理产物；外部效果是世界状态。parent 的新计划必须引用已核对的效果，而不是把旧分支从上下文里删掉就当它不存在。

03

组合图、阻断与重分解

1. 画出依赖，不把计划图误当执行顺序

核对日历与核对权限是两个只读 option，可并行；预订是写入 option，必须等两者返回 succeeded_verified、输入 intent digest 相同、输出仍在有效期内，才进入启动 guard。通知依赖预订的权威 booking ID，而不是依赖预订节点发出的“完成”文本。图中的边类型应显式区分数据依赖、控制依赖与副作用依赖：读取房间列表能供选择，审批解除的是执行门，预订成功才允许外部通知。一个节点可能消费多个前驱的交集，而非任意一个 green。

2. 每个依赖门做三次检查

第一，语义：输出满足下游前置条件吗？B 房间若不满足无障碍要求，不能用“预订成功”绕过用户约束。第二，新鲜度：房间可用性来自 10 分钟前，当前版本或租约还有效吗？第三，权威：子节点是否具有相应工具 scope，结果是否来自系统记录而非模型推测？这三者任何一项未知，就返回 blocked/needs_reconcile，而不是让 LLM 用合理措辞填空。

3. 区分 failure、cancellation 与 unknown

查日历失败可以重试只读查询；权限被拒绝则必须阻断预订；预订调用超时却可能已提交，状态是 outcome_unknown，不能启动“换个房间再预订”，否则可能制造双预订。取消信号首先停止新的 dispatch，然后要求每个在途 child 报告已提交操作 ID 与可核验状态。若无法在 deadline 内确认，parent 保留 reconciliation 责任并给用户如实状态。取消一个 subtree 不意味着撤销 sibling 已完成的合法副作用，更不意味着数据库事务式回滚。

4. 用 plan version 栅栏处理迟到结果

用户把时间从 14:00 改为 15:00 后，parent 生成 plan v2，旧 14:00 的房间可用性与预订结果不能推进 v2。每条 child event 携带 planId、intent digest、节点 ID、attempt、effect ID。event 到来时先按版本归属；旧版本的结果进入 reconciliation ledger，确认是否须释放旧预订，再决定 v2 的下一步。版本栅栏阻止错误推进，但不会自动抵消旧效果。效果账本记录“已请求、已提交、已核验、释放待核验”等状态，并与真实系统读回对齐。

5. 重分解只改变未执行的部分

若房间不可用，可以把“预订指定房间”重新分解成“找备选、请用户选择、预订选择项”；保留已核验的参会人和权限结果，前提是它们对新 intent 仍适用。若用户换了租户或会议性质，原权限检查失效，必须重做。重分解时控制器比较新旧图的输入合同和后置条件：可复用的节点明确 carry forward，不可复用的节点标记 invalidated，在途写入标记 reconcile。模型可以提出新图；runtime 决定哪些节点可复用和哪些动作需要新授权。

on_child_result(event):
  record_effect(event.effect_id, event.state)
  if event.plan_id != active_plan.id:
    reconcile_old_effect(event); return
  if event.outcome == OUTCOME_UNKNOWN:
    block_dependents(event.node_id); reconcile(event); return
  if event.outcome != SUCCEEDED_VERIFIED:
    block_dependents(event.node_id); maybe_replan(event); return
  for node in newly_ready_dependents(event.node_id):
    if inputs_match(node) and evidence_fresh(node) and authorized_now(node):
      dispatch(node)

6. parent 的完成门晚于所有关键子结果

如果房间已预订而通知失败，parent 不得输出“会议安排完成”，也不必假装全部失败。应返回 partial_verified：房间 ID、时间、通知失败详情、可恢复操作和用户需要知道的风险。若目标合同要求必须通知，最终成功门在通知的送达/被接受的权威语义上；如果系统只能证明“已提交发送”，就不能声称“所有人已收到”。完成门以用户目标为准，不由图中最后一个节点决定。

04

必要的组合数学

无需重讲昨天的 semi-MDP 价值式。组合图可写成 G=(V,E)，V 为 option 实例，E 为带类型的依赖边。对节点 v，定义前驱集合 pred(v) 与启动门：

Ready(v) = Guard(v) ∧ ∧u∈pred(v) [Verified(u,v) ∧ Fresh(u,v) ∧ Match(u,v)]

Guard(v) 是该节点自身启动约束，Verified 表示前驱结果的必要后置条件有权威证据，Fresh 表示证据仍适用，Match 表示输入与目标版本一致。合取符号意味着所有必需前驱都要满足；实际实现可以有“任一候选可用”的 OR 门，但 OR 也必须明确候选互斥规则及副作用，不能把它默认为“随便一个成功就好”。工程意义是：依赖关系在 runtime 中可检查，而非藏在 prompt 描述里。

对写入节点，完成门还要检查效果集合。设 R 是目标所要求的已核验后置条件集合，O 是可观察的已核验条件，U 是仍未知的外部副作用集合：

Success = (R ⊆ O) ∧ (|U| = 0) ∧ IntentCurrent

R、O、U 都是集合，不是 LLM 信心分数。|U|=0 表示没有无人负责的未决写入；若业务允许带已披露风险的部分完成，应输出独立的 partial 状态，不能把 Success 改成一个模糊概率。IntentCurrent 表示用户目标版本仍是当前版本。这样 parent 的完成判断可审计、可复现。

层级是否节省计算还可作近似成本核算：C_total ≈ C_plan + Σ C_option + C_gate + C_reconcile。C_plan 是 parent 重规划成本，Σ C_option 是子节点模型与工具成本，C_gate 是检查依赖和证据的成本，C_reconcile 是未知结果追查成本。抽象减少 C_plan 不保证总成本下降：若 option 太大、不断返回 unknown，C_reconcile 可能吞掉节省。式子是工程记账框架，不是论文测得的普适定律。

05

对 Agent 系统的影响

延迟与并发

只读核对可并行缩短关键路径；写入在合取门之后串行或受资源锁约束。优化目标应是用户可接受的已核验完成时间，而非模型输出首字延迟。过度并行会让多个子 option 读取同一旧状态，随后竞争写入；版本检查与执行点重验必须覆盖这段竞争窗口。

权限与信任

parent 的计划节点不是授权票据。每个 option 实例拥有最小子工具 scope，重分解和替代节点需重新通过权限与预算门。来自外部文档的“请先预订”只能作为任务数据，不得改变图的授权边。安全审计应记录谁批准目标、哪个节点用哪个 credential 执行了哪个 effect，以及验证证据来自哪里。

可观察性与人工接管

trace 需要包含 parent plan version、child attempt、依赖门拒绝原因、effect ledger、重规划原因与用户可见状态。人工接管时应交付“已做、未做、未知”三栏，而不是完整的模型思维链。追查者需要能从 booking ID 读回系统状态，并能确定旧版本迟到回调有没有改变当前图。

06

取舍、评测与发布门

图太细：每个 API 都成为 option，parent 在高频协调上花掉 token 与延迟，还产生大量版本边。图太粗：“安排整个活动”一个大 option 隐藏过多关键状态，无法定位失败，也不易收窄权限。切分依据应是可复用、可验证的中间后置条件，以及遇到失败时谁拥有恢复责任。

静态图还是动态重分解：静态 DAG 易审计、易预测，但遇到新约束会僵硬；动态重分解能适应观察，却可能频繁抖动、反复请求审批或扩大工具面。为重分解设置预算、最小变化阈值与版本迁移规则。出现未知写入时先 reconcile，再发新的竞争写入。无法证明某旧效果已消失，就把它留在账本里，不能靠“重新计划”抹掉。

层级评测要同时看三层。子 option 层测启动 guard、typed outcome 校准、后置条件证据、取消与超时；组合层测依赖正确性、迟到结果隔离、重复副作用、权限不升级、部分完成语义；端到端层测用户目标的已核验成功率、耗时、成本、人工接管率与伤害事件。单看子节点通过率会掩盖“各自正确、组合错误”。可以用包含时间变更、权限撤销、写入超时、回调乱序、恶意文档指令的故障注入轨迹，而不只用顺利完成的演示。

安全发布门：先用只读/模拟工具回放，再让写入在隔离环境运行；核对效果账本与权威系统是否一致；对高风险动作要求明确授权；上线时用小流量和可回退策略监测 unknown outcome、重复写入与误报成功。回滚部署不能回滚现实中的通知与预订，所以发布门必须验证补偿与人工恢复路径。这里的门槛是建议的工程准则，不是上述论文报告的统一行业阈值。

07

可以带走的判断

  1. 把 option 输出当成有类型、有来源、有版本的证据边；不要让“完成”文本驱动下游写入。
  2. 依赖门同时检查后置条件、新鲜度、目标匹配和当前权限；任一未知就阻断或追查。
  3. 重规划替换的是未来路径，旧版迟到事件与已提交副作用仍要登记、核对、处置。
  4. 层级评测分子节点、组合与端到端；发布前故障注入必须覆盖乱序、超时、撤权和部分完成。

How Can Multiple Options Compose Without Amplifying Errors?

Move from one subgoal’s typed outcome to dependency graphs, interruption propagation, dynamic redecomposition, and hierarchical release gates. Abstraction should reduce search without erasing evidence, authority, or unresolved effects.

2026-11-0620 min readHierarchical control / Options / Planning / Evaluation / Agent safety
01

Today's proposition

Yesterday we defined one option by its initiation set I, internal policy π, and termination rule β. A production runtime adds guards, narrow authority, budgets, cancellation, and a typed outcome. Today the parent decomposes “arrange a customer meeting” into calendar inspection, permission checking, room booking, and participant notification. How does it prevent one child's apparent completion from becoming a false claim that the entire task is done? Hierarchy is useful because a reusable multi-step subgoal becomes a high-level action: the parent need not search over every primitive tool at every turn. Yet an abstraction can hide a delayed write, stale evidence, or an authority change precisely when the parent needs to know about it.

The proposed engineering rule is that a parent consumes only typed, attributable, versioned child results. A dependency gate decides whether downstream work may start. A new plan version fences off results from a superseded plan, and every in-flight side effect retains an owner and reconciliation path. The graph, version fence, and release gates below are editorial engineering synthesis, not a shared API specified by the options, MAXQ, or ReAct papers.

The criterion: overall success is not a collection of green child labels. The intent must still be valid, required postconditions must be verified by authoritative sources, authority must hold at the action boundary, and unresolved effects must be accounted for.
02

From one option to a control graph

Treat yesterday's typed result as an evidence-bearing edge rather than a prose summary. An “available room” result needs the room and interval, data version, observation time, source identifier, and expiry condition. A “booked room” result additionally needs a booking identifier, an authoritative readback, and any in-flight effect identifier. A parent can decide from a compact result if that result preserves the minimum information required by the next gate.

This connects to MAXQ's decomposition of a high-level task into subtasks and its value-function decomposition. A business workflow, however, cannot express all success conditions as one scalar return. If booking succeeds and notification fails, summing rewards does not tell an operator whether the room is still held, whether a message may already have been delivered, or whether retrying is safe. Hierarchy assigns decision responsibility; result contracts carry factual and side-effect responsibility.

It also connects to ReAct's observation-and-action pattern. A new observation can change the next step, but “thinking again” cannot undo an action committed outside the model. The plan is replaceable reasoning state; an external effect is part of the world. A new parent plan must incorporate reconciled effects from the old branch instead of deleting that branch from the prompt and pretending it never happened.

03

Composition, blocking, and redecomposition

1. Name dependencies without confusing the graph with a fixed script

Calendar inspection and authority checking are read-only options that may run in parallel. Booking is a write option: its initiation guard waits until both predecessors report succeeded_verified, their intent digests match, and their outputs are still valid. Notification depends on an authoritative booking ID, not on the booking child's prose saying “done.” Edge types should be explicit. A data edge supplies a room candidate; a control edge grants permission to start; an effect edge confirms a committed booking. A successor often needs the conjunction of several predecessor conditions, not any green label.

2. Run three checks at every dependency gate

First is semantic fit: does the output satisfy the successor's precondition? A successfully booked room B does not satisfy a request for wheelchair access if B lacks it. Second is freshness: is a room-availability observation from ten minutes ago still valid under the resource version or lease? Third is authority: did the child run with the relevant tool scope, and does its result come from an authoritative record rather than the model's inference? If any one is unknown, the gate returns blocked or needs_reconcile. The LLM should not fill the gap with plausible language.

3. Separate failure, cancellation, and an unknown outcome

A failed calendar read may be retried as a read. A denied permission check blocks booking. A timed-out booking write may have committed; its status is outcome_unknown. Starting a “book another room” branch at that point risks a duplicate reservation. Cancellation first stops new dispatches and then asks every in-flight child for committed operation IDs and observable state. If the deadline expires before confirmation, the parent retains reconciliation ownership and reports uncertainty accurately. Cancelling one subtree neither reverses a legitimate side effect in a sibling nor creates database-transaction rollback semantics.

4. Fence late results with a plan version

Suppose the user changes the meeting from 14:00 to 15:00. The parent creates plan v2; a 14:00 availability or booking result must not advance v2. Each child event carries a plan ID, intent digest, node ID, attempt number, and effect ID. On arrival, the runtime first assigns the event to its version. An old-version result enters a reconciliation ledger: perhaps the old booking must be released and verified before v2 proceeds. The fence prevents an incorrect state transition, but it does not compensate for an old effect by itself. The ledger records requested, committed, verified, and release-pending states, then aligns them with an authoritative readback.

5. Redecompose only the unfinished part

If a room is unavailable, the controller can replace “book specified room” with “find alternatives, request a choice, book the chosen one.” Verified attendees and authority checks may be carried forward only if their contracts still apply to the revised intent. A different tenant or meeting class invalidates the earlier permission result. Redecomposition compares old and new input contracts and postconditions: reusable nodes are explicitly carried forward, unusable ones are marked invalidated, and in-flight writes are marked reconcile. The model may suggest the new graph; the runtime decides reuse, invalidation, and where renewed authority is needed.

on_child_result(event):
  record_effect(event.effect_id, event.state)
  if event.plan_id != active_plan.id:
    reconcile_old_effect(event); return
  if event.outcome == OUTCOME_UNKNOWN:
    block_dependents(event.node_id); reconcile(event); return
  if event.outcome != SUCCEEDED_VERIFIED:
    block_dependents(event.node_id); maybe_replan(event); return
  for node in newly_ready_dependents(event.node_id):
    if inputs_match(node) and evidence_fresh(node) and authorized_now(node):
      dispatch(node)

6. The parent completion gate comes after critical child results

If the room is booked and notification fails, the parent must not announce “meeting arranged,” but neither should it pretend nothing happened. A partial_verified result reports the booking ID and time, the notification failure, recoverable operations, and any material risk. If notification is required by the user's goal, final success waits for the authoritative delivery or acceptance semantics available from that channel. If the system proves only “send submitted,” it cannot claim that everybody received the invitation. The user's goal defines the completion gate; the last node in a graph does not.

04

The minimal mathematics of composition

We need not repeat yesterday's semi-MDP value equation. Represent the composition as G=(V,E): V contains option instances and E contains typed dependency edges. For a node v, let pred(v) be its required predecessors. Its start gate is:

Ready(v) = Guard(v) ∧ ∧u∈pred(v) [Verified(u,v) ∧ Fresh(u,v) ∧ Match(u,v)]

Guard(v) is v's own initiation constraint. Verified says a predecessor's required postcondition has authoritative evidence; Fresh says the evidence still applies; Match says it belongs to the intended input and plan version. The conjunction means every required predecessor must satisfy the gate. An implementation may also have an OR gate for alternative room candidates, but it must specify mutual exclusion and side effects explicitly. “Any green child is fine” is not a valid default. The engineering gain is that dependencies become runtime-checkable conditions rather than narrative instructions in a prompt.

For write nodes, the parent completion gate also tracks effects. Let R be the set of postconditions required by the user's goal, O the set of postconditions supported by authoritative observations, and U the set of unresolved external effects:

Success = (R ⊆ O) ∧ (|U| = 0) ∧ IntentCurrent

R, O, and U are sets, not confidence scores from the LLM. |U|=0 says that no external write is left without an accountable disposition. If the business domain permits a partially completed outcome with disclosed risk, expose a distinct partial state instead of softening Success into a vague probability. IntentCurrent means the user's goal version still applies. These terms make the parent's completion decision auditable and reproducible.

Hierarchy also needs a cost account: C_total ≈ C_plan + Σ C_option + C_gate + C_reconcile. C_plan is parent planning and replanning cost; Σ C_option is child model and tool cost; C_gate is checking dependencies and evidence; C_reconcile is investigating unknown outcomes. Abstracting primitive actions can reduce C_plan without reducing the total. An oversized option that frequently returns unknown may make C_reconcile dominate. This equation is an engineering accounting device, not a universal empirical law measured by the cited papers.

05

Implications for agent systems

Latency and concurrency

Read-only checks may run concurrently to shorten the critical path. Writes wait behind a conjunction gate and, where needed, a resource lock. The target metric is time to a user-acceptable, verified outcome, not time to the model's first token. Excessive concurrency can let multiple children read the same old state and then race to write. Resource versions and a fresh check at the execution point must cover that gap.

Authority and trust

A node in a parent plan is not a capability grant. Each option instance receives the minimum child-tool scope; redecomposition and replacement nodes pass authority and budget checks again. An instruction embedded in an external document such as “book this first” is task data, not a change to the graph's authorization edges. Audit records should show who authorized the goal, which node used which credential for each effect, and where verification evidence came from.

Observability and human takeover

A useful trace includes the parent plan version, child attempt, dependency-gate rejection reason, effect ledger, replanning reason, and user-visible status. A human handoff should supply “done, not done, unknown” with evidence and action IDs, not an unbounded model thought trace. The investigator must be able to read booking state by ID and determine whether a late callback from an old plan changed the current graph.

06

Trade-offs, evaluation, and release gates

A graph that is too fine: making every API call an option spends tokens and latency on parent coordination and creates too many versioned edges. A graph that is too coarse: a single “organize the whole event” option hides consequential state, makes failure localization difficult, and resists narrow authority. Split at reusable, verifiable intermediate postconditions and at boundaries where recovery ownership changes.

Static graph versus dynamic redecomposition: a static DAG is easier to audit and predict but brittle when new constraints appear. Dynamic redecomposition adapts to observations, yet can oscillate, request approval repeatedly, or expand the tool surface. Give it a budget, a minimum-change threshold, and explicit version migration rules. Reconcile an unknown write before dispatching a competing write. If the disappearance of an old effect cannot be proved, retain it in the ledger; a revised plan cannot erase it.

Evaluate at three levels. At the child-option level, test initiation guards, typed-outcome calibration, postcondition evidence, cancellation, and timeout behavior. At the composition level, test dependency correctness, isolation of late results, duplicate effects, non-escalation of authority, and partial-result semantics. At the end-to-end level, measure verified user-goal success, time, cost, human takeover, and harmful events. A high child pass rate can conceal a graph in which each child is locally correct but the composition is wrong. Fault-injection traces should change meeting times, revoke authority, time out writes, reorder callbacks, and include hostile instructions in retrieved documents. Happy-path demos alone will miss the central risks.

Safe release gates: replay with read-only or simulated tools, then run writes in an isolated environment. Compare the effect ledger with authoritative system state. Require explicit authorization for consequential actions. During a limited rollout, watch unknown outcomes, duplicate writes, and false success reports with a rollback and human recovery path. Rolling back a deployment does not undo a notification or reservation in the world. These gates are proposed engineering criteria, not common numerical thresholds reported by the cited papers.

07

Reusable judgments

  1. Treat option outputs as typed, attributable, versioned evidence edges. Never let a “done” message authorize a downstream write.
  2. A dependency gate checks postconditions, freshness, intent match, and current authority; uncertainty blocks execution or triggers reconciliation.
  3. Replanning changes future paths. Late events and committed effects from old versions still need an owner, readback, and disposition.
  4. Evaluate child options, graph composition, and the end-to-end goal separately; inject reordered callbacks, timeouts, revoked authority, and partial completion before release.

Sources and evidence boundaries

  • Sutton, Precup & Singh, Between MDPs and Semi-MDPs — original work on options and temporal abstraction; it does not specify this article's business DAG or effect ledger.
  • Dietterich, Hierarchical Reinforcement Learning with MAXQ Value Function Decomposition — author research on hierarchical tasks and value decomposition; scalar reward is not a business postcondition contract.
  • Bacon, Harb & Precup, The Option-Critic Architecture — author research on learning internal policies and termination; it provides no authority model.
  • Yao et al., ReAct — the authors propose interleaved reasoning and acting and report experimental results; that does not prove cancellation reverses external effects.
