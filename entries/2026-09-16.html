Agent Runtime 内核 · 第 1/4 篇

Agent 不是 while loop，而是一台状态机

从显式状态、事件与命令出发，拆开一次 tool call 的准备、授权、派发、结果关联和终止语义，建立可恢复 Agent runtime 的控制面。

01

今日命题

最小 Agent demo 常写成 while (!done) { model(); tool(); }。这个 loop 能解释控制流，却隐藏了生产系统最关键的问题：进程在 tool 完成后、结果写入前崩溃怎么办？两个并行调用哪个结果属于谁？取消与 timeout 到底终止模型、网络请求还是业务副作用？模型说“完成”是否足以结束任务？

可靠 runtime 必须把隐式 call stack 展开成可持久化状态、带身份的事件、受 policy 约束的命令。模型输出只是提出一个 transition candidate；runtime 校验当前状态、权限与不变量，记录将要发生的动作，再驱动工具。tool response 也不是一段随便 append 的文本，而是对应某个 call identity 的事件，只有合法 transition 才能进入下一轮 context。

核心判断：Agent loop 是状态机的一种执行器，不是状态本身。若任务阶段、call ID、attempt、审批、deadline、结果和完成条件只存在内存或 prompt 中，系统就无法可靠恢复、去重、审计或证明完成。
02

连接你熟悉的 Agent loop

你熟悉的 reason/action loop 描述的是顺序：构造 context、调用模型、发现 tool call、执行、追加 observation、继续。状态机视角再问三件事：现在处于哪个可命名阶段？什么事件允许它离开？离开时必须保持哪些不变量？

例如模型产生 charge_card 并不等于调用已发生。runtime 可先进入 proposed，解析 schema 后进入 validated，通过用户与 policy approval 后进入 authorized，把 intent 与 idempotency key 持久化后进入 dispatched。只有收到与 call ID 匹配的 outcome，才能转为 succeeded、failed 或 outcome_unknown。每个状态拥有不同的合法操作。

03

机制：把执行分成三条平面

1. State plane：事实快照

保存 taskId、phase、version、activeCalls、budgets、approval records、artifacts 和 terminal status。它只包含 runtime 能解释的结构化事实，不把模型自然语言 plan 当作权威状态。每次写入带 expected version，防止两个 worker 同时覆盖。

2. Event plane：发生过什么

事件是不可变记录，例如 ModelTurnCompleted、ToolCallAuthorized、ToolResultObserved、CancellationRequested。事件携带 eventId、taskId、turnId、callId、attempt、timestamp 与 provenance。状态可由事件 fold 得到；即使使用 snapshot 加速，也保留足够日志审计与 replay。

3. Command plane：希望发生什么

命令是待执行意图，例如 InvokeModel、DispatchTool、RequestApproval。它可以失败、超时或被拒绝，因此不能在产生时就写成事实。outbox 模式把 state transition 与待发送 command 放在同一数据库事务中，再由 dispatcher 投递，减少“状态已更新但消息没发”或相反的裂缝。

4. Reducer 与 effect handler

decision = reduce(currentState, incomingEvent)
assert invariants(decision.nextState)
transaction {
  writeState(decision.nextState, expectedVersion)
  appendEvents(decision.events)
  enqueueOutbox(decision.commands)
}
dispatcher.deliver(outbox)  # side effects outside reducer

reducer 应尽量 deterministic：同一 state+event 得到同一 next state 与 commands。模型调用、当前时间、随机数和网络 I/O 属于 effect handler；其结果作为新事件返回。这样 replay 不会在重放时再次发邮件或扣款。

5. Tool-call correlation

一个逻辑 call 使用稳定 callId；每次传输尝试使用 attemptId。tool result 必须同时校验 task/turn/call identity，迟到结果若已被 supersede，应记录但不能覆盖新状态。模型看到的 observation 从 recorded outcome 构造，并带状态（success/error/unknown）、结构化 payload 与可追溯引用。

6. Completion

terminal transition 由 runtime predicate 决定，例如 required artifacts 存在、外部订单状态已确认、无 active calls、审批已满足。模型的 final 只是 completion proposal。系统可以接受、要求 verifier、或返回 observation 让模型继续；完成后到达 completed、failed、cancelled 等互斥 terminal states。

7. Schema evolution

durable task 可能跨越数天与多个部署版本，state、event 和 tool schema 都会变化。每条记录应带 schemaVersion；reader 使用显式 upcaster 把旧 event 转成当前内部形式，或让 reducer 支持多个版本。不要原地改写历史语义。若新版本改变授权或 completion 条件，旧任务需要 migration gate、人工确认或继续由旧 worker 处理，不能假设重放自然得到相同结果。

8. Context projection

模型不需要看到完整 event log。projector 根据当前 phase 生成最小上下文：目标、有效约束、尚未完成的 calls、已接受 outcomes 与 artifact references。被 supersede 的 attempt、内部审计字段和 credentials 不进入 prompt。projection 带 source event IDs，便于把模型后续引用追溯到事实。摘要器可以压缩文本，但不能改变 canonical state。

04

必要数学：转移、不变量与交付语义

Transition function

δ : S × E → S × C

S 是持久状态集合，E 是输入事件，C 是发出的命令集合。δ 不执行副作用，只决定下一状态与 intents。若 event 在当前 phase 不合法，应得到明确 rejection/no-op event，而非由模型猜测修复。工程价值是所有合法边都可枚举、测试和审计。

Invariant

∀ transition s→s′,   I(s) ∧ guard(s,e) ⇒ I(s′)

I 是必须始终为真的条件，例如 terminal task 没有新的 side-effect command；未授权 call 不能 dispatched；一个 call 最多有一个 accepted terminal outcome。guard 校验 event version、identity 与 phase。模型输出永远不能绕过 invariant。

Optimistic concurrency

UPDATE task SET state=s′, version=v+1 WHERE id=k AND version=v

若更新行数为 0，说明其他 worker 已推进状态；当前 worker 必须重新读取并 reduce，而不是覆盖。这个 compare-and-swap 把并发冲突显式化，却不自动解决业务合并。

Delivery semantics

At-most-once 避免重复但可能丢失；at-least-once 避免静默丢失但可能重复；端到端 exactly-once effect 通常需要 tool 参与幂等/事务协议，不能由 runtime 单方面承诺。若发送 timeout，runtime 只知道 reply 未到，不知道 effect 未发生，因此必须进入 outcome_unknown 并 reconcile。

Progress measure

B′ = B − cost(command),   B ≥ 0

B 可表示 token、tool calls、wall time 或 monetary budget。每个 command 消耗显式 budget；达到 0 时转到等待审批、降级或 terminal，而不是无限 loop。budget 是 safety bound，不是任务是否完成的定义。

05

对 Agent 系统的影响

1. Prompt 只投影状态，不拥有状态

context builder 从 durable state/events 选择模型需要的视图。压缩或截断 prompt 不会删除真实审批、call outcome 或 artifact。反之，模型在文本中声称“已批准”也不会创建 approval record。

2. 每个 tool call 都是业务 transaction boundary

schema validation、authorization、intent persistence、dispatch、outcome reconciliation 和 observation construction 分开记录。这样“工具失败”才能区分 validation error、policy denial、transport timeout、remote rejection 与 ambiguous outcome。

3. 审计必须能回答因果链

谁/哪个模型在何种 state 提出什么 call？哪条 policy 批准？哪个 attempt 被发送？哪个结果被接受？它如何改变下一轮 context？只有带 identity 的 event chain 能回答，而聊天 transcript 只展示部分投影。

4. Human approval 是等待状态

等待用户不是阻塞线程；状态机进入 awaiting_approval，持久化 proposal、risk、expiry 与 resume token。批准/拒绝作为事件回来，进程可在期间重启。approval 必须绑定精确参数和版本，参数变化后旧批准失效。

5. Cancellation 是请求，不是事实

收到 cancel 后记录 CancellationRequested，停止尚未派发的命令，并尝试取消 in-flight work。远端副作用可能已经发生，因此最终状态需等待 acknowledgement/reconciliation。UI 的“已取消”不应早于业务事实。

6. Model routing 不能破坏状态协议

不同模型可负责 planning、tool selection 或 summarization，但都通过同一 command/event contract。更换模型只改变 proposal quality，不改变 authorization、call identity、invariants 和 completion predicate。

7. Observability 围绕 transition，而非日志字符串

指标应按 phase 和 transition 统计：proposed→authorized 的拒绝率、dispatched→outcome 的延迟、unknown outcome 的数量、迟到结果、version conflict、budget exhaustion 与 terminal reason。trace span 使用 task/turn/call/attempt IDs 关联模型、队列和工具。这样 p95 上升能定位在审批、排队、远端执行还是 reconciliation，而不是只看到“Agent 很慢”。

8. 测试状态空间，而不只测 happy path

表驱动测试枚举每个 state 对每类 event 的结果；property test 检查 invariants；故障注入在 intent commit、dispatch、remote effect、outcome commit 各边界杀进程。还要发送重复、乱序、迟到与未知 ID 的 events。若系统只能在理想顺序下通过，它仍不是 durable runtime。

06

取舍与失败模式

显式状态 vs 开发速度：状态/事件 schema 增加代码与 migration 成本，却把 crash、并发和审计从隐含 bug 变成可测试协议。高风险或长运行任务通常值得；一次性无副作用问答可保持简单。

Event sourcing vs snapshot CRUD：完整事件流利于审计/replay，但存储、版本演进和隐私删除更复杂。常见折中是 current snapshot + append-only audit events，而不是为所有数据做纯 event sourcing。

Deterministic reducer vs 灵活逻辑：把 I/O 排除在 reducer 外使 replay 可预测，却要求显式 command/event plumbing。若 reducer 直接读时间或调用模型，历史 replay 会产生新决策和副作用。

严格 lifecycle vs latency：每次持久化、授权和 outbox 增加延迟。可按风险分级：只读、可重试工具走轻路径；不可逆 side effect 走完整 intent/approval/reconcile 路径。但分类本身必须由确定性 policy 决定。

状态粒度：过粗无法区分 sent 与 succeeded；过细造成状态爆炸。优先建模影响恢复和合法动作的差异。仅用于 UI 文案的细节可放事件 metadata，不必成为 phase。

隐私删除 vs append-only audit：事件不可变不等于数据永不删除。敏感 payload 可放受生命周期管理的 encrypted blob，event 只保存引用与最小 metadata；删除时销毁 blob/key，同时保留必要审计骨架。若把用户原文、credential 或 tool secret 复制进每条 event，后续 retention 与访问控制会非常困难。

最危险的失败模式：timeout 被当作 failure 后自动重试不可逆工具；迟到 response 覆盖新 attempt；模型文本被当作授权；进程内变量被当作 durable truth；terminal 后仍接受 tool result。它们都是状态协议缺失，而非 prompt 不够好。

07

可复用判断

  • Agent loop 是状态机执行器；durable state、events 与 commands 必须分离。
  • 模型输出只提出 transition；runtime guard、authorization 与 invariant 决定是否合法。
  • tool call 需要稳定 callId、独立 attemptId 和明确的 success/failure/outcome-unknown 结果状态语义；unknown 仍等待 reconciliation。
  • 先持久化 intent 再派发 effect，按 identity 持久化 outcome 后才构造下一轮 observation。
  • 完成、取消与审批都是 runtime state transition，不能由模型文本或 UI 单方面宣告。

Agent Runtime Internals · Part 1 of 4

An Agent Is a State Machine, Not a While Loop

Start from explicit state, events, and commands; then separate preparation, authorization, dispatch, result correlation, and termination semantics for a recoverable agent runtime.

2026-09-1620 min readAgent runtime / State machine / Tool lifecycle / Control plane / Durable execution
01

Today's proposition

A minimal agent demo is often written as while (!done) { model(); tool(); }. That loop explains control flow while hiding the production questions that matter most: what happens if the process crashes after a tool finishes but before its result is stored? Which parallel result belongs to which call? Does cancellation terminate model generation, an HTTP request, or the underlying business side effect? Is the model saying “done” sufficient to complete the task?

A reliable runtime expands the implicit call stack into durable state, identity-bearing events, and policy-constrained commands. Model output merely proposes a transition candidate. The runtime validates current state, authorization, and invariants; records the intended action; then drives the tool. A tool response is not arbitrary text to append. It is an event correlated to one call identity, and only a legal transition may feed the next model context.

Core judgment: an agent loop is one executor for a state machine; it is not the state itself. If task phase, call ID, attempt, approval, deadline, result, and completion criteria live only in memory or in the prompt, the system cannot reliably recover, deduplicate, audit, or prove completion.
02

Connect it to the agent loop you know

The reason/action loop you already know describes order: build context, call the model, detect a tool call, execute it, append an observation, and continue. A state-machine view asks three additional questions: which named phase are we in, which event permits us to leave it, and which invariants must remain true during the transition?

For example, a model emitting charge_card does not mean a charge occurred. The runtime can enter proposed, move to validated after schema parsing, reach authorized after user and policy approval, persist intent plus an idempotency key in recorded, and only then enter dispatched. An outcome correlated to the call ID moves the machine to succeeded, failed, or outcome_unknown. Each state permits a different set of actions.

03

Mechanism: separate three execution planes

1. State plane: the factual snapshot

Persist task ID, phase, version, active calls, budgets, approvals, artifacts, and terminal status. Store structured facts that the runtime can interpret; do not treat a natural-language model plan as authoritative workflow state. Every write carries an expected version so two workers cannot silently overwrite each other.

2. Event plane: what happened

Events are immutable records such as ModelTurnCompleted, ToolCallAuthorized, ToolResultObserved, and CancellationRequested. They carry event ID, task ID, turn ID, call ID, attempt, timestamp, and provenance. State can be folded from events. Snapshots may accelerate loading, while sufficient history remains for audit and replay.

3. Command plane: what should happen

Commands express intended work such as InvokeModel, DispatchTool, and RequestApproval. A command can fail, time out, or be rejected, so producing it does not make it a fact. The outbox pattern stores the state transition and outbound command in one database transaction; a dispatcher later delivers it, reducing the gap between “state committed but message lost” and its inverse.

4. Reducer and effect handler

decision = reduce(currentState, incomingEvent)
assert invariants(decision.nextState)
transaction {
  writeState(decision.nextState, expectedVersion)
  appendEvents(decision.events)
  enqueueOutbox(decision.commands)
}
dispatcher.deliver(outbox)  # side effects outside reducer

The reducer should be deterministic: the same state and event produce the same next state and commands. Model calls, wall-clock time, random numbers, and network I/O belong in effect handlers; their results return as new events. Replay then does not send an email or charge a card again.

5. Tool-call correlation

One logical call uses a stable callId; each transport attempt gets an attemptId. A result must match task, turn, and call identity. A late result after supersession is recorded but cannot overwrite newer state. The observation shown to the model is built from a recorded outcome and carries status—success, error, or unknown—plus structured payload and a traceable reference.

6. Completion

A runtime predicate owns terminal transitions: required artifacts exist, an external order is confirmed, no calls remain active, and approvals are satisfied. A model’s final output is merely a completion proposal. The runtime can accept it, invoke a verifier, or return an observation and continue. Completion ends in mutually exclusive terminal states such as completed, failed, or cancelled.

7. Schema evolution

A durable task may span days and several deployments while state, event, and tool schemas evolve. Every record carries a schema version. Readers use explicit upcasters to translate old events into current internal forms, or reducers support several versions. Do not rewrite historical meaning in place. If a release changes authorization or completion conditions, old tasks need a migration gate, human confirmation, or execution by the old worker; replay cannot be assumed to produce the same result automatically.

8. Context projection

The model does not need the complete event log. A projector builds minimal context for the current phase: objective, effective constraints, unfinished calls, accepted outcomes, and artifact references. Superseded attempts, internal audit fields, and credentials stay out of the prompt. The projection carries source event IDs so later model references remain traceable to facts. A summarizer may compress prose but cannot mutate canonical state.

04

Essential math: transitions, invariants, and delivery semantics

The transition function

δ : S × E → S × C

S is the set of durable states, E the input events, and C the emitted commands. δ performs no side effect; it decides the next state and intents. An event illegal in the current phase should produce an explicit rejection or no-op event rather than asking the model to guess a repair. Every legal edge can therefore be enumerated, tested, and audited.

An invariant

∀ transition s→s′,   I(s) ∧ guard(s,e) ⇒ I(s′)

I is a condition that must always remain true: a terminal task emits no new side-effect command; an unauthorized call cannot be dispatched; one call has at most one accepted terminal outcome. The guard validates event version, identity, and phase. Model output can never bypass an invariant.

Optimistic concurrency

UPDATE task SET state=s′, version=v+1 WHERE id=k AND version=v

If zero rows update, another worker already advanced the state. The current worker must reload and reduce again rather than overwrite. This compare-and-swap makes concurrency conflicts explicit; it does not automatically decide how business state should merge.

Delivery semantics

At-most-once avoids duplicates while permitting loss. At-least-once avoids silent loss while permitting duplicates. End-to-end exactly-once effect generally requires the tool to participate through idempotency or a transaction protocol; a runtime cannot promise it unilaterally. After a send timeout, the runtime knows only that no reply arrived—not that no effect happened—so it enters outcome_unknown and reconciles.

A progress measure

B′ = B − cost(command),   B ≥ 0

B can represent tokens, tool calls, wall-clock time, or money. Every command consumes explicit budget. At zero, transition to approval, degradation, or a terminal state rather than looping indefinitely. A budget is a safety bound, not the definition of task completion.

05

Implications for agent systems

1. A prompt projects state; it does not own state

The context builder selects a model-facing view from durable state and events. Compressing or truncating a prompt does not delete a real approval, call outcome, or artifact. Conversely, a model claiming “approved” in text does not create an approval record.

2. Every tool call is a business transaction boundary

Record schema validation, authorization, intent persistence, dispatch, outcome reconciliation, and observation construction separately. “Tool failure” can then distinguish validation error, policy denial, transport timeout, remote rejection, and ambiguous outcome.

3. Audit must answer the causal chain

Who or which model proposed which call in what state? Which policy approved it? Which attempt was sent? Which result was accepted? How did it alter the next context? Only an identity-bearing event chain answers those questions. A chat transcript is only a partial projection.

4. Human approval is a waiting state

Waiting for a person does not block a thread. The machine enters awaiting_approval and persists proposal, risk, expiry, and resume token. Approval or rejection returns as an event, and the process may restart meanwhile. Approval binds exact arguments and version; changed arguments invalidate it.

5. Cancellation is a request, not a fact

On cancel, record CancellationRequested, stop undispatched commands, and attempt to cancel in-flight work. A remote side effect may already have happened, so final state waits for acknowledgement or reconciliation. The UI must not claim “cancelled” before the business fact is known.

6. Model routing must preserve the state protocol

Different models may handle planning, tool selection, or summarization, but all speak the same command and event contract. Replacing a model changes proposal quality, not authorization, call identity, invariants, or the completion predicate.

7. Observability centers on transitions, not log strings

Measure by phase and transition: proposal-to-authorization rejection rate, dispatch-to-outcome latency, unknown outcomes, late results, version conflicts, budget exhaustion, and terminal reasons. Trace spans correlate models, queues, and tools through task, turn, call, and attempt IDs. A p95 regression can then be located in approval, queueing, remote execution, or reconciliation instead of summarized as “the agent is slow.”

8. Test the state space, not only the happy path

Table-driven tests enumerate each event in each state; property tests assert invariants; fault injection kills the process at intent commit, dispatch, remote effect, and outcome commit boundaries. Send duplicate, out-of-order, late, and unknown-ID events. A system that passes only ideal ordering is not yet a durable runtime.

06

Trade-offs and failure modes

Explicit state versus development speed: state and event schemas add code and migration cost, but turn crashes, concurrency, and audit from implicit bugs into a testable protocol. High-risk or long-running work usually justifies it; a one-shot, side-effect-free answer may remain simple.

Event sourcing versus snapshot CRUD: a full event stream improves audit and replay while complicating storage, version evolution, and privacy deletion. A common compromise is a current snapshot plus append-only audit events rather than pure event sourcing for every datum.

Deterministic reducer versus flexible logic: excluding I/O from the reducer makes replay predictable but requires explicit command/event plumbing. A reducer that reads wall-clock time or calls a model can generate new decisions and side effects while replaying history.

Strict lifecycle versus latency: persistence, authorization, and outbox steps add latency. Risk-tiered paths can let read-only, retryable tools use a lighter protocol while irreversible side effects use full intent, approval, and reconciliation. Deterministic policy—not the model—must own classification.

State granularity: states that are too coarse cannot distinguish sent from succeeded; states that are too fine create an explosion. Model differences that change recovery or legal actions. Details used only for UI copy can remain event metadata rather than phases.

Privacy deletion versus append-only audit: immutable events do not imply retaining every payload forever. Sensitive content can live in lifecycle-managed encrypted blobs while events store references and minimal metadata. Deletion destroys the blob or key while retaining a necessary audit skeleton. Copying user text, credentials, or tool secrets into every event makes retention and access control extremely difficult.

The most dangerous failure modes: treating timeout as failure and retrying an irreversible tool; allowing a late response to overwrite a new attempt; treating model text as authorization; treating process memory as durable truth; accepting tool results after terminal state. These are missing state protocols, not weak prompts.

07

Reusable judgments

  • An agent loop executes a state machine; durable state, events, and commands must remain separate.
  • Model output only proposes a transition. Runtime guards, authorization, and invariants decide whether it is legal.
  • A tool call needs a stable call ID, separate attempt IDs, and explicit success, failure, or outcome-unknown result-state semantics; unknown still awaits reconciliation.
  • Persist intent before dispatching an effect; persist the identity-correlated outcome before constructing the next observation.
  • Completion, cancellation, and approval are runtime state transitions, not declarations made unilaterally by model text or UI.

  • Amazon States Language specification — specifies JSON state machines, states, transitions, and terminal and error semantics. This article does not claim agents must use AWS Step Functions.
  • Temporal Workflow Execution documentation — the official explanation of workflow execution, event history, durability, and recovery; concrete replay constraints belong to Temporal’s product model.
  • Azure Durable Functions overview — officially overviews orchestrators, activities, entities, state management, checkpoints, retries, and recovery. This article does not use that page as evidence for event-sourcing implementation details.
  • Transactional Outbox pattern — describes storing business state and an outbound message in one transaction, then delivering with a separate relay.
  • RFC 9457: Problem Details for HTTP APIs — standardizes structured error types, status, and details useful for tool-error observations; it does not define an agent lifecycle.
  • Yao et al., ReAct — establishes interleaved reasoning, action, and observation. This article extends the discussion to durable state and effect boundaries in production runtimes.

The state names, three-plane separation, and agent tool lifecycle are an editorial architecture synthesis from workflow and messaging principles, not the sole implementation prescribed by any one source.

09

What is established and where we continue

Established today: an agent runtime separates durable state, immutable events, and side-effect commands. Every tool call moves through proposed, validated, authorized, recorded, and dispatched, then correlates success, failure, or unknown outcome by call identity. The model proposes transitions; the runtime owns guards, invariants, and the completion predicate.

Still unresolved: when a model proposes several tool calls, which may run concurrently? How should the runtime bound fan-out, handle conflicts on shared resources, propagate cancellation, and apply backpressure when downstream systems slow down?

Next starting point: Agent Runtime Internals 2/4 will cover structured concurrency: task groups, dependency DAGs, deadline and cancellation propagation, semaphores, queues, and backpressure—showing why “parallel tool calls” is not simply Promise.all.
