Agent Reproducible Execution Internals · 第 1/2 篇

同样的 Prompt 和 Seed，为什么 Agent 仍复现不了昨天？

Agent 结果由模型、工具、权限、环境、数据与并发顺序共同形成。区分历史记录、桩重放、隔离重执行和当前再跑，才能准确说明每种证据证明了什么。

01

今日命题

一个 Agent 昨天成功生成并发送审计报告。今天工程师用同样的用户 prompt、temperature=0 和 seed 重跑，却选了另一项工具、读到更新后的数据，最终内容也不同。有人说“模型不稳定”，有人说“工具变了”。仅保存 prompt 和 seed，无法区分这两类原因，更不能安全地重新发送昨天的邮件来“复现”副作用。

今日命题：Agent 可复现性不是单个模型调用的字节一致性。一次任务是模型决策、工具响应、权限判断、环境状态、并发事件顺序和外部效果构成的轨迹。首先说明要复现什么：历史中实际记录的事实、相同边界输出下的控制流、固定隔离环境中的行为，还是当前世界下的目标完成能力。四种主张需要不同证据，不能都叫 replay。

9 月 Runtime 系列讲过事件溯源与 crash recovery；10 月讲过 trace 不能自动证明正确；11 月讲过评测轨迹和工具观察版本。本篇不重复“如何从日志恢复运行”，而是讨论证据可重复性：哪些输入必须固定，哪些不可控输出应记录，为什么重放旧副作用有害，以及结果不同时怎样定位第一处分歧。下一篇处理审计包的完整性与跨版本验证。

核心界限：seed 是一个输入，不是整个世界的快照；重跑成功也不证明昨天做过相同动作。
02

把模型随机性放回完整执行链

模型 token 选择可能受采样、实现和服务版本影响；即使模型输出相同，工具后端数据也可能更新，权限被撤销，并发回调到达顺序也可能改变。PyTorch 官方 reproducibility 文档明确提醒不同 release、平台或 CPU/GPU 路径不保证完全可复现；它说明固定随机种子只是其中一项控制，不代表任意托管 LLM 的行为。Reproducible Builds 社区关注输入、工具链与构建环境的一致，OCI descriptor 的 digest 可标识镜像内容；镜像固定仍不固定远端 API 与时间。

因此，Agent 的“输入”要扩展到 goalVersion、完整 system/developer/user/context packet、模型与 tokenizer 标识、采样参数、工具目录与 schema、runtime 代码、sandbox image、权限政策、数据快照或 watermark、时区/时钟、调度顺序。W3C PROV 的实体与活动关系能帮助记录哪些内容由哪些步骤派生，Trace Context 帮助跨组件关联；但哈希和 trace 只能证明记录关联或完整性，不能替 verifier 判断动作是否满足目标。

对一次审计任务，工程师若只想查“昨天为何发给错收件人”，先读原始事件与最终发送凭证，根本不需要重跑模型。若要验证新 runtime 在相同已记录响应下是否还会选择同一分支，用桩重放。若要比较新版模型在固定环境里的行为，才用隔离重执行。选择模式前先写清问题，能避免把实验结果冒充历史事实。

03

四种重放模式的实现边界

1. 记录可复现性 manifest

每个 taskId 的启动清单包含目标/验收版本、prompt/context packet 的内容摘要与可授权读回引用、模型标识与参数、工具 catalog/schema/连接身份、runtime commit、环境镜像 digest、依赖版本、数据集快照 ID、政策版本和时间源。秘密值不进入普通日志，只留安全引用。manifest 说明“我们认为哪些输入需要固定”，并非宣称外部世界已冻结；无法固定的源要显式标 volatile。

2. 捕获每个非确定性边界的输出

模型 response、工具 observation、审批决定、回调、超时和人工 signal 都以 event ID、发生/记录时间、来源、输入参数摘要及关联 operation ID 存档。工具返回“成功”时还保留权威资源读回，防止把 API ack 误当目标完成。并行调用须记录发起、完成和被 reducer 消费的顺序；同样两个结果若顺序不同，模型看到的 context 可能不同。日志可以做内容哈希和访问控制，但不能为了便于重放保存明文秘密或扩大原数据的可见范围。

3. 查看历史记录不等于执行

inspection 模式读取 manifest、事件流和 effect receipt，回答“当时记录了什么、由哪个版本决定、哪些结果仍未知”。它不调用模型或工具，因此不能证明新代码会重做同一选择。若缺少某条外部回执，应标 evidence_missing，不用模型补写一条看似合理的 observation。审计中先保留原始时间序和派生链，再生成可读摘要。

4. 桩重放验证控制流，不验证新世界

stub replay 按记录顺序把模型与工具的历史输出注入 runtime，检查 reducer、状态迁移和派发决策是否与原版一致。所有外部写入被替换为模拟 effect handler；否则重放会再次发送邮件或预订房间。它适合诊断新代码是否改变了对同一事件的解释，却不能证明模型会再次生成同样文本，也不能证明今天的权限和数据仍相同。

5. 隔离重执行测试模型与工具组合

isolated rerun 在固定 image、数据快照、工具桩或可检查沙箱里重新调用候选模型与工具。记录新的随机种子、模型/工具版本和每个 observation。若供应方不提供精确模型 snapshot、并行硬件路径变化或后端 API 未冻结，就只能声称“在此受控条件下取得了某种结果”，而非字节级复现。工具一旦选择日志未覆盖的新分支，必须由隔离环境实际生成反馈；不能把旧分支 observation 移植过去。

6. 当前世界再跑是新任务

live rerun 使用今天的价格、权限、用户目标与工具数据，是验证当前能力而非历史复现。对有副作用动作须重新授权、重新生成 operation ID，并遵守当前风险门；不能为了研究昨天的行为就给客户再发一次邮件。与昨天比较时可看目标层接受条件、动作类型和 first divergence，但不要因为结果不同就一概说“回归”：外部世界变了也可能是正确响应。

manifest = load_run_manifest(task_id)
events = load_authorized_event_refs(task_id)
if mode == INSPECT: return explain_record(manifest, events)
if mode == STUB: return reducer_with_recorded_boundaries(events, writes=SIMULATED)
if mode == ISOLATED: return execute_in_pinned_sandbox(manifest, writes=SIMULATED)
if mode == CURRENT: return new_authorized_task(current_goal, current_world)

这四种模式和 manifest 字段是本文编辑性工程综合；规范与文档分别提供构建、来源或随机性方面的局部证据。

04

字节复现与结果复现不是一回事

可把一次运行抽象为 R=F(G,P,M,T,E,O,S)：G 是目标版本，P 是完整 prompt/context，M 是模型及采样设置，T 是工具合同，E 是运行环境与政策，O 是边界观察，S 是事件调度顺序。写成函数只方便列依赖，不表示现实中 F 一定确定；隐藏服务状态和硬件非确定性可能仍影响输出。固定 seed 只固定 M 中一项，不能固定 O 或 S。

R = F(G,P,M,T,E,O,S)

定义 ExactText(R′,R) 表示最终文本字节相同，VerifiedGoal(R′) 表示独立 verifier 证实目标达成，SameVerdict(R′,R) 表示两次验收结论相同。它们没有简单等价关系：

ExactText(R′,R) ⇏ VerifiedGoal(R′)；SameVerdict(R′,R) ⇏ ExactText(R′,R)

相同文字若外部世界不同，未必达成目标；不同措辞也可满足同一验收。工程上应明确要检查哪一级等价：诊断工具序列、审计原始记录还是比较最终用户结果；不要把“输出文本一样”直接当成功。

事件哈希链可提高改写检测：hᵢ=H(hᵢ₋₁∥canonical(eventᵢ))。hᵢ 是当前链值，H 是加密哈希，canonical 给事件稳定序列化，∥ 表示连接。若中间事件被改，后续 hash 会变；但链完整不证明事件内容真实，也不让有权限的人自动读到受限原文。需要来源签名、访问控制与外部读回共同支撑审计。

05

对 Agent 系统的影响

可靠性与成本

不同目标使用不同重放模式。故障诊断先 inspection；runtime 迁移用桩重放；模型升级用隔离重执行；线上验证用经授权的新任务。全量保存每次模型原始 prompt 与大工具输出很昂贵且有隐私风险，可保存受控原文库引用与摘要，但关键决策字段要可读回。节省日志成本不能以失去故障第一分歧点为代价。

沟通与责任

报告里可以写“在固定工具响应下控制流可复现”，也可以写“新版模型在隔离环境 80% 轨迹达成同一验收”，不能合并成“生产结果可复现”。对用户，说明昨天的外部操作 ID 与已核验状态，比承诺今天能生成相同文字更有用。

06

取舍与失败模式

固定太少：只存 prompt、seed 与最终答案，无法区分模型、工具、权限或事件顺序变化；无法审计“何时发给谁”。固定太多：把秘密、客户全文与所有远端响应永久存档，增加成本和越权风险。按决策边界保留 digest、受控原文引用、版本和权威 effect receipt，并设保留期限。

重放写入：测试 harness 若把历史 send_email 原样派发，会制造真实重复效果。stub/isolated 模式必须强制沙箱和 egress broker，给模拟 operation ID，禁止误连生产凭据。模拟成功不等于外部系统当时成功，历史成功要以原始读回证明。

并发重排：固定旧顺序有利于复现特定 bug，却可能掩盖另一个合法顺序下的竞态。先 exact replay 定位，再在隔离环境中系统性重排无因果先后关系的事件，观察 invariants 是否仍成立；不要将重排轨迹误标为历史事实。

供应方边界：模型 endpoint 的版本别名、不可见服务配置或更新的工具后端可能无法完全固定。把这些列为 volatile 与证据限制，而不是假定 seed=0 就锁住整个模型。跨平台重执行结果不同也不必然说明一方错误；核验应对照目标与资源后置条件。

评测：构造相同 prompt 不同工具版本、相同事件不同完成顺序、相同模型不同数据快照、外部写入超时与审批撤回。检查 manifest 是否完整、桩重放是否无副作用、隔离环境是否真生成新分支观察，以及报告是否准确标明证据等级。若审计包 hash 完整但原始事实被错误标注，仍须判失败。

07

可以带走的判断

  1. 先声明复现目标：历史记录、固定输出控制流、隔离重执行或当前新任务，各自证据不同。
  2. prompt 与 seed 远远不够；模型、工具、环境、权限、数据与并发消费顺序都影响轨迹。
  3. 测试重放不得重新触发真实副作用；历史效果由原 operation ID 和权威读回证明。
  4. 字节一致、控制流一致与目标一致不是同一验收，报告应标清模式和限制。
08

  • PyTorch Reproducibility Notes — 官方文档说明跨版本/平台完全可复现的限制；不直接代表任意托管 LLM。

Same Prompt and Seed: Why Can’t an Agent Reproduce Yesterday?

An agent outcome depends on model, tools, authority, environment, data, and event order. Separate inspection, stub replay, isolated re-execution, and a current rerun so each evidence claim stays within what it actually proves.

2026-11-2220 min readReproducibility / Replay / Agent traces / Nondeterminism / Execution evidence
01

Today's proposition

An agent generated and sent an audit report yesterday. Today an engineer reruns it with the same user prompt, temperature zero, and seed. It chooses another tool, reads updated data, and produces different content. One observer blames model instability; another blames the tool. A prompt and seed alone cannot distinguish those causes. Re-sending yesterday's email to “reproduce” the side effect would be unsafe.

Today's proposition: agent reproducibility is not byte identity for one model call. A task is a trajectory of model decisions, tool responses, authority decisions, environment state, concurrent event order, and external effects. First define what is meant to be reproduced: what the historical record says happened, control flow under recorded boundary outputs, behavior in a pinned isolated environment, or goal completion in today's world. Those four claims need different evidence and should not all be called replay.

The September Runtime series covered event sourcing and crash recovery. October established that a trace alone does not prove correctness. November covered evaluation trajectories and observation versions. We do not repeat how to resume a crashed workflow. The subject here is evidentiary reproducibility: which inputs to pin, which uncontrollable outputs to record, why real side effects must not be replayed, and how to locate the first divergence when results differ. The next part covers audit-package integrity and cross-version validation.

Boundary: a seed is one input, not a snapshot of the world. Succeeding again does not prove that the same action happened yesterday.
02

Put model randomness in the full execution chain

Token choice can vary with sampling, implementation, and service version. Even if a model emits identical text, a tool backend may have new data, authority may be revoked, and concurrent callbacks may arrive in another order. PyTorch's official reproducibility note warns that complete reproducibility is not guaranteed across releases, platforms, or CPU and GPU paths. It illustrates why fixing a random seed is only one control; it is not a claim about a particular hosted LLM. Reproducible Builds focuses on stable inputs, toolchains, and build environments. An OCI descriptor digest identifies image content, not remote APIs or time.

The “input” to an agent therefore includes goalVersion, complete system/developer/user and context packets, model and tokenizer identity, sampling parameters, tool catalog and schemas, runtime code, sandbox image, authority policy, data snapshot or watermark, time zone and clock, and scheduling order. W3C PROV can represent which entities and activities produced an artifact, and Trace Context correlates components. Hashes and traces establish relationships or integrity, not whether an action met its goal; a verifier still does that.

If the question is “why did yesterday's audit go to the wrong recipient?”, inspect historical events and the actual send receipt; no model rerun is necessary. To ask whether new runtime code follows the same branch under recorded responses, use stub replay. To compare a new model under pinned conditions, use isolated re-execution. Naming the question first prevents an experiment from masquerading as history.

03

Implementation boundaries for four replay modes

1. Record a reproducibility manifest

A taskId's start manifest includes goal and acceptance version; digests and authorized readback references for prompt and context packets; model identity and parameters; tool catalog, schemas and connection identity; runtime commit; environment image digest; dependency versions; dataset snapshot ID; policy version; and time source. Ordinary logs hold secure references rather than raw secrets. The manifest says which inputs we intend to pin. It does not claim that external services are frozen. Mark sources that cannot be fixed as volatile.

2. Capture outputs at nondeterministic boundaries

Archive model responses, tool observations, approvals, callbacks, timeouts, and human signals with event IDs, occurrence and record times, provenance, input-argument digests, and operation IDs. A tool saying “success” also needs authoritative resource readback so an API acknowledgement is not confused with goal completion. For concurrent calls, record launch, completion, and reducer-consumption order. The same two responses in another order can change model context. Hash and access-control logs where appropriate, but do not store plaintext secrets or broaden source-data visibility merely for replay convenience.

3. Inspecting history does not execute it

Inspection reads the manifest, events, and effect receipts to answer what was recorded, which version made a decision, and what remains unknown. It calls neither model nor tool, so it cannot prove that new code would choose the same path. A missing external receipt stays evidence_missing; the model must not fabricate a plausible observation to fill the gap. Preserve original ordering and derivation before making a human-readable summary.

4. Stub replay tests control flow, not today's world

Stub replay injects recorded model and tool outputs into the runtime in their recorded order, testing reducer behavior, state transitions, and dispatch decisions. Every external write is replaced by a simulated effect handler; otherwise replay would send mail or book a room again. This mode diagnoses whether new code interprets the same events differently. It does not establish that the model would regenerate identical text or that today's authority and data remain unchanged.

5. Isolated re-execution tests the model-tool combination

An isolated rerun calls the candidate model and tools again inside a pinned image, data snapshot, tool stubs, or inspectable sandbox. Record the new seed, model and tool versions, and each observation. If a provider offers no exact model snapshot, parallel hardware paths change, or a backend API was not frozen, the result supports “this happened under these controlled conditions,” not byte-for-byte reproduction. If the candidate chooses a branch absent from the log, the isolated environment must generate that branch's feedback; an old observation cannot be transplanted onto it.

6. A current-world rerun is a new task

A live rerun uses today's prices, authority, user goal, and tool data. It evaluates present capability rather than reconstructing history. Side-effecting actions need renewed authorization and a new operation ID under current risk gates. Do not send a customer a second email merely to study yesterday's behavior. Compare goal acceptance, action type, and first divergence with the historical run, but do not automatically call every difference regression: a changed world may require a different correct response.

manifest = load_run_manifest(task_id)
events = load_authorized_event_refs(task_id)
if mode == INSPECT: return explain_record(manifest, events)
if mode == STUB: return reducer_with_recorded_boundaries(events, writes=SIMULATED)
if mode == ISOLATED: return execute_in_pinned_sandbox(manifest, writes=SIMULATED)
if mode == CURRENT: return new_authorized_task(current_goal, current_world)

These four modes and manifest fields are editorial engineering synthesis. The cited specifications and documents contribute narrower ideas about builds, provenance, tracing, or randomness.

04

Byte reproduction and outcome reproduction differ

Abstract one run as R=F(G,P,M,T,E,O,S). G is goal version, P the complete prompt and context, M model and sampling setup, T tool contracts, E environment and policy, O boundary observations, and S event scheduling order. Function notation lists dependencies; it does not assert that F is deterministic in a real service. Hidden provider state and hardware nondeterminism may still affect output. A seed fixes only one part of M, not O or S.

R = F(G,P,M,T,E,O,S)

Let ExactText(R′,R) mean identical final-text bytes, VerifiedGoal(R′) mean an independent verifier confirms success, and SameVerdict(R′,R) mean the two runs receive the same acceptance outcome. They have no simple equivalence:

ExactText(R′,R) ⇏ VerifiedGoal(R′); SameVerdict(R′,R) ⇏ ExactText(R′,R)

Identical text under a changed world may fail a goal. Conversely, two differently worded reports can both meet the same acceptance contract. State the equivalence level before testing: tool-sequence diagnosis, audit of original records, or user-outcome comparison. Do not treat identical prose as success by itself.

An event hash chain can help detect modification: hᵢ=H(hᵢ₋₁∥canonical(eventᵢ)). hᵢ is the current chain value, H a cryptographic hash, canonical a stable event serialization, and ∥ concatenation. Changing a middle event changes later hashes. An intact chain still does not prove the event was truthful or authorize broad reading of restricted source text. Source authentication, access control, and external readback remain necessary for audit.

05

Implications for agent systems

Reliability and cost

Choose replay mode by question. Diagnose an incident through inspection, test a runtime migration with stubs, test a model upgrade by isolated re-execution, and validate current service with a newly authorized task. Retaining every raw prompt and long tool response is costly and may expose private data. Controlled source-store references and summaries can reduce storage while decisive fields remain readable. Saving log cost must not erase the first divergence needed for diagnosis.

Communication and ownership

A report may say “control flow reproduced under recorded tool responses” or “the new model reached the same acceptance result on 80% of isolated trajectories.” It may not collapse these into “production outcomes are reproducible.” For a user, yesterday's external operation ID and verified status matter more than a promise to generate the same wording today.

06

Trade-offs and failure modes

Pinning too little: a prompt, seed, and final answer cannot distinguish model, tool, authority, or event-order change and cannot audit who received a message. Pinning too much: keeping raw secrets, customer text, and every remote response forever increases cost and exposure. Retain digests, access-controlled source references, versions, and authoritative effect receipts at decision boundaries with explicit retention periods.

Replaying writes: a test harness that dispatches historical send_email calls can create real duplicates. Stub and isolated modes require a sandbox and egress broker, simulated operation IDs, and no accidental production credentials. Simulated success is not proof of what an external service did yesterday; historical success needs the original readback.

Concurrency reordering: fixing the old order helps reproduce one bug but can hide a race under another valid order. First replay exactly to locate divergence, then systematically reorder events with no causal precedence inside isolation and test invariants. A reordered trace is a counterfactual test, not historical fact.

Provider boundary: a model alias, invisible service configuration, or updated tool backend may not be pinable. Mark these volatile and state the resulting evidence limit instead of assuming seed zero locks the model. A different result across platforms need not mean either is wrong; verify against the goal and resource postconditions.

Evaluation: pair identical prompts with changed tool versions, identical events with different completion order, identical models with changed data snapshots, timed-out external writes, and withdrawn approvals. Check manifest completeness, side-effect-free stub replay, genuine feedback on a new branch in isolation, and accurate evidence labels in the report. An intact audit-package hash with a false original claim still fails.

07

Reusable judgments

  1. Declare the target: historical record, control flow under recorded outputs, isolated re-execution, or a new current task. Each has different evidence.
  2. A prompt and seed are far from sufficient; model, tools, environment, authority, data, and concurrent consumption order all shape the trajectory.
  3. Test replay must not reissue real side effects. Original effects need original operation IDs and authoritative readback.
  4. Byte identity, control-flow identity, and goal-level equivalence are different criteria; name the mode and its limits in every report.
08

Sources and evidence boundaries

  • Reproducible Builds Documentation — first-party community guidance on fixed inputs, toolchains, and environments; external agent services add boundaries.
  • PyTorch Reproducibility Notes — official limitations across releases and platforms; not a direct claim about a hosted LLM.
  • OCI Image Spec: Descriptor — official source specification for image digests, which do not pin remote data or authority.
  • W3C PROV-DM and Trace Context — official provenance and cross-component correlation specifications; neither proves business correctness automatically.
  • Chandy & Lamport, Distributed Snapshots — original work on concurrent-system snapshots; four agent replay modes here are engineering extensions.

Links and titles were checked on 2026-11-22. The reproducibility manifest, four modes, and hash chain are editorial engineering synthesis. No current model service is claimed to guarantee byte-level determinism.

09

Where this series stands

Established today: an agent run depends on goal, complete context, model and sampling, tools, environment and policy, external observations, and event order; a seed fixes only one corner. Inspection, stub replay with recorded boundary outputs, isolated re-execution, and a new task in the current world are distinct modes. The manifest and boundary events locate first divergence; test replay avoids real side-effect duplication. Byte and goal equivalence need different evidence.

Still open: how can we establish that the manifest and event chain are complete and unmodified? When model or tool versions cannot be pinned exactly, how should a conditional reproduction claim be reported? How can privacy-sensitive raw sources be withheld from ordinary logs while available to an authorized verifier? Which later environment or policy changes invalidate audit evidence?

Next starting point: Part 2 of Agent Reproducible Execution Internals begins with a run manifest containing volatile boundaries and builds an access-controlled audit bundle, integrity checks, first-divergence analysis, cross-version comparison, and release gate. It will not repeat today's four mode definitions.
