01

今日命题

用户共享屏幕，指着卡片 A 说‘把这个移到明天’。声音经过一条网络路径，画面经过另一条；等语音转写到达 Agent，屏幕已经滚到卡片 B。若系统把‘最新收到的帧’与‘最新收到的词’拼在一起，就会很自信地改错卡片。两条流都各自正确，组合仍可能错误。跨模态对齐首先是时间与因果问题，不是把两个 embedding 拼接起来的问题。

昨天完成 Audio & Realtime Agent Internals：波形/转写不是同物，turn commit 与工具提交不同步，发布要看授权终态。更早的视觉专题说明截图坐标需要 observation ID 与动作前复核。今天开始 Realtime Multimodal Coordination 1/2，只回答‘哪段声音能配哪一帧、在当时能否被 Agent 看见’：采集时间、传输到达、不同 clock domain、缓冲水位和迟到证据。下一篇才讨论‘同一时间的证据互相冲突或说话人不明时，Agent 怎样决定工具动作’；不重复声学帧、视觉 patch 或 WER。

核心判断：同一时间范围内的音视频是候选关联，不自动证明同一说话人、同一物体，更不自动形成可执行授权。
02

承接语音 turn 与视觉 observation

纯语音系统可以为一句话保存开始/结束时间、partial→final 修订和 turn epoch；纯视觉系统可以为截图保存采集时间、视口、滚动位置和 observation ID。跨模态时，‘用户说这个’中的‘这个’必须落到某个视觉状态。若把一整段转写当成一个瞬时点，把滚动后的截图当成说话时的画面，即使 ASR 与视觉识别都满分，指代仍会错。Agent runtime 应保留原始时间范围与来源，而不是只存一段文字加一张最后截图。

这里还有两个容易混淆的时间。event time 是音频样本或视频帧实际采集、呈现的时刻；availability time 是它完成传输、解码和预处理、可供某次模型调用使用的时刻。‘事后能对齐’不等于‘当时能用’。离线回放若让模型看到未来到达的帧，会人为提高准确率，却不能重现实用延迟。业务动作还有第三个时刻：执行前 UI 可能又变了，所以历史对齐用于解释用户指向，当前状态复核用于安全执行，两者缺一不可。

RTP 的标准为同一媒体流提供时间戳；不同流的原始 RTP 时间戳有各自频率与随机偏移，不能直接比较。RFC 3550 用 RTCP sender report 中的 NTP/RTP 对应关系在已知共同钟关系时支持跨媒体同步。若系统不是 RTP，也必须显式定义共同单调时钟或估计时钟映射。服务端接收时间只是到达时间，不会神奇地变回采集时间。

03

机制：把两个流映射到一条有截止点的时间线

1. 采集时记录四层时间，不在末端补猜

对每个音频 chunk 与视频帧，记录媒体内序号、原时钟时间戳、估计采集时刻、服务端收到时刻、完成解码/模型预处理的时刻，以及 clock mapping 版本和不确定度。音频识别出的词最好带区间，而不是只有整句 final 时间；视频帧要记采样或曝光时刻、视口与画面版本。时间元数据应和内容 ID 一起穿过 ASR、视觉 encoder、LLM 和工具 runtime。只有末端一行‘用户说了这个’与一张截图，无法事后修复错配。

2. 将不同 clock domain 映到共同轴

一个手机麦克风按采样时钟计数，摄像头按视频时钟计数，服务端按自己的单调时钟收包。即使都叫 timestamp，单位和起点可能不同。RTP/RTCP 可提供映射对；本地采集也可在同一 monotonic clock 上为两路打点。映射需要随会话更新，处理漂移、重连、设备切换和突然跳变；不能拿墙上时钟的日期字符串做毫秒级关联。同步消息丢失时保留误差范围，超界则标记‘无法可靠对齐’，不要硬塞给融合模型。

3. 使用 event-time 候选窗口，不盲选最新帧

将‘这个’所在词区间映到共同时间轴，从附近帧、手势或屏幕状态里生成候选，而不是只拿 arrival order 最后的帧。例：卡片 A 的画面采集于 1.00 s，用户说‘这个’于 1.05 s；卡片 B 的画面采集于 1.20 s，但 B 包在 1.22 s 到达，音频转写 1.27 s 才完成。1.27 s 的‘最新画面’是 B，却不是说话时的 A。这里数字只为说明排序反转。候选窗口还要考虑帧率、ASR 时间戳误差、网络抖动与手势持续时间；不能凭一个全局固定毫秒阈值解决所有设备。

4. 决定要等多久、何时拒绝迟到证据

流处理器可为每路维护 event-time watermark：在当前观测下，早于该时间的事件预计基本到齐。它是关于迟到上界的工程假设，不是保证。若用户在 1.05 s 说了‘这个’，Agent 可以等一个短的对齐宽限期以取得 1.00 s 左右的帧；等得太短会缺画面，等得太久会破坏实时交互。对尚未到的帧，回复‘我看到的是哪张卡片？’比猜测安全。晚到帧可用于日志纠错与下一轮澄清，但不能被倒灌进已经提交的旧工具调用。

5. 以因果快照喂模型，执行前再复核

每次决策冻结一个 evidence bundle：音频区间/转写修订、候选帧 ID、两路映射与误差、各证据的 available_at、决策截止时刻、UI observation 版本。只允许 available_at≤截止时刻的证据进入这次调用；模型输出仍是‘卡片 A’候选解释，而非工具授权。执行器再用当前 UI/DOM 或新截图核实卡片 A 的稳定 ID 和参数，并遵守权限门。若用户说话后卡片已被删除或列表重排，旧帧可证明指代，却不保证现在能安全点击。

6. 让故障暴露为不同状态

测试中分别注入音频迟到、视频迟到、帧丢失、时钟漂移、设备切换、ASR 回改和 UI 重排。记录‘当时可用证据’与‘事后完整证据’两个视图。若事后可对齐、当时不可用，这是延迟/缓冲问题；若都不可对齐，是采集或时钟问题；若对齐正确却选错卡片，是融合/指代问题；若选对但点错，是动作与当前状态问题。分类让优化能落在正确层，避免所有失败都被归给多模态模型。

04

必要数学：时钟映射、误差与等待成本

把某路源时钟的计数 x 映到共同单调时间 t，局部可近似写成 t≈a·x+b。a 是时钟速率换算与漂移，b 是起点偏移；两路各自有 a、b。只用一个固定 b，设备时钟略快或略慢时，长会话的错位会随时间累积。用带时钟关系的同步点更新映射，并为估计保留误差范围。RFC 3550 说明不同媒体流的原始 RTP timestamp 不可直接比较，RTCP sender report 给出 RTP 与 NTP 的对应关系；上式是本文的简化工程模型，不是 RFC 指定的估计算法。

若音频词的共同时间区间为 I_a=[t_start,t_end]，候选帧采集于 t_v，且两路合计对齐不确定度上界为 ε，可先将 t_v∈[t_start−ε,t_end+ε] 作为候选筛选。t_start、t_end 是词的开始/结束，ε 汇集时钟映射、采集标记与分段误差；这个点采样条件只说‘时间上可能相关’，不证明嘴型、说话人或物体指代。若帧代表一段持续的画面状态，实际应比较两个时间区间是否重叠，而不是只比较采样点。错误并非总能简单相加成严格上界，需依据测量方式校准 ε。

令决策截止时刻为 D，证据 i 的可用时刻为 A_i。在线决策只可使用 A_i≤D 的证据；离线评测也应重放同一约束。若给迟到视频增加等待 Δ，完成证据的比例通常上升，但最坏情况下的决策截止点会后移 Δ；证据早到时无需等满。工程上绘制‘缺失关联证据率 vs. 端到端延迟’曲线，并按任务风险选点。高风险工具宁可追问或暂停，不应把低延迟作为自动猜测理由。

05

对 Agent runtime 与评测的影响

输入 API 不应只返回‘一段转写 + 一张图’，而应返回可追溯的时序 observation：流 ID、chunk/frame ID、事件区间、到达/可用时刻、映射版本、置信范围和内容引用。LLM 可以消费简化后的候选包，但 runtime 保存完整元数据。这样模型说‘卡片 A’时，审计者能追问它依据的是说话时的 A，还是滚动后的 B。日志可在隐私约束下保存受控引用与必要时间戳，不要求无限留存视频或原声。

模型的上下文窗口也因此要按‘决定时可用’构造，而不是按最终收齐的素材做漂亮摘要。ASR partial 改写、视频帧迟到和字幕对齐修正都要生成新版本；旧版本工具提案随 turn/observation epoch 失效。跨模态 embedding 能把语音与视觉语义放进同一表示空间，但不能替 runtime 解决 packet arrival、时钟漂移或当前 UI 是否仍可操作。AV-HuBERT 作者研究音视频语音表征，Video-LLaMA 作者展示音视频理解模型；这些研究结果不等于真实 Agent 已拥有因果调度和业务授权。

验收要分别报告离线事后对齐、在线截止时对齐、指代正确、工具后置条件与 latency/cost。只看离线准确率会奖励‘偷看未来’；只看在线速度会奖励盲猜。对长会议、远程桌面、网络切换和双人说话做切片，并故意交换两路延迟顺序，验证系统不会把到达顺序误当事件顺序。可恢复 trace 应使迟到证据能推动下一轮澄清，而不是悄悄改写已执行历史。

06

取舍与失败模式

  • 按到达顺序配对：传输和解码延迟可逆转音视频先后；按 event time 建候选并记录 available_at。
  • 直接比较两个 RTP timestamp：流的频率和随机偏移不同；先用映射点转到共同轴。
  • 只给 ASR 终稿时间：‘这个’可能在整句话开头；保留词或片段区间及其修订。
  • 多等总是更准：可得到迟到帧，却增加交互延迟；以水位与任务风险选宽限期。
  • 离线对齐高分即可上线：离线可看到决策后才到的帧；重放在线可用性约束。
  • 时间重合就是同一人/同一物：背景视频、旁人和重叠说话会制造巧合；下一篇处理身份与语义冲突。
  • 旧帧已证明对象可点击：UI 可能重排；动作前在当前环境复核稳定 ID 与权限。

更完整的时间元数据会占用传输、存储和处理预算，也可能包含敏感行为轨迹。用短生命周期的受控引用和抽样 trace 保留诊断能力。省略这些元数据看似简单，却会让错配无法归因，最后只能把所有故障模糊归咎于模型‘看错了’。

07

可复用的技术判断

  • 音频与视频各有采集、到达和模型可用时刻；到达顺序不是发生顺序。
  • 不同 clock domain 先映射到共同单调轴，并保留漂移与误差；原始 RTP 时间戳不能跨流直接比较。
  • 词区间与候选帧只建立时间关联，不证明说话人、指代或权限。
  • 在线模型只能用决策截止前可用证据；迟到材料用于澄清或审计，不能倒灌旧动作。
  • 历史帧解释用户所指，当前环境复核决定能否安全执行。
08

一手资料与证据等级

  • RFC 3550: RTP — 协议规范明确不同媒体流原始 RTP 时间戳不可直接比较，并定义 RTCP sender report 的 RTP/NTP 对应。
  • RFC 8834: Media Transport and Use of RTP in WebRTC — WebRTC 媒体传输的规范背景；不规定本文 Agent 的水位和工具策略。
  • AV-HuBERT — 作者研究音视频语音表征；论文训练与评测不是通用实时 Agent 的调度保证。
  • Video-LLaMA — 作者报告音视频视频理解模型；不据此推断在线 clock mapping 或工具授权。
  • ImageBind — 作者研究跨模态共享 embedding；语义邻近不等于采集时间同步。

When the User Says ‘This,’ Which Frame Should the Agent See?

Separate capture time, arrival time, clock mapping, and causal watermarks in a realtime audio-visual agent.

01

Today's proposition

A user shares a screen, points to card A, and says, 'Move this to tomorrow.' The audio follows one network path and the video another. By the time the transcript reaches the agent, the screen has scrolled to card B. Pairing the latest received frame with the latest received words confidently changes the wrong card. Each stream may be internally correct while their combination is wrong. Cross-modal alignment starts as a time-and-causality problem, not an embedding-concatenation problem.

Yesterday completed Audio & Realtime Agent Internals: waveform and transcript are different representations, turn commitment and tool commitment are distinct, and release depends on authorized outcomes. The earlier visual series showed why a screenshot needs an observation ID and pre-action recheck. Today begins Realtime Multimodal Coordination Part 1 of 2. We ask which sound interval can be associated with which frame and whether that frame was actually available to the agent at decision time. Capture time, network arrival, clock domains, buffering watermarks, and late evidence are the subject. Part 2 will handle conflicting evidence, uncertain speakers, and tool decisions without replaying acoustic framing, visual patches, or word error rate.

Core judgment: audio and video in the same time range are candidate associations. They do not prove one speaker, one object, or authorization to act.
02

Connecting voice turns to visual observations

A voice-only system can retain an utterance start and end, partial-to-final revisions, and a turn epoch. A vision-only system can retain screenshot capture time, viewport, scroll position, and observation ID. In a combined system, 'this' must resolve against a visual state. If an entire transcript is treated as one instant and a post-scroll screenshot is substituted for the scene during speech, reference can fail even with perfect ASR and image recognition. The runtime needs original intervals and provenance rather than a text string plus the last screenshot.

Two kinds of time are especially easy to confuse. Event time is when an audio sample or video frame was captured or presented. Availability time is when transport, decoding, and preprocessing made that evidence usable by a particular model call. 'Alignable in hindsight' does not mean 'available at the time.' An offline replay that reveals a frame arriving in the future can inflate accuracy while hiding real latency. A business action has a third moment: the UI may change again before execution. Historical alignment explains what the user pointed at; a fresh state check makes execution safe. Both are required.

RTP timestamps recover timing within a media stream, but raw timestamps from different streams have their own clock rates and random offsets and cannot simply be compared. RFC 3550 describes RTCP sender reports that pair RTP and NTP times for cross-media synchronization when the clocks have a known relationship. If the system is not based on RTP, it still needs an explicit common monotonic clock or an estimated clock mapping. Server receive time is arrival time; it does not magically reconstruct capture time.

03

Mechanism: map streams onto a deadline-bound timeline

1. Record four layers of time at capture, not by guessing at the end

For each audio chunk and video frame, retain an in-stream sequence number, original clock timestamp, estimated capture time, server receive time, decode or model-preprocessing completion time, clock-mapping version, and uncertainty. Recognized words should carry intervals when available, rather than only a final timestamp for the whole sentence. A video frame needs sampling or exposure time, viewport, and scene version. Time metadata travels with content IDs through ASR, vision encoder, LLM, and tool runtime. One final string saying 'the user said this' and one screenshot cannot repair a mistaken association after the fact.

2. Map clock domains onto a common axis

A phone microphone counts samples with an audio clock; a camera uses a video clock; a server timestamps packet receipt with its own monotonic clock. Even if every field is called a timestamp, units and origins differ. RTP and RTCP can supply mapping pairs. Local capture can instead stamp both streams against one monotonic clock. Update the mapping during a session to handle drift, reconnection, device replacement, and discontinuities. A wall-clock date string is not a millisecond-grade alignment primitive. If synchronization messages are missing, retain a wider uncertainty interval. Beyond a defined bound, mark the evidence unreliable for alignment rather than silently forcing it through a fusion model.

3. Generate candidates in event time, not latest-arrival order

Map the interval containing 'this' to the common axis and consider nearby frames, gestures, or screen states. Do not select only the last frame to arrive. For example, the view of card A was captured at 1.00 s and the user says 'this' at 1.05 s. The view of card B was captured at 1.20 s; its packet arrives at 1.22 s, while the audio transcript completes only at 1.27 s. At 1.27 s the newest frame is B, but the scene at utterance time was A. These times merely illustrate an ordering reversal. Candidate windows also depend on frame rate, ASR timestamp error, network jitter, and gesture duration. No universal millisecond threshold works for every device and task.

4. Decide how long to wait and what late evidence may do

A stream processor can maintain an event-time watermark per stream: under the current lateness assumption, events older than that watermark are expected to have mostly arrived. This is an engineering assumption about lateness, not a guarantee. When 'this' occurred near 1.05 s, the agent can wait a short alignment grace period for a frame around 1.00 s. Waiting too little loses visual evidence; waiting too long makes the conversation sluggish. If the frame is not available, 'Which card do you mean?' is safer than a guess. A late frame may help audit and the next clarification turn, but it must not be retroactively injected into an already committed tool action.

5. Give the model a causal evidence snapshot; recheck before execution

Freeze an evidence bundle for each decision: audio interval and transcript revision, candidate frame IDs, mapping and uncertainty for each stream, each item’s available_at time, decision deadline, and UI observation version. Only evidence with available_at no later than that deadline may enter this call. The model's 'card A' output remains a proposed interpretation, not tool authority. Before acting, the executor checks card A's stable identifier and parameters against the current UI, DOM, or fresh screenshot and enforces the permission gate. If the card was deleted or the list reordered after speech, an old frame can explain reference while failing to establish that a click is safe now.

6. Expose failures as distinct states

Inject late audio, late video, dropped frames, clock drift, device switches, ASR revision, and UI reordering. Preserve two views: evidence available at decision time and complete evidence recovered later. If retrospective alignment works but online alignment did not, investigate latency or buffering. If neither works, inspect capture and clock mapping. If alignment is right but the card choice is wrong, investigate fusion and reference resolution. If the card choice is right but the action misses, investigate the executor and current state. This taxonomy directs improvement to the right layer instead of blaming every failure on a multimodal model.

04

Essential mathematics: clock mapping, error, and waiting cost

A local mapping from source-clock count x to a common monotonic time t can be approximated as t≈a·x+b. The scale a converts clock rate and captures drift; b is the offset. Each media stream has its own a and b. A fixed offset alone gradually fails over a long session if a device clock runs slightly fast or slow. Update the mapping from synchronization points with a defined clock relationship, retaining an uncertainty range. RFC 3550 explains why raw RTP timestamps from different streams cannot be directly compared and how RTCP sender reports pair RTP and NTP time. This affine form is an editorial engineering approximation, not an estimation algorithm prescribed by the RFC.

Suppose the word's mapped audio interval is I_a=[t_start,t_end], a candidate frame was captured at t_v, and a calibrated upper uncertainty allowance is ε. One preliminary filter is t_v∈[t_start−ε,t_end+ε]. t_start and t_end bound the word; ε accounts for clock mapping, capture stamping, and segmentation error. This sampled-point filter identifies possible temporal association only. It does not prove a matching mouth, speaker, or referent. If a frame represents a scene state lasting over an interval, the implementation should test interval overlap rather than only the sample point. Errors are not always safely summed into a strict bound; calibrate ε against the actual measurement process.

Let D be the decision deadline and A_i the availability time of evidence item i. An online decision can use only items satisfying A_i≤D; offline evaluation must replay the same constraint. Waiting an extra Δ for late video usually improves evidence completeness, but the worst-case decision deadline moves back by Δ; evidence that arrives early need not wait the full period. Plot missing-association evidence against end-to-end delay, then select an operating point by task risk. A high-risk tool should ask or pause rather than treat low latency as a license to guess.

05

Implications for agent runtime and evaluation

An input API should return more than one transcript and one image. It needs a traceable temporal observation: stream ID, chunk or frame ID, event interval, arrival and availability time, mapping version, uncertainty, and controlled content reference. The LLM may receive a simplified candidate bundle, while the runtime retains the full metadata. When the model says 'card A,' an auditor can determine whether it relied on A at speech time or B after scrolling. Privacy constraints can still favor controlled references and necessary timestamps over indefinite video or raw-audio retention.

Construct the model context from what was available at decision time, not an elegant summary of material collected later. ASR partial revisions, late video, and corrected caption alignment create new versions; old tool proposals expire with their turn or observation epoch. A cross-modal embedding may put speech and visual semantics into one representation space, but it does not solve packet arrival, clock drift, or whether the current UI remains actionable. AV-HuBERT studies audiovisual speech representations, and Video-LLaMA reports an audiovisual video-understanding model. Neither author result implies a deployed agent already has causal scheduling or business authorization.

Acceptance should separate retrospective offline alignment, alignment at the online deadline, correct reference, authoritative tool postcondition, and latency or cost. An offline-only score rewards 'looking into the future'; an online speed-only score rewards guessing. Slice long meetings, remote desktops, network changes, and two speakers, and deliberately reverse which stream arrives first. The system should not confuse arrival order with event order. A recoverable trace lets late evidence inform the next clarification turn, not silently rewrite an executed history.

06

Trade-offs and failure modes

  • Pair by arrival order: transport and decode delay can reverse audiovisual order. Form candidates in event time and record available_at.
  • Compare raw RTP timestamps: streams have different rates and random offsets. Map them to a common axis first.
  • Keep only final ASR time: 'this' may occur near the start of a long utterance. Preserve word or segment intervals and revisions.
  • Waiting longer is always better: more late frames arrive, but conversation latency rises. Choose a grace period from watermarks and task risk.
  • High offline alignment means ready to ship: offline replay can see frames that arrived after the decision. Reproduce online availability.
  • Time overlap means the same person or object: background video, bystanders, and overlapping speech create coincidental overlap. Part 2 handles identity and semantic conflict.
  • An old frame proves an object is clickable: the UI can reorder. Recheck a stable ID and authorization in the current environment.

Richer temporal metadata costs bandwidth, storage, and processing and can reveal sensitive behavior. Use short-lived controlled references and sampled traces for diagnosis. Omitting metadata looks simpler, but then misalignment cannot be attributed and every failure gets vaguely blamed on a model that 'saw the wrong thing.'

07

Reusable technical judgments

  • Audio and video each have capture, arrival, and model-availability times. Arrival order is not event order.
  • Map clock domains onto a common monotonic axis with drift and uncertainty. Raw RTP timestamps cannot be compared across streams.
  • A word interval and candidate frames establish temporal association, not speaker, referent, or authority.
  • An online model uses only evidence available before its decision deadline. Late material may clarify or audit, never retroactively justify an old action.
  • Historical frames explain the user's reference; the current environment check determines whether action is safe.
08

Primary sources and evidence tiers

  • RFC 3550: RTP — the protocol explains why raw RTP timestamps from distinct media streams are not directly comparable and specifies RTP/NTP pairs in RTCP sender reports.
  • RFC 8834: Media Transport and Use of RTP in WebRTC — standards context for WebRTC media transport, not a specification for our agent watermarks or tool policy.
  • AV-HuBERT — the authors study audiovisual speech representation; training and benchmark results are not a scheduling guarantee for every realtime agent.
  • Video-LLaMA — the authors report an audiovisual video-understanding model, not an online clock mapper or tool authorization policy.
  • ImageBind — the authors study a shared cross-modal embedding; semantic proximity is not capture-time synchronization.

Links and titles were checked on 2026-10-30. Event versus availability time, affine clock estimation, alignment grace periods, causal evidence bundles, and pre-action checks are editorial engineering designs. These sources do not jointly prescribe one agent protocol.

09

Established and next starting point

Established today: building on the speech series' turn epoch and the visual series' observation ID, audio and video need separate capture, arrival, and availability times. Their clock domains are mapped onto a common axis with uncertainty. Alignment creates candidates, while a watermark and decision deadline constrain what evidence the online agent can use. Late frames cannot be injected into executed actions. Historical video explains 'this'; current UI verification makes action permissible.

Still unresolved: even with correct timing, the person on screen may not be the speaker and 'this' may identify multiple objects. When background audio, overlapping speakers, gestures, captions, and screen content conflict, how should provenance and uncertainty be handled? When should the agent clarify, refuse an unauthorized tool, or execute, and how should full-conversation fusion be evaluated?
