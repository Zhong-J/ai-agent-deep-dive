Agent Runtime 内核 · 第 2/4 篇

并行工具调用，为什么不能只是 Promise.all？

用 structured concurrency、dependency DAG、deadline、cancellation propagation、bounded fan-out 与 backpressure，构造可控的 Agent 并行执行。

2026-09-17约 20 分钟Structured concurrency / Cancellation / Backpressure / Agent scheduler / Tool parallelism
01

今日命题

模型一次返回多个 tool calls，不代表它们应该立刻并行。调用之间可能有数据依赖、共享资源冲突、不同风险等级和不同 deadline。无界 Promise.all 会同时占满连接池、打爆下游 rate limit；其中一个失败后，其他调用仍可能继续产生副作用；父任务取消时，孤儿请求可能继续运行并在更晚回写过期结果。

Structured concurrency 的核心不是某个语言 API，而是生命周期原则：子任务必须属于一个可命名 scope；父 scope 在退出前知道所有子任务的终态；deadline、cancellation 和 failure policy 沿结构传播；并发度由 runtime budget 约束，而不是由模型生成多少 calls 决定。

核心判断：并行是一种资源与一致性策略，不是性能按钮。模型可以提出“这些工作看似独立”，但 runtime 必须验证 dependency、effect class、resource key、budget 和 join policy 后，才决定哪些 calls 真正并发。
02

承接显式状态机

上一篇把单个 tool call 展开成 proposed→validated→authorized→recorded→dispatched→outcome。多个 calls 出现时，runtime 不只是复制这条 lifecycle，而要建立一个 execution graph：节点是逻辑 calls，边表示“B 必须读取 A 的 accepted outcome”；没有依赖边也不保证可以并发，因为两个节点可能写同一文件、同一订单或同一用户记录。

因此 state 中需要 task group、dependency edges、resource claims、child deadlines 与 join policy。事件不再只有 ToolResultObserved，还包括 ChildStarted、CancellationRequested、ChildCancelled、JoinSatisfied 和 CapacityReleased。父 turn 只有在 join 条件满足后，才能构造一致的 observation 给模型。

03

机制：一个 bounded scheduler

1. 先验证 graph

runtime 将模型 proposal 编译成内部 DAG，检查 call ID 唯一、依赖存在、无 cycle、tool schema 合法、权限已满足。模型引用未知 node 或产生环时，返回结构化 planning error，而不是执行一半再发现。

2. 计算 ready set

只有所有 predecessors 达到 join policy 所需状态的 node 才 ready。默认要求 dependencies succeeded；也可显式定义“任一成功”“允许 partial failure”或“finally/compensation”。join semantics 属于 runtime contract，不能从自然语言猜。

3. 取得多层 capacity

scheduler 同时检查 global concurrency、tenant quota、tool-specific semaphore 与 resource key。读工具可能共享，写同一对象需要互斥或 optimistic version。取得 capacity 后先记录 ChildStarted，再 dispatch；正常完成或异常返回时用 finally 释放 permit；进程崩溃无法执行 finally，因此分布式 permit 需要带 owner 与 expiry 的 lease，并由 reaper/reconciliation 回收。

4. Deadline 与 timeout

deadline 是父 scope 的绝对最晚时间；child timeout 是单次 operation 的局部预算。child deadline 应为 min(parent deadline, now+tool timeout)。排队时间也消耗 deadline，不能等真正发出请求才开始计时。若剩余时间不足完成有意义的工作，scheduler 应拒绝启动。

5. Cancellation propagation

父 cancel 先改变 durable state，使新 children 不再启动，再向 running children 发送 cancellation token。协作式 tool 在安全点停止并返回 acknowledgement；不可取消或已经提交副作用的工具进入 cancelling/outcome_unknown，等待 reconcile。不能把取消 promise 当作副作用已撤销。

6. Failure policy 与 sibling fate

fail-fast 在关键 child 失败时取消 siblings；collect-all 等所有结果并聚合；quorum 在获得足够成功后取消剩余读取。policy 应按 group 声明。写操作通常不能因为 sibling 失败就盲目 cancel；可能需要补偿或人工介入。

7. Backpressure

ready nodes 不直接变成 running，而进入有界 queue。queue 满时，producer 等待或减速才是 backpressure；入队前拒绝、降级或减少计划属于 admission control/load shedding。两者共同防止无限堆内存。dispatcher 根据 capacity 拉取（pull/demand），tool 返回 429/503 或 latency 上升时减少 permits。模型只收到“capacity deferred” observation，不获得提高 limit 的权限。

8. Deterministic join

并发完成顺序不应随机改变 prompt。runtime 按 node ID、dependency topology 或计划顺序稳定排列 accepted outcomes，并显式标记 cancelled/failed/missing。若 partial results 已经流给模型，必须记录每次 projection version，避免后来的结果使旧决策看似基于完整信息。

while group.open:
  ready = graph.nodesWithSatisfiedDependencies(state)
  for node in stableOrder(ready):
    if budget.expired(node): recordSkipped(node)
    else if capacity.tryAcquire(node.tool, node.resourceKey):
      recordStarted(node)
      spawnInScope(node, childDeadline(node))
  event = await nextChildEventOrCancellation()
  state = reduce(state, event)
  applyFailureAndJoinPolicy(state)
04

必要数学：关键路径、队列与失败放大

DAG critical path

Tmin ≥ maxpath p Σi∈p ti

tᵢ 是节点服务时间。即使无限并发，总延迟也不能短于最长依赖路径；只并行非关键节点可能几乎不降 latency。真实时间还加 queue、serialization 与 join overhead。

Little's Law

L = λW

L 是系统平均在途请求数，λ 是稳定到达率，W 是平均停留时间。若工具每秒接收 10 个 calls、平均停留 2 秒，平均约 20 个在途。Little's Law 本身只关联稳定状态下的平均量。Agent fan-out 可提高 λ，下游变慢可提高 W，从而提高 L；无界 queue 可能持续积压，而有界 queue 会饱和并阻塞或拒绝。并发上限必须结合测得 latency，而非固定拍脑袋。

Utilization

ρ = λ / (cμ) < 1

c 是并行 worker/permit 数，μ 是单 worker 服务率。对无界 queue，长期 ρ≥1 意味着 arrival 超过 capacity 并持续积压；有界 queue 则会饱和，转为阻塞、降级或拒绝。接近 1 时 tail latency 通常急剧恶化。backpressure 的目标不是让所有 worker 永远 100% busy，而是维持可恢复余量。

Fan-out failure

P(any failure) = 1 − (1−p)n

若 n 个独立 calls 各以概率 p 失败，至少一个失败的概率随 fan-out 增长：p=1%、n=50 时约 39.5%。现实失败常相关（同一 outage/rate limit），此时独立公式不再适用；正相关通常放大同时多节点失败的 blast radius，但不保证至少一次失败概率相对独立估计只向一个方向变化。parallelism 提高速度的同时扩大 failure surface。

Deadline allocation

dchild = min(dparent, now + btool)

d 是绝对 deadline，btool 是局部 timeout budget。传递绝对 deadline 比层层重置 timeout 更能防止嵌套调用超出用户总预算。还应预留 join、verification 与 persistence 时间，不能把全部剩余时间给最后一个 tool。

05

对 Agent 系统的影响

1. Tool metadata 必须包含 scheduling contract

除了 input schema，还应声明 read/write effect、resource-key extractor、default timeout、cancellation capability、retry class、rate-limit bucket 与 max concurrency。模型看简化描述，runtime 使用可信 metadata；不能让模型自报“我是只读”。

2. 计划与调度分离

planner 输出 dependency/rationale，但 scheduler 独立验证 DAG 和 capacity。被拒绝的并行建议返回原因，例如 cyclic dependency、conflicting write 或 budget exhausted，让模型重新规划，而不是扩大权限。

3. Partial result 需要版本语义

早到结果可以加速下一步，但模型基于 projection v3 做出的动作不能在 v5 到来后被重新解释。后续结果若推翻前提，应产生 invalidation event，取消尚未执行的 descendants，并让 runtime 显式 replan。

4. Cancellation 必须可观察

记录 requested、signal-delivered、acknowledged、effect-reconciled 四个时间点。用户看到“正在取消”比虚假的瞬时完成更正确。tool manifest 应说明 cancel 是停止等待、停止计算，还是能撤回业务动作。

5. Fairness 防止一个 Agent 垄断资源

global semaphore 不够；一个高 fan-out task 可能占满所有 permits。按 tenant/task 做 weighted fair queue 或 per-task cap，并为交互请求保留容量。queue position 与 estimated start 可成为 observation，避免模型通过重复 calls 争抢。

6. Result ordering 是 prompt determinism 的一部分

同一批并发结果若按到达顺序 append，网络抖动会改变 prompt、后续 logits 和 tool trajectory。稳定 join order、explicit timestamps 与 call IDs 能减少无意义 nondeterminism，同时保留真实完成时间供诊断。

7. Rate limit 是共享状态

429 不是单 call 私有错误。runtime 更新 tool/tenant bucket，暂停相关 queue 并遵守 Retry-After；若每个 child 独立 backoff，会形成 retry storm。模型不应反复换同义 call 绕过 quota。

8. Admission control 发生在入队前

backpressure 若只在 worker 端生效，queue 仍会吞掉内存和 deadline。runtime 在接受 graph 时估算节点数、cost、tool bucket 与用户剩余预算；超限时拒绝整图、裁剪低价值 speculative nodes，或拆成需要审批的 batch。被拒绝必须成为 durable event，防止重启后又重新接受同一计划。

9. Bulkhead 隔离故障域

搜索、浏览器、数据库写入和外部通知不应共享一个 semaphore/queue。为每类 dependency 建 bulkhead，使慢浏览器不会耗尽数据库 permit，高 fan-out 搜索也不会阻塞审批回调。global budget 仍在上层约束总量，避免每个隔舱都各自满载后共同压垮进程。

10. 相同读取可以 coalesce

多个 children 若请求相同的纯读取且 freshness/authorization scope 一致，scheduler 可共享一个 in-flight future，并把结果 fan-out 给多个 call IDs。coalescing 不是缓存：任一调用取消不应自动取消仍有订阅者的底层请求；写操作、不同租户或不同授权上下文不能合并。记录共享关系才能正确审计成本和 provenance。

06

取舍与失败模式

并发度 vs tail latency：增加 permits 可降低 queue time，直到下游饱和；之后 contention、429 和重试让 p95/p99 更差。寻找 knee point，而不是最大吞吐数字。

Fail-fast vs useful partial work：搜索类 fan-out 可在一个失败后保留其他结果；事务链的关键 prerequisite 失败应阻止 descendants。统一策略会浪费信息或放大错误。

Cancellation responsiveness vs consistency：频繁检查 token 能快速取消，但增加代码和状态；不可分割事务保证一致性却延迟响应。清楚标注 safe points 和不可取消区间。

Static DAG vs adaptive replanning：静态图易验证、审计；Agent 根据 partial result 动态加节点更灵活。每次扩图必须形成新 graph version，重新检查 cycle、budget 和 authorization，不能原地偷偷修改。

Queue durability vs overhead：内存 queue 快但进程崩溃丢失；durable queue 可恢复却增加序列化、租约和重复 delivery。副作用 calls 通常需要 durable command；可重新推导的只读 speculative work 可以短暂。

Resource locks vs optimistic concurrency：锁避免冲突但可能死锁、降低并发；version check 允许并发读取/计算，提交时可能重做。对外部 API 若无 version/idempotency 支持，runtime 的本地锁无法协调其他系统写入者。

最危险的失败模式：unbounded fan-out；父结束后 orphan children；cancel 被当作 rollback；排队不计 deadline；到达顺序改变 prompt；重复 429 各自重试；写冲突被模型“合理化”。这些是 scheduler/control-plane 缺陷，不是更强模型能消除的问题。

07

可复用判断

  • 并行 eligibility 由 dependency、effect/resource conflict 与 capacity 三类独立约束决定。
  • structured concurrency 要求子任务归属 scope，父退出前收敛 child 状态，并传播 deadline/cancellation。
  • bounded queue 与 pull-based permits 才能形成 backpressure；模型不能通过 fan-out 决定并发度。
  • cancel 是异步协议，不是 rollback；不可确认的副作用进入 cancelling/outcome-unknown 并 reconcile。
  • 并发结果必须按稳定规则 join，并记录 projection version，避免完成顺序随机改变 Agent 决策。

Why Parallel Tool Calls Are More Than Promise.all

Use structured concurrency, dependency DAGs, deadlines, cancellation propagation, bounded fan-out, and backpressure to build controlled parallel agent execution.

2026-09-1720 min readStructured concurrency / Cancellation / Backpressure / Agent scheduler / Tool parallelism
01

Today's proposition

A model returning several tool calls in one response does not mean they should all start immediately. Calls can have data dependencies, conflicts on shared resources, different risk classes, and different deadlines. An unbounded Promise.all can exhaust connection pools and downstream rate limits. When one call fails, siblings may continue producing side effects. When a parent task is cancelled, orphaned requests may keep running and write stale results later.

The core of structured concurrency is not a particular language API but a lifetime principle: every child belongs to a named scope; the parent knows every child’s terminal state before leaving; deadlines, cancellation, and failure policy propagate through the structure; and concurrency is bounded by runtime budgets rather than by however many calls the model generated.

Core judgment: parallelism is a resource and consistency policy, not a performance switch. A model may propose that work appears independent, but the runtime must validate dependencies, effect classes, resource keys, budgets, and join policy before deciding which calls truly run concurrently.
02

Continue from the explicit state machine

The previous installment expanded one tool call into proposed, validated, authorized, recorded, dispatched, and outcome states. With several calls, the runtime does more than replicate that lifecycle. It builds an execution graph: nodes are logical calls, and an edge says that B must consume A’s accepted outcome. Missing dependency edges still do not prove calls can run together; two nodes may write the same file, order, or user record.

State therefore needs a task group, dependency edges, resource claims, child deadlines, and a join policy. Events now include not only ToolResultObserved but ChildStarted, CancellationRequested, ChildCancelled, JoinSatisfied, and CapacityReleased. A parent turn constructs one coherent model observation only after the join condition is satisfied.

03

Mechanism: a bounded scheduler

1. Validate the graph first

The runtime compiles the model proposal into an internal DAG and verifies unique call IDs, existing dependencies, acyclicity, valid tool schemas, and satisfied authorization. An unknown node reference or cycle returns a structured planning error rather than being discovered after half the graph executes.

2. Compute the ready set

A node becomes ready only when every predecessor satisfies the declared join policy. The default may require all dependencies to succeed; alternatives explicitly permit any-success, partial failure, or finally and compensation behavior. Join semantics belong to the runtime contract and must not be inferred from prose.

3. Acquire layered capacity

The scheduler checks global concurrency, tenant quota, a tool-specific semaphore, and resource keys. Reads may share; writes to the same object need exclusion or optimistic versions. After capacity is acquired, record ChildStarted before dispatch. Release permits in a finally path on normal completion or exceptions. A process crash cannot execute finally, so distributed permits need owner-and-expiry leases plus reaping or reconciliation.

4. Deadlines and timeouts

A deadline is the parent scope’s absolute latest time. A child timeout is a local budget for one operation. The child deadline is min(parent deadline, now + tool timeout). Queueing consumes deadline too; timing must not begin only when a request is sent. If remaining time cannot support meaningful work, the scheduler should refuse to start.

5. Cancellation propagation

Parent cancellation first changes durable state so no new child starts, then signals running children. A cooperative tool stops at a safe point and acknowledges. A non-cancellable tool—or one whose side effect may already be committed—enters cancelling or outcome_unknown and awaits reconciliation. Cancelling a promise does not prove a business effect was undone.

6. Failure policy and sibling fate

Fail-fast cancels siblings after a critical child fails. Collect-all waits and aggregates every result. Quorum cancels remaining reads after enough successes. The group declares its policy. Writes generally cannot be blindly cancelled because a sibling failed; compensation or human intervention may be required.

7. Backpressure

Ready nodes enter a bounded queue rather than becoming running immediately. When full, making the producer wait or slow down is backpressure. Rejecting, degrading, or shrinking a plan before enqueueing is admission control or load shedding. Together they prevent unbounded memory growth. A dispatcher pulls according to capacity. It lowers permits when tools return 429 or 503 or latency rises. The model receives a “capacity deferred” observation but no permission to raise limits.

8. Deterministic join

Concurrent completion order should not randomly reorder the prompt. The runtime orders accepted outcomes by node ID, dependency topology, or plan order and explicitly marks cancelled, failed, and missing nodes. If partial results are streamed to the model, record every projection version so a later result cannot make an earlier decision appear to have used complete information.

while group.open:
  ready = graph.nodesWithSatisfiedDependencies(state)
  for node in stableOrder(ready):
    if budget.expired(node): recordSkipped(node)
    else if capacity.tryAcquire(node.tool, node.resourceKey):
      recordStarted(node)
      spawnInScope(node, childDeadline(node))
  event = await nextChildEventOrCancellation()
  state = reduce(state, event)
  applyFailureAndJoinPolicy(state)
04

Essential math: critical paths, queues, and failure amplification

The DAG critical path

Tmin ≥ maxpath p Σi∈p ti

tᵢ is node service time. Even with unlimited parallelism, total latency cannot be shorter than the longest dependency path. Parallelizing only non-critical nodes may barely improve latency. Real time also includes queueing, serialization, and join overhead.

Little's Law

L = λW

L is average work in the system, λ the stable arrival rate, and W average time in system. If a tool receives ten calls per second and each spends two seconds, average in-flight work is about twenty. Little's Law itself only relates stable averages. Agent fan-out can raise λ and a slower dependency can raise W, thereby raising L. An unbounded queue may accumulate, while a bounded queue saturates and blocks or rejects. Concurrency limits must use observed latency rather than intuition alone.

Utilization

ρ = λ / (cμ) < 1

c is worker or permit count and μ one worker’s service rate. With an unbounded queue, sustained ρ≥1 means arrivals exceed capacity and backlog accumulates. A bounded queue instead saturates and turns excess load into blocking, degradation, or rejection. Near one, tail latency generally deteriorates sharply. Backpressure aims for recoverable headroom, not permanent 100 percent utilization.

Fan-out failure

P(any failure) = 1 − (1−p)n

If n independent calls each fail with probability p, at least one failure becomes more likely with fan-out. At p=1 percent and n=50 it is about 39.5 percent. Real failures are often correlated by the same outage or rate limit, so the independence formula no longer applies. Positive correlation commonly increases the blast radius of simultaneous failures, but it does not guarantee that the probability of at least one failure moves in only one direction relative to the independent estimate. Parallelism reduces time while expanding the failure surface.

Deadline allocation

dchild = min(dparent, now + btool)

d is an absolute deadline and btool a local timeout budget. Propagating absolute deadlines prevents nested calls from resetting timeouts beyond the user’s total budget. Reserve time for joining, verification, and persistence rather than giving the final tool every remaining millisecond.

05

Implications for agent systems

1. Tool metadata needs a scheduling contract

Beyond input schemas, declare read or write effect, resource-key extraction, default timeout, cancellation capability, retry class, rate-limit bucket, and maximum concurrency. The model sees a simplified description while the runtime uses trusted metadata. The model cannot self-declare that a call is read-only.

2. Separate planning from scheduling

The planner proposes dependencies and rationale; the scheduler independently validates the DAG and capacity. Rejected parallelism returns a reason—cyclic dependency, conflicting write, or exhausted budget—so the model can replan without gaining authority.

3. Partial results need version semantics

An early result can accelerate the next step, but an action based on projection v3 cannot later appear to have used v5. When a later result invalidates an assumption, emit an invalidation event, cancel undispatched descendants, and make replanning explicit.

4. Cancellation must be observable

Record requested, signal-delivered, acknowledged, and effect-reconciled timestamps. “Cancelling” is more honest than false instant completion. A tool manifest states whether cancellation stops waiting, stops computation, or can reverse a business action.

5. Fairness prevents one agent from monopolizing capacity

A global semaphore is insufficient; one high-fan-out task can consume every permit. Use weighted fair queues or per-task caps and reserve capacity for interactive work. Queue position and estimated start may become observations so repeated calls cannot win a race for quota.

6. Result order is part of prompt determinism

If concurrent results are appended in arrival order, network jitter changes the prompt, later logits, and the tool trajectory. Stable join order, explicit timestamps, and call IDs reduce meaningless nondeterminism while retaining real completion times for diagnosis.

7. A rate limit is shared state

A 429 is not a private error for one call. The runtime updates the tool or tenant bucket, pauses related queues, and respects Retry-After. Independent child backoff can create a retry storm. The model must not bypass quota by generating synonymous calls.

8. Admission control happens before enqueueing

Backpressure applied only at workers still lets the queue consume memory and deadlines. When accepting a graph, the runtime estimates node count, cost, tool buckets, and remaining user budget. It can reject the graph, remove low-value speculative nodes, or split work into an approval-gated batch. Rejection is a durable event so restart cannot silently accept the same plan.

9. Bulkheads isolate failure domains

Search, browser work, database writes, and external notifications should not share one semaphore and queue. Separate bulkheads prevent a slow browser from consuming database permits and high-fan-out search from blocking approval callbacks. A global budget still caps the aggregate so every compartment cannot saturate the process simultaneously.

10. Identical reads may be coalesced

If several children request the same pure read under identical freshness and authorization scopes, the scheduler may share one in-flight future and fan the result out to several call IDs. Coalescing is not caching: cancelling one subscriber must not cancel the underlying request while others remain. Writes, different tenants, or different authorization contexts cannot be merged. Recording the sharing relationship preserves cost attribution and provenance.

06

Trade-offs and failure modes

Concurrency versus tail latency: more permits reduce queue time until the dependency saturates; then contention, 429s, and retries worsen p95 and p99. Find the knee rather than maximizing one throughput number.

Fail-fast versus useful partial work: search fan-out can retain other results after one failure; a failed critical prerequisite in a transaction chain must block descendants. One policy either wastes information or amplifies errors.

Cancellation responsiveness versus consistency: frequent token checks cancel quickly but add code and state. An indivisible transaction protects consistency while delaying cancellation. Declare safe points and non-cancellable regions.

Static DAG versus adaptive replanning: a static graph is easy to validate and audit. Dynamically adding nodes from partial results is flexible, but every expansion creates a new graph version and repeats cycle, budget, and authorization checks. It cannot mutate invisibly.

Durable queues versus overhead: an in-memory queue is fast but disappears with the process. A durable queue recovers while adding serialization, leases, and duplicate delivery. Side-effect commands generally need durability; recomputable read-only speculation may remain ephemeral.

Resource locks versus optimistic concurrency: locks prevent conflict but reduce concurrency and can deadlock. Version checks permit parallel reading and computation but may redo work at commit. If an external API lacks version or idempotency support, a local lock cannot coordinate other writers.

The most dangerous failure modes: unbounded fan-out; orphan children after parent exit; treating cancel as rollback; ignoring queue time in deadlines; arrival order changing prompts; independent retries after 429; asking the model to rationalize write conflicts. These are scheduler and control-plane defects that a stronger model cannot remove.

07

Reusable judgments

  • Parallel eligibility is determined independently by dependencies, effect or resource conflicts, and capacity.
  • Structured concurrency gives children a scope, converges their states before parent exit, and propagates deadlines and cancellation.
  • Bounded queues and demand-based permits create backpressure; model fan-out cannot determine concurrency.
  • Cancellation is an asynchronous protocol, not rollback. Unconfirmed effects enter cancelling or outcome-unknown and reconcile.
  • Concurrent results join in stable order with projection versions so completion order does not randomly change agent decisions.

Primary sources

  • OpenJDK JEP 505: Structured Concurrency — the official JEP manages child lifetimes, cancellation, and observability through task scopes. Its Java API is not the only implementation of this article’s architecture.
  • Python asyncio Task Groups — officially documents awaiting all tasks in an async context, cancelling siblings on failures, and ExceptionGroup semantics. Concrete behavior is Python-version-specific.
  • Go context package — the official contract for propagating deadlines, cancellation signals, and request-scoped values across API boundaries, including the requirement to call cancellation functions to release resources.
  • Reactive Streams — the initiative and JVM specification entry for non-blocking backpressure in asynchronous streams. This article maps demand and boundedness principles to agent scheduling.
  • Azure Architecture Center: Bulkhead pattern — officially describes isolating resources into pools to limit failure propagation; this article maps it to separate tool queues.
  • Go singleflight package — official package documentation for duplicate-call suppression and shared results; this article additionally requires matching authorization and freshness scopes.
  • RFC 8290: The Flow Queue CoDel Packet Scheduler — standardizes per-flow queueing and fairness for network packets. This article borrows the fairness principle without equating agent queues to network queues.
  • AWS Builders' Library: Timeouts, retries, and backoff with jitter — an official engineering article about timeouts, retry amplification, token buckets, and jitter; it reports AWS practice rather than a universal theorem.
  • Little, A Proof for the Queuing Formula L = λW — the original 1961 paper for Little's Law; the JSTOR record provides paper metadata and the DOI is 10.1287/opre.9.3.383.

The DAG compiler, resource-key contract, projection versions, admission policy, and agent-specific join policy are editorial synthesis from concurrency and queueing principles, not a framework mandated by any one source.

09

What is established and where we continue

Established today: several tool calls compile into a DAG constrained independently by dependencies, resource conflict, and capacity. Children belong to a task group, inherit deadlines and cancellation, and receive backpressure through bounded queues. Join policy and stable result ordering determine when and how observations are projected to the model.

Still unresolved: under at-least-once delivery, worker crashes, duplicate results, and checkpoint replay, how does the runtime prevent repeated side effects? Which operations are safe to retry, and which require reconciliation or compensation?
