只激活两个专家，MoE 推理为何仍可能更慢？

把一个 MoE layer 摆到多台 GPU 上，逐段核算 token permutation、all-to-all、expert GEMM、权重/KV 驻留与 Agent 多轮成本。

2026-10-16约 20 分钟MoE serving / Expert parallelism / All-to-all / Prefill and decode / Tail latency
01

今日命题

MoE 1/3 建立了 top-k 路由：一层里有 E 个 FFN experts，每个 token 只运行 k 个。于是有人把‘活跃 FFN FLOPs 少’直接翻译成‘推理一定更快、更省显存’。这个推断漏了服务端最贵的几笔账：所有 expert 权重必须可访问，token 要按目标 expert 重排和跨设备搬运，热门 expert 拖住同一批其它 token，decode 时每个 expert 的小矩阵乘可能吃不满 GPU；共享 attention 的 KV cache 仍随序列增长。

对一个 Agent，多轮 tool loop 会反复带入增长的历史和大小不一的工具结果。单次短回答的 tokens/second 甚至不足以预测整个任务的完成时间。今天把一层 MoE 在多设备上的实际路径拆成 placement→permutation→dispatch→expert compute→return→combine，并在 prefill 与 decode 两种时间尺度下核算。

核心判断：稀疏专家省的是被跳过 FFN 的算术，不自动省总权重、网络与 KV。MoE 是否比质量相当的 dense 路线快，要在目标 batch、长度、硬件拓扑和业务任务上比较端到端尾延迟与经验证结果。
02

承接训练路由，但换一张服务账本

昨天已建立四件事：MoE 只在部分 Transformer 层替换 FFN；router 按 token/层选择少数 experts；top-k 降低的是 expert FFN 算术，共享层、总权重与通信仍在；capacity、overflow、负载均衡和梯度覆盖决定训练能否用好这些参数。今天不重复辅助 loss。我们假设模型已训练好，观察这些路由结果怎样变成 GPU 的数据流。专家编号仍非可解释的 Agent 角色，内部路由也不授予工具权限。

此前 LLM 推理课区分 prefill/decode 和 KV cache；Long Context 课又把 attention 算术、HBM IO 和有效使用分开。MoE layer 常位于共享 attention 后：attention 为当前位置准备 hidden state 和 KV，router 决定该 hidden state 要到哪些 FFN 权重。KV 是按请求、层、位置累积的 attention 状态；专家权重是模型参数。两者会争用 HBM，却不能当成同一个 cache。

Agent runtime 的模型路由也在更外层：它决定任务是否使用该 MoE 模型、何时升级或 abstain。模型内部 expert parallelism 对这层 policy 不透明；即便某个 token 被发往 E7，也不能绕过外部 verifier、预算或审批。要把‘MoE 便宜’变成产品判断，最终仍应算每个 verified outcome 的所有轮次、排队、重试与人工成本。

03

机制：一个 MoE layer 的跨设备往返

1. 先摆放全部权重

设模型有多个 MoE layers，每层 E 个 experts。若每台 GPU 都复制全部权重，通信可少些，但总模型可能放不下；若按 expert parallelism 把 experts 分给 P 台设备，每台只驻留一部分，token 就要去对应设备。共享 attention 可复制、tensor-parallel 或另作切分，与 expert placement 共同决定 topology。所谓‘只激活两个’只说明一个 token 的两条 FFN 路径；一批不同 token 仍可能触及所有 experts，因此服务集群须可访问全体权重。

2. 将 token 变成每 expert 的连续工作

router 给每个 token 的 top-k expert IDs 与 combine weights。runtime 保存原始请求/位置索引，将 hidden states 按目标 expert 重新排列；top-2 的同一 token 可能复制到两个 expert buffer。还要携带返回位置、权重和序列身份，防止结果 scatter 到错的请求。ragged 的 expert token 数难直接套一个规整 GEMM；可 padding 到固定容量、用 grouped GEMM 或 block-sparse kernel。MegaBlocks 论文展示不丢 token 的 block-sparse 训练路径，但推理系统仍须验证其当前实现是否适用。

3. 跨设备 dispatch 和 return

若目标 expert 不在本地，第一轮 all-to-all 把 activation 送到持有权重的设备；本地 expert 完成 FFN 后，第二轮将输出送回原设备并逆重排。每个 MoE layer 都可能重走一遍，多个层上的小通信会累积。网络 fabric、跨节点与否、PCIe/NVLink、消息大小和拓扑决定成本；‘活跃 FLOPs 减半’完全没计入这两次搬运。FastMoE、GShard、Tutel 和 DeepSpeed-MoE 分别报告在不同设备/软件栈的实现，不能跨论文直接比较百分比。

4. 最慢 expert 决定 batch 的同步尾部

设 expert e 本批收到 nₑ 个 token。即使平均 nₑ 接近 kT/E，只要一个热门 expert 明显高于其他设备，return/combine 仍要等它。训练的均衡 loss 约束长期分布，不能保证线上某一个语言、代码补丁或工具输出 batch 不偏斜。服务层可以复制热门 expert、按负载重排 placement、拆微批或调整 admission；每种方案都以更多权重、通信、调度复杂度或尾延迟作交换。静默丢掉溢出 token 来保 SLA，对 Agent 高风险任务尤其不可接受。

5. Prefill 和 decode 不是同一负载

prefill 一次有较多 token states，可把相同 expert 的输入凑成较大的 GEMM，吞吐较高，却会生成大量 dispatch 字节、争用网络并增加 TTFT。decode 每序列每一步只有一个新 token，活跃 T 约等于当前 batch 的序列数；分到 E 个 experts 后，每个 expert 的工作可能很小，kernel launch、all-to-all 固定开销和等待热门 expert 反而主导 ITL。continuous batching 能增加活跃序列，却受 KV 显存与 deadline 约束；不是把 batch 无限加大就好。

6. Expert weight cache 与 KV cache 分别算

在高显存集群中，expert 权重通常常驻所分配设备；全体专家的总权重仍占集群内存。资源不足时可将冷门 experts 放 CPU/主存并按需取回，减少 GPU 驻留但增加命中依赖和传输延迟。MoE-Infinity 作者在个人设备、小 batch 的模型/任务上报告 activation-aware expert cache 收益，这并不证明高并发服务有同样命中率。另一方面，attention KV cache 依每个请求的上下文长度增长，与专家权重竞争 HBM；expert cache 命中也不能减少完整长上下文 KV 的体积。

7. Agent tool loop 放大这些阶段

一次 tool call 后，Agent 常用更长的 history 和新 tool output 发起下一次模型调用；无精确 prefix reuse 时，这又触发 prefill、逐层路由与跨设备搬运。短输出阶段进入 decode，反复付小 batch 的同步税。工具结果可能使路由分布从普通聊天切到代码、JSON、异常日志的热点，令训练平均值不能预测线上 p99。Agent runtime 可限制不必要的 tool payload、稳定 prefix、按风险选择路由和并发，但不能改写模型内部的 expert 权限或假装未观察到的结果成功。

8. 以可归因指标运营

每层记录 token counts/expert、最大与平均负载、远端路由比例、两次 collective 时长、排列/逆排列、expert GEMM 尺寸、expert cache miss、KV residency 和 overflow policy。按 prefill/decode、任务切片及 batch size 分解 TTFT/ITL/p95/p99，再联到 Agent 的 verified success、repair turns 和终态延迟。只报平均 tokens/s 或‘活跃参数 13B’不足以证明相对 dense 模型的成本质量前沿。

04

必要数学：通信、慢专家和驻留成本

设一个 MoE layer 当前有 T 个 token states、每 token 选 k 个专家、hidden 维度 d、每元素 b 字节，远端路由比例为 ρ。若每个远端选择都需发送 activation 并返回同大小输出，payload 量级为 B_net≈2ρkTdb 字节；前面的 2 是出与回。它忽略 expert IDs、对齐、协议、拓扑和本地路由，不能直接当实际网络账单。该层若在 Lₘ 个 MoE layers 重复，还要逐层累计；减少 expert FFN 算术不会让 B_net 自动为零。

令 nₑ 为 expert e 收到的 token 数、Fₑ 为每 token FFN 算术量、Rₑ(nₑ) 为该 shape 下实际有效吞吐，则其计算时间可粗写为 tₑ≈nₑFₑ/Rₑ(nₑ)。跨专家同步的关键路径取决于 maxₑ tₑ 而非平均 tₑ。小 nₑ 时 Rₑ 可能远低于大 GEMM 峰值；负载偏斜使 max 更高。层级时间近似还需加 router/permutation、两次 collective、combine 与等待；融合和重叠会改变实际相加方式。

总权重占用可概写为 M_weight≈b_w(P_shared+ΣₑPₑ)，P_shared 是共享参数量、Pₑ 是各 expert 参数量、b_w 是每参数字节数。这是集群总量，不等于单设备占用。Attention KV 另约 M_KV≈2LNH_kv d_h b_kv：L 层、每请求长度 N、KV heads H_kv、head 维 d_h、元素字节 b_kv，前面的 2 为 key/value。量化、分片、缓存共享和 batch 会修改常数与归属，但两类内存不会因为每 token 只激活 k 个 experts 就合并成一笔。

05

对 Agent 系统的影响

能力：MoE 提供较高总参数容量、较低每 token 专家算术的可能组合；实际质量必须与 dense 基线按 Agent task slices 对齐，不能拿不同能力等级模型只比延迟。

可靠性：专家 placement、溢出/排队与 offload 是执行条件。若推理为保 SLA 静默丢 token 路径，就可能改变结构化 tool call 或关键否定词输出；必须让策略可观测、可版本化并回归。

延迟：prefill 的网络字节、decode 的小 GEMM/collective 固定成本、热门 expert 的 max 时间和 KV 容量共同决定 TTFT、ITL 与尾部。Agent 多轮时终态 latency 是跨轮累计而非首轮 ITL。

经济性：需同时算设备数量、总权重驻留、网络 fabric、KV、offload miss、失败修复与 verified outcome。活跃参数只是其中一个维度。

06

取舍与失败模式

  • 按活跃参数估显存：不同 token 可选所有 experts；总权重需在集群可访问，offload 则付传输延迟。
  • 平均 expert 负载当 SLA：同步由热门 expert 决定；按 batch 和任务测最大/均值比与 p99。
  • 只测 prefill 吞吐：decode 小 batch 的 all-to-all 与小 GEMM 可主导交互延迟。
  • 只测 decode ITL：长 tool output 的 prefill dispatch 和 KV admission 会抬高 TTFT。
  • 训练 drop 策略搬到推理：高风险请求不可为保时延静默丢 FFN 路径；用显式排队、分批或失败终态。
  • expert cache 命中率外推：个人设备 batch-one 的局部性不等于多租户流量；按工作负载测 miss。
  • 网络传输当免费：两次 all-to-all、跨节点拓扑与同步会吞掉算术节省。
  • 单次 tokens/s 评估 Agent：忽略多轮重复 prefill、工具等待、重试和验证；比较每个 verified outcome 的全链路成本。
07

可复用的技术判断

  • expert parallelism 省单设备权重驻留，却把 token dispatch/return 变成多层网络关键路径。
  • 按 expert 打包和逆排列必须保留 token、序列、位置与 combine 权重身份；最慢 expert 影响尾部。
  • prefill 倾向较大 expert GEMM 和较多网络字节；decode 倾向小 GEMM 与固定 collective 开销。
  • 总专家权重与每请求 KV 是分离、相互争用 HBM 的两笔账；offload 用延迟换驻留。
  • 用 quality-matched dense 基线、Agent 全轮次和 verified outcome 判断效率，不从活跃参数单独推断。
08

一手资料与证据等级

  • GShard 与 FastMoE — 作者分别展示 MoE expert 分片与跨加速器训练实现；硬件收益不通用。
  • Tutel — 作者报告适应动态 expert 负载的并行/流水线系统，包括其推理实验；百分比限定于论文设置。
  • MegaBlocks — 作者以 block-sparse GPU kernel 处理不均匀 expert token 数并报告无 drop 的训练；非任意推理系统保证。
  • DeepSpeed-MoE — 作者研究大型 MoE 训练与推理的系统及压缩，速度成本为其对照实验。
  • MoE-Infinity — 作者报告个人设备 batch-one 的 activation-aware expert offload/cache；不能直接外推高并发。
  • PagedAttention / vLLM — 作者讨论动态 KV 内存与 batching；这里仅借其区分 KV 与专家权重。
  • Mixtral of Experts — 作者描述 decoder-only top-2 experts 的模型实例；其 benchmark 不作为本篇 serving 保证。

两次通信的 payload 估算、Agent tool-loop 账本和质量匹配验收是本文的工程分析，不是这些系统在用户环境中的已验证表现。

Only Two Experts Active—Why Can MoE Inference Still Be Slow?

Place an MoE layer across GPUs and account for token permutation, all-to-all, expert GEMMs, weight and KV residency, and repeated agent turns.

2026-10-1620 min readMoE serving / Expert parallelism / All-to-all / Prefill and decode / Tail latency
01

Today's proposition

Part 1 established top-k routing: an MoE layer has E FFN experts but executes only k for each token. It is tempting to translate 'fewer active FFN FLOPs' into 'inference must be faster and use less memory.' That skips expensive serving ledgers. All expert weights must remain accessible. Tokens need permutation and often cross-device transfers. A hot expert stalls a batch. During decode, tiny per-expert matrix multiplications may underutilize a GPU. The KV cache for shared attention still grows with sequence length.

An agent adds another scale of work: its tool loop repeatedly resubmits a growing history and variable-size tool observations. Tokens per second for a single short answer is not enough to predict time to a verified task outcome. Today we trace one distributed MoE layer through placement, permutation, dispatch, expert computation, return, and combine, then account for prefill and decode separately.

Core judgment: sparse experts save arithmetic for skipped FFNs. They do not automatically save total weight residency, network traffic, or KV. Compare MoE with a quality-matched dense route on the actual batch, length, hardware topology, and business task—using end-to-end tail latency and verified outcomes.
02

Carry training routing into a different serving ledger

Yesterday established four things. MoE replaces FFNs at selected Transformer layers; a router chooses a few experts per token and layer; top-k reduces expert-FFN work while shared layers, total weights, and communication remain; and capacity, overflow, load balance, and gradient exposure determine whether training uses those weights effectively. We do not repeat the auxiliary loss. Assume the model is trained and inspect how its routing decisions become GPU data flow. Expert IDs remain neither interpretable agent roles nor sources of tool authority.

The earlier inference lesson separated prefill, decode, and the KV cache. The Long Context series separated attention arithmetic, HBM IO, and useful evidence handling. An MoE layer often follows shared attention: attention prepares a hidden state and KV at the position, while the router decides which FFN weights process that state. KV is per-request attention state accumulating by layer and position. Expert weights are model parameters. They compete for device memory but are not the same kind of cache.

Agent-runtime model routing sits farther out. It chooses whether a task uses this MoE model, when to escalate, and when to abstain. Internal expert parallelism is not an override of that policy. A token going to E7 cannot bypass an external verifier, budget, or approval. To turn 'MoE is cheaper' into a product claim, count all agent turns, queueing, retries, and human work per verified outcome.

03

Mechanism: a round trip through a distributed MoE layer

1. Place all weights first

Suppose a model contains several MoE layers with E experts per layer. Replicating every expert on every GPU reduces remote communication but may exceed device memory. Expert parallelism instead assigns subsets to P devices, so a token must travel to the device that owns its chosen expert. Shared attention may be replicated, tensor-parallel, or partitioned another way, and that placement determines topology with expert weights. 'Only two experts active' describes the two FFN paths of one token. A batch of different tokens may touch every expert, so the serving system must have access to all weights.

2. Pack tokens into per-expert work

The router returns top-k expert IDs and combine weights for each token. Runtime preserves original request and position indices while permuting hidden states into buffers by expert. Under top-two routing the same token may be copied into two buffers. Return location, weight, and sequence identity must travel with the assignment so scatter does not put an output into the wrong request. Ragged token counts do not form one tidy GEMM. Padding to fixed capacity, grouped GEMMs, or block-sparse kernels are possible. MegaBlocks demonstrates a block-sparse no-token-drop training path; a serving system must still verify whether its own implementation supports the same behavior.

3. Dispatch across devices and return

If an expert is remote, an initial all-to-all transfers activations to its owner. After local expert FFN computation, a second collective returns outputs to the original device for inverse permutation and combine. This can recur at every MoE layer, so small communications accumulate across depth. Fabric, inter-node versus intra-node placement, PCIe or NVLink, message size, and topology determine cost. 'Half the active FLOPs' omits both transfers. FastMoE, GShard, Tutel, and DeepSpeed-MoE report implementations on different hardware and software stacks; percentage results cannot be compared across their papers as if they were one benchmark.

4. The slowest expert sets the synchronized tail

Let expert e receive nₑ tokens in the current batch. Even if the mean is near kT/E, one hot expert may have much more work than other devices. Return and combine wait for that straggler. A training balance loss constrains longer-run distributions but cannot guarantee that one live batch of code, another language, or tool output is balanced. Serving may replicate a hot expert, move placement, split microbatches, or adjust admission. Each trades more weights, communication, scheduling complexity, or latency. Silently dropping overflow tokens to preserve an SLA is unacceptable for a high-risk agent task.

5. Prefill and decode have different shapes

Prefill processes many token states at once and can aggregate enough work per expert for larger GEMMs. It may have strong throughput while generating substantial dispatch bytes, contending for network capacity, and increasing time to first token. During decode, each sequence adds only one new token per step. Active T is roughly the number of active sequences; spread over E experts, work per expert may be tiny. Kernel-launch cost, fixed all-to-all latency, and waiting for a hot expert can dominate inter-token latency. Continuous batching increases active sequences but is constrained by KV memory and deadlines. Infinite batch growth is not a solution.

6. Separate expert-weight and KV caches

In a high-memory cluster, expert weights often remain resident on their assigned devices; total expert weight still occupies cluster memory. With insufficient GPU memory, cold experts may live in CPU memory and be fetched on demand. This reduces GPU residency but adds cache-hit dependence and transfer latency. The authors of MoE-Infinity report benefits from activation-aware expert caching on personal devices and small-batch models and tasks. That does not establish the same hit rate in high-concurrency service. Attention KV, meanwhile, grows with the context length of each request and competes with expert weights for HBM. An expert-cache hit does not shrink full long-context KV.

7. Agent tool loops multiply the phases

After a tool call, an agent often sends a longer history and new tool result in the next model request. Without exact prefix reuse, this triggers more prefill, per-layer routing, and cross-device transfers. Short output phases enter decode and pay a small-batch synchronization tax repeatedly. Tool material can shift routing away from ordinary-chat patterns toward code, JSON, or error-log hotspots, so training averages may not predict live p99. Runtime can limit irrelevant tool payload, stabilize prefixes, and route or schedule by risk and budget. It cannot change internal expert authority or count an unobserved result as successful.

8. Operate with attributable metrics

By layer, record token count per expert, maximum versus mean load, remote-route fraction, both collective durations, permutation and inverse permutation, expert GEMM sizes, expert-cache misses, KV residency, and overflow policy. Split time to first token, inter-token latency, p95, and p99 by prefill versus decode, task slice, and batch size. Join those traces to agent verified success, repair turns, and terminal latency. Average tokens per second or '13B active parameters' alone does not establish a cost-quality frontier against a dense alternative.

04

Essential mathematics: traffic, stragglers, and residency

At one MoE layer let T token states each select k experts, with hidden width d, b bytes per activation element, and remote-route fraction ρ. If every remote selection sends one activation and returns an equal-sized output, payload is on the order of B_net≈2ρkTdb bytes. The factor two is outbound and return. This omits expert IDs, alignment, protocols, topology, and local routes; it is not a network bill. Repeat over Lₘ MoE layers and the payload recurs. Saving expert-FFN arithmetic does not force B_net to zero.

Let nₑ be tokens assigned to expert e, Fₑ arithmetic per token, and Rₑ(nₑ) effective throughput at that particular GEMM shape. An illustrative compute time is tₑ≈nₑFₑ/Rₑ(nₑ). A synchronized expert batch depends on maxₑ tₑ, not the average. At small nₑ, Rₑ can be far below large-GEMM peak; skew raises the maximum further. The layer path also includes routing and permutation, both collectives, combine, and queueing. Fusion and communication overlap change how actual timings compose.

Total weight occupancy can be written M_weight≈b_w(P_shared+ΣₑPₑ), with shared parameter count P_shared, per-expert parameter count Pₑ, and bytes per parameter b_w. This is a cluster total, not one-device occupancy. Attention KV is separate, roughly M_KV≈2LNH_kv d_h b_kv for L layers, per-request length N, KV heads H_kv, head width d_h, and bytes per KV element b_kv. The two counts key and value. Quantization, sharding, cache sharing, and batching alter constants and ownership. Activating k experts per token does not merge these two memory ledgers.

05

Implications for agent systems

Capability: MoE offers a possible combination of larger total capacity and less expert arithmetic per token. Compare quality with a dense baseline on matched agent-task slices; do not compare latency between models of different capability and call it an efficiency win.

Reliability: expert placement, overflow or queue policy, and offload are execution conditions. Silently dropping a token route to protect an SLA may change a structured tool call or a decisive negation. Expose, version, and regress those policies.

Latency: prefill network bytes, small decode GEMMs and fixed collective overhead, maximum hot-expert time, and KV capacity jointly shape time to first token, inter-token latency, and tails. For a multi-turn agent, terminal latency accumulates across rounds rather than equaling first-turn ITL.

Economics: include device count, total weight residency, network fabric, KV, offload misses, failure repair, and verified outcomes. Active parameters are only one axis.

06

Trade-offs and failure modes

  • Memory estimated from active parameters: different tokens can select all experts. The cluster needs access to all weights; offload pays transfer latency.
  • Average expert load used as an SLA: synchronization waits for the hot expert. Measure batch-level max-to-mean ratio and p99 by task.
  • Only prefill throughput measured: small-batch decode all-to-all and tiny GEMMs may dominate interactive latency.
  • Only decode ITL measured: a long tool result adds prefill dispatch and KV admission pressure to TTFT.
  • Training drop policy copied to inference: high-risk requests cannot silently lose an FFN route to meet latency. Queue, split, or fail explicitly.
  • Expert-cache hits extrapolated: batch-one locality on a personal machine differs from multitenant traffic. Measure misses on the intended workload.
  • Network treated as free: two all-to-alls, inter-node topology, and synchronization can consume compute savings.
  • One-call tokens per second used for an agent: that omits repeated prefill, tool waits, retries, and verification. Compare full-chain cost per verified outcome.
07

Reusable technical judgments

  • Expert parallelism lowers per-device weight residency but puts token dispatch and return on a repeated network path.
  • Pack and inverse-permute with token, sequence, position, and combine-weight identity intact; the slowest expert affects the tail.
  • Prefill tends toward larger expert GEMMs and more network bytes; decode tends toward tiny GEMMs and fixed collective costs.
  • Total expert weights and per-request KV are separate, competing HBM ledgers; offload trades residency for latency.
  • Judge efficiency against a quality-matched dense route over every agent turn and verified outcome, not from active parameter count alone.
08

Primary sources and evidence tiers

  • GShard and FastMoE — the authors demonstrate expert sharding and cross-accelerator training implementations; hardware gains are not universal.
  • Tutel — the authors report adaptive parallelism and pipelining under dynamic expert load, including inference experiments in their setting.
  • MegaBlocks — the authors use block-sparse GPU kernels for uneven expert token counts and report no-drop training, not a guarantee for arbitrary inference systems.
  • DeepSpeed-MoE — the authors study large-MoE training, inference, and compression; speed and cost figures are their controlled comparisons.
  • MoE-Infinity — the authors report activation-aware expert cache and offload on personal, batch-one devices; this does not directly generalize to high concurrency.
  • PagedAttention / vLLM — the authors examine dynamic KV memory and batching, used here only to distinguish KV from expert weights.
  • Mixtral of Experts — the authors describe a decoder-only top-two expert instance; its benchmarks do not certify this article's serving claims.

The two-transfer payload estimate, agent-tool-loop ledger, and quality-matched acceptance rule are engineering analysis, not measured performance of these systems in the reader's environment.
