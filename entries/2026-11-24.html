Agent 失败时，模型、工具和人到底谁造成了结果？

把失败轨迹变成有证据等级的因果图：区分触发、传播、拦截缺口与资源效果，避免按时间先后或组件数量重复归罪。

01

今日命题

一个 Agent 把报告发给了错误收件人。检索工具返回过期联系人，模型选了该地址，审批界面只显示姓名，发送工具按结构化参数提交，邮件服务回执显示投递成功。事故复盘若在模型、检索、审批和工具四栏各记一次“造成错误发送”，会把同一个结果重复计为四次；若只找轨迹里最早的异常，又会把过期数据当作唯一原因，忽略本可拦截错误的关口。

今日命题：因果归因不是从 trace 中挑一个最像罪魁的 span。要先固定失败结果与验收口径，把已观察的事实和候选依赖连接成有类型的图，再问哪些改变能在同一任务条件下阻断结果。答案应标注是触发、传播、拦截缺口、效果证据还是未知；同一事故的不同贡献不能被当成独立事故求和。

本文讨论工程系统的故障机制，不从日志推断人员责任。人的审批是否构成实质决策，取决于当时实际看到了什么、是否有权拒绝、是否执行了批准动作。模型的流畅事后解释同样不是观察证据。

02

从审计包走向因果问题

昨天的 audit bundle 解决“哪些字节、事件和效果可以被有权者读回”，按因果 ID 找第一可比分歧。它为今天提供原料，但第一分歧不等于根因。一次过期检索可能是最早的差异，却未必足以让邮件发错；模型可以识别冲突，审批者可以拒绝，发送工具可以比较收件人 ID。反过来，若没有检索差异，错误也可能由模型解析地址的 bug 触发。需要把可观察顺序、信息依赖和阻断条件分开。

分布式 trace 的 parent/child span 和 link 说明一次调用如何被关联；Lamport 的 happened-before 只给出可证明的部分顺序，时间戳靠近、先发生、甚至处在同一 trace 都不自动形成因果边。W3C PROV 的 used/wasGeneratedBy 可描述实体与活动的来源。把这些规范用于 Agent 时，要增加“模型实际消费了哪段证据”“审批显示了哪些字段”“工具实际提交了哪些资源参数”等应用语义；规范本身不会证明错误的必要原因。

因此，审计包回答证据能否核实，因果图回答哪些机制可能连接到结果，隔离干预才尝试回答“若改一个条件，结果是否会变”。三者各自有边界：保留了原文仍可能缺少关键变量；画了箭头仍可能只是相关；重放了旧 observation 的分支也不等于真正反事实。

03

构造有证据等级的故障图

1. 固定 outcome 和分析单位

先定义任务 T 的失败变量：邮件服务在批准窗口内把报告投递到规范化地址 B，而当时有效批准只允许地址 A。以一个 task/run 与一次资源效果为分析单位，保存 goalVersion、批准版本、收件人规范化规则、时间窗、operation ID 和资源回执。不要把“模型说已发送”当结果，也不要把客户端 timeout 当“未发送”：后者可能是 unknown，必须向资源侧对账。多个 span 指向同一个 operation ID 时，只记一个错误投递。

2. 从证据建节点，给边分级

节点分为外部数据、模型输入与决策、授权/人工展示、工具参数与提交、资源观察、验收结果。每个节点保存原始证据引用、版本、观察者、时间和缺口。边至少标 调用依赖、数据消费、授权约束、资源效果之一。模型输入实际包含检索片段，才可把检索到模型画作已观察的数据消费；检索与错误答案同时出现而无输入记录，只能标候选。审批仅显示姓名时，不能从“approve”事件推断审核者见过邮箱地址。

3. 区分四种角色

过期联系人是触发候选；模型选择该地址是传播/转换；审批界面省略规范化地址、发送工具缺少地址校验，是拦截缺口；邮件服务回执是效果证据。一个节点可有多种角色，但角色不是“责任份额”。问“哪个单点修复最早可以阻断路径”与问“为什么最初出现错误值”是两个不同问题。报告需要分别回答，不能让一个答案吞掉另一个。

4. 用可执行的隔离对照挑战边

在无真实发送能力的隔离环境中固定任务、批准快照、模型/工具版本与记录边界，分别替换过期检索、完整显示审批地址、启用发送前地址校验。每次只改变已声明条件，重新生成其下游输入与观察。若只把旧轨迹中的模型输出粘到新检索之后，得到的是不一致拼接，不是干预。比较节点、动作和结果；新分支无法真实获取的观察标 unsupported。独立 verifier 以规范化地址和资源模拟回执判断，不用模型自评。

5. 形成一个不重复计数的结论

输出一条 incidentId 与唯一 outcome，附带多个 contribution 记录：证据等级、候选机制、可阻断的干预、无法观察的条件。组件质量指标可分别记录“过期数据率”“错误地址提出率”“门禁漏检率”，但事故总数仍是一次。若多个错误一起才造成结果，使用组合条件；若证据不足，保留 unknown，不硬分配 25% 给四个组件。

outcome = verify(resource_receipt, approved_recipient)
graph = link(observed_events, consumed_inputs, policy_versions)
for candidate in graph.paths_to(outcome):
    label(candidate, evidence_level, role, missing_observations)
    if safe_isolation_exists(candidate):
        rerun_downstream_with_one_intervention(candidate)
report_one_incident(outcome, contributions, unsupported_branches)
04

必要数学：必要条件不是唯一原因

用小模型说明而非代替真实系统。令 X=1 表示检索给出过期地址，M=1 表示模型提交错误地址，G=1 表示发送前门禁未拦截，S=1 表示资源实际执行发送，Y=1 表示错误投递。一个候选结构是 M=f(X,P,U)，Y=M ∧ G ∧ S。P 是当时 prompt/批准上下文，U 是未记录的模型与环境扰动；f 是待检验的转换机制，不是“有 X 就必有 M”的断言。后一式只说在这个简化路径上，错误选择、门禁漏检、真实发送同时成立才出现 Y。真实系统还可能有独立路径，例如工具自己改写地址，必须加入图而不能硬套此式。

对已观察的一次执行，若隔离地把 G 设为 0 并重新执行下游，得到 Y(do(G=0))=0，则门禁对这条路径有阻断作用。do 表示主动设置变量，区别于在历史日志里筛出 G=0 的其他任务；后者可能任务风险和收件人类型都不同。若同时把 X 修好也得到 Y=0，X 与 G 都可成为有效干预点，并不矛盾，更不能把同一个 Y 算两次。对未观测 U、无法固定的外部状态或不可安全重放的发送，只能给出条件性证据，不宣称完整反事实已证实。

工程上尤其要防“可观察性偏差”：日志里有模型输出、没有审批屏幕快照，不能据此把模型贡献标成已证实、审批标成无贡献。缺证本身需要作为图上的未观测变量与调查请求。百分比责任分摊需要另一个明确的目标函数和规范依据；这里的二值结构方程不产生它。

05

对 Agent 系统的影响

运行时采集：traceId 不够；保存 taskId、operation ID、模型输入引用、被消费的检索版本、审批展示字段、授权版本、规范化工具参数、资源回执与 verifier 结果。敏感内容采用受控引用与权限读回，不能为归因把完整客户数据塞进普通日志。跨异步回调要用 span link 和业务 ID 对齐，不能用时钟排序替代依赖。

安全设计：将“建议值生成”与“不可逆提交”分开。模型和检索可提供候选地址；提交边界用规范化身份、当时批准范围与资源侧状态执行确定性校验。审批 UI 必须展示足以判断的身份字段，否则人的点击不能充当对隐藏参数的有效复核。把阻断责任前移到可验证边界，比在事故后追问模型为什么没想起来更可靠。

评测与修复：把一次事故转成同一因果链的多层回归：输入数据过期测试、模型冲突识别测试、审批信息呈现测试、发送门禁测试、资源效果对账测试。每层有自己的分母；整体任务成功与事故数另算。修复某一层后仍需端到端验收，因为另一条路径可能绕过它。

06

取舍与失败模式

时序误判：span 先发生只说明候选顺序，不说明它的值被后续步骤消费。并行检索、缓存、重试和迟到回调尤其容易制造错误箭头。没有消费证据就把边降级为假设；无法对齐的分支标 unalignable。

反事实拼接：把新检索结果和旧模型选择放到一起，再说“修数据也没用”，违反下游重算。隔离重执行成本高、模型非确定性强；可先做确定性门禁单元对照，再以多次全链实验估计范围，并标明环境限制。

多重充分路径：修一个 guard 后，另一路工具可能仍可直写。只报告“单点修复令一次重放通过”，会低估其他路径。图中必须保留替代路径，发布门用端到端负例与权限边界检验。

人和模型的证据不对称：模型输出常被完整保存，人的所见却未记录。按日志量分配责任会系统性偏向指责可见组件。按权限保存审批屏幕字段、动作与版本，但避免记录不必要的个人信息；缺失就明确 unknown。

组织归因：本文的 causal contribution 不等于个人过错、法律责任或团队绩效。Google SRE 的 blameless postmortem 强调理解系统条件与改进控制。事故复盘应输出可验证的修复点、残余风险和证据缺口；不要把“模型”“工具”“人”拟人化为单一责任桶。

07

可以带走的判断

  1. 先定义一个资源侧可验收的失败结果和 incidentId，再记录多个贡献；不要按 span 或组件重复计数。
  2. 时间顺序、数据消费、授权约束和因果阻断是不同关系；图的边必须附证据等级。
  3. 触发错误值、传播它、未能拦截它、证实效果，是四种不同角色；第一分歧并不自动独占原因。
  4. 反事实要安全地重算下游；无法固定的观察保留 unknown，修复后仍做端到端验收。

When an Agent Fails, What Actually Caused the Outcome?

Turn a failed trajectory into an evidence-graded causal graph. Separate trigger, propagation, missing interception, and resource effect without assigning cause by timestamp or counting the same failure against every component.

2026-11-2420 min readAgent failure / Causal attribution / Distributed traces / Counterfactuals / Safety gates
01

Today's proposition

An agent sends a report to the wrong recipient. Retrieval returned an outdated contact. The model chose that address. The approval screen displayed only a name. The send tool submitted structured arguments, and the mail service returned a successful delivery receipt. A review that records “caused wrong delivery” once each for model, retrieval, approval, and tool counts one outcome four times. A review that picks only the earliest anomaly treats stale data as the sole cause and overlooks gates that could have stopped the error.

Today's proposition: causal attribution is not selecting the most suspicious span in a trace. Fix the failed outcome and its acceptance rule; connect observed facts and candidate dependencies in a typed graph; then ask which changes, under the same task conditions, would prevent that outcome. Label each finding as trigger, propagation, missing interception, effect evidence, or unknown. Several contributions to one incident are not several incidents to be summed.

This is engineering analysis of a failure mechanism, not a personnel judgment. Whether a human approval was a meaningful decision depends on what that person actually saw, whether rejection was possible, and what action they took. A fluent retrospective explanation from the model is not observation evidence either.

02

From audit bundle to causal question

Yesterday's audit bundle established which bytes, events, and effects an authorized reviewer can retrieve, and how to find a first comparable divergence by causal ID. That gives today's investigation its material. Yet the first divergence is not automatically the root cause. A stale retrieval may be the earliest difference without being sufficient for wrong delivery: the model might detect a conflict, an approver might reject, or the send tool might compare canonical recipient IDs. Conversely, an address-parsing model bug could cause wrong delivery even when retrieval is current. Observable order, information dependency, and interception conditions must be separate.

A distributed trace's parent-child spans and links correlate calls. Lamport's happened-before relation establishes a partial order; nearby timestamps, earlier occurrence, or presence in one trace do not themselves create a causal edge. W3C PROV's used and wasGeneratedBy relations describe provenance of entities and activities. An agent investigation adds application semantics: which evidence span the model consumed, which fields the approval screen showed, and which resource arguments the tool actually submitted. The standards structure evidence; they do not prove a necessary cause of the error.

Thus the audit bundle asks whether evidence can be checked, the causal graph asks which mechanisms may connect to the outcome, and an isolated intervention tests what changes if a condition is altered. Each has limits. Raw evidence may omit a decisive variable; a drawn arrow may encode correlation; replaying an old observation after branching is not a valid counterfactual.

03

Construct an evidence-graded failure graph

1. Fix the outcome and unit of analysis

Define the failed variable for task T: within the approval window, the mail service delivered a report to canonical address B while the effective approval allowed only canonical address A. Use one task/run and one resource effect as the unit. Preserve goalVersion, approval version, address-normalization rule, time window, operation ID, and resource receipt. A model's “sent” statement is not the outcome. Nor does a client timeout prove “not sent”; it may be unknown until reconciled with the resource. If several spans refer to the same operation ID, count one wrong delivery.

2. Make evidence nodes and grade edges

Node types include external data, model inputs and decisions, authorization and human display, tool arguments and commit, resource observation, and acceptance verdict. Each node carries a reference to original evidence, versions, observer, time, and gaps. Type edges as call dependency, consumed data, authorization constraint, or resource effect. If the recorded model input actually contains the retrieved passage, the retrieval-to-model data-consumption edge is observed. If retrieval and a bad answer merely co-occur without an input record, that edge remains a hypothesis. An “approve” event on a screen that displayed only a name cannot establish that the person saw the email address.

3. Separate four causal roles

The outdated contact is a candidate trigger; the model's address selection propagates or transforms it; a screen that omits the canonical address and a tool without a recipient guard are interception gaps; the service receipt is effect evidence. A node may play several roles. Roles are not percentages of responsibility. “Which single repair could stop this path?” and “why did the wrong value first arise?” are different questions. An incident report should answer both rather than letting an early trigger erase the missing gates.

4. Challenge edges with executable isolated comparisons

In an environment without a real send capability, hold the task, approval snapshot, model and tool versions, and recorded boundary contract fixed. Independently replace the stale retrieval, display the full recipient identity at approval, and enable the pre-send address guard. State exactly what is changed each time, then regenerate downstream inputs and observations. Pasting an old model output after a new retrieval creates an inconsistent splice, not an intervention. Compare nodes, actions, and outcomes; mark a branch unsupported when its new observation cannot be obtained. An independent verifier evaluates canonical addresses and a simulated resource receipt rather than accepting model self-evaluation.

5. Report one incident with several contributions

Emit one incident ID and unique outcome, plus contribution records with evidence level, candidate mechanism, blocking intervention, and unobserved conditions. Component quality metrics may separately track stale-data rate, wrong-address proposal rate, and guard miss rate. The incident count remains one. When several failures are jointly required, record the combination. With insufficient evidence, keep unknown; assigning 25 percent to each of four components creates false precision.

04

Essential mathematics: necessary is not exclusive

Use a deliberately small model as an explanation, not as a substitute for the real system. Let X=1 mean retrieval supplied an outdated address, M=1 mean the model submitted the wrong address, G=1 mean the pre-send gate failed to intercept it, S=1 mean the resource actually sent, and Y=1 mean wrong delivery. A candidate structure is M=f(X,P,U) and Y=M ∧ G ∧ S. P is the prompt and approval context at the time. U contains unrecorded model and environment disturbances. The function f is a mechanism to test, not an assertion that X always forces M. The second equation says that on this simplified path, wrong selection, a missed gate, and an actual send are jointly needed. A real system may have another path, such as a tool rewriting the address; add it to the graph rather than forcing it into this equation.

For the observed run, if safely setting G to zero and re-executing downstream yields Y(do(G=0))=0, the gate could block this path. The do notation denotes active intervention, unlike selecting other historical tasks where G happened to be zero; those tasks may differ in risk or recipient type. If fixing X also yields Y=0, both X and G are useful intervention points. That is not contradictory and does not create two incidents. If U is unobserved, an external state cannot be fixed, or the send cannot safely be replayed, the evidence is conditional. Do not claim a complete counterfactual was proven.

Observe the missingness bias: a log may preserve model output but omit the approval screen. That does not make the model's contribution proven while the approval path is exonerated. Represent absent evidence as an unobserved variable and a concrete investigation request. Allocating responsibility percentages needs a separate objective and normative basis; these binary structural equations do not produce one.

05

Implications for agent systems

Runtime capture: traceId alone is insufficient. Preserve taskId, operation ID, references to model input, versions of retrieved material actually consumed, fields shown at approval, authorization version, canonical tool arguments, resource receipt, and verifier result. Keep sensitive content behind access-controlled references; attribution does not justify dumping customer data into general logs. Align asynchronous callbacks through span links and business IDs, not clock order mistaken for dependency.

Safety design: separate proposing a value from committing an irreversible action. Models and retrieval may propose addresses. At the commit boundary, deterministic checks compare canonical identity, contemporaneous approval scope, and resource state. The approval UI must display identity fields sufficient for judgment. A click cannot review parameters that were hidden from the person. A verifiable boundary guard is more dependable than hoping the model later explains why it missed an error.

Evaluation and repair: turn one incident into layered regressions on the same causal chain: stale input, model conflict recognition, approval display, pre-send gate, and effect reconciliation. Each layer has its own denominator; whole-task success and incident count are measured separately. Repairing one layer still needs an end-to-end acceptance run because another path may bypass it.

06

Trade-offs and failure modes

Temporal false positives: an earlier span supplies a possible order, not proof that its value was consumed. Parallel retrieval, caches, retries, and late callbacks produce misleading arrows. Without consumption evidence, downgrade the edge to a hypothesis; mark a branch unalignable when alignment fails.

Counterfactual splicing: combining a new retrieval with the old model choice, then declaring “fixing data would not help,” fails to recompute downstream behavior. Isolated re-execution costs money and may face model nondeterminism. Start with deterministic gate comparisons; then use repeated whole-chain experiments to bound a claim, labeling environment limitations.

Multiple sufficient paths: a repaired guard may leave a different tool path capable of a direct write. “One replay passed after one fix” can miss that path. Retain alternatives in the graph and challenge the release gate with end-to-end negative cases and authority boundaries.

Evidence asymmetry between people and models: model output is often captured in detail while what the approver saw is not. Allocating cause by log volume will systematically favor the visible components. Record the approval display fields, action, and version with access controls, without unnecessary personal data. If absent, say unknown.

Organizational attribution: causal contribution here is not personal fault, legal responsibility, or a team performance score. Google's SRE guidance on blameless postmortems emphasizes system conditions and improved controls. Produce testable repairs, residual risk, and evidence gaps rather than treating “model,” “tool,” and “human” as personified blame buckets.

07

Reusable judgments

  1. Define one resource-verifiable failed outcome and incident ID, then record several contributions. Do not count by span or component.
  2. Temporal order, consumed data, authorization constraint, and causal interception are different relations; grade every edge by evidence.
  3. Introducing a wrong value, propagating it, failing to intercept it, and proving an effect are different roles. First divergence does not monopolize cause.
  4. A counterfactual must safely recompute downstream behavior. Keep unfixable observations unknown and run end-to-end acceptance after a repair.
08

Sources and evidence boundaries

  • Lamport, Time, Clocks, and the Ordering of Events in a Distributed System — original paper on partial order in distributed events, not proof that temporal precedence is causal.
  • W3C PROV-DM — specification for entities, activities, generation, and use relations.
  • OpenTelemetry Traces — official documentation of spans, parent-child relationships, and links.
  • Halpern, A Modification of the Halpern-Pearl Definition of Causality — author paper showing that formal actual-cause definitions require counterfactual conditions; we do not use that definition as an automatic responsibility allocator.
  • Google SRE, Postmortem Culture — official engineering guidance on blameless review and systemic improvement.

Links and titles checked on 2026-11-24. The node taxonomy, evidence grades, incident counting rule, and isolated-intervention workflow are editorial engineering synthesis, not standards-based validation of any particular agent product.

09

The equation modeled one path and did not promote candidate edges into facts.

Still open: a real system may have several harmful paths, some variables may be unobserved, and replay can vary with model and environment. Identifiable intervention matrices, common causes and interactions, marginal repair value, and residual risk need a separate treatment.
