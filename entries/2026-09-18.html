工具超时后，Agent 到底该不该重试？

从 ambiguous outcome 出发，拆开 idempotency key、dedup ledger、retry/backoff、checkpoint/replay、reconciliation 与 compensation。

01

今日命题

请求已 dispatch 后的 timeout 只证明 runtime 没有按时收到结果，不证明远端没有执行；若 admission/queue 阶段在 dispatch 前超时，则可以证明没有远端 effect。支付可能已经扣款、邮件可能已经发送、工单可能已经创建，只是 response 在网络或进程崩溃中丢失。若 Agent 把 timeout 直接分类为 failure 并重新调用，就可能把一次不确定结果变成确定的重复副作用。

可靠恢复必须把逻辑操作与传输尝试分开：一个稳定 operation/call identity 可以经历多个 attempts；idempotency key 让远端识别“这是同一个逻辑意图”；dedup ledger 记录 key、request fingerprint、状态与已提交结果；retry policy 只处理可重试类别；无法证明结果时进入 reconciliation，而不是靠模型猜“应该没成功”。

核心判断：at-least-once delivery + idempotent effect 可以实现“重复投递、单一业务结果”的体验，但 exactly-once 不是一句 runtime 配置。它要求副作用系统参与 key/transaction，或提供可查询的业务 identity；否则跨故障边界只能管理不确定性，不能消除它。
02

承接 lifecycle 与 structured concurrency

1/4 建立了 callId、attemptId 与 outcome_unknown；2/4 建立了 task group、deadline、cancellation 与 bounded queue。今天把 failure recovery 放进同一状态机。callId/idempotency key 在重试间保持稳定，attemptId 每次变化；parent deadline 和 retry budget 限制尝试次数；任何 late result 都按 call identity 与 ledger version 去重。

关键 crash window 位于“远端 effect commit”和“本地 outcome commit”之间。即使 runtime 先记录 intent 再派发，仍无法用本地事务包住外部系统。解决方式不是再加一次 prompt，而是让远端以 key 原子地查重并保存结果，或在 timeout 后按 business identifier 查询真实状态。

03

机制：从 key 到恢复协议

1. 生成稳定 identity

operationId 标识业务级意图，例如“为订单 O 收款一次”；一个 operation 可含多个逻辑 tool calls。callId 标识其中一次逻辑工具调用，attemptId 标识该 call 的一次传输执行。idempotency key 可由 operationId 派生，但必须在所有 retries、worker handoff 与 replay 中保持不变；重新生成 key 就是新操作。

2. Fingerprint 请求

ledger 同时保存 key 与 canonical request hash：tool/version、tenant、授权主体、规范化参数、目标 resource。相同 key+相同 hash 可返回已有状态；相同 key+不同 hash 必须拒绝，不能悄悄把旧 key 用于新金额或新收件人。敏感原文可外置加密，hash 只用于一致性而非授权。

3. 远端原子 dedup

理想 endpoint 在一个事务中执行：插入 key 的 in_progress（若不存在）、完成业务 effect、将 result/status 保存为 succeeded/failed。重复请求读回相同 outcome。若 dedup record 与 effect 分属两个不能原子提交的存储，内部仍存在 crash window，需要 outbox/inbox 或业务 reconciliation。

4. Retry classifier

只读操作可按 contract 对 transient failure 自动 retry；写操作必须能证明未提交，或由 effect owner 以同一 key 提供幂等保护，generic transient 标签本身不够。validation、authorization、semantic rejection 不重试；rate limit 遵守 Retry-After；timeout/connection reset 对无保护且无法证明未提交的 effect 进入 unknown。classifier 由 tool contract 和错误类型决定，不由模型读 error string 后自由选择。

5. Backoff、jitter 与 retry budget

attempt 使用 exponential backoff 加随机 jitter，避免大量 Agent 同时重试。max attempts、absolute deadline、per-tool token bucket 与全局 retry budget 同时约束。一个层级负责 retry；若 SDK、runtime、workflow 各自最多发出 3 个总 attempts（initial + 2 retries），最坏放大为 27 次；若每层是 initial + 3 retries，则是 4³=64 次。

6. Checkpoint 与 replay

checkpoint 保存 state version、event cursor、open calls、keys、attempts、deadlines 与 accepted outcomes。恢复时 reducer replay events 重建 decisions，但不直接重做 side effects；effect command 若已 recorded 未完成，则查询 ledger/tool 状态或以同一 key 重投。wall clock、随机数和模型响应必须作为历史 events 读取，而不是 replay 时重新生成。

7. Reconciliation

当 tool 不支持 key，但提供查询 API，runtime 用 business key（orderId、messageId、externalReference）查询真实状态。结果唯一则补写 outcome；不存在且 deadline/budget 允许才考虑新 attempt；多条匹配或无法查询则进入 manual review。reconciliation 是一等 workflow，不是后台日志。

8. Concurrent duplicates 与 in-progress lease

两个 attempts 可能同时携带同一 key 到达。ledger 的 unique insert 只能选出一个 owner；其余不能同时执行 effect，而应等待、返回 conflict/in-progress，或读取完成结果。owner 持有带 expiry 的 lease、heartbeat 与单调递增 fencing token；接管者通过 CAS 提升 token。effect owner 若能校验 fencing token，应拒绝旧 token；若远端只支持 idempotency key，则 key 仍防重复 effect。两者都不支持时，lease expiry 和 reconciliation 不能排除旧 owner 复活并发，必须暂停自动接管或转人工。简单删除“卡住的 in_progress”会重新打开重复执行窗口。

9. Poison work 与 dead-letter state

持续失败不应无限轮回。超过 attempt/deadline budget 后写入 retry_exhausted，保存最后错误、attempt history 与下一操作建议；需要人工的进入 review queue。dead letter 不是垃圾桶：必须有 owner、SLO、redrive policy，并在 redrive 时复用原 key 或显式创建经批准的新 operation。

10. Compensation

不可撤销 effect 无法 rollback；Saga 用后续业务动作补偿，例如退款、关闭工单、发送更正。compensation 自身也会失败、需要 idempotency，并可能不是严格逆操作。runtime 记录 compensation_required/in_progress/failed/completed，不能把“已请求退款”展示成“原扣款从未发生”。

onDispatch(call):
  persistIntent(call.id, key, requestHash)
  outcome = remote.execute(args, idempotencyKey=key)
  persistOutcomeOnce(call.id, outcome)

onRecovery(call):
  if localOutcome(call): return it
  if remote.lookup(key): persistAndReturn(remote.result(key))
  if call.effectIsKeyProtected && retryBudget.allows(): retrySameKey()
  else transitionToReconciliationOrManualReview()
04

必要数学：退避、放大与一致性不变量

Exponential backoff with full jitter

bk = min(bmax, b0·2k),   waitk ∼ U(0,bk)

k 是 attempt index，b₀ 是基础 delay，bmax 是上限。full jitter 的期望等待为 bₖ/2，把同步重试打散。backoff 只减轻压力，不让不可重试操作变安全；deadline 到期应停止。

Truncated attempts

E[N] = Σk=0n−1(1−q)k = (1−(1−q)n)/q

若每次独立成功概率为 q，最多 n 次，期望发出次数如上。例如 q=0.8、n=3，E[N]=1.24。真实失败常相关且 retry 会改变负载，此式仅展示 amplification 直觉，不是容量预测。

Layered retry amplification

Amax = ∏l=1m nl

m 个层级各最多发出 nₗ 个总 attempts（包含 initial）时，一个用户 operation 最坏放大为乘积；若配置写的是 retry count rₗ，则 nₗ=rₗ+1。应在最了解 effect/idempotency 的层级集中 retry，其他层传递结构化状态。

Idempotency invariant

same(K) ∧ same(H(request)) ⇒ same(committed outcome)

K 是 key，H 是 canonical fingerprint。若 key 相同但 hash 不同，必须 conflict；若相同，则多次 attempts 返回同一逻辑 outcome。ledger 的 unique constraint 与 effect transaction 共同维护 invariant，而不是模型承诺。

Retention bound

TTLdedup ≥ max retry horizon + max message delay + clock/error margin

dedup record 删除过早，迟到 retry 会被当新操作；保存过久增加成本与隐私风险。TTL 必须覆盖所有 transport/workflow 的最大重试与延迟窗口，并与业务审计、数据删除 policy 协调。

05

对 Agent 系统的影响

1. Tool contract 必须声明 retry semantics

metadata 包含 effect class、是否支持 idempotency key、key scope/TTL、lookup API、retryable errors 与 compensation。缺失这些信息时，runtime 对写操作默认不自动 retry。模型说“再试一次”不能覆盖 contract。

2. Key 绑定已授权的精确 intent

用户批准金额 10 和收件人 A 后生成 request fingerprint；模型后续改变任一参数必须新 approval/new operation，而不是沿用旧 key。key 不是 capability token，也不能跨 tenant 重用。

3. Checkpoint 不应复制 secrets

持久化 key reference、credential handle 与 encrypted payload pointer，不把 access token 写入 event log。恢复时重新解析短期 credential，并再次验证 authorization 是否仍有效；旧 checkpoint 不赋予永久权限。

4. Late result 仍有价值

timeout 后进入 reconciliation 的 call 若收到 late success，应通过 ledger 完成，而不是丢弃；若 compensation 已启动，则状态机需决定接受原结果、继续补偿或人工介入。arrival order 不能绕过 version guard。

5. UI 必须展示 certainty level

区分“重试中”“结果未知”“正在核对”“补偿中”“已补偿”与“成功/失败”。把 outcome_unknown 显示成失败会诱导用户重复操作；把 compensation requested 显示成已恢复会掩盖风险。

6. Evals 必须故障注入

在 intent commit 前后、remote effect 前后、result commit 前后杀进程；注入重复 delivery、迟到 response、ledger TTL expiry、429 与 lookup 不一致。只测 happy path 无法证明 recovery protocol。

7. 模型不负责 retry classifier

LLM 可解释错误或提出人工建议，但 retry/reconcile/compensate transition 由确定性 policy 决定。否则模型的随机文本会成为重复副作用的控制面。

8. Recovery telemetry 要区分原因

分别统计 initial attempt success、key dedup hit、transient retry success、unknown outcome、reconciliation resolution、compensation success 与 manual queue age。一个总“tool success rate”会掩盖系统靠大量重试或人工补救维持成功。trace 用 operation/call/attempt/key-reference 关联，但日志不记录原始 key 或敏感 payload。

06

取舍与失败模式

Long key retention vs privacy/cost：长 TTL 覆盖迟到 retry，却扩大存储与敏感 metadata 暴露。使用最小 fingerprint、加密 payload、按业务风险设置 retention，并让 expiry 后的 retry 进入人工确认而非新执行。

Key entropy 与 scope：key 必须难以猜测且仅在明确 tenant/tool scope 内唯一，防止他人通过枚举 key 读取旧结果。server 仍需正常 authentication/authorization；知道 key 不等于有权访问 outcome。

Cached failure vs retry：有些 provider 对同 key 缓存首个 terminal failure；有些只缓存成功。contract 必须明确。若 validation failure 被永久缓存，修正参数需要新 operation/key；不能用相同 key 偷换 payload。

Replay determinism vs code evolution：旧 history 用新 reducer replay 可能产生不同 commands。version workflow code、upcast events，并在 deployment 前 replay corpus。无法兼容时让旧任务留在旧 worker 或显式 migration。

Automatic compensation vs human control：自动退款/撤销降低恢复时间，却可能在原 outcome 迟到时产生第二个错误。高价值或不可逆操作需要 reconciliation barrier 和人工审批。

Reconciliation read consistency：查询 API 可能 eventual consistent，立即查不到不等于 effect 不存在。contract 应给 visibility delay、pagination 与唯一性字段；runtime 在安全窗口内重复 query，而不是看到一次空结果就重新执行。

Remote idempotency vs local dedup：本地 ledger 防止同 runtime 重复 dispatch，但不能阻止另一个 client 或远端在 ack 丢失时重复 effect。真正边界必须靠 effect owner；本地记录只是其中一层。

Exactly-once within one log vs across systems：同一事务域可原子提交 input offset、state 与 output；跨数据库、支付、邮件系统时则需要各方 transaction/idempotency，或接受 at-least-once + dedup + reconciliation。不要把消息系统的 exactly-once label 外推到业务效果。

最危险的失败模式：每次 retry 生成新 key；key 不绑定 payload；dedup TTL 短于 retry horizon；SDK/runtime/workflow 多层重试；replay 重新调用模型与工具；compensation 被当作 rollback；unknown 被 UI 显示为 failed。

07

可复用判断

  • timeout 表示 acknowledgement 未到，不表示副作用未发生；非幂等写入应进入 outcome_unknown。
  • 逻辑 operation/call 使用稳定 key，attempt 使用独立 identity；key 必须绑定 canonical request fingerprint。
  • retry 对只读 transient failure 生效；写操作还必须证明未提交或受 effect-owner idempotency 保护，并受 backoff、jitter、deadline 与 retry budget 约束。
  • checkpoint replay 重建 decisions，不重复 side effects；未决命令先 lookup/reconcile，再决定是否同 key 重投。
  • compensation 是新的、可能失败的业务动作，不是时间倒流；exactly-once effect 需要 effect owner 参与。

Should an Agent Retry After a Tool Timeout?

Start from ambiguous outcomes and unpack idempotency keys, deduplication ledgers, retry and backoff, checkpoints and replay, reconciliation, and compensation.

01

Today's proposition

A timeout after dispatch proves only that the runtime did not receive a result on time; it does not prove the remote operation did not execute. An admission or queue timeout before dispatch can establish that no remote effect ran. A payment may be captured, an email sent, or a ticket created while the response is lost to the network or a process crash. If an agent classifies timeout as failure and calls again, it can turn one uncertain outcome into a definite duplicate side effect.

Reliable recovery separates the logical operation from its transport attempts. One stable operation or call identity may have several attempts. An idempotency key tells the remote system that attempts represent the same intent. A deduplication ledger records the key, request fingerprint, state, and committed result. A retry policy handles only retryable classes. When the outcome cannot be proven, the runtime reconciles rather than asking the model to guess that it probably failed.

Core judgment: at-least-once delivery plus an idempotent effect can produce “duplicate delivery, one business result.” Exactly once is not a runtime toggle. The side-effect system must participate through a key or transaction, or expose a queryable business identity. Otherwise the runtime manages uncertainty across failure boundaries; it cannot eliminate it.
02

Continue from lifecycle and structured concurrency

Part 1 established call IDs, attempt IDs, and outcome_unknown. Part 2 established task groups, deadlines, cancellation, and bounded queues. Today failure recovery enters the same state machine. The call ID and idempotency key stay stable across retries; the attempt ID changes. Parent deadlines and retry budgets bound attempts. Late results deduplicate against call identity and ledger version.

The critical crash window lies between remote effect commit and local outcome commit. Recording intent before dispatch does not let a local transaction encompass another system. The solution is not another prompt. The remote endpoint must atomically deduplicate by key and store the result, or the runtime must query actual state by a business identifier after timeout.

03

Mechanism: from a key to a recovery protocol

1. Generate a stable identity

An operation ID identifies business intent, such as “capture payment once for order O”; one operation may contain several logical tool calls. A call ID identifies one logical tool invocation, and an attempt ID identifies one transport execution of that call. An idempotency key may derive from the operation ID, but it stays unchanged across retries, worker handoffs, and replay. A new key represents a new operation.

2. Fingerprint the request

The ledger stores the key with a canonical request hash: tool and version, tenant, authorization principal, normalized arguments, and target resource. Same key plus same hash may return existing status. Same key plus a different hash must be rejected; a key cannot silently move to a new amount or recipient. Sensitive payloads may live in encrypted storage. A hash checks consistency, not authorization.

3. Deduplicate atomically at the remote boundary

An ideal endpoint runs one transaction: insert an in_progress key if absent, perform the business effect, and save result and status as succeeded or failed. A duplicate reads the same outcome. If the dedup record and effect live in stores that cannot commit atomically, an internal crash window remains and requires outbox, inbox, or business reconciliation.

4. Classify retries

A read-only operation may retry contract-declared transient failures. A write must either be proven uncommitted or be protected by effect-owner idempotency under the same key; a generic transient label alone is insufficient. Validation, authorization, and semantic rejections do not retry. Rate limiting respects Retry-After. Timeout and connection reset on an unprotected effect that cannot be proven uncommitted become unknown. The classifier comes from the tool contract and structured error type, not from a model improvising over an error string.

5. Use backoff, jitter, and a retry budget

Attempts use exponential backoff plus random jitter so many agents do not retry simultaneously. Maximum attempts, absolute deadline, per-tool token buckets, and a global retry budget all bound work. One layer owns retries. If an SDK, runtime, and workflow each issue three total attempts—initial plus two retries—worst-case amplification is twenty-seven. If each means initial plus three retries, it is 4³=64 requests.

6. Checkpoint and replay

A checkpoint stores state version, event cursor, open calls, keys, attempts, deadlines, and accepted outcomes. Recovery replays events through reducers to rebuild decisions but does not directly repeat side effects. A recorded but incomplete effect command triggers a ledger or tool lookup, or redispatch with the same key. Wall-clock readings, randomness, and model responses are consumed as historical events rather than regenerated during replay.

7. Reconcile

When a tool lacks key support but exposes a query API, the runtime searches by a business key such as order ID, message ID, or external reference. One unique result completes the local outcome. No result may permit a new attempt if deadline and budget allow. Multiple matches or an unqueryable system enters manual review. Reconciliation is a first-class workflow, not a background log.

8. Concurrent duplicates and an in-progress lease

Two attempts may arrive with the same key concurrently. A unique ledger insert elects one owner. Others must wait, return conflict or in-progress, or read the completed result rather than execute the effect too. The owner holds an expiring lease, heartbeats, and a monotonically increasing fencing token; takeover advances the token with compare-and-swap. An effect owner that supports fencing rejects stale tokens; otherwise a shared idempotency key still prevents duplicate effect. If neither is supported, lease expiry plus reconciliation cannot exclude a revived old owner, so automatic takeover must pause or escalate. Simply deleting a stuck in-progress record reopens the duplicate-effect window.

9. Poison work and a dead-letter state

Persistent failure must not loop forever. After attempt or deadline budget is exhausted, record retry_exhausted with the last error, attempt history, and next-action guidance. Human-required work enters a review queue. A dead letter is not a trash can: it needs an owner, SLO, and redrive policy. Redrive reuses the original key or creates an explicitly approved new operation.

10. Compensate

An irreversible effect cannot be rolled back. A Saga uses a later business action—refund, close ticket, send correction—to compensate. Compensation can fail, needs idempotency, and may not be a strict inverse. The runtime records compensation_required, in_progress, failed, and completed. “Refund requested” must not be displayed as “the charge never happened.”

Essential math: backoff, amplification, and consistency invariants

Exponential backoff with full jitter

bk = min(bmax, b0·2k),   waitk ∼ U(0,bk)

k is the attempt index, b₀ the base delay, and bmax the cap. Full jitter has expected wait bₖ/2 and spreads synchronized retries. Backoff reduces pressure; it does not make an unsafe operation retryable. Stop at the deadline.

Truncated attempts

E[N] = Σk=0n−1(1−q)k = (1−(1−q)n)/q

If attempts independently succeed with probability q and at most n are issued, expected attempts follow the expression. At q=0.8 and n=3, E[N]=1.24. Real failures are correlated and retries alter load, so this illustrates amplification rather than predicting capacity.

Layered retry amplification

Amax = ∏l=1m nl

If m layers each issue at most nₗ total attempts including the initial one, one user operation amplifies to their product in the worst case. If configuration specifies retry count rₗ, then nₗ=rₗ+1. Centralize retries in the layer that understands effect and idempotency; other layers propagate structured state.

The idempotency invariant

same(K) ∧ same(H(request)) ⇒ same(committed outcome)

K is the key and H a canonical fingerprint. Same key with a different hash is a conflict. Same key and hash makes many attempts return one logical outcome. A unique ledger constraint and the effect transaction maintain the invariant—not a model promise.

A retention bound

TTLdedup ≥ max retry horizon + max message delay + clock/error margin

Deleting a dedup record too soon turns a late retry into a new operation. Retaining it too long increases cost and privacy exposure. TTL covers the maximum retry and delivery windows across transports and workflows while respecting audit and deletion policy.

05

Implications for agent systems

1. A tool contract declares retry semantics

Metadata includes effect class, idempotency-key support, key scope and TTL, lookup API, retryable errors, and compensation. When this information is missing, the runtime defaults to no automatic retry for writes. A model saying “try again” cannot override the contract.

2. Bind the key to the exact authorized intent

After the user approves amount 10 and recipient A, create the request fingerprint. If the model changes either argument, it needs new approval and a new operation rather than reusing the key. A key is not a capability token and cannot cross tenants.

3. A checkpoint should not copy secrets

Persist key references, credential handles, and encrypted payload pointers—not access tokens in the event log. On recovery, resolve short-lived credentials again and verify authorization remains valid. An old checkpoint grants no permanent authority.

4. Late results remain valuable

If a call under reconciliation receives a late success, complete it through the ledger rather than discarding it. If compensation has started, the state machine decides whether to accept the original result, continue compensation, or escalate. Arrival order cannot bypass a version guard.

5. The UI displays certainty levels

Distinguish retrying, outcome unknown, reconciling, compensating, compensated, succeeded, and failed. Showing unknown as failed encourages duplicate action; showing compensation requested as restored conceals risk.

6. Evaluations inject faults

Kill the process before and after intent commit, remote effect, and result commit. Inject duplicate delivery, late responses, ledger TTL expiry, 429s, and lookup disagreement. A happy-path test cannot establish a recovery protocol.

7. The model does not own the retry classifier

An LLM may explain an error or suggest human action, but deterministic policy owns retry, reconcile, and compensate transitions. Otherwise stochastic prose becomes the control plane for duplicate side effects.

8. Recovery telemetry separates causes

Measure initial-attempt success, key deduplication hits, transient-retry success, unknown outcomes, reconciliation resolution, compensation success, and manual-queue age separately. One tool-success rate can hide a system sustained by heavy retries or manual repair. Traces correlate operation, call, attempt, and key references without logging raw keys or sensitive payloads.

06

Trade-offs and failure modes

Long key retention versus privacy and cost: long TTL covers late retries while expanding storage and sensitive-metadata exposure. Use minimal fingerprints, encrypted payloads, and risk-based retention. A retry after expiry should require confirmation rather than execute as new.

Key entropy and scope: keys must be unguessable and unique inside an explicit tenant and tool scope so another party cannot enumerate keys to retrieve old results. The server still performs normal authentication and authorization; knowing a key does not grant access to its outcome.

Cached failure versus retry: some providers cache the first terminal failure for a key; others cache only success. The contract must say. If a validation failure is cached, corrected arguments need a new operation and key; the same key cannot hide a changed payload.

Replay determinism versus code evolution: replaying old history under a new reducer can emit different commands. Version workflow code, upcast events, and replay a corpus before deployment. Incompatible old tasks stay on old workers or pass an explicit migration.

Automatic compensation versus human control: automatic refund or reversal shortens recovery while a late original outcome can create a second error. High-value or irreversible operations need a reconciliation barrier and human approval.

Reconciliation read consistency: a query API may be eventually consistent, so one empty read does not prove the effect is absent. The contract defines visibility delay, pagination, and unique fields. The runtime repeats queries through a safe window rather than re-executing after one miss.

Remote idempotency versus local deduplication: a local ledger stops one runtime from dispatching twice but cannot stop another client or a remote service from duplicating an effect after acknowledgement loss. The effect owner defines the true boundary; the local ledger is one layer.

Exactly once inside one log versus across systems: one transaction domain can atomically commit input offset, state, and output. Across databases, payments, and email, participants need transactions or idempotency—or the design accepts at-least-once plus deduplication and reconciliation. Do not extrapolate a messaging system’s exactly-once label to a business effect.

The most dangerous failure modes: creating a new key for every retry; failing to bind key to payload; dedup TTL shorter than retry horizon; SDK, runtime, and workflow all retrying; replay calling models and tools again; treating compensation as rollback; showing unknown as failed.

07

Reusable judgments

  • A timeout means acknowledgement did not arrive, not that the effect did not happen. A non-idempotent write becomes outcome unknown.
  • A logical operation or call uses a stable key; attempts have separate identities. The key binds a canonical request fingerprint.
  • Retry read-only transient failures, or writes proven uncommitted or protected by effect-owner idempotency, all bounded by backoff, jitter, deadlines, and retry budgets.
  • Checkpoint replay rebuilds decisions without repeating side effects. Pending commands lookup or reconcile before redispatch with the same key.
  • Compensation is a new business action that can fail, not time reversal. Exactly-once effect requires participation from the effect owner.

09

What is established and where we continue

Established today: a stable idempotency key, request fingerprint, and effect-owner deduplication ledger converge several attempts into one business outcome. A deterministic classifier, backoff and jitter, deadline, and budget control retries. Checkpoint replay does not repeat effects; ambiguous calls recover through lookup, reconciliation, and compensation.

Still unresolved: when a task spans hours or days, approvals, deployments, and external callbacks, how does the control plane manage leases, timers, signals, versioning, human involvement, and observability—and prove eventual convergence?
