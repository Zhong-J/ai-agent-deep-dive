Agent Whole-Task Economics Internals · 第 1/2 篇

单次模型调用便宜，为什么整个 Agent 任务反而更贵？

把模型 token、工具、核验、重试、修复、人工和等待时间归到同一目标与任务。只有按已核验结果核算，才能比较执行策略。

01

今日命题

一个团队把每次模型调用从 4 分钱降到 1 分钱，却发现月度账单和用户等待时间都上升了。便宜模型更常选错工具，verifier 发现错误后需要再次调用强模型，偶尔还要人工核对已发出的外部效果。若报表只记录首次 token 费用，优化看似成功；按“用户目标经核验完成”的任务计算，它可能更贵、更慢、风险更高。

今日命题：Agent 的经济单位不是 request 或 token，而是带 goalVersion、taskId、所有 attempt 和终态 verdict 的完整任务。成本账本要把模型、工具、核验、重试、修复、人工与延迟分开，又归到同一任务。失败任务也要入账，不能只在成功样本上算平均成本；unknown outcome 的追查预算不能藏在“平台开销”里。

10 月 5 日讲过系统级 SLO、预算与成本归因，10 月 9 日讲过模型路由，10 月 20 日讲过推理服务调度。本篇不重复“选便宜模型还是强模型”的路由流程。我们先把一条真实 Agent 轨迹如何产生账单、何处产生条件性修复，以及成功分母如何定义讲透；下一篇才讨论在价格、延迟和成功率变化时怎样选完整执行策略。

核心问题：降价的是哪一段调用？它是否增加了后续工具、核验、修复和失败成本？
02

把账单接到 Agent 状态机

熟悉的 Agent loop 会先调用模型、选工具、观察、再调用模型；外层 runtime 可验证、重试、补偿。每一步都是一次成本事件，但同一 taskId 可能跨多次模型 response、工具 attempt 和人工操作。模型账单按输入/输出 token 结算，工具可能按调用量或数据量收费，sandbox 有计算与存储，verifier 本身也可调用模型。等待远端或审批不一定形成云账单，却会造成用户延迟与错过截止时间的业务损失。把所有量都称作“美元”会掩盖机制；应在账本中保留货币、时间和风险三条维度。

FrugalGPT 的作者研究了通过多模型策略降低调用成本，并报告特定基准的质量/成本结果；它说明路由可能有经济收益，不保证任何任务的完整成本都下降。The Tail at Scale 研究大规模系统的尾部延迟，提醒多阶段服务的等待并非平均值相加就能代表用户体验。OpenTelemetry 的 GenAI 语义规范提供模型调用与 token 用量的观测字段，Trace Context 为跨组件关联提供标准；但“核验后每个任务花了多少”仍要由业务控制层把事件接到 taskId 和 goal verdict。

一条完整账本至少区分 incurred（已发生）、reserved（为可能重试或人工核对预留）和 projected（基于当前估计的未来成本）。把 projected 当实际账单会误导财务；只记 incurred 又会在接近预算上限时低估任务完成所需资源。预算与会计都需要，但语义不同。

03

一条完整任务成本账本如何形成

1. 先定义可比较的任务终态

用同一个 goalVersion 与验收条件比较策略。succeeded_verified 需要权威后置条件；failed、cancelled、partial_verified、outcome_unknown 分开记录。若小模型给出流畅答案但没有完成外部目标，它不能进入成功分母。任务类别、风险、用户群与工具版本要入账，否则“单任务成本下降”可能只是任务 mix 变简单。一个可核验结果能有多个 attempt，但不能被算成多个成功任务。

2. 每个成本事件带因果标识

记录 taskId、goalVersion、planVersion、operationId、attemptId、model/tool/provider/version、时间戳、输入与输出用量、计费单位和价格版本、wall time、资源占用、是否缓存命中、verifier 结果及关联 effect。一次工具超时后的 readback 是原任务的核对费用，不应成为一个“新任务”；并行 worker 的费用分别记，再汇总到 parent。共享批处理的 GPU 或检索索引费用可以按可解释规则分摊，难以归因的部分单列 shared overhead，别凭空让每个任务看起来零成本。

3. 区分前台、修复与背景支出

首条候选路径的模型/工具开销是前台成本。verifier 发现错误后，诊断、重新检索、强模型升级和测试构成修复成本；它们只在某些轨迹发生，平均值需按失败率加权。用户取消后仍在追查是否已发出的邮件，是 effect reconciliation，不应被丢到“后台忽略”。可选预取和 speculative duplicate 有可能降低尾部延迟，但失败副本仍真实花钱；取消消息到达前的在途工作也要入账。

4. 用三条账避免混淆

第一条是货币账：模型 token、外部 API、计算、存储、人工工时的价格快照。第二条是时间账：关键路径上的排队、模型、工具与人工等待；并行分支的耗时不能简单相加为用户延迟。第三条是风险账：误发、未核验成功与权限错误的已观察事件和保守损失估计。业务决策可在约束下比较三条账，不能把“低 token 费”直接当“最优”。风险预算并非每次都转成现金支付，仍须列为门控条件。

5. 处理缓存、价格与版本漂移

缓存命中可能降低模型或工具边际费用，但缓存构建、失效和误用旧数据有成本。价格表变化时给每个事件保存 priceVersion，重算历史策略时既可按历史真实价格呈现，也可按同一新价格做公平 counterfactual；两种图不要混用。工具 schema 或模型版本变化影响失败率，不能只替换单价不更新质量估计。provider 账单可用于总额对账，task ledger 用于因果归因；对不上时记录缺口，不为凑平而把费用任意摊给成功任务。

6. 报告任务分层与尾部

按任务类别、风险、成功/失败终态报告每个已验证成功所需平均费用、所有尝试的费用、p50/p95/p99 用户延迟、工具费、核验费、修复费和人工率。极少但昂贵的 unknown outcome 不能被总体均值抹掉。可比较“强模型一次完成”与“小模型后续常升级”的完整轨迹，而不是比较单次推理价格。若某策略更便宜但更常越权或不满足目标，硬安全门先于成本排名。

on_cost_event(event):
  ledger[event.task_id].append(event.with_price_version())
on_terminal_verdict(task_id, verdict):
  money = sum_incurred(ledger[task_id])
  latency = critical_path_elapsed(ledger[task_id])
  reserve = remaining_repair_or_reconcile_budget(task_id)
  report(task_id, verdict, money, latency, reserve, risk_events(task_id))

此账本与分摊逻辑是本文编辑性工程设计；标准遥测字段并不自动形成业务目标成本。

04

把条件性重试算进期望成本

用一个简化的单策略模型看出“便宜调用反而贵”的可能性。假设一次 attempt 的模型+工具+核验成本为 c，独立尝试以概率 q 达到已核验成功，失败后先付修复成本 r 再以相同策略重试，且允许一直重试。则期望总成本 E 满足：

E = c + (1−q)(r + E)，所以 E = [c + (1−q)r] / q

c 是每轮实际支出，q 是任务类别内校准的已核验成功概率，r 是失败时的额外诊断/修复费用。公式说明：降低 c 若同时显著降低 q，E 可能上升。例：小模型 c=1、q=0.6、r=2，则 E=3；强模型 c=2、q=0.9、r=2，则 E≈2.44。单位可理解为相同的成本单位，只是教学例子，不代表任何产品报价。

真实 Agent 的重试不独立，也不能无限重试：错误可能相关、预算会耗尽、外部副作用禁止重放。此式只展示机制，不应直接拿它预测生产。有限次数策略可用真实轨迹估计条件成功率、修复次数分布与尾部；若任务失败后必须人工接管，还需把人工成本和失败损失单列。分母 q 也必须是“目标经核验成功”，不能是“模型回复未报错”。

延迟与货币不能用同一 E 代表。串行修复放大用户等待，多个并行工具分支则增加花费而未必增加关键路径长度。完整策略选择要同时约束成本、p95/p99 延迟与风险，下一篇处理。

05

对 Agent 系统的影响

路由与预算

同一初始模型价格变化，只影响账本的一部分。调度器应按任务类别估计完整轨迹，而非看到更便宜单价就全局替换。预算预留须覆盖可能的核验与修复；否则执行到最后才发现没钱验证，会把成功误报成“已完成”。

产品体验

用户感受的是从提交请求到可用结果的时间，以及失败后补救是否可靠。服务可以更快输出首字却更慢完成任务；也可以花更多核验费用换取少量重大错误减少。把 verified outcome、延迟和成本并列，才能让 PM 与工程一起讨论取舍。

06

取舍与失败模式

账本过细：每个底层 GPU kernel 都归因到任务会增加遥测开销且未必改善决策；应先记录模型、工具、核验、修复、人工和 shared overhead 的稳定边界。账本过粗：只看 API 请求或总云账单，无法发现某条路径反复重试或 verifier 成本突增。粒度由实际策略决策所需的因果问题决定。

成功样本偏差：仅对 completed tasks 算平均费用，会把最贵的失败、取消与 unknown 留在外面。报告所有启动任务的总支出，并另给每个已验证成功的成本；后者不能单独用来评价风险。某些任务本来更难，比较策略时需按任务 mix 和风险分层，否则路由器可能通过拒绝难例制造“便宜高成功率”。

缓存与共享费：共享 prompt cache、批处理和工具索引使单位成本分摊不唯一。给出可复现的分摊规则与未分摊池，避免把会计选择伪装成模型效率。缓存带来的质量变化也要验收；命中率升高而旧证据误用增加，不是净收益。

尾部与副作用：重试会放大 p99 延迟，speculative duplicate 可能降低尾部却提高总支出。带外部效果的超时不得为了控制延迟直接重发；unknown 的核对费应保留在原 taskId。若重大伤害的概率难估，单纯期望成本排序不足以允许行动，必须先满足权限与风险硬门。

评测：使用相同 goalVersion、任务 mix、工具版本与验收标准回放策略，记录每条路径的实际费用、延迟和终态。对照包括简单成功、错误工具、核验失败、工具超时但效果已发生、人工接管和取消后核对。若只把 token 账单和平均回复时间做成 dashboard，整条链的经济风险仍不可见。

07

可以带走的判断

  1. 以已核验目标任务为经济单位，将所有 attempt、工具、核验、修复与人工费用归同一 taskId。
  2. 货币、用户延迟和风险分开记账；首次 token 价格不能代表完整任务成本。
  3. 便宜模型若降低成功率，条件性修复与重试可能让期望总成本更高。
  4. 失败、取消和未知结果必须计入分母与账本；硬安全门先于成本排名。

Why Can a Cheap Model Call Make the Whole Agent Task More Expensive?

Attribute model tokens, tools, verification, retries, repair, human review, and elapsed time to one goal and task. Strategies become comparable only against verified outcomes.

2026-11-1620 min readAgent economics / Task cost / Verification / Retries / Latency
01

Today's proposition

A team cuts the price of each model call from four cents to one, yet its monthly bill and user wait both increase. The cheaper model selects the wrong tool more often. A verifier catches errors and asks a stronger model to repair them; occasionally a human must reconcile an external effect. If a dashboard records only first-call token charges, the optimization looks successful. Measured per user goal that reaches verified completion, it may be more expensive, slower, and riskier.

Today's proposition: the economic unit of an agent is not a request or token but a whole task with goalVersion, taskId, every attempt, and a terminal verdict. A cost ledger separates model, tool, verification, retry, repair, human, and latency components while attributing them to the same task. Failed tasks must enter the ledger rather than disappearing from a success-only average. The cost of investigating outcome_unknown cannot be hidden as “platform overhead.”

October 5 covered system SLOs, budgets, and cost attribution; October 9 covered model routing; October 20 covered inference-service scheduling. We will not repeat the router's cheap-versus-strong decision tree. First we need to understand how one real trajectory creates cost, where conditional repair enters, and how the verified-success denominator is defined. The next part will compare complete execution strategies as price, latency, and success rates change.

Ask of every price reduction: which call became cheaper, and did that change increase later tool, verification, repair, or failure cost?
02

Connect the bill to the agent state machine

The familiar agent loop calls a model, selects a tool, observes a result, and calls the model again. The outer runtime may verify, retry, or compensate. Each step creates cost events, yet one taskId may span many model responses, tool attempts, and human operations. Model billing may follow input and output tokens; tools can charge per call or byte; sandboxes consume compute and storage; a verifier may itself use a model. Waiting for a remote system or approval may not appear on a cloud invoice but adds user latency and deadline loss. Calling all of these “dollars” obscures the mechanism. Preserve money, time, and risk as separate ledger dimensions.

FrugalGPT's authors studied multi-model strategies and reported quality and cost results on specific benchmarks. It shows a route can have economic benefit, not that every complete task becomes cheaper. The Tail at Scale studied tail latency in large services and reminds us that a multi-stage workflow's user experience is not captured by an average per-call time. OpenTelemetry's GenAI semantic conventions offer observable model-operation and token-usage fields, while Trace Context standardizes cross-component correlation. A business control layer still has to connect events to taskId and a verified goal verdict to compute whole-task cost.

A complete ledger also distinguishes incurred cost already spent, reserved capacity for possible retries or human investigation, and projected future cost under a current estimate. Treating projections as actual invoices misleads finance. Recording only incurred cost near a budget boundary understates what completion may require. Budgeting and accounting both matter but have different semantics.

03

Build a ledger for the complete task

1. Define comparable terminal outcomes first

Compare strategies against the same goalVersion and acceptance conditions. succeeded_verified needs authoritative postconditions. Keep failed, cancelled, partial_verified, and outcome_unknown distinct. A fluent answer from a small model that did not achieve the external goal cannot enter the success denominator. Record task class, risk, user cohort, and tool version so a lower “cost per task” is not merely an easier task mix. One verified outcome may involve several attempts but should not become several successful tasks.

2. Give every cost event causal identifiers

Record taskId, goalVersion, planVersion, operationId, attemptId, model or tool or provider version, timestamp, input and output usage, billing unit and price version, wall time, resource occupancy, cache hit, verifier result, and linked effects. A readback after a timed-out tool call is reconciliation cost for the original task, not a new task. Parallel workers each incur cost before their parent total is computed. Shared GPU batches or retrieval indexes can be allocated by a documented rule; hard-to-attribute capacity remains a visible shared-overhead pool rather than magically becoming zero per task.

3. Separate initial path, repair, and background spending

The first candidate route's model and tool calls are initial-path cost. When a verifier detects error, diagnosis, another retrieval, stronger-model escalation, and testing become repair cost. They occur conditionally and should be weighted by failure frequency in a forecast. Checking whether mail was sent after a user cancels is effect-reconciliation cost, not ignorable background work. Prefetch and speculative duplicates may reduce tail latency, but losing copies still spend real resources. Work already in flight before cancellation is part of the task ledger.

4. Keep three ledgers rather than one misleading number

The money ledger records price snapshots for model tokens, external APIs, compute, storage, and human time. The time ledger records queueing, model execution, tools, and human waits on the critical path; parallel branch durations are not simply added into user latency. The risk ledger records observed false sends, unverified successes, authority errors, and conservative loss estimates. Strategy choice compares these dimensions under constraints. A low token bill is not an optimum, and a risk reserve need not be an immediate cash payment to remain a binding gate.

5. Account for cache, price, and version drift

A cache hit can reduce marginal model or tool charges, but cache construction, invalidation, and stale-data errors also cost money. Save priceVersion with each event. Historical actual-cost reports use historical prices, while a fair counterfactual comparison can reprice both strategies under one new schedule; do not mix the two views. A changed tool schema or model version also changes failure probability, so replacing only a unit price is not a valid forecast. Provider invoices reconcile aggregate cash; a task ledger supports causal attribution. If they differ, record the gap rather than distributing it arbitrarily across successful tasks.

6. Report task strata and tails

By task type, risk, and terminal outcome, report mean spending per verified success, spending across all attempts, p50/p95/p99 user latency, tool and verifier and repair charges, and human-review rate. Rare expensive unknown outcomes must remain visible outside the aggregate mean. Compare complete trajectories for “strong model once” and “small model with frequent escalation,” not just first-call prices. If a cheaper strategy violates authority or goal acceptance more often, a hard safety gate precedes economic ranking.

on_cost_event(event):
  ledger[event.task_id].append(event.with_price_version())
on_terminal_verdict(task_id, verdict):
  money = sum_incurred(ledger[task_id])
  latency = critical_path_elapsed(ledger[task_id])
  reserve = remaining_repair_or_reconcile_budget(task_id)
  report(task_id, verdict, money, latency, reserve, risk_events(task_id))

This ledger and attribution policy are editorial engineering design. Standard telemetry fields do not automatically produce business-goal cost.

04

Include conditional repair in expected cost

A simplified single-strategy model shows how a cheaper call can create a more expensive task. Suppose one attempt's model, tool, and verification cost is c. Independent attempts reach verified success with probability q; after failure, a repair cost r is paid and the same strategy is retried indefinitely. Expected total cost E satisfies:

E = c + (1−q)(r + E), hence E = [c + (1−q)r] / q

c is actual spending per attempt, q is the task-class calibrated probability of verified success, and r is extra diagnosis and repair after failure. Reducing c while lowering q enough can increase E. For illustration, a small-model route with c=1, q=0.6, r=2 gives E=3. A stronger route with c=2, q=0.9, r=2 gives E≈2.44 in the same arbitrary cost units. These are teaching numbers, not prices for any product.

Real agent retries are not independent and cannot continue forever. Errors can correlate, budgets end, and an external side effect may forbid replay. The equation demonstrates a mechanism, not a production forecast. For a finite policy, estimate conditional success, repair-count distribution, and tails from real trajectories. If failure leads to human takeover, show human cost and failure loss separately. q must mean verified goal success, not merely “the model response had no error.”

Money and elapsed time also cannot share one E. Serial repair expands user wait; parallel tool branches spend more money without necessarily lengthening the critical path. A complete strategy comparison must constrain spend, p95/p99 latency, and risk together. The next part develops that choice.

05

Implications for agent systems

Routing and budget

A change in the initial model's price affects only one part of the ledger. A scheduler should forecast complete trajectories by task class instead of globally replacing a model when a unit price falls. Reserve enough budget for likely verification and repair. Otherwise the agent may reach the final step without resources to prove success and then report “done” prematurely.

Product experience

Users experience time from request to usable outcome and how reliably a failure is repaired. A service may stream its first token faster yet complete the task later. It may spend more on verification to prevent a few severe mistakes. Reporting verified outcome, latency, and spending side by side gives product and engineering teams a common basis for trade-offs.

06

Trade-offs and failure modes

Ledger too fine: attributing every GPU kernel to a task adds telemetry cost without necessarily improving decisions. Start with stable model, tool, verifier, repair, human, and shared-overhead boundaries. Ledger too coarse: an API-request count or cloud invoice total cannot reveal repeated retries on one path or a sudden verifier-cost increase. Choose granularity by the causal question a strategy decision needs to answer.

Successful-case bias: average cost over completed tasks omits expensive failures, cancellations, and unknown outcomes. Report total spending across all started tasks and cost per verified success separately. The latter alone cannot assess risk. Some tasks are inherently harder; compare policies by task mix and risk strata so a router cannot create an attractive “cheap high-success” metric merely by refusing difficult cases.

Cache and shared cost: shared prompt caches, batching, and tool indexes make per-task allocation nonunique. Publish a reproducible allocation rule and an unallocated pool rather than disguising accounting choice as model efficiency. Cache-related quality also needs verification. A higher hit rate with more stale-evidence errors is not a net win.

Tail and side effects: retries amplify p99 latency. Speculative duplicates may shorten the tail while increasing total spending. A timeout after an external write must not trigger an immediate resend to improve latency; its reconciliation cost stays with the original taskId. If severe harm probabilities cannot be estimated credibly, expected-cost ranking alone cannot authorize an action. Authority and risk hard gates come first.

Evaluation: compare strategies on the same goalVersion, task mix, tool version, and acceptance criteria, recording actual cost, latency, and terminal outcome for each path. Include easy success, wrong tool, verifier failure, tool timeout with committed effect, human takeover, and reconciliation after cancellation. A dashboard of token bills and mean response time leaves the whole chain's economics hidden.

07

Reusable judgments

  1. Use the verified user-goal task as the economic unit, attributing all attempts, tools, verification, repair, and human effort to one taskId.
  2. Keep money, user latency, and risk separate. First-call token price is not complete task cost.
  3. A cheap model with lower success can create higher expected total cost through conditional repair and retry.
  4. Failed, cancelled, and unknown outcomes remain in the ledger and denominator. Hard safety gates precede economic ranking.
