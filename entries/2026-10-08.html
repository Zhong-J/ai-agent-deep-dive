多个 Agent 并行时，谁拥有“真相”？

从 delegation contract、shared state、single-writer ownership、lease/fencing、merge/conflict 到终态集成。

2026-10-08约 20 分钟Multi-agent / Coordination / Shared state / Delegation / Conflict resolution
01

今日命题

把任务拆给多个 Agent，吞吐可能提高，也会把一个推理问题变成分布式系统问题。两个 worker 可能同时修改同一文件、重复调用同一副作用 tool、基于不同版本的 plan 做出相反结论，或都声称“任务完成”。自然语言消息不能自动提供原子性、顺序、ownership 或 exactly-once；“大家互相同步一下”也不能消除 crash window。

可靠 multi-agent system 需要明确控制面：parent 将 goal 编译为有输入快照、输出 contract、资源范围、deadline、budget 和 verifier 的 delegation；shared state 通过版本化 event/task store 传播；可变资源有 single writer 或 merge protocol；lease 只管理调度活性，fencing/version precondition 才阻止旧 worker 提交；集成器验证每个 child artifact 和全局 claims 后，才宣布完成。

核心判断：Agent 是不确定的 proposal producer，不是共享状态的权威 owner。并行安全来自 ownership、version、idempotency、conflict detection 和 independent verification，而不是来自更多对话轮次。
02

承接 Runtime 与 Reliability：并行边界必须可恢复、可证明

Runtime 系列已区分 workflow/run/operation/call/attempt，并建立 structured concurrency、idempotency 和 durable control plane；Reliability 系列又要求 claims/evidence/verdict、authorization、sandbox 和 SLO。multi-agent 并非另一套架构，而是把 child task 的执行者从一个 worker 扩展为多个自治 planner。已有边界必须继续成立：parent deadline 约束 children，取消向下传播，副作用复用 operation identity，终态由 verifier 而非 child 自报。

共享 context 也不能等同 shared truth。每个 Agent 可以拥有自己的局部 prompt、summary 和 hypotheses，但 canonical task state、accepted artifacts、resource versions、approvals 与 unresolved effects 存在控制面。Message 可以建议 state transition，只有 reducer/CAS/transaction 能提交。

因此协调有两条流：data plane 传递任务、evidence、artifact 和 proposal；control plane 分配 ownership、记录 version、仲裁冲突、回收 lease、执行 integration 和 terminal gate。将两者混在群聊里，会让恢复只能靠重读 transcript 猜发生了什么。

03

机制：delegation、ownership 与 integration protocol

1. 编译 delegation contract

child task 包含 taskId、parentId、goal/acceptance claims、inputSnapshotId、dependencies、owned resources、allowed tools/capabilities、deadline、cost/retry budget、output schema、artifact destination、verifier 和 escalation policy。不要只发送一句“调查这个问题”；否则 child 无法判断完成、冲突与权限边界。

2. 构建 dependency DAG

任务节点声明 consumes/produces artifacts 和 prerequisite claims。只有依赖 satisfied 才 runnable；failure/cancel 按 edge policy 传播。DAG 不是永久 plan：新 evidence 可创建 revision，但已运行 child 继续绑定旧 revision，结果提交时检查 planVersion，避免旧工作污染新版。

3. 分配 ownership

不可交换 mutable resource 使用 single-writer owner，例如同一文件区域、工单、deployment 或 final report section。可交换工作（搜索候选、独立测试）允许多 writer，但结果进入 set/append log，不直接覆盖。ownership scope 细到 path/section/entity/action，避免粗粒度锁消除并行。

4. Lease 与 fencing

scheduler 给 worker leaseId、expiry 和单调 fencingToken。Heartbeat 仅证明近期活跃。Lease 过期可重派，但旧 worker 可能复活；canonical store/effect owner 拒绝低于 current token 的 commit。没有 fencing/CAS 的资源不能仅凭 timeout 安全接管，应暂停或人工。

5. Snapshot isolation

worker 读取 inputSnapshot 的 immutable state/artifacts，在独立 worktree/temp DB/browser profile 中工作。禁止共享可写 workspace 和 ambient credentials。所有 writes 先成为 proposal/patch/artifact，带 baseVersion、content digest、source evidence、tests 和 declared effects。

6. Shared-state update protocol

状态变更使用 expectedVersion CAS 或 transaction：若当前 version 不等于 baseVersion，则 reject conflict，不让最后写入覆盖。append-only observations 可按 eventId 去重；counter/sets 可用定义明确的 commutative merge；自然语言 conclusion 不自动 CRDT 化。

7. Communication as typed events

Agent-to-agent message 类型化为 RequestEvidence、ProposeChange、Question、Blocker、Cancel、Result、ReviewFinding，不是无限聊天。每条带 sender/recipient/task/stateVersion/evidence refs。消息本身无授权；recipient 仍按自己的 contract/policy 行动。重要 decision 写 task store，不只留在 inbox。

8. Conflict detection

冲突包括 write/write、read/write stale assumption、semantic disagreement、duplicate effect、policy conflict 和 resource contention。Integrator 对 patches 做 three-way merge，对 claims 比 authority/provenance，对 effects 查 idempotency ledger。无法自动仲裁就保留 conflict set 并指定 owner/human review，不让模型选“听起来更好”的版本。

9. Review independence

reviewer 使用目标 contract 和 canonical artifact，不只读 worker summary。高风险结果需不同 worker/model/toolchain 或 deterministic verifier，减少 correlated errors。Reviewer 不能在同一 review 中偷偷修改 artifact；finding 作为 proposal，owner 修复或 integrator 应用受控 patch。

10. Integration

integrator 拓扑排序 accepted outputs，检查 dependency versions、schemas、tests、provenance、permission/effect ledger，并生成 candidate aggregate artifact。局部 pass 不保证全局一致：API/schema consumers、重复 assumptions、跨模块 invariants 与 end-to-end test 在 integration 阶段验证。

11. Completion 与 cancellation

Parent 只有 global required claims pass、children terminal、无 unresolved conflicts/effects、aggregate artifact verified 才 complete。Sibling failure 按 policy cancel dependents 或允许 optional branch 失败。Cancellation 先 revoke child capabilities，再停止 work，收集 partial evidence，执行 teardown；迟到 result 以 task/version/token 判断 discard/review。

12. Recovery 与 audit

控制面持久化 task DAG/version、lease/fencing、messages、proposals、accepted artifacts、conflicts、effects 与 verdicts。Crash 后 scheduler 从 store 恢复，不重放自然语言聊天决定。Trace 可以回答谁基于哪个 snapshot 做了什么、谁接受、为何合并、哪个 verifier 证明终态。

13. Speculation 与 straggler policy

对只读、无副作用、结果可验证且 tail variance 高的 child，可在超过 percentile threshold 后启动不同 worker/model 的 speculative duplicate，首个通过 verifier 的结果获胜，其余取消。写操作、昂贵外部 API 和共享资源任务默认不 speculation。所有副本复用 logical taskId、拥有不同 attemptId，并消耗全局 extra-work budget；否则系统在过载时会因 hedging 进一步过载。

14. Backpressure 与 bounded coordination

parent 不无限 spawn。每个 workflow 有 max runnable children、per-tool concurrency、message/event rate、artifact bytes、review queue 与 integration budget。若 downstream verifier/integrator 堵塞，scheduler 暂停新 fan-out，而不是让 completed proposals 堆满存储。Backpressure signal 进入 task state，可选择缩小搜索 breadth、提高 evidence threshold 或排队。

04

必要数学：并行收益、冲突成本与提交条件

Critical path

DAG 节点耗时 dᵢ，总工作 W=Σdᵢ，critical path L 是最长依赖路径。P 个 workers 的完成时间下界 T≥max(W/P,L)。增加 Agent 只能压缩非关键、可并行工作；若 integration/verifier 在关键路径，盲目 fan-out 不会线性加速。

冲突概率

若每对并行任务发生不可自动 merge 冲突概率 p，N tasks 的 pair 数 N(N−1)/2，期望冲突约 E[C]≈p·N(N−1)/2。即使 p 小，N 增长也会让 review/repair 成本二次增长。Ownership 与更好 partition 的价值是降低 p，而非只提高 worker 数。

提交谓词

proposal 提交条件可写 Commit=(baseVersion=currentVersion)∧(fence≥currentFence)∧claimsPass∧policyAllow∧effectsResolved。任何一项 false 拒绝；证据不足是 unknown，进入等待/review。这个谓词把“worker 说完成”转换为可判定 control-plane transition。

05

对 Agent 系统的影响

能力：multi-agent 适合可分区 search、independent analysis、tests 和 artifact generation；不适合高度耦合、共享写频繁的小任务。Router 应依据 DAG/ownership/conflict 历史决定 fan-out，而非固定 agent count。

可靠性：局部 context 可丢，canonical state 不依赖聊天；lease loss、worker crash、duplicate result、late message、stale plan 都有 typed transition。Integrator 与 verifier 给出唯一接受点。

安全：delegation 不扩权，child capability 为 parent scope 与 child task policy 的交集。每个 workspace/browser/credential 隔离；messages/results 是 data。Reviewer independence 降低同源错误和恶意 worker 自证。

成本：并行缩短 wall time，却增加 total tokens、重复 retrieval、coordination messages、sandbox cold start、integration/review。指标拆 critical-path latency、total work、idle/wait、conflict/merge rate、duplicate effort、verified outcome cost，而不是只看 agents busy。

06

设计取舍与失败模式

  • 群聊即协调：无 canonical state/version；typed events 和 task store。
  • 共享写 workspace：静默覆盖/脏读；isolated snapshots、single owner、CAS/merge。
  • lease=安全锁：旧 worker 可复活；fencing token/effect-owner check。
  • last writer wins：丢失有效结果；显式 conflict set/three-way merge。
  • 更多 agents=更快：critical path 与冲突二次增长；DAG-aware bounded fan-out。
  • reviewer 读 summary：继承 worker framing；独立 contract/artifact/evidence。
  • delegation 扩权：child 获 ambient parent secrets；capability intersection 和隔离。
  • 所有 child pass=全局 pass：跨模块 invariant 未测；integration/global verifier。
07

可复用的技术判断

  • multi-agent 是 distributed workflow，不是多个模型的群聊。
  • delegation contract 明确 snapshot、claims、resources、capabilities、budget、output 和 verifier。
  • 可变资源用 single writer/版本/CAS；lease 负责活性，fencing 负责旧 worker 安全。
  • workers 产出 proposal/artifact，integrator 仲裁 conflict，verifier 决定 global terminal state。
  • 并行收益受 critical path 限制，冲突成本随任务对数近似 N²；fan-out 必须有界且基于 partition。

When Agents Work in Parallel, Who Owns the Truth?

From delegation contracts and shared state to single-writer ownership, leases and fencing, merge conflicts, and terminal integration.

2026-10-0820 min readMulti-agent / Coordination / Shared state / Delegation / Conflict resolution
01

Today's proposition

Delegating work to several agents may improve throughput, but it turns one reasoning problem into a distributed-systems problem. Two workers may edit the same file, repeat the same side-effecting tool, act from different plan versions, or both declare completion. Natural-language messages do not provide atomicity, ordering, ownership, or exactly-once semantics. “Keep each other updated” does not close crash windows.

A reliable multi-agent system needs an explicit control plane. A parent compiles the goal into delegations with input snapshots, output contracts, resource scopes, deadlines, budgets, and verifiers. Versioned event and task stores distribute shared state. Mutable resources use a single writer or an explicit merge protocol. Leases manage scheduling liveness, while fencing or version preconditions stop stale workers from committing. An integrator validates child artifacts and global claims before declaring completion.

Core judgment: agents are nondeterministic proposal producers, not authoritative owners of shared state. Parallel safety comes from ownership, versions, idempotency, conflict detection, and independent verification, not more conversation turns.
02

Parallel boundaries must be recoverable and verifiable

The Runtime series distinguished workflow, run, operation, call, and attempt identities and established structured concurrency, idempotency, and a durable control plane. Reliability added claims, evidence, verdicts, authorization, sandboxes, and SLOs. Multi-agent execution is not a replacement architecture; it expands child-task executors from one worker to several autonomous planners. Existing boundaries remain: parent deadlines bound children, cancellation propagates downward, side effects reuse operation identity, and verifiers—not child self-report—decide terminal state.

Shared context is not shared truth. Each agent may have a local prompt, summary, and hypotheses, but canonical task state, accepted artifacts, resource versions, approvals, and unresolved effects live in the control plane. A message may propose a state transition; only a reducer, compare-and-swap, or transaction commits it.

Coordination therefore has two flows. The data plane carries tasks, evidence, artifacts, and proposals. The control plane assigns ownership, records versions, arbitrates conflict, reclaims leases, integrates results, and applies the terminal gate. Mixing both into a group chat makes recovery depend on rereading prose and guessing what happened.

03

Mechanism: delegation, ownership, and integration protocol

1. Compile a delegation contract

A child task includes task and parent IDs, goal and acceptance claims, input snapshot ID, dependencies, owned resources, allowed tools and capabilities, deadline, cost and retry budgets, output schema, artifact destination, verifier, and escalation policy. “Investigate this” is insufficient because the child cannot determine completion, conflict, or authority boundaries.

2. Build a dependency DAG

Task nodes declare consumed and produced artifacts plus prerequisite claims. A node becomes runnable only after dependencies pass, and failure or cancellation propagates according to edge policy. The DAG can be revised when evidence changes, but running children remain bound to their captured revision and validate plan version at submission.

3. Assign ownership

Non-commutative mutable resources use a single writer: a file region, ticket, deployment, or final-report section. Commutative work such as candidate search or independent tests allows multiple writers, but results enter a set or append log rather than overwrite state. Scope ownership to paths, sections, entities, and actions so coarse locks do not erase parallelism.

4. Use leases with fencing

The scheduler gives a worker a lease ID, expiry, and monotonically increasing fencing token. Heartbeat proves only recent activity. Expiry permits reassignment, but a stale worker may revive; canonical stores and effect owners reject commits below the current token. A resource lacking fencing or compare-and-swap cannot be safely taken over merely because a timeout fired.

5. Isolate snapshots

A worker reads immutable state and artifacts from its input snapshot and works in a separate worktree, temporary database, or browser profile. Shared writable workspaces and ambient credentials are forbidden. Every write first becomes a proposal, patch, or artifact with base version, content digest, source evidence, tests, and declared effects.

6. Define a state-update protocol

State changes use expected-version compare-and-swap or transactions. If current version differs from base version, the commit is rejected as conflict; last writer does not win silently. Append-only observations deduplicate by event ID. Counters and sets may use a defined commutative merge. Natural-language conclusions do not become CRDTs automatically.

7. Communicate with typed events

Agent messages are RequestEvidence, ProposeChange, Question, Blocker, Cancel, Result, or ReviewFinding rather than endless chat. They carry sender, recipient, task, state version, and evidence references. A message grants no authority; recipients still follow their contracts and policies. Important decisions enter the task store rather than remaining only in an inbox.

8. Detect conflicts explicitly

Conflicts include write-write, stale read-write assumptions, semantic disagreement, duplicate effects, policy conflict, and resource contention. Integrators use three-way merge for patches, authority and provenance for claims, and idempotency ledgers for effects. If arbitration is unsafe, preserve a conflict set and assign an owner or human review rather than asking a model to choose the nicest prose.

9. Preserve reviewer independence

A reviewer receives the target contract and canonical artifact, not only the worker's summary. High-risk results use another worker, model, toolchain, or deterministic verifier to reduce correlated error. The reviewer does not silently edit the artifact during review; findings are proposals, and the owner or integrator applies controlled fixes.

10. Integrate globally

The integrator topologically orders accepted outputs, validates dependency versions, schemas, tests, provenance, permissions, and effect ledgers, then creates a candidate aggregate artifact. Local passes do not prove global consistency. API consumers, duplicate assumptions, cross-module invariants, and end-to-end tests run during integration.

11. Complete and cancel correctly

The parent completes only when global required claims pass, children are terminal, no conflict or effect is unresolved, and the aggregate artifact is verified. Sibling failure cancels dependents or allows optional branches according to policy. Cancellation revokes capabilities, stops work, collects partial evidence, and tears down. Late results are discarded or reviewed by task, version, and token.

12. Recover and audit

The control plane persists task DAG and version, leases and fencing, messages, proposals, accepted artifacts, conflicts, effects, and verdicts. After a crash, the scheduler reconstructs from the store rather than replaying prose decisions. A trace explains who acted from which snapshot, who accepted the result, why it merged, and which verifier proved terminal state.

13. Speculation and straggler policy

For read-only, side-effect-free, verifiable children with high tail variance, the scheduler may launch a speculative duplicate on another worker or model after a percentile threshold. The first result that passes verification wins and the rest cancel. Writes, expensive external APIs, and shared-resource tasks do not speculate by default. Copies share one logical task ID but have separate attempt IDs and consume a global extra-work budget; otherwise hedging under overload produces more overload.

14. Backpressure and bounded coordination

A parent cannot spawn without bound. Every workflow limits runnable children, per-tool concurrency, message and event rates, artifact bytes, review queue, and integration budget. If the verifier or integrator becomes the bottleneck, the scheduler pauses fan-out instead of filling storage with completed proposals. Backpressure enters task state and may narrow search breadth, raise evidence thresholds, or queue work.

04

Essential mathematics: parallel speedup, conflict cost, and commit conditions

Critical path

For DAG node durations dᵢ, total work is W=Σdᵢ and critical path L is the longest dependency path. With P workers, completion has lower bound T≥max(W/P,L). Adding agents compresses only non-critical parallel work. If integration or verification dominates the critical path, fan-out cannot produce linear speedup.

Conflict probability

If each pair of parallel tasks has probability p of a non-mergeable conflict, N tasks contain N(N−1)/2 pairs and expected conflicts are roughly E[C]≈p·N(N−1)/2. Even small p causes quadratic review and repair growth as N increases. Ownership and better partitioning reduce p rather than merely adding workers.

Commit predicate

A proposal commit may require Commit=(baseVersion=currentVersion)∧(fence≥currentFence)∧claimsPass∧policyAllow∧effectsResolved. Any false condition rejects. Missing evidence yields unknown and waits or reviews. The predicate turns “the worker says done” into a decidable control-plane transition.

05

Implications for agent systems

Capability: multi-agent execution fits partitionable search, independent analysis, tests, and artifact generation. It fits poorly when small tasks are tightly coupled and frequently share writes. Routing should choose fan-out from the DAG, ownership, and conflict history rather than a fixed agent count.

Reliability: local context may disappear while canonical state survives outside chat. Lease loss, worker crash, duplicate result, late message, and stale plan become typed transitions. The integrator and verifier provide one acceptance point.

Security: delegation cannot expand authority. Child capability is the intersection of parent scope and child-task policy. Workspaces, browsers, and credentials remain isolated, and messages and results are data. Reviewer independence reduces correlated error and malicious worker self-attestation.

Cost: parallelism shortens wall time while increasing total tokens, duplicate retrieval, coordination messages, sandbox cold starts, integration, and review. Metrics separate critical-path latency, total work, idle and wait, conflict and merge rate, duplicate effort, and cost per verified outcome rather than counting busy agents.

06

Trade-offs and failure modes

  • Group chat is coordination: no canonical state or version. Use typed events and a task store.
  • Shared writable workspace: silent overwrites and dirty reads. Use isolated snapshots, one owner, and compare-and-swap or merge.
  • Lease equals safety lock: a stale worker may revive. Use fencing tokens and effect-owner checks.
  • Last writer wins: valid work disappears. Preserve conflict sets and three-way merge.
  • More agents means faster: critical paths remain and conflicts grow quadratically. Use DAG-aware bounded fan-out.
  • Reviewer reads the summary: inherits worker framing. Review independent contracts, artifacts, and evidence.
  • Delegation expands power: children receive ambient parent secrets. Intersect capabilities and isolate.
  • Every child passes means global pass: cross-module invariants remain untested. Run integration and global verification.
07

Reusable technical judgments

  • Multi-agent systems are distributed workflows, not model group chats.
  • A delegation contract specifies snapshot, claims, resources, capabilities, budget, output, and verifier.
  • Mutable resources use single writers, versions, and compare-and-swap. Leases provide liveness; fencing protects against stale workers.
  • Workers create proposals and artifacts, integrators arbitrate conflicts, and verifiers decide global terminal state.
  • Parallel speedup is bounded by the critical path, while conflict cost grows roughly with task pairs. Fan-out must be bounded and partition-aware.

09

What is established and where we continue

Established today: multi-agent execution combines a parent scheduler, versioned task and state store, isolated workers, single-writer ownership, leases and fencing, proposals and merge, independent review, and a global verifier. Natural-language messages are data; canonical state updates only through a decidable commit predicate.

Still unresolved: one task may dynamically select several models as well as several agents. How are uncertainty, capability, latency, cost, and risk routed? How do cascades, escalation, and ensembles work without making the router an opaque single point of failure?
