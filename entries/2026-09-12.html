一次梯度，怎样变成模型能力？

打开 AdamW、learning-rate schedule、batch、gradient clipping、数据混合与 compute-optimal scaling，理解训练 recipe 如何决定 LLM 学到什么。

01

今日命题

上一篇的 cross-entropy 只定义“往哪个方向更好”：提高真实 next token 的概率。它没有决定参数每次走多远、多少样本合成一个方向、哪些数据出现得更频繁，也没有决定固定算力该分给更大模型还是更多 token。真正得到什么模型，取决于objective × optimizer × schedule × data mixture × compute allocation 的组合。

训练不是把知识逐条写入数据库。每个 batch 产生一个高维、带噪声的 gradient；optimizer 把当前 gradient 与历史统计变成 parameter update。数十万次 update 共同改变模型的表示和条件分布。相同架构和 token 数，如果 learning rate 不稳定、batch 组织不同或高质量代码被低质量重复文本淹没，也可能得到能力完全不同的 checkpoint。

核心判断：scaling law 描述特定实验范围内 average loss 随 model/data/compute 的规律，不是“参数越多就自动会用工具”的定律。训练 recipe 决定算力是否转化为可迁移能力；Agent 的具体可靠性仍需任务级、闭环 eval。
02

承接 cross-entropy

上一篇停在 loss.backward()：automatic differentiation 得到每个参数的 gradient。把它类比为 Agent runtime：loss 像 verifier 给出的局部误差信号，gradient 像针对所有参数的建议方向，但它还不是副作用。optimizer 才像执行 policy——决定实际改哪些参数、改多少，并保存 momentum 等跨 step 状态。

不同点也同样重要。Agent verifier 可以返回可解释的业务错误；gradient 只是 loss 对参数的局部导数。它不携带“这是事实更新”“这是安全规则”的标签。一个 batch 中代码、新闻和聊天样本的 gradients 会在同一参数空间相加，有时协同，有时冲突。数据 sampler 实际上决定哪些目标更频繁地获得表决权。

03

机制：一条 training recipe

1. Global batch 与 gradient accumulation

显存通常放不下完整 global batch。训练把它拆成每张设备上的 microbatch，执行多次 forward/backward，把 gradients 累积后再同步更新。global batch 近似为 microbatch × accumulation steps × data-parallel workers。更大 batch 降低 gradient 方差、提高并行效率，但每个 token 带来的新信息会递减；如果 learning rate 不随之调整，优化动态也会改变。

2. Gradient clipping

长序列或异常 batch 可能产生极大 gradient norm。global-norm clipping 在 norm 超过阈值时等比例缩小全部 gradients并保留方向。它约束的是送入 optimizer 的 raw gradient norm；AdamW 还包含历史 moments、自适应缩放与 decay，因此 parameter-update norm 并未被同一阈值直接限制。它是训练稳定器，不会修复脏数据或错误 loss；阈值过低会把正常信号长期压扁。

3. AdamW 的状态

Adam 为每个参数维护一阶动量 m 与二阶矩 v，用历史均值平滑噪声，并按近期平方梯度自适应缩放。AdamW 将 weight decay 与 loss gradient 解耦，直接按比例收缩参数，避免把 L2 penalty 混入 Adam 的自适应归一化。代价是 optimizer states 常以较高精度存储，显存可能是权重本身的数倍；大规模训练需 sharding。

4. Warmup、peak 与 decay

训练初期 moments 尚未稳定，直接使用 peak learning rate 易发散，因此常线性 warmup；中段保持或缓慢变化；后段 cosine 或 linear decay 让参数在较小步长下收敛。schedule 按 step 还是 token 计数、是否在断点恢复时保持一致，都会影响结果。loss spike 后盲目继续可能传播坏 optimizer state，需要 checkpoint、数据定位与回退策略。

5. Mixed precision 与分布式同步

大模型常用 BF16/FP16 做矩阵计算，以较高精度保留部分 master weights、moments 或累积量。低精度提高吞吐、降低显存，却可能 overflow、underflow 或累积舍入误差。FP16 常用 loss scaling 防止很小的 gradients underflow；BF16 的 exponent range 更宽，通常不需要同样处理，而 loss scaling 也不会普遍修复 activation overflow。data-parallel workers 正常情况下各自处理不同 microbatches，再用 all-reduce 合成 global-batch gradient；故障边界是 collective 未完成，或 workers 的 model version、step、scale/scheduler state 不一致。tensor/pipeline parallel 则切分单个模型。因此 checkpoint 不只保存权重，还应记录 optimizer、scheduler、随机数、sampler 与已消费 token 位置，才能避免恢复后重复或跳过数据。

6. 数据 mixture 与去重

sampler 按权重从 web、code、books、math 或领域数据取样。权重不是原始语料占比的被动反映，而是训练目标的一部分。重复数据会让少数文本获得过量 gradient votes，增加 memorization 并浪费 compute；过滤过强又会丢掉稀有语言或专业知识。高质量小域可被 upsample，但过多 epoch 会过拟合。数据 provenance、dedup、contamination 检查与 held-out eval 是 recipe 的一部分。

for step in schedule:
    zero_grad()
    for microbatch in accumulate(global_batch):
        loss = model(microbatch) / accumulation_steps
        loss.backward()
    all_reduce_gradients()
    clip_global_norm(threshold)
    adamw_step(lr=lr_schedule(step), weight_decay=wd)
    if validation_or_checkpoint(step): persist_and_measure()
04

必要数学：update 与 compute allocation

AdamW update

mₜ=β₁mₜ₋₁+(1−β₁)gₜ;   vₜ=β₂vₜ₋₁+(1−β₂)gₜ²
θₜ₊₁=(1−ηₜλ)θₜ − ηₜ · m̂ₜ/(√v̂ₜ+ε)

gₜ 是当前 gradient，mₜ/vₜ 是其一阶/二阶指数移动平均，β₁/β₂ 控制记忆长度；帽子表示早期 bias correction。ηₜ 是当前 learning rate，λ 是 decoupled weight decay，ε 防止除零。直觉上，持续同向的 gradient 累积 momentum；近期波动大的参数被较大 v 缩小步长。工程意义是 optimizer 有状态：只保存 weights 不能无损恢复训练。

Gradient clipping

g′ = g · min(1, τ / ||g||₂)

τ 是 clipping threshold。若 norm 未超过阈值，gradient 不变；超过时整体缩放到 τ。这不同于逐元素截断，后者会扭曲方向。监控 clip fraction 能区分偶发 outlier 与长期 learning-rate/data 问题。

训练 compute 的粗略账本

C ≈ 6ND

N 是 non-embedding parameters，D 是训练 tokens，C 是 dense Transformer training FLOPs 的常用数量级近似；系数 6 粗略包含 forward 与 backward。它忽略 attention 的序列长度项、稀疏/MoE、embedding、硬件利用率和通信，不能用于精确账单，但能暴露固定 compute 下的核心选择：增大 N 就必须减少 D，反之亦然。

Kaplan 等报告 loss 随 model size、dataset size 和 compute 呈平滑 power law；Hoffmann 等在其更广实验中发现，当固定 compute 时，model parameters 与 training tokens 应更均衡地增长，许多大模型训练 token 不足。这里的事实边界是：论文拟合的是特定架构、数据与 loss 的 empirical law；“compute-optimal”意为在该预算下最小化预测 loss，不自动等于最小推理成本、最佳 Agent 成功率或最安全模型。

05

对 Agent 系统的影响

1. Model size 不是能力 provenance

参数量与训练 compute 不能告诉你模型看过多少 code、tool traces、错误恢复或特定语言。两个同尺寸模型的 data mixture 与 post-training 可完全不同。Agent 选型应同时看 target workflow eval、context/latency/cost 与模型卡披露，而不是用参数量代替证据。

2. Domain continued pretraining 有遗忘与污染成本

在企业代码或文档上继续预训练能调整领域 token distribution，但 learning rate、数据重复和 mixture 权重不当会过拟合、损害通用能力或记住敏感文本。需要保留通用 replay data、独立 validation、canary prompts 和隐私治理。它也不会自动学会实时权限；runtime authorization 仍外置。

3. Agent traces 是训练数据，不是天然真相

把生产轨迹回灌可以增加 tool schema 与恢复模式覆盖，但轨迹包含旧模型错误、用户 PII、tool injection 和偶然成功。先做 provenance、去重、redaction、结果验证和 outcome filtering。否则 optimizer 会忠实强化系统过去的坏习惯。

4. Scaling 提高平均能力，不消除 tail risk

loss 改善可能使更多工具调用正确，却不保证罕见 destructive action、long-horizon recovery 或新 schema。随模型升级保留固定 regression set，并增加真实 rollout distribution；报告按风险分层的 pass rate，而非一个总体 benchmark。

5. 训练与 serving economics 要共同优化

compute-optimal checkpoint 可能参数更大、推理更贵。对高调用量 Agent，稍小但训练 token 更多的模型可能以相近能力换取更低 latency；routing 可以把常规步骤交给小模型、关键规划交给大模型。最终目标应是每个成功任务的总成本，而非最低 pretraining loss。

6. Ablation 才能回答 recipe 因果

一条训练曲线同时混入数据、seed、batch、schedule 和代码版本，不能凭最终 checkpoint 的差异断言“代码数据提升了工具能力”。有预算时使用小规模 proxy run 或 controlled ablation，一次只改变一个因素；记录 consumed-token lineage、配置哈希和 checkpoint eval。超大训练无法完全重复时，至少在扩容前验证趋势、在训练中安排固定 probe，并为异常保留可定位的 batch 与系统 telemetry。否则团队得到的是相关性故事，而不是可复用的训练知识。

06

取舍与失败模式

大 batch vs 泛化与新鲜 gradient：大 batch 提高硬件效率、降低噪声，却减少固定 token budget 下的 update 次数；超过 critical batch 后收益递减。不是越大越好，需共同调 learning rate 与 schedule。

高 learning rate vs 稳定：过低浪费 compute、停在次优区域；过高产生 loss spike 或不可逆损坏。warmup、clipping 和 rollback 只降低风险，不能替代 batch/data 诊断。

Weight decay vs capacity：适度收缩可改善优化与泛化；过强会持续擦除参数幅度。对 normalization、bias 等参数是否 decay 常需分组配置。

更多 token vs 更好 token：重复低质量 token 可降低其域内 loss，却占用 compute 并放大偏差。质量过滤提高平均信号，但过滤器自身带文化/语言偏差。数据 mixture 是多目标治理，不是单一质量分。

Scaling-law 外推：power law 在观测区间内有用，跨架构、tokenizer、数据质量、context length 或 post-training 外推可能失效。涌现式 benchmark 跳变也可能来自指标阈值，不应从平滑 loss 曲线直接承诺产品能力。即使整体趋势稳定，具体能力也可能受少量数据域、提示格式和评测污染支配；外推前应核对训练边界，并用目标任务上的小规模 checkpoint 验证斜率是否仍然成立。

07

可复用判断

  • objective 给方向；AdamW、batch、clipping 与 schedule 决定每次真实 parameter update。
  • optimizer 是持久状态机；weights、moments、step/token counter 与 sampler 状态共同决定可恢复性。
  • 数据 mixture 与去重改变每类样本获得的 gradient 权重，因此是能力与风险设计的一部分。
  • C≈6ND 只提供 dense training 的粗略 compute 直觉；compute-optimal loss 不等于最佳 Agent 或最低 serving 成本。
  • 参数量和 average loss 不能替代 tool-use、恢复、权限边界与长轨迹的闭环 eval。

How Does a Gradient Become Model Capability?

Open up AdamW, learning-rate schedules, batches, gradient clipping, data mixtures, and compute-optimal scaling to see how a training recipe determines what an LLM learns.

2026-09-1220 min readLLM training / AdamW / Scaling laws / Data mixture / Compute budget
01

Today's proposition

Cross-entropy from the previous installment specifies only a direction of improvement: raise the probability of the observed next token. It does not determine how far parameters move, how many examples are combined into one direction, which data appears more often, or whether a fixed compute budget should buy a larger model or more training tokens. The resulting model is determined by the combination of objective × optimizer × schedule × data mixture × compute allocation.

Training does not write facts into a database one record at a time. Every batch produces a noisy vector in a very high-dimensional parameter space. The optimizer combines the current gradient with running statistics and emits a parameter update. Hundreds of thousands of updates jointly reshape representations and conditional distributions. Two runs with the same architecture and token count can yield very different checkpoints when one uses an unstable learning rate, organizes batches differently, or allows low-quality repeated text to overwhelm high-signal code and reasoning examples.

Core judgment: a scaling law describes how average loss changes with model size, data, and compute inside a measured regime. It is not a law that “more parameters automatically produce better tool use.” The training recipe controls whether compute becomes transferable capability; an agent’s concrete reliability still requires task-level, closed-loop evaluation.
02

Continue from cross-entropy

The previous installment stopped at loss.backward(), where automatic differentiation provides a gradient for every parameter. An agent-runtime analogy is useful: loss resembles a verifier’s local error signal, and the gradient is a proposed direction over all parameters, but neither has yet created a side effect. The optimizer acts more like execution policy. It decides the actual update size and preserves cross-step state such as momentum.

The differences matter too. An agent verifier can report an interpretable business error. A gradient is only the local derivative of loss with respect to parameters; it contains no label saying “this is a factual update” or “this is a safety rule.” Gradients from code, news, and chat examples are added in the same parameter space. They can reinforce or conflict with one another. The data sampler therefore decides which objectives receive more frequent votes.

03

Mechanism: one training recipe

1. Global batches and gradient accumulation

The full global batch rarely fits in accelerator memory. Training divides it into per-device microbatches, runs several forward and backward passes, accumulates gradients, and synchronizes before an update. Global batch is approximately microbatch × accumulation steps × data-parallel workers. A larger batch reduces gradient variance and improves parallel efficiency, but additional examples eventually provide diminishing new information. Optimization dynamics also change if the learning rate is not adjusted appropriately.

2. Gradient clipping

Long sequences or anomalous batches can produce a very large gradient norm. Global-norm clipping rescales all gradients proportionally when the norm exceeds a threshold, preserving direction. It bounds the raw gradient norm entering the optimizer. AdamW still applies historical moments, adaptive normalization, and decay, so the same threshold does not directly bound the parameter-update norm. Clipping is a stability mechanism, not a repair for corrupt data or an incorrect loss. A threshold that is too low suppresses ordinary learning signal on many steps.

3. AdamW state

Adam maintains first-moment state m and second-moment state v for every parameter. The first smooths noisy gradients; the second adaptively scales updates according to recent squared gradients. AdamW decouples weight decay from the loss gradient and shrinks parameters directly, avoiding the interaction between an L2 penalty and Adam’s adaptive normalization. The cost is memory: optimizer states are commonly stored at relatively high precision and can consume multiples of parameter memory, motivating state sharding at scale.

4. Warmup, peak, and decay

Optimizer moments are poorly established at the beginning, so immediately applying the peak learning rate can destabilize training. Recipes commonly use linear warmup, a peak or plateau region, and cosine or linear decay so late updates become smaller. Whether a schedule counts steps or tokens, and whether checkpoint recovery restores it exactly, affects the final model. Blindly continuing after a loss spike can carry damaged optimizer state forward; robust runs need checkpoints, data-batch attribution, and rollback policy.

5. Mixed precision and distributed synchronization

Large models commonly use BF16 or FP16 for matrix operations while retaining selected master weights, moments, or accumulators at higher precision. Lower precision improves throughput and memory use but introduces overflow, underflow, and rounding risk. FP16 commonly uses loss scaling to prevent tiny gradients from underflowing; BF16’s wider exponent range usually avoids that requirement, and loss scaling does not generally repair activation overflow. Data-parallel workers normally consume distinct microbatches and all-reduce their gradients into the global-batch gradient. Failure occurs when a collective is incomplete or workers disagree on model version, step, scale, or scheduler state—not because their samples differ. Tensor and pipeline parallelism instead split one model across devices. Faithful checkpoints therefore include optimizer, scheduler, random-number, sampler, and consumed-token state—not weights alone—so recovery neither repeats nor silently skips data.

6. Data mixtures and deduplication

A sampler draws from web, code, books, mathematics, and domain corpora according to explicit weights. Those weights are not a passive reflection of raw corpus sizes; they are part of the learning objective. Duplicates give selected text excessive gradient votes, increase memorization, and waste compute. Over-aggressive filtering can erase rare languages or specialized knowledge. A small high-quality domain can be upsampled, but repeated epochs may overfit it. Provenance, deduplication, contamination checks, and held-out evaluations belong inside the recipe.

04

Essential math: updates and compute allocation

The AdamW update

mₜ=β₁mₜ₋₁+(1−β₁)gₜ;   vₜ=β₂vₜ₋₁+(1−β₂)gₜ²
θₜ₊₁=(1−ηₜλ)θₜ − ηₜ · m̂ₜ/(√v̂ₜ+ε)

gₜ is the current gradient; mₜ and vₜ are exponential moving averages of its first and second moments; β₁ and β₂ determine memory length. Hats denote early-step bias correction. ηₜ is the current learning rate, λ is decoupled weight decay, and ε prevents division by zero. Intuitively, persistent gradients build momentum while a large recent squared gradient reduces the adaptive step. The engineering implication is that the optimizer is stateful: weights alone cannot resume training faithfully.

Gradient clipping

g′ = g · min(1, τ / ||g||₂)

τ is the clipping threshold. If the norm is below it, the gradient is unchanged; otherwise the entire vector is scaled to norm τ. This differs from clipping each element, which distorts direction. Tracking the fraction of clipped steps helps separate occasional outliers from a persistent learning-rate or data problem.

A rough training-compute ledger

C ≈ 6ND

N is the number of non-embedding parameters, D is the number of training tokens, and C is a commonly used order-of-magnitude approximation for dense Transformer training FLOPs. The factor six roughly represents forward and backward work. It omits sequence-length effects in attention, sparse or mixture-of-experts routing, embeddings, hardware utilization, and communication. It is not an exact bill, but it exposes the central fixed-compute choice: increasing N requires reducing D, or vice versa.

Kaplan and colleagues reported smooth power-law relationships between loss and model size, dataset size, and compute. Hoffmann and colleagues, using a broader experimental sweep, reported that compute-optimal training should grow parameter count and training tokens more evenly, concluding that many large models had been undertrained. The boundary of those claims matters: the papers fit empirical laws for particular architectures, data, and prediction losses. “Compute optimal” means minimizing predictive loss under the studied budget, not automatically minimizing inference cost, maximizing agent success, or producing the safest model.

05

Implications for agent systems

1. Model size is not capability provenance

Parameter count and training compute do not reveal how much code, tool-use trace data, error recovery, or a particular language the model saw. Two models of equal size can use radically different mixtures and post-training. Agent model selection should combine workflow-specific evaluation with context, latency, cost, and disclosed model-card evidence rather than substituting parameter count for evidence.

2. Domain continued pretraining carries forgetting and contamination costs

Continued pretraining on enterprise code or documents can shift domain token distributions, but an excessive learning rate, repetition, or mixture weight can overfit, damage general capability, or memorize sensitive text. A robust plan includes general replay data, independent validation, canary prompts, and privacy governance. It still does not teach live authorization automatically; runtime policy remains external.

3. Agent traces are training data, not ground truth

Recycling production trajectories can improve coverage of tool schemas and recovery patterns, but traces also contain old-model mistakes, user PII, tool-output injection, and accidental success. Establish provenance, deduplicate, redact, verify outcomes, and filter trajectories before training. Otherwise the optimizer faithfully reinforces the system’s historical bad habits.

4. Scaling improves averages without eliminating tail risk

Lower prediction loss may improve many tool calls while leaving rare destructive actions, long-horizon recovery, or a new schema unreliable. Preserve fixed regression sets across model upgrades and add samples from the live rollout distribution. Report pass rates by risk class instead of collapsing everything into one benchmark.

5. Training and serving economics must be optimized together

A compute-optimal checkpoint may be larger and more expensive to serve. For a high-volume agent, a smaller model trained on more tokens may deliver comparable workflow quality at lower latency. Routing can send routine steps to a smaller model and critical planning to a stronger one. The operational objective is total cost per successful task, not minimum pretraining loss.

6. Ablations establish recipe causality

One training curve combines data, seed, batch, schedule, and code revision, so a final-checkpoint difference cannot by itself prove that code data caused better tool use. When budgets allow, use small proxy runs or controlled ablations that vary one factor. Record consumed-token lineage, configuration hashes, and checkpoint evaluations. When a full run cannot be repeated, validate trends before scaling, schedule fixed probes during training, and retain batch-level and system telemetry for anomaly attribution. Otherwise the organization accumulates correlation stories rather than reusable training knowledge.

06

Trade-offs and failure modes

Large batches versus generalization and fresh gradients: large batches improve hardware efficiency and reduce noise, but produce fewer optimizer updates under a fixed token budget. Beyond a critical batch regime, returns diminish. Bigger is not inherently better; learning rate and schedule must be tuned with batch size.

High learning rates versus stability: a rate that is too low wastes compute and may remain in a poor region; one that is too high causes loss spikes or unrecoverable damage. Warmup, clipping, and rollback reduce risk but do not replace diagnosis of the batch and data.

Weight decay versus capacity: moderate shrinkage can improve optimization and generalization, while excessive decay continuously erases parameter magnitude. Normalization and bias parameters are often configured separately.

More tokens versus better tokens: repeated low-quality tokens can lower loss on their own domain while consuming compute and amplifying bias. Quality filters increase average signal but carry cultural and language biases of their own. A mixture is multi-objective governance, not one universal quality score.

Scaling-law extrapolation: power laws are useful inside measured regimes. They may fail across architecture, tokenizer, data quality, context length, or post-training changes. Abrupt benchmark “emergence” can also reflect metric thresholds, so a smooth loss curve cannot directly support a product-capability promise. Even a stable aggregate trend can be dominated by a small data domain, prompt format, or evaluation contamination for one capability. Check training boundaries and test the slope on target-task checkpoints before extrapolating.

07

Reusable judgments

  • The objective supplies direction; AdamW, batches, clipping, and the schedule determine each actual parameter update.
  • An optimizer is a persistent state machine. Weights, moments, step or token counters, and sampler state jointly determine faithful recovery.
  • Data mixtures and deduplication change the gradient weight assigned to each kind of example, making them part of capability and risk design.
  • C≈6ND gives only a rough intuition for dense training compute. Compute-optimal loss is not equivalent to the best agent or lowest serving cost.
  • Parameter count and average loss cannot replace closed-loop evaluation of tool use, recovery, authorization boundaries, and long trajectories.
08

Primary sources

  • Kingma & Ba, Adam: A Method for Stochastic Optimization — introduces Adam’s first and second moments, adaptive updates, and bias correction.
  • Loshchilov & Hutter, Decoupled Weight Decay Regularization — introduces AdamW’s decoupling of weight decay from the gradient update.
  • Pascanu et al., On the Difficulty of Training Recurrent Neural Networks — a classic treatment of gradient-norm clipping. The paper studies RNNs, while the clipping mechanism is used more broadly in deep learning.
  • Kaplan et al., Scaling Laws for Neural Language Models — reports power-law relationships between loss and model, data, and compute, plus the authors’ compute-allocation conclusion at that time.
  • Hoffmann et al., Training Compute-Optimal Large Language Models — the Chinchilla experiments revise parameter/token allocation and report more balanced compute-optimal scaling.
  • Xie et al., DoReMi: Optimizing Data Mixtures Speeds Up Language Model Pretraining — optimizes domain weights with a proxy model; reported gains are bounded to the paper’s data and experiments.

Connecting optimizer state, data governance, and scaling to agent routing and trace evaluation is editorial engineering analysis, not one deployment prescription directly validated by the cited papers.

09

What is established and where we continue

Established today: a gradient is only a local direction. AdamW moments, the learning-rate schedule, global batch, and clipping determine the actual update. Mixtures and deduplication determine the relative weight of objectives. Fixed compute must be divided between parameters and training tokens, while compute-optimal average loss is not agent-optimal behavior.

Still unresolved: once training produces logits, how does a runtime turn that distribution into a token? How do temperature, greedy decoding, top-k, top-p, seeds, and constrained decoding change randomness, repetition, tool arguments, and reproducibility?

Starting from the mathematics of logit transformation, we will establish the agent-engineering boundary between diversity and determinism—and explain why temperature zero still does not create system-level determinism.
