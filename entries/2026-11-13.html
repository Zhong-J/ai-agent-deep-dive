Agent 什么时候能按下不可撤销的发送键？

从草稿与预演走到真实外发：区分可逆、可补偿和不可逆效果，给提交门绑定当前证据、权限、内容摘要和风险预算，并在未知结果时停止重试。

01

今日命题

一个 Agent 正在准备向一万名客户发送故障公告。它已检索日志、写好草稿，并通过了语言检查。继续查可能发现范围还在变化；立即发送可能减少客户等待，却也可能把错误归因公开。按下“发送”后，删除本地草稿并不能让收件箱里的消息消失。问题不是泛泛的“何时停止搜索”，而是在什么可检验条件下，系统可以从可改写的内部准备跨过真实世界的提交边界？

10 月 10 日讲过研究 Agent 的信息缺口与停止，11 月 2 日讲过主动观察的信息价值，11 月 4 日讲过风险约束下的规划。本篇从这些决策之后继续：将动作按外部效果分类，明确 prepare、commit、verify 三阶段，给不可逆动作设置剩余风险预算、当前授权与具体内容的门。更多信息的期望价值不再足够高，只是可能考虑行动的一个理由；它不能替代验收、权限与最坏后果约束。

核心判断：“准备完成”不等于“获准提交”，“请求发出”不等于“结果已发生或已核验”。在两道边界上都需要独立证据。
02

把决策门接到已有 Agent 机制

前文建立了当前 goalVersion、逐项进度证据、option typed outcome 和效果账本。提交门把它们接起来：公告草稿只是一份候选 artifact；权威故障范围、用户授权、准确收件人、内容版本和风险评估必须共同支持最终动作。一个子 Agent 说“已审阅”不自动等于目标 owner 批准；模型说“我很确定”也不是可校准的错误概率。

先区分三类效果。可逆是还没离开受控环境的草稿或模拟输出，丢弃即可恢复原状态。可补偿如预订房间：可以再取消，但已占用时间或发出的通知未必能被抹去。不可逆如公开公告或向外部邮箱发送敏感内容：可发更正，却无法保证所有接收者忽略旧信息。分类按真实资源和接收者确定，不按工具名“dryRun”或 HTTP 方法名猜测。一个名叫 preview 的 API 若会创建外部共享链接，仍有副作用。

RFC 9110 把 HTTP safe 与 idempotent 方法的语义区分开：安全方法预期不请求状态改变，幂等强调重复相同请求的预期效果。业务工具可能不遵循这些语义，且“幂等”并不等于“可撤销”。Sagas 研究把长事务拆成步骤与补偿，提醒我们补偿是后续动作而非时间倒流。分布式事务提交论文讨论协调提交的条件，但普通邮件或网页发布系统未必提供真正的 prepare/commit/abort 接口。

03

准备、提交、核验三段控制

1. 将不可逆效果写成精确对象

先定义 effect contract：公告接收者集合、渠道、正文及附件 digest、所引用故障事实与时间窗、不得声称的未知项、可接受发布期限、所需批准和 operation ID 规则。Agent 不能只提出“发公告”；若最终收件人比预演时多一组、正文把“正在调查”改成“已确认根因”，就是新的效果，旧批准不适用。对用户可见的风险是泄露、误导和重复触达，而不仅是工具调用失败。

2. 在准备区尽量做可逆工作

先收集可核验事实、形成草稿、模拟渲染、检查域名/收件人、校验链接、比较内容与证据。可运行无副作用的 dry-run，但要实际验证它不会创建外部资源。准备区保存 artifact 版本与检查结果，允许修改；任何输出从沙箱进入共享空间都需要重新分类。准备阶段可并行开展观察，但不因“更多 worker 同意”就跳过来源去重和权威读回。

3. 提交门做三选一，而非一个布尔按钮

若缺少某个会改变行动的权威观察，而且还能在期限内取得，返回 observe_more，并指向具体来源。若当前证据与目标吻合、授权和内容检查通过、风险预算仍足够，返回 commit_ready。若关键条件未知、上限风险越界或剩余时间不足以核实，返回 hold/escalate，明确需要谁决定或如何缩小效果。停止检索不是自动批准：在无法补证时也可能必须弃权。

4. 在真正派发前重新冻结动作

门控记录 goalVersion、证据版本、payload digest、收件人、审批、风险评估版本和派发许可期限。broker 在执行点重验这些字段及当前资源权限。若内容在审阅后被模型改动，旧 gate result 失效，必须重新审阅；若收件人列表变化，也不能沿用旧 idempotency key。一次性 permit 或稳定的业务操作 ID 防止两个并发 attempt 同时发送。若外部服务没有可核验的幂等接口，runtime 应按单写者约束收紧并对失败保守处理。

5. 认识提交点的真实位置

本地标记“prepared”不会阻止外部系统在 API 请求到达后立即生效。不能把邮件服务叫成两阶段提交参与者，除非它确实提供可隔离的 prepare 与原子 commit/abort。派发后若超时，可能已送达；状态是 outcome_unknown，不能因为“重试可能更快”就再发送。runtime 按 operation ID 或外部记录核对；未决效果拥有 owner、期限和对用户如实可见的状态。

6. 核验与补救遵循效果类型

权威读回证实公告发布、收件人集合及内容版本，才可报告 succeeded_verified。若部分渠道成功、部分失败，返回 partial_verified，不把一个绿色状态覆盖全局。可补偿动作的补偿也需单独授权与核验；不可逆公告的更正要说明原消息仍可能被阅读。结束时将使用的风险预算、审批与实际效果写入审计链，为下一次发布提供经验，但不能把本次侥幸没出事当永久降低门槛的证据。

candidate = prepare_effect(goal, evidence, recipients, payload)
decision = commit_gate(candidate, current_policy, risk_budget)
if decision == OBSERVE_MORE: return request_named_observation()
if decision != COMMIT_READY: return hold_or_escalate(decision)
frozen = bind_digest_and_approval(candidate)
operation = dispatch_once_if_current(frozen)
return verify_or_reconcile(operation.id)

这段伪代码和三选一门是编辑性工程设计；它们不声称外部发送工具天然支持事务提交。

04

风险预算和硬上限

给提交门一个粗略但可审计的剩余风险核算。设故障类型 i 的发生概率上界为 pᵢ、损失为 Lᵢ，则候选动作 a 的期望损失上界可写为：

RiskUpper(a) = Σᵢ pᵢ·Lᵢ

pᵢ 来自经过校准的历史案例、环境测试或保守专家估计，而不是模型自报 confidence；Lᵢ 包含误发、泄露、重复发送和延迟的业务后果。它是一个风险记账近似：尾部严重损失不能仅被很小的平均概率“冲淡”，还要有独立的硬禁令或最大损失门。若概率无法可靠界定，应标 unknown 并升级，而不是填一个方便通过的数字。

设任务允许的总风险预算 B，已提交动作消耗的风险上界合计为 R_used。新动作的预算门是：

R_used + RiskUpper(a) ≤ B ∧ HardConstraints(a)

R_used 只统计已接受真实效果的预算消耗；准备草稿不按发送风险扣账。HardConstraints 包含当前权限、目标版本、批准、收件人范围及不可逾越的安全限制。即使预算仍有余额，硬约束不满足也不能执行。相反，预算耗尽时可以收窄动作，例如先给内部审批人一份只读草稿，而非对外发送。预算值由业务 owner 设定，公式不提供普适数字。

继续观察的选择可借用前文的信息价值框架，但此处有额外条件：观察必须在提交期限前改变可执行选择，且不能自身触发不可接受效果。若没有这样的观察，决策可能是提交，也可能是暂停，取决于上述门，而非自动“搜索结束即执行”。

05

对 Agent 系统的影响

能力与延迟

分段准备让模型在低风险区发挥生成和调查能力，在提交点由可复现条件接管。预演、收件人核对与权威事实验证增加延迟，但能减少更正公告和人工补救的代价。对紧急场景，可降低公告的主张强度，先发布“我们正在调查”的受限内容，而不是因为期限逼近就编造根因。

可观察性

trace 应连接候选内容 digest、来源证据、风险预算、审批、提交门 verdict、资源 operation ID 与最终读回。这样可以分析误发是证据错、内容漂移、权限绕过还是重复派发。用户界面不必显示一个抽象“风险分”，但应说明本次是准备中、等待观察、等待批准、发送状态未知还是已核验送达。

06

取舍、评测与失败模式

过度预演：反复检查可消耗关键时间，且外部世界在检查后继续变化。门控应绑定具体版本与有效期，并只对会影响效果的变化失效。收件人变更是关键，文案中的无关空格或许不是；但判断“无关”需要明确规范化规则，不能让模型随意忽略差异。

伪事务感：本地 prepare 并非数据库两阶段提交；普通 API 未必支持锁定收件人、隔离资源或原子 abort。把“准备好了”误当远端承诺，会让系统在崩溃后重复发送。若服务提供真实事务/幂等语义，应按其官方合同使用；否则保持单写者、稳定操作 ID 和结果核对。

补偿幻觉：预订取消可能释放资源，但通知已经泄露信息；公告更正不保证所有读者看到更正。对外输出应描述可补偿动作的残余伤害和不可逆边界，而非把 saga compensation 翻译成“撤销”。如果没有安全补救，提交门应更严格或交人。

评测：注入检查后收件人变化、内容摘要变化、审批撤回、同一 operation 并发重放、远端超时后实际成功、部分渠道送达、无幂等接口与期限逼近的情形。分别测误放行率、误阻断率、重复副作用率、unknown 核对时长、事实错误率、延迟和人工接管率。离线只看最终文本会遗漏真实副作用；模拟环境应保留能验证的外部状态。发布门要求高风险轨迹中没有未经批准的提交，未知发送不自动重试，补偿与核对责任明确。论文和规范提供机制边界，不提供本系统的通用风险阈值。

07

可以带走的判断

  1. 把准备、提交、核验分开；草稿可撤销，已送达公告不能靠删草稿撤回。
  2. 提交门返回追加观察、可提交或暂停升级；搜索结束本身不是批准。
  3. 风险预算是必要核算，当前目标、权限、内容摘要和灾难性后果硬约束不能被平均风险冲淡。
  4. 远端超时是 outcome_unknown；先核对，再决定重试或补救。

When May an Agent Cross an Irreversible Commit Boundary?

Move from draft and preview to real-world delivery: classify reversible, compensatable, and irreversible effects; bind a commit gate to current evidence, authority, content digest, and risk budget; and stop retries on unknown outcomes.

2026-11-1320 min readIrreversible actions / Commit gates / Risk budget / Effect verification / Agent reliability
01

Today's proposition

An agent is preparing an outage notice for ten thousand customers. It has searched logs, written a draft, and passed a language review. More investigation might reveal that impact scope is still changing; sending now could reduce customer uncertainty but also publish a false attribution. Once the send action crosses into customer inboxes, deleting the local draft does not make the message disappear. The question is more specific than “when should research stop?” It is under which checkable conditions may the system cross from revisable preparation into a real-world commit?

October 10 covered research gaps and stopping, November 2 covered the value of active observation, and November 4 covered risk-constrained planning. We start after those choices. Classify actions by external effect, separate prepare, commit, and verify, then require a residual-risk budget, current authority, and an exact content gate for an irreversible action. Low expected value from another observation may make action worth considering. It does not replace acceptance criteria, permission, or a worst-consequence constraint.

Core judgment: “prepared” is not “authorized to commit,” and “request sent” is not “effect happened and was verified.” Each boundary needs its own evidence.
02

Connect the gate to mechanisms you know

Earlier issues established a current goalVersion, condition-by-condition progress evidence, typed option outcomes, and an effect ledger. A commit gate connects them. The notice draft is only a candidate artifact. Authoritative impact scope, user authority, exact recipients, content version, and risk assessment must jointly support the final effect. A child agent reporting “reviewed” is not automatically approval from the goal owner, and a model's “high confidence” is not a calibrated error probability.

Classify effects in three groups. Reversible work remains inside a controlled environment, such as a draft or simulation that can be discarded. Compensatable work, such as a room booking, can be followed by cancellation, but occupied time and notifications may not be erased. Irreversible work, such as a public notice or sensitive email, can be corrected but the original information may already have been copied. Classification depends on the real resource and recipients, not a tool name like dryRun or an HTTP method. A preview API that creates an external sharing link has a side effect.

RFC 9110 distinguishes HTTP safe from idempotent semantics: a safe method is not intended to request state change, while idempotence concerns the intended effect of repeating the same request. Business tools may not honor those semantics, and idempotent does not mean undoable. The Sagas paper models long transactions with compensating steps, illustrating that compensation is another action rather than time travel. Work on distributed transaction commit explains coordinated commits, but an ordinary email or publishing service may not expose a real prepare/commit/abort protocol.

03

Three stages: prepare, commit, verify

1. Define the irreversible effect precisely

Write an effect contract first: recipient set, channel, body and attachment digest, cited incident facts and time window, unknowns that must not be stated as confirmed, publication deadline, required approval, and operation-ID rule. “Send a notice” is not specific enough. If final recipients include another group or the body changes from “investigating” to “root cause confirmed” after preview, the effect changed and old approval does not apply. User-facing risk includes disclosure, misinformation, and duplicate contact, not merely a failed tool call.

2. Keep as much work as possible in a reversible preparation area

Collect verified facts, draft the notice, preview rendering, check domains and recipients, validate links, and compare text with its evidence. A dry run is useful only after confirming that it creates no externally visible resource. The preparation area stores artifact versions and check results and remains editable. Any output leaving a sandbox for a shared location must be reclassified. Observations may be gathered concurrently, but agreement among more workers does not remove the need for source deduplication and authoritative readback.

3. Make the commit gate a three-way decision

If a named authoritative observation can still change the action and be obtained before the deadline, return observe_more with that source. If present evidence fits the goal, current authority and content checks pass, and the risk budget remains sufficient, return commit_ready. If a necessary condition is unknown, the upper risk bound is exceeded, or time is too short to verify, return hold or escalate with the responsible decision-maker or a smaller effect. Stopping retrieval is not automatic approval. When evidence cannot be obtained, abstention may be the correct result.

4. Freeze and recheck the actual action at dispatch

The gate records goalVersion, evidence versions, payload digest, recipients, approval, risk-assessment version, and permit expiry. The broker rechecks these and current resource authority at execution. If the model edits text after review, the old gate result expires and the new text needs review. A changed recipient set also cannot reuse the old idempotency key. A one-use permit or stable business operation ID prevents two concurrent attempts from both sending. Without a verifiable idempotency interface at the external service, the runtime must use stricter single-writer control and conservative failure handling.

5. Locate the real commitment point

A local “prepared” marker does not stop an external service from acting when its API receives a request. The mail service is not a two-phase-commit participant unless it actually offers isolated prepare and atomic commit or abort semantics. A timeout after dispatch may mean the notice was delivered. Its outcome is unknown; “a retry might be faster” is not enough to send it again. Reconcile against operation ID or external records, and retain an owner, deadline, and honest user-visible status for the unresolved effect.

6. Verify and repair according to effect type

Report succeeded_verified only after authoritative readback confirms publication, recipient set, and content version. If one channel succeeded and another failed, return partial_verified rather than let one green status cover the whole action. Compensation for a compensatable effect needs separate authority and verification. A correction to an irreversible notice must disclose that the original may still be read. Record consumed risk budget, approvals, and actual effects in the audit trail. One lucky execution is not evidence that the gate can be permanently weakened.

candidate = prepare_effect(goal, evidence, recipients, payload)
decision = commit_gate(candidate, current_policy, risk_budget)
if decision == OBSERVE_MORE: return request_named_observation()
if decision != COMMIT_READY: return hold_or_escalate(decision)
frozen = bind_digest_and_approval(candidate)
operation = dispatch_once_if_current(frozen)
return verify_or_reconcile(operation.id)

The pseudocode and three-way gate are editorial engineering design. They do not imply that outbound tools naturally support transactional commit.

04

Risk budget and hard limits

Give the commit gate an auditable, approximate residual-risk account. Let pᵢ be an upper estimate of the probability of failure mode i and Lᵢ its loss. An upper expected-loss estimate for candidate action a is:

RiskUpper(a) = Σᵢ pᵢ·Lᵢ

pᵢ should come from calibrated historical cases, environment tests, or conservative expert judgment, not model self-reported confidence. Lᵢ includes business consequences of false notices, disclosure, duplicate sending, and delay. This is an accounting approximation. A rare catastrophic loss cannot be made acceptable merely by averaging it down; it also needs an independent hard prohibition or maximum-loss gate. If probabilities cannot be bounded credibly, mark them unknown and escalate instead of inserting convenient numbers.

Let B be the task's total risk budget and R_used the upper-risk amount consumed by already accepted effects. The gate for a new action is:

R_used + RiskUpper(a) ≤ B ∧ HardConstraints(a)

R_used concerns committed external effects; drafting alone does not consume the risk of sending. HardConstraints includes current authority, goal version, approval, recipient scope, and non-negotiable safety conditions. A remaining budget does not permit an action that fails a hard constraint. If budget is exhausted, a smaller action may still be possible, such as supplying a read-only draft to an internal reviewer instead of mailing customers. A business owner sets the budget; the formula provides no universal number.

The choice to observe more may borrow the information-value framework covered earlier, with an added constraint: the observation must be capable of changing the choice before the commit deadline and must not itself create an unacceptable effect. If no such observation exists, the result may be commit or hold depending on the gates above. “Search finished” is never an automatic send signal.

05

Implications for agent systems

Capability and latency

Staged preparation lets a model generate and investigate in a lower-risk area while reproducible checks govern the commit point. Preview, recipient inspection, and authoritative fact verification add latency but may avoid the much greater cost of corrective notices and human repair. In urgent situations, reduce the strength of the claim and send a scoped “we are investigating” statement if authorized, rather than invent a root cause as a deadline approaches.

Observability

A trace should connect candidate-content digest, source evidence, risk budget, approval, commit-gate verdict, resource operation ID, and final readback. That allows analysis of whether a wrong send came from faulty evidence, content drift, authority bypass, or duplicate dispatch. The user interface need not show an abstract “risk score,” but it should distinguish preparing, awaiting observation, awaiting approval, unknown send status, and verified delivery.

06

Trade-offs, evaluation, and failure modes

Over-preparation: repeated checks consume time, and the world keeps changing after each check. Bind gate results to concrete versions and validity periods, invalidating only changes that affect the effect. A recipient change is material; an unrelated whitespace change may not be. But “unrelated” requires an explicit normalization rule, not the model's discretionary judgment.

False transaction analogy: a local prepare step is not database two-phase commit. An ordinary API may offer no locked recipients, isolated resource, or atomic abort. Mistaking “prepared” for a remote promise creates duplicate sends after crashes. If a service actually offers transactional or idempotent semantics, use its official contract. Otherwise retain single-writer control, a stable operation ID, and outcome reconciliation.

Compensation illusion: cancelling a booking may free a resource after a notice has already disclosed information; correcting an announcement cannot guarantee readers see the correction. Describe residual harm and irreversible boundaries instead of translating saga compensation as “undo.” If safe repair is unavailable, the commit gate must be stricter or hand off to a person.

Evaluation: inject a recipient change after preview, a changed payload digest, withdrawn approval, concurrent replay of one operation, a remote timeout followed by actual success, partial channel delivery, no idempotency interface, and an approaching deadline. Measure false allowance, false blocking, duplicate effects, time to reconcile unknown outcomes, factual errors, latency, and human takeover separately. Offline evaluation of final prose misses real side effects; a simulated environment needs inspectable external state. A release gate requires no unapproved commit in high-risk traces, no automatic retry on unknown sends, and clear ownership for compensation and reconciliation. Papers and specifications define mechanisms, not universal risk thresholds for this system.

07

Reusable judgments

  1. Separate prepare, commit, and verify. A draft can be discarded; a delivered notice cannot be recalled by deleting the draft.
  2. The gate returns observe more, commit ready, or hold and escalate. Exhausting research is not approval.
  3. A risk budget is necessary accounting, but current goal, authority, payload digest, and catastrophic hard constraints cannot be averaged away.
  4. A remote timeout yields outcome_unknown. Reconcile before any retry or repair.
08

Sources and evidence boundaries

  • RFC 9110, HTTP Semantics — standard distinction between safe and idempotent methods; it does not make arbitrary business tools undoable.
  • Garcia-Molina & Salem, Sagas — original work on long transactions and compensation; compensation does not erase an external effect that occurred.
  • Gray & Lamport, Consensus on Transaction Commit — original research on coordinated commit; this article does not claim that mail or notice services implement the protocol.
  • Amodei et al., Concrete Problems in AI Safety — author research on negative side effects and safe exploration; the business commit gate and thresholds here are engineering extensions.
