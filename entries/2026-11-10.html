Dynamic Capability Boundaries Internals · 第 2/2 篇

权限不够时，Agent 怎样升级而不自己批准自己？

从 hold/rebind/escalate 走到可审查的升级请求、受限短期许可、执行点重验与到期核对。审批应绑定具体效果，不能变成一句泛泛的“允许继续”。

01

今日命题

昨天的 Agent 在 t₀ 制订计划，t₁ 派发前却发现财务数据权限已撤销、工具合同变了。runtime 正确返回 hold、rebind 或 blocked。现在业务确实需要一个例外：用户想把特定报告发送给特定审计人，Agent 当前没有外发权限。它能不能问一句“请允许我继续”，得到“好”，再自行调用发送工具？不能把这段对话当成通用授权。“继续”没说明收件人、数据范围、具体效果、有效期和发生变化时该怎么办。

今天建立的是一条可审查升级链：Agent 提出最小必要动作和证据；独立批准者在自己权限内拒绝或授予受限许可；broker 将许可绑定到规范化动作、目标版本和短期窗口；资源系统在执行点再次强制检查；已发出的效果以 operation ID 核验，许可到期与撤销只阻断未来动作。请求者、批准者、执行者和效果核验者的职责不同。

10 月 3 日已讲过 prompt injection 攻击权限边界和“human approval 绑定 effect”。本篇不重复 taint 传播或能力 token 的概览；它具体展开当能力漂移使原计划失效后，升级请求怎样形成、审批如何避免范围漂移、临时许可如何关闭，以及拒绝时系统如何继续有用地服务用户。

技术命题：审批是针对一组可枚举动作的决策记录，而非交给模型的广域权限。批准也不等于成功；成功仍需资源侧读回。
02

承接 Hold、Rebind、Escalate

上一篇用能力快照保留计划来历，用当前执行门判断是否可行动。现在把三个“不能直接派发”的结果细分。hold 表示授权服务或资源状态未知，先等待或换可核验来源，不向人请求一个未知边界的永久放行。rebind 表示工具语义或参数版本改变，重新生成规范化提案并校验目标，若权限没变也不应无故索要新权限。escalate 仅用于明确缺少某项必要权限且任务目标仍有效的情况。明确 revoked 不自动变成 escalate：撤权可能是有意政策，必须先识别拒绝原因与可用替代。

OAuth Rich Authorization Requests 提供结构化授权细节的标准语义；OAuth Token Exchange 描述令牌交换和代表他人行动的协议框架。但标准没有替业务规定“谁能批准外发这份报告”。Macaroons 论文展示附加 caveat 可收窄凭据的技术思想。本文借这些原理设计 Agent 控制流，不声称任何现有产品默认具备单次、按效果授权。NIST Zero Trust 的当前上下文评估也支持执行点重验，而不是信任昨天的审批截图。

重要的分界：批准者只能在其自身 authority 范围内批准；Agent 只能提案，不能通过选择批准者、改写说明或拆分请求来扩大这条上限。如果一个更小的只读方案已能满足目标，应优先展示它。升级是稀缺、可审计的路径，不是每遇到工具错误就弹一次许可框。

03

受限升级的执行链

1. 将需求转成规范化请求

请求对象包含 taskId、intentVersion、principal、操作类型、资源 ID、准确收件人、输出数据摘要、允许的字段或行范围、最大次数与金额、截止时间、必要来源证据、若拒绝的替代方案，以及对外可见副作用。报告发送例中，用户说“发给审计人”仍需确认邮件地址是否在允许域、附件版本是否已核对、是否包含客户敏感数据。模型可起草理由，但这些字段由 runtime 从受信数据和用户意图中规范化；请求文本不得暗藏额外工具或“顺便再发给团队”。

2. 审批界面呈现差异与后果

批准者看到原任务、为什么当前许可不足、所请求动作与已有权限的差异、具体资源/对象/收件人、数据分类、预计外部效果、有效期和可选的更小方案。批准者可拒绝、缩小范围或批准指定版本；不能被迫在“全给”与“任务失败”间二选一。拒绝理由作为结构化 outcome 返回，Agent 可完成允许的部分并说明阻断点，不能换一个 prompt 或工具名重试同一被拒绝动作。审批 UI 中的文档和工具输出属于待审资料，不能代表批准者发指令。

3. 生成受限许可，不交出广域凭据

许可绑定申请的 canonical action digest、intentVersion、批准者和政策版本，限定 audience（可接收许可的 broker/资源服务）、资源、操作、收件人、最大使用次数、有效期和必要的 nonce。允许的动作集合应是申请、批准者权限与政策的交集，而非 Agent 所希望的并集。短期许可或 broker 内部记录均可实现这种合同；不一定向模型暴露令牌。若必须委派给 child，child 的 scope 只能进一步收窄，不能通过 token exchange 隐式扩大。签名或 hash 证明记录未被调包，不证明申请本身合理；批准者判断仍不可省。

4. 派发时比较实际效果与批准效果

broker 规范化最终参数，重新检查当前 principal、资源状态、tool schema、policy epoch、许可未过期且未用尽，并比较动作摘要。若模型把收件人从 A 改为 A+B、把附件从 v3 改为 v4，旧批准失效，即使自然语言仍叫“发送报告”。若工具默认值变化，不能只比较原始 JSON 字符串；应先展开默认值再 fingerprint。资源侧仍执行自己的权限检查，避免 broker 成为唯一防线。审批与 dispatch 之间若授权撤销，返回 blocked，不能以“刚刚批准过”继续。

5. 处理竞态、重放与未知效果

两个并发 attempt 不应重复消费单次许可。broker 对 permitId/nonce 做原子消费或资源侧幂等控制，并把 operation ID 记录到 effect ledger。请求超时但可能已提交，状态是 outcome_unknown；不能因为许可快过期就再发一次。许可到期阻止新 dispatch，不会撤回已送达邮件。真实 effect readback 决定 succeeded_verified、failed、unknown；unknown 有追查 owner 和时限，必要时人工接管。

6. 关闭授权并留下可重放审计链

完成后撤销或自然到期临时许可；未完成的任务也要使许可失效。审计记录连接原计划 snapshot、变化事件、升级理由、替代方案、批准者决策、精确许可范围、dispatch 参数摘要、资源侧状态与撤销时间。批准被拒、用户修改目标、模型或工具再次换版，均开启新 decision，不修改旧批准记录。用户需要看到“未发送、因为许可被拒；已完成允许的汇总；若要发送需新的指定批准”，而不是看到 agent 悄悄切换到另一个外发通道。

request = normalize(intent, action, resources, recipients, limits)
decision = independent_approver.review(request, evidence, alternatives)
if decision.kind != APPROVED: return PARTIAL_OR_BLOCKED(decision)
permit = broker.issue_narrow_grant(request, decision)
gate = live_gate(permit, normalize(actual_call), current_policy)
if gate != ALLOW: return gate
operation = broker.dispatch_once(permit, actual_call)
return verify_effect(operation.id)  // unknown remains owned

这是本文的编辑性工程伪代码；RFC 定义令牌交换、授权细节和撤销等局部协议，不共同定义此 Agent 审批状态机。

04

把许可定义成集合与条件

将具体可执行动作看成集合元素。申请动作集合 R、批准者本身可授权的集合 A、当前政策允许的集合 P，那么真正可授予的集合 G 必须满足：

G ⊆ R ∩ A ∩ P

R 是所请求的资源、操作、收件人与参数组合；A 是批准者权限上限；P 是组织政策。交集表达“每层都允许”，子集允许批准者进一步缩小范围。若 R 中包含两位收件人而 A 只允许一位，G 不会自动补齐另一位。实现时不能拿不相容的“scope 字符串”直接求交集；要先把它们映射到同一套具体动作语义。

即使 a 属于 G，时间和状态也会改变结果。派发门可写为：

Allow(a,t) = [a ∈ G] ∧ [t < expiry] ∧ [usesRemaining > 0] ∧ IntentCurrent ∧ PolicyCurrent ∧ ResourceAuthorizes(a,t)

a 是已规范化动作，t 是派发时刻；expiry 是截止时间；usesRemaining 防重放；IntentCurrent 与 PolicyCurrent 要求目标与政策版本仍匹配；ResourceAuthorizes 是资源服务在当前时刻的强制检查。任一项未知不能当 true。批准记录的 hash 可以绑定这些字段，防止调包，但 hash 不是授权判断本身。工程意义是：人的批准只是必要输入，实时系统门仍决定能否执行。

到期后的在途操作不重新套用 Allow 以推断“从未发生”。它已有 operation ID，应走核验状态机。这样许可生命周期与效果生命周期被明确分开。

05

对 Agent 系统的影响

体验与效率

高质量升级请求让批准者只判断差异和后果，不必重读整段 Agent 对话。批复可缩小范围，Agent 仍可完成部分目标。对低风险只读任务可通过预先定义的窄权限避免频繁弹窗；对外发、财务写入和敏感数据跨边界移动，明确的人类或政策门通常值得延迟成本。

审计与责任

系统能回答“谁要求、谁批准、批准了什么、何时派发、资源实际做了什么、何时失效”。每一跳均可独立核验，而不是从聊天摘要反推。审批者不替模型证明事实，模型也不替审批者决定风险；事实证据、授权决策和效果读回保留各自来源。

06

取舍、失败模式与发布门

审批疲劳：每个小动作都弹窗会诱导机械点击；把整天任务一次性放行又失去边界。按风险与效果分组，允许同一批精确、可枚举的动作共享一个短期许可；超过数量、收件人或数据范围则新决策。不得用“用户已经很烦”作自动扩大权限的理由。

批准与实际动作漂移：附件更新、默认值变化、用户改目标、模型重写参数，都可能使旧许可不再对应新效果。对规范化动作做 digest 和版本绑定，并在 dispatch 重验。仅在 UI 里展示漂亮自然语言摘要、却对实际调用不做比较，是典型 confused-deputy 风险。

撤销延迟：RFC 7009 描述撤销接口，RFC 7662 描述令牌状态查询；两者都不保证某个具体资源系统毫秒级停止所有已发请求。关键写入应由资源侧实施当前政策和幂等门。发现撤销后，broker 立即停止新派发、追踪在途 operation，不把“撤销请求成功”误报为“外部效果全被撤回”。

变更注入评测：测试批准后收件人被模型增加、工具默认值变化、policy epoch 更新、grant 到期、同一 nonce 并发重放、审批者权限被收窄、授权服务离线、在途写入超时与资源返回晚到。分别量化越权放行率、误阻断率、重复副作用率、unknown 核对完成率、审批次数与人工负担。发布门至少要求高风险轨迹中没有未授权派发，拒绝能真正阻断所有替代路径，已提交效果能读回并分配 owner。指标阈值必须按本系统损失设定，不由引用规范自动给出。

07

可以带走的判断

  1. hold、rebind 和 escalate 是不同结果；仅在缺少明确必要权限时提出升级。
  2. 审批对象是规范化的具体效果和短期范围，批准者只能在自己的权限与政策交集内收窄授权。
  3. 派发时比较实际参数与批准版本，资源侧仍做当前授权；模型不得持有广域凭据。
  4. 到期与撤销阻断未来派发，已提交效果继续核对；拒绝要阻断替代通道。

Dynamic Capability Boundaries Internals · Part 2 of 2

When an Agent Needs More Authority, Who Grants It—and for What?

Move from hold, rebind, and escalate to a reviewable request, narrow temporary grant, live dispatch check, and expiry reconciliation. Approval must bind a concrete effect, not a vague instruction to continue.

01

Today's proposition

Yesterday an agent planned at t₀, but before dispatch at t₁ its finance-data grant had been revoked and a tool contract had changed. The runtime correctly returned hold, rebind, or blocked. Now suppose the business goal genuinely requires an exception: the user wants a particular report sent to a named auditor, while the agent lacks outbound authority. Can it ask “may I continue?”, receive “yes,” and then decide on its own how to call the send tool? That exchange is not a general grant. “Continue” does not bind recipients, data scope, effect, expiry, or what happens after another change.

Today's mechanism is a reviewable escalation chain. The agent proposes the least necessary action with evidence. A separate approver denies it or grants a narrow permit within the approver's own authority. A broker binds the permit to a normalized action, intent version, and short time window. The resource system enforces current policy at execution. The resulting effect is checked by operation ID, while expiry and revocation stop future dispatches. Requester, approver, dispatcher, and effect verifier have different responsibilities.

October 3 already covered prompt injection against authority boundaries and the principle of binding human approval to an effect. We do not repeat taint propagation or introduce capability tokens at survey level. Instead we follow a plan invalidated by capability drift: how it becomes a reviewable request, how approval avoids scope drift, how a temporary grant closes, and how the system remains useful after denial.

Technical claim: approval is a decision record over an enumerable set of actions, not broad authority handed to a model. Approval is also not success; success requires authoritative effect readback.
02

Continue from hold, rebind, and escalate

The previous part kept a capability snapshot for plan provenance and used a current dispatch gate for action. Now distinguish three reasons dispatch cannot proceed. Hold means the authorization service or resource state is unknown: wait or use another authoritative check rather than asking a person for a permanent pass across an unknown boundary. Rebind means a tool's semantics or arguments changed: produce a newly normalized proposal and check it against the goal; unchanged authority does not justify asking for broader access. Escalate applies only when a specific necessary grant is missing and the task intent is still current. Explicit revocation does not automatically imply escalation; it may express deliberate policy, so inspect the reason and permitted alternatives first.

OAuth Rich Authorization Requests defines structured authorization details, while OAuth Token Exchange defines a protocol framework for exchanging tokens and acting on behalf of another party. Neither standard decides which person may approve sending this particular report. The Macaroons paper shows a technical pattern in which caveats attenuate a credential. We borrow these ideas for an agent control flow; we do not claim that existing products automatically supply single-use, effect-bound grants. NIST Zero Trust likewise motivates evaluating current context at execution rather than trusting yesterday's approval screenshot.

The boundary is that an approver can grant only within their own authority, while the agent can propose but cannot enlarge that limit by choosing a convenient approver, rewriting the description, or splitting one request into smaller ones. If a narrower read-only alternative meets the goal, show it first. Escalation is a scarce, auditable path, not a permission dialog for every tool error.

03

The execution chain for a narrow upgrade

1. Normalize the need into a concrete request

The request carries taskId, intentVersion, principal, operation type, resource IDs, exact recipients, output-data digest, permitted fields or row scope, maximum uses or amount, deadline, required source evidence, a fallback if denied, and externally visible effects. In the report example, “send to the auditor” still requires checking the address against an allowed domain, the attachment version, and whether customer-sensitive data is included. The model may draft a rationale, but the runtime normalizes these fields from trusted data and the user's intent. The prose request must not smuggle in extra tools or “also copy the team.”

2. Show the difference and consequences to an approver

The approver sees the original task, why current authority is insufficient, the delta between requested and existing access, exact resources, objects and recipients, data classification, expected external effects, expiry, and narrower alternatives. The approver may deny, narrow, or approve one specific version; the interface should not force a choice between “grant everything” and “task failed.” Denial returns as a structured outcome. The agent can complete permitted portions and explain the blocker, but it must not retry the same denied effect under a different prompt or tool name. Documents and tool outputs displayed in the approval interface are material to review, not instructions from the approver.

3. Issue a narrow permit rather than handing out a broad credential

The permit binds a canonical action digest, intentVersion, approver, and policy version. It constrains audience (the broker or resource service that may accept it), resource, operation, recipients, maximum uses, expiry, and a nonce where needed. The permitted action set is the intersection of the request, approver authority, and policy, not the union of what the agent would like to do. A short-lived token or broker-internal record can implement the contract; the model need not see raw credentials. A child delegation may attenuate the scope further, but token exchange must not silently broaden it. A signature or hash proves that a record was not swapped; it does not prove that the request deserved approval.

4. Compare the actual effect with the approved effect at dispatch

The broker normalizes final arguments and rechecks the current principal, resource state, tool schema, policy epoch, permit expiry, remaining uses, and action digest. If the model changes the recipient from A to A+B or replaces attachment v3 with v4, the old approval no longer applies even though the prose still says “send report.” If a tool default changed, comparing raw JSON strings is insufficient: expand defaults before fingerprinting. The resource service still enforces its own policy rather than making the broker the sole defense. A revocation between approval and dispatch yields blocked, not “approved just now, so continue.”

5. Handle races, replay, and unknown effects

Two concurrent attempts must not both consume a single-use permit. The broker atomically consumes permitId and nonce or relies on resource-side idempotency, and records the operation ID in an effect ledger. A timed-out request may have committed; its outcome is unknown. An impending permit expiry is not a reason to send it again. Expiry stops new dispatches but cannot unsend a delivered message. An authoritative effect readback yields succeeded_verified, failed, or unknown. Unknown remains assigned to an investigation owner with a deadline and, where needed, human takeover.

6. Close the grant and retain a replayable audit chain

After completion, revoke the temporary grant or let it expire; an abandoned task must also close it. Audit records link the original planning snapshot, change event, escalation rationale, alternatives, approver decision, exact permit scope, dispatch-argument digest, resource-side state, and revocation time. A denial, changed user intent, or subsequent model or tool version change creates a new decision rather than editing the old approval record. The user should see “not sent because the grant was denied; the permitted summary is complete; sending requires a new specific approval,” not an agent silently switching to another outbound channel.

decision = independent_approver.review(request, evidence, alternatives)
if decision.kind != APPROVED: return PARTIAL_OR_BLOCKED(decision)
permit = broker.issue_narrow_grant(request, decision)
gate = live_gate(permit, normalize(actual_call), current_policy)
if gate != ALLOW: return gate
operation = broker.dispatch_once(permit, actual_call)
return verify_effect(operation.id)  // unknown remains owned

This is editorial engineering pseudocode. The RFCs define local semantics for token exchange, authorization details, and revocation; they do not jointly define this agent approval state machine.

04

Model a permit as a set and a live predicate

Treat each concrete executable action as an element of a set. Let R be requested actions, A the actions the approver may authorize, and P actions current policy permits. The actual grant G must satisfy:

G ⊆ R ∩ A ∩ P

R contains combinations of resources, operations, recipients, and arguments. A is the approver's ceiling; P is organizational policy. Intersection means all three layers permit an action. The subset relation allows the approver to narrow further. If R includes two recipients and A allows one, G does not somehow include the second. An implementation cannot intersect incompatible scope strings directly; each layer must first map to a common concrete-action semantics.

Membership in G is still insufficient because time and state change. A dispatch gate can be written as:

Allow(a,t) = [a ∈ G] ∧ [t < expiry] ∧ [usesRemaining > 0] ∧ IntentCurrent ∧ PolicyCurrent ∧ ResourceAuthorizes(a,t)

a is the normalized action and t the dispatch time. expiry is the deadline; usesRemaining prevents replay. IntentCurrent and PolicyCurrent require matching goal and policy versions. ResourceAuthorizes is live enforcement by the resource service. An unknown condition is not true. A hash can bind these recorded fields against substitution, but a hash is not an authorization decision. Human approval is a necessary input; the current system gate still decides whether execution may occur.

An in-flight operation after expiry must not be retroactively evaluated with Allow to infer that it never happened. It has an operation ID and enters the verification state machine. Permit lifecycle and effect lifecycle are deliberately separate.

05

Implications for agent systems

Experience and efficiency

A well-formed escalation lets an approver review the change and its consequences without rereading an entire agent chat. The approver may narrow the grant, and the agent can still complete a permitted portion of the goal. Predefined narrow grants can avoid frequent dialogs for low-risk reads. For outbound messages, financial writes, and movement of sensitive data across boundaries, an explicit human or policy gate is often worth the latency.

Audit and responsibility

The system can answer who requested, who approved, exactly what was approved, when dispatch occurred, what the resource actually did, and when the grant closed. Every hop can be verified without reconstructing intent from chat summaries. The approver does not prove the model's factual claims, and the model does not decide the approver's risk. Evidence, authorization, and effect readback retain separate provenance.

06

Trade-offs, failure modes, and release gates

Approval fatigue: a dialog for every tiny step teaches people to click mechanically; a blanket grant for the entire day loses the boundary. Group a short list of precise, enumerable effects by risk and allow them one short-lived permit. Exceeding its use count, recipient set, or data scope requires a new decision. An irritated user is not a reason for automatic authority expansion.

Drift between approval and action: an updated attachment, changed tool default, revised user intent, or model-rewritten arguments can make an old permit describe the wrong effect. Bind a digest and versions to the normalized action, then recheck at dispatch. Showing attractive prose in the approval interface while failing to compare the actual call is a classic confused-deputy failure.

Revocation delay: RFC 7009 defines a revocation endpoint and RFC 7662 describes token-state introspection. Neither guarantees that a particular resource system stops every already-dispatched request in milliseconds. Important writes need current resource-side enforcement and idempotency controls. On revocation, the broker stops new dispatches immediately and tracks in-flight operations; “revocation request succeeded” must not be reported as “all external effects were reversed.”

Change-injection evaluation: after approval, add a recipient through model output, change a tool default, advance the policy epoch, expire the grant, replay one nonce concurrently, narrow the approver's authority, take the authorization service offline, time out an in-flight write, and deliver its result late. Measure unauthorized-allow rate, false-block rate, duplicate-effect rate, resolution of unknown outcomes, approval count, and human burden separately. A release gate should require no unauthorized dispatch in high-risk traces, effective denial across alternate paths, and an owner and readback for committed effects. Thresholds depend on this system's losses; no cited specification supplies universal values.

07

Reusable judgments

  1. Hold, rebind, and escalate mean different things. Request an upgrade only for a specific necessary missing grant.
  2. Approval covers normalized concrete effects and a short scope; an approver can narrow only within their own authority and policy.
  3. At dispatch, compare actual arguments with the approved version, while the resource enforces current authority. The model need not hold a broad credential.
  4. Expiry and revocation block future dispatch; committed effects still require reconciliation, and denial must block alternate paths too.

Sources and evidence boundaries

  • RFC 9396, OAuth 2.0 Rich Authorization Requests — standard semantics for structured authorization details; business approval fields here are an editorial design.
  • RFC 8693, OAuth 2.0 Token Exchange — standard framework for exchange and acting on behalf of another party; it does not guarantee least authority by itself.
  • RFC 7519, JSON Web Token — standard aud, exp, and jti claims; this article does not require JWT as the implementation.
  • RFC 7009, Token Revocation and RFC 7662, Token Introspection — revocation and status-query semantics, not guaranteed propagation times for a particular system.
  • Macaroons: Cookies with Contextual Caveats — author research on credential attenuation with caveats; reported performance and deployment claims are bounded to that work.
  • NIST SP 800-207 — official zero-trust architectural guidance motivating contextual access decisions.
