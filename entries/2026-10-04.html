Agent 在 Sandbox 里，为什么仍可能伤到宿主机？

拆解 process/container/VM 边界、capability brokers、ephemeral workspace、browser profile、egress、resource quotas、cleanup 与 escape testing。

2026-10-04约 20 分钟Sandboxing / Computer use / Isolation / Capability broker / Resource quotas
01

今日命题

“代码运行在 sandbox 里”不是一个完整安全结论。子进程可能继承环境变量和 open handles；容器与宿主共享 kernel；browser automation 可能接管已登录 profile；只读 workspace 可能通过 symlink、mount 或 build daemon 间接写出；网络可把读取到的数据外泄；CPU、内存、磁盘和进程数耗尽也能伤害同机任务。隔离强度取决于攻击者可触达的真实 kernel、device、broker 和 credential boundary，而不是产品标签。

另一方面，完全无权限的 sandbox 也无法完成工作。可靠设计把 code execution 与 privileged operations 分开：sandbox 默认无 ambient credential、无任意网络、无 host namespace；filesystem、network、browser、secret、process 和 artifact publishing 由 host broker 提供窄 capability。每个 capability 绑定 principal、task、resource、operation、expiry、quota 与 audit，并在使用时重验。

核心判断：sandbox 不是“安全房间”，而是一组可验证的 deny boundaries 加受控出口。安全性来自最小 attack surface、brokered capabilities、ephemeral state、resource limits、外部 observation、可靠 teardown 和独立 kill switch 的组合。
02

承接授权模型：capability 必须在隔离边界外兑现

2/4 已把模型降级为 proposal generator，policy engine 签发最小 capability。Sandbox 是 capability 的执行边界：即使 prompt injection 诱导 Agent 生成恶意 shell/code，sandbox 内代码仍看不到 raw credential；它只能向 broker 请求“读取 workspace 内这个 file”或“访问已批准 origin”，broker 再根据 capability token、真实 resolved resource 和当前 revocation 决定。

这解释了为什么“把命令放进 Docker”不够。若把宿主 Docker socket、home directory、SSH agent、cloud metadata、浏览器 profile 或 broad OAuth token mount 进容器，容器进程已经获得高权限出口。Namespace 隔离没有撤销被显式映射的能力。权限边界必须从 workload 视角枚举：能打开哪些 path、连接哪些 address、调用哪些 device/daemon、继承哪些 handles、影响哪些用户 session。

统一 evidence model 也进入这里：sandbox 自报“没有联网”不算证据。Host 要从 broker、kernel/audit、network proxy、cgroup/hypervisor 和 artifact store 观察实际行为，并把 teardown/cleanup 也形成 claim 和 verdict。

03

机制：最小隔离基线与 brokered computer use

1. 选择隔离级别

同进程 language VM 只适合低风险纯计算；子进程增加 crash/resource 隔离但共享 host kernel/user 权限；container 增加 namespaces/cgroups/filesystem view，但仍共享 kernel；microVM/VM 提供独立 guest kernel，隔离更强、启动和运维成本更高。依据 code trust、secret/data sensitivity、network/effect risk 选择，不用一个默认覆盖全部任务。

2. 建最小 root filesystem

image content-addressed 且只读，删除 package manager、compiler、shell 等非必要工具；工作目录使用 task-specific ephemeral volume。只 mount 明确 workspace subpaths，默认只读；输出写 staging area，经 broker 验证后 publish。禁止 host root/home/docker socket/device node；处理 symlink/junction/hardlink、path case、race 与 mount propagation。

3. 降低 kernel attack surface

使用独立 user/pid/mount/network/ipc namespaces（平台支持时）、非 root UID、drop capabilities、no-new-privileges、seccomp/syscall allowlist、只读 proc/sys、限制 devices。Container root 不等于 host root，但高危 capabilities、privileged mode 或 host namespaces 会重新打开边界。Kernel/VM 必须 patch，并记录 image/kernel/hypervisor version。

4. Resource quotas

cgroups/job objects/hypervisor 限制 CPU time/weight、memory/max+OOM、pids、I/O bandwidth、disk bytes/inodes、wall deadline、open files 与 output size。配额触发 typed resource_exhausted，不让 runtime 无限 retry。fork bomb、zip bomb、日志洪泛、GPU/VRAM 和 browser tabs 都进入测试。

5. Filesystem broker

broker 接收 canonical path capability，不接收任意 host path。以 directory handle/openat-like resolution 防 TOCTOU 和 symlink escape，验证最终 object 位于 root；读写分权限，写入通过 temp+fsync+atomic replace，并保存 before/after digest。删除走 trash/tombstone 或明确 irreversible policy。

6. Network egress broker

sandbox 默认无直连 socket。Proxy 按 scheme/origin/method/port/DNS-resolved address/data class 控制，阻止 loopback/link-local/private/metadata、每跳 redirect 重验、防 DNS rebinding、限制 request/response bytes/time/content type。HTTP allowlist 不等于允许 WebSocket、DNS tunnel 或 arbitrary CONNECT。

7. Secret broker

尽量不把 raw secret 注入 env/file。Broker 接受 audience-bound operation，例如“以 service identity 请求这个 API”，在隔离外附加短期 credential；token scope/resource/TTL 与 task 绑定，response 经 DLP。必须使用 secret 时，single-use handle、不可导出、日志 redaction、立即 revoke；sandbox snapshot 不含凭据。

8. Browser/computer-use broker

使用 dedicated ephemeral browser profile，不复用用户日常 profile、cookies、password manager、extensions 或 open tabs。Browser sandbox 不等于 agent isolation；automation endpoint/remote debugging 是高权限控制面，只对 broker 暴露。Navigation/domain/download/upload/clipboard/dialog 权限分开，敏感输入由 secure fill 操作注入，模型不读取值。

9. UI identity 与 confirmation

computer use 前确认目标 app/window/tab identity，防 overlay、tab swap 和 look-alike origin。高风险 click/submit 前重新截图/DOM/URL 并校验 canonical action digest；用户 approval 显示真实 destination、data 与 effect。不要批准坐标，批准语义操作。

10. Lifecycle 与 cleanup

每个 run 创建 sandbox ID、image/config digest、capability snapshot 和 ephemeral resources。Cancellation 先 revoke brokers/tokens，再终止 process tree/VM，等待 bounded grace，强 kill，unmount/wipe ephemeral state，扫描残留 processes/ports/handles，最后生成 teardown evidence。Cleanup fail 不是 warning，而是隔离 incident。

11. Output/artifact gate

产生的文件不直接进入 host workspace。Broker 检查 size/type、path、archive traversal、malware/policy、secret/PII、executable bit、symlink 与 provenance，然后 atomic publish 到批准位置。HTML/PDF/document 打开也可能主动内容；consumer 按 data 处理。Build artifact 绑定 source/input/toolchain digest。

12. Escape testing 与 attestation

测试 known syscall/device/kernel surfaces、mount/namespace escape、broker parser differential、symlink race、SSRF、credential theft、side channels、resource exhaustion、cleanup race 和 browser profile bleed。Oracle 来自 host/hypervisor/audit/network，而非 workload。定期 red team、patch cadence、image scanning 与 runtime attestation 证明实际配置等于批准 config。

04

必要数学：隔离强度、配额与残留风险

Residual risk

对攻击路径 j，可写 R_j=P(exploit_j)·Impact_j·Exposure_j。sandbox 降低 P，最小 capability/TTL/quota 降低 Exposure，effect-owner authorization 降低可达 Impact。多层控制不保证独立，不能简单把概率相乘；应分析共享 kernel、parser、identity 等 correlated failure。

Resource budget

若 N 个并发 sandboxes，每个 CPU quota c、memory m、disk d，理论上限 CPU≤Nc, Memory≤Nm, Disk≤Nd，但 host 需保留 headroom H 和 burst policy。Admission 必须满足 Σrequests+H≤capacity；否则排队/拒绝，而不是依赖 OOM 后恢复。

Cleanup SLO

定义 revocation-to-deny 延迟 T_d、termination 延迟 T_k、residue-free verdict 延迟 T_c。高风险要求 T_d≪T_k≤T_c≤SLO：先立即阻断能力，再结束计算，最后证明清理。只测 process exit 会遗漏 credential、mount、port、browser profile 和 artifact residue。

05

对 Agent 系统的影响

能力：Agent 可运行不受信 code 和 computer use，但只通过 brokers 获得 task-scoped 能力。不同风险任务选择不同 isolation tier，不必让所有任务承担 VM 成本。

可靠性：resource exhaustion、broker deny、sandbox crash、timeout、cleanup fail 都是 typed lifecycle states。Runtime 可区分业务失败与隔离故障，避免错误 retry；artifacts 只有通过 publish gate 才进入 durable state。

安全：raw secrets 不进 sandbox，network default-deny，browser profile 临时，workspace 写入 staged，effect owner 重验。即使 code escape 某一语言 runtime，仍需跨 OS/VM、broker 和 downstream authorization。

经济性：microVM/remote worker 提高隔离却增加 cold start、memory 和运营成本。按 risk route：纯计算用 lightweight runtime，中风险用 hardened container，高风险 code/browser 用 microVM/remote disposable host。指标拆 startup、broker latency、quota utilization、denials、escape signals、cleanup SLO 和 per-task cost。

06

设计取舍与失败模式

  • container=VM：共享 kernel 风险被忽略；按 threat model 选择 isolation tier。
  • mount host socket/home：显式高权限出口使 namespace 失效；通过 broker 替代。
  • secret 注入 env：子进程/日志/snapshot 泄漏；operation broker 和短期 handle。
  • network allow all：exfiltration/SSRF；default deny、resolved-address/redirect/DLP。
  • 复用浏览器 profile：cookies/passwords/extensions/用户 tab 泄漏；ephemeral dedicated profile。
  • 只 kill 父进程：child/daemon/port/mount 残留；process tree/VM teardown 与 residue scan。
  • 只读 mount 即安全：symlink/daemon/cache/side effect；final-object resolution 和 broker。
  • artifact 自动 publish：active/malicious/secret 内容进入 host；staging gate 和 provenance。
07

可复用的技术判断

  • sandbox 是 deny boundaries + controlled exits，不是一个产品标签。
  • process/container/VM 共享程度不同；按 code/data/secret/network/effect risk 选择 tier。
  • filesystem/network/browser/secret/process 通过外部 broker 以 resource/action/TTL/quota capability 访问。
  • computer use 使用临时 profile，审批语义 action 而非坐标，高风险 submit 前重验 UI identity。
  • teardown、artifact publish 与 escape testing 都需外部 evidence；cleanup fail 是 isolation incident。

Reliability and Safety Internals · Part 3 of 4

Why Can a Sandboxed Agent Still Harm the Host?

Dissect process, container, and VM boundaries, capability brokers, ephemeral workspaces, browser profiles, egress, resource quotas, cleanup, and escape testing.

2026-10-0420 min readSandboxing / Computer use / Isolation / Capability broker / Resource quotas
01

Today's proposition

“The code runs in a sandbox” is not a complete security claim. A child process may inherit environment variables and open handles. A container shares the host kernel. Browser automation may control an already authenticated profile. A read-only workspace may still write through symlinks, mounts, or a build daemon. Network access can exfiltrate what was read. CPU, memory, disk, and process exhaustion can harm neighboring workloads. Isolation strength depends on the real kernel, device, broker, and credential boundaries reachable by an attacker, not the product label.

A sandbox with no permissions, however, cannot perform useful work. A reliable design separates code execution from privileged operations. The sandbox starts without ambient credentials, arbitrary network access, or host namespaces. Host brokers provide narrow filesystem, network, browser, secret, process, and artifact-publishing capabilities. Each capability binds principal, task, resource, operation, expiry, quota, and audit context and is revalidated when used.

Core judgment: a sandbox is not a “safe room.” It is a set of testable deny boundaries plus controlled exits. Security comes from combining minimal attack surface, brokered capabilities, ephemeral state, resource limits, external observation, reliable teardown, and an independent kill switch.
02

Capabilities are enforced outside the isolated workload

Part 2 reduced the model to a proposal generator and let a policy engine issue minimal capabilities. A sandbox is where those capabilities become enforceable. Even if prompt injection induces hostile shell or code, the workload never sees a raw credential. It can only ask a broker to read a particular file inside the workspace or connect to an approved origin. The broker resolves the real resource and checks capability token plus current revocation.

This explains why “run it in Docker” is insufficient. Mounting the host Docker socket, home directory, SSH agent, cloud metadata access, browser profile, or a broad OAuth token gives the container a privileged exit. Namespace isolation does not revoke capabilities that were explicitly mapped in. The boundary is enumerated from the workload's point of view: which paths it can open, addresses it can reach, devices and daemons it can call, handles it inherits, and user sessions it can influence.

The unified evidence model applies here too. A sandbox claiming “I did not use the network” is not evidence. The host observes actual behavior through brokers, kernel or audit, network proxy, cgroup or hypervisor, and artifact storage. Teardown and cleanup also become claims with verdicts.

03

Mechanism: a minimal isolation baseline with brokered computer use

1. Select an isolation level

An in-process language VM fits low-risk pure computation. A child process improves crash and resource isolation but shares kernel and user authority. A container adds namespaces, cgroups, and a filesystem view while sharing the host kernel. A microVM or VM adds a guest kernel with stronger isolation and higher startup and operations cost. Choose by code trust, data and secret sensitivity, and network and effect risk rather than one default.

2. Build a minimal root filesystem

Use a content-addressed, read-only image and remove package managers, compilers, shells, and other unnecessary tools. Give each task an ephemeral working volume. Mount explicit workspace subpaths, read-only by default; write into staging and publish through a broker. Never mount host root, home, Docker socket, or device nodes. Handle symlinks, junctions, hard links, path case, races, and mount propagation.

3. Reduce kernel attack surface

Where available, use user, PID, mount, network, and IPC namespaces, a non-root UID, dropped capabilities, no-new-privileges, a seccomp syscall allowlist, read-only proc and sys, and restricted devices. Container root is not host root, but privileged mode, dangerous capabilities, or host namespaces reopen the boundary. Patch the kernel or VM and record image, kernel, and hypervisor versions.

4. Enforce resource quotas

Use cgroups, job objects, or hypervisor limits for CPU time and weight, memory and OOM behavior, process count, I/O bandwidth, disk bytes and inodes, wall deadline, open files, and output size. A quota breach returns typed resource exhausted rather than causing infinite retry. Test fork bombs, zip bombs, log floods, GPU or VRAM use, and browser-tab explosions.

5. Broker filesystem access

The broker accepts a canonical-path capability, never an arbitrary host path. Resolve through directory handles or openat-style APIs to prevent TOCTOU and symlink escape, then verify the final object stays inside the root. Separate read and write permission. Write through temporary files, fsync, and atomic replace while retaining before and after digests. Delete through trash or tombstones unless irreversible policy is explicit.

6. Broker network egress

The sandbox has no direct socket access. A proxy controls scheme, origin, method, port, resolved DNS address, and data class; blocks loopback, link-local, private, and metadata ranges; revalidates every redirect; resists DNS rebinding; and limits request and response size, time, and content type. An HTTP allowlist does not authorize WebSocket, DNS tunnels, or arbitrary CONNECT.

7. Broker secrets as operations

Avoid raw secrets in environment or files. A broker accepts an audience-bound operation such as “call this API as service identity,” then attaches a short-lived credential outside the sandbox. Token scope, resource, TTL, and task bind together; responses pass DLP. If a secret must be used, prefer a single-use non-exportable handle, redact logs, revoke immediately, and exclude credentials from snapshots.

8. Broker browsers and computer use

Use a dedicated ephemeral browser profile, never the user's daily profile, cookies, password manager, extensions, or open tabs. Browser sandboxing does not equal agent isolation. Automation and remote-debugging endpoints are privileged control planes exposed only to the broker. Navigation, domains, downloads, uploads, clipboard, and dialogs receive separate permissions. Secure-fill operations insert sensitive values without revealing them to the model.

9. Verify UI identity and confirmation

Before computer use, verify target application, window, tab, and origin to resist overlays, tab swaps, and look-alike sites. Before high-risk clicks and submissions, recapture screenshot, DOM, and URL and compare the canonical action digest. User approval shows real destination, data, and effect. Approve semantic operations, not coordinates.

10. Treat teardown as a verified lifecycle

Each run creates sandbox ID, image and configuration digest, capability snapshot, and ephemeral resources. Cancellation first revokes brokers and tokens, terminates the process tree or VM with bounded grace, force-kills, unmounts and wipes state, scans remaining processes, ports, and handles, then emits teardown evidence. Cleanup failure is an isolation incident, not a warning.

11. Gate output and artifacts

Generated files do not enter the host workspace directly. The broker checks size and type, path, archive traversal, malware and policy, secret and PII, executable bits, symlinks, and provenance, then atomically publishes to an approved location. HTML, PDF, and documents may be active content and remain data to consumers. Build artifacts bind source, input, and toolchain digests.

12. Test escape and attest configuration

Test known syscall, device, and kernel surfaces; mount and namespace escape; broker parser differentials; symlink races; SSRF; credential theft; side channels; resource exhaustion; cleanup races; and browser-profile bleed. Oracles come from the host, hypervisor, audit, and network rather than the workload. Regular red teaming, patch cadence, image scanning, and runtime attestation prove the actual configuration matches the approved one.

04

Essential mathematics: isolation strength, quotas, and residual risk

Residual risk

For attack path j, write R_j=P(exploit_j)·Impact_j·Exposure_j. A sandbox reduces exploitability, minimal capability, TTL, and quotas reduce exposure, and effect-owner authorization reduces reachable impact. Layers are not necessarily independent, so probabilities cannot simply be multiplied. Analyze correlated failures in shared kernels, parsers, and identities.

Resource budget

With N concurrent sandboxes and per-sandbox CPU quota c, memory m, and disk d, theoretical bounds are CPU≤Nc, Memory≤Nm, Disk≤Nd, while the host reserves headroom H and burst policy. Admission requires total requests plus H within capacity; otherwise queue or reject rather than relying on OOM recovery.

Cleanup SLO

Define revocation-to-deny latency T_d, termination latency T_k, and residue-free-verdict latency T_c. High-risk systems require T_d≪T_k≤T_c≤SLO: block capability immediately, stop computation, then prove cleanup. Testing process exit alone misses credentials, mounts, ports, browser profiles, and artifact residue.

05

Implications for agent systems

Capability: agents run untrusted code and computer use while acquiring task-scoped power only through brokers. Different risk classes select different isolation tiers, so every task need not pay VM cost.

Reliability: resource exhaustion, broker denial, sandbox crash, timeout, and cleanup failure are typed lifecycle states. Runtime distinguishes business failure from isolation failure and avoids incorrect retries. Artifacts enter durable state only through the publication gate.

Security: raw secrets stay outside, network is default-deny, browser profiles are ephemeral, workspace writes are staged, and effect owners reauthorize. Even if code escapes a language runtime, it still confronts OS or VM, brokers, and downstream authorization.

Economics: microVMs and remote workers strengthen isolation while adding cold start, memory, and operations cost. Route by risk: lightweight runtime for pure computation, hardened containers for medium risk, and microVMs or disposable remote hosts for high-risk code and browsers. Metrics separate startup, broker latency, quota utilization, denials, escape signals, cleanup SLO, and per-task cost.

06

Trade-offs and failure modes

  • Container equals VM: shared-kernel risk is ignored. Select isolation tier from threat model.
  • Mount host socket or home: an explicit privileged exit defeats namespaces. Replace it with a broker.
  • Secret in environment: child processes, logs, and snapshots leak it. Use operation brokers and short-lived handles.
  • Allow all network: exfiltration and SSRF follow. Default-deny with resolved-address, redirect, and DLP checks.
  • Reuse browser profile: cookies, passwords, extensions, and user tabs leak. Use a dedicated ephemeral profile.
  • Kill parent only: children, daemons, ports, and mounts remain. Tear down process tree or VM and scan residue.
  • Read-only mount is safe: symlinks, daemons, caches, and side effects remain. Resolve final objects through a broker.
  • Auto-publish artifacts: active, malicious, or secret content reaches the host. Use a staging gate and provenance.
07

Reusable technical judgments

  • A sandbox is deny boundaries plus controlled exits, not a product label.
  • Processes, containers, and VMs share different amounts of host state. Select tiers by code, data, secret, network, and effect risk.
  • Filesystem, network, browser, secret, and process access goes through external brokers with resource, action, TTL, and quota capabilities.
  • Computer use gets an ephemeral profile, approval binds semantic actions rather than coordinates, and high-risk submission rechecks UI identity.
  • Teardown, artifact publication, and escape testing require external evidence. Cleanup failure is an isolation incident.
