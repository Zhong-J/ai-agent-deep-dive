LLM 内核 · 第 1/3 篇

下一个 token，如何变成 Agent 的下一步行动？

LLM 没有隐藏的任务调度器。它反复预测符号；Agent runtime 把其中一部分符号解释成有副作用的动作。理解这条边界，是理解 tool calling、loop 与可靠性的起点。

2026-09-08约 18 分钟LLM / Next-token prediction / Tool calling / Agent runtime
01

今日命题

一个常见但危险的心智模型是：LLM 在内部先形成一个完整计划，再把计划逐字打印出来。更接近事实的说法是：在每个位置，模型根据当前上下文计算词表上所有候选 token 的分布，选择一个 token，把它追加到上下文，然后重复。一次工具调用、一个 JSON 参数、甚至一句“我需要先搜索”，都必须经过这条逐 token 的生成链。

token 也不等于“一个词”。tokenizer 可能把中文单字、英文词根、空格、标点、JSON 引号或协议控制符切成不同单元。同一个工具参数在字符层看似简单，在模型看来可能要经过许多次局部选择。这解释了为什么长 ID、罕见路径、精确引号和嵌套 JSON 容易出错：模型必须连续多步都落在正确 token 上。schema constraint 能缩小每一步的候选集合，但不能替模型理解参数含义。

这并不意味着模型“只是 autocomplete”，因而不能规划。训练把大量语言、代码、推理轨迹和工具使用模式压进参数；上下文则把当前目标、工具定义和历史结果放到模型面前。模型可以在逐步生成中实现复杂计算，就像 CPU 由简单指令组成却能运行大型程序。关键区别是：CPU 的转移规则由程序确定，LLM 的转移是条件概率分布；Agent 的可靠性因此不能只靠模型。

还要避免另一个极端：说“只是预测 token”并没有解释模型如何得到分布。Transformer 在每一步进行大量向量运算，hidden state 可以编码尚未写出的中间特征、候选计划和不确定性；只是这些内部表示并不自动获得系统权限，也不是可直接执行的动作。工程边界仍然落在可观察的输出协议上。

今天要建立的边界：模型负责提出下一段符号；runtime 负责判定这些符号是文本还是动作、是否允许执行、怎样执行，以及结果如何回到下一轮上下文。
02

连接你熟悉的 loop

你已经熟悉典型 loop：构造上下文 → 调模型 → 发现 tool call → 执行工具 → 把结果追加回上下文 → 再调模型。现在把“调模型”这一步展开：runtime 发送的不是抽象意图，而是一串 token，包括 system/developer instructions、用户消息、工具名称、描述和参数 schema。模型返回的也不是 JavaScript 函数对象，而是协议定义的输出 token，服务端或 SDK 将其解析成结构化 item。

因此 agent loop 实际上是两层状态机的组合。内层是模型的自回归 token loop，终止于 end token、tool-call 边界或长度限制；外层是 runtime 的 action loop，负责验证、执行与重新组装上下文。很多“模型问题”其实发生在两层交界：schema 含糊导致参数分布发散，工具输出过长污染下一轮上下文，runtime 重试造成重复副作用，或者 stop condition 把仍需继续的轨迹提前截断。

while (!done) {
  response = model(context, toolSchemas)   // 内层：逐 token 生成
  if (response.type === "tool_call") {
    call = validate(response)
    result = await executeWithPolicy(call) // 外层：真实副作用
    context.push(call, result)
  } else {
    done = acceptFinal(response)
  }
}
03

从 logits 到副作用

一次生成从 tokenization 开始。文本和协议标记被映射成整数 ID；embedding table 把 ID 映射成向量。经过多层 Transformer 后，最后位置的 hidden state 被投影成一个与词表同宽的 logits 向量。logit 不是概率，只是每个候选 token 的未归一化分数；softmax 才把它转换成概率分布。

假设上下文中有用户目标“查北京天气”和工具定义 get_weather(location)。训练让模型学到：在相似上下文里，产生工具调用标记、工具名和合法参数往往比直接编造天气更符合目标。于是第一枚特殊 token 可能落在 tool_call 分支。之后工具名与参数仍然逐 token 生成，只是 decoding 可以受到 grammar 或 JSON Schema 约束：不合法的下一 token 被屏蔽，剩余概率重新归一化。

在真实 API 中，协议层还会把这条 token 流包装成 output item。streaming 客户端可能先收到“工具调用开始”，再收到参数 delta，最后才收到完整 call；runtime 不应在参数尚未闭合时执行。一个 call ID 用于把之后的 tool result 与原请求配对。这些 item 是传输与状态管理抽象，不改变底层自回归事实，却决定了重试、并行调用和断线恢复能否正确实现。

schema-constrained decoding 提高的是语法符合率，不是语义正确率。参数可以完全符合 JSON Schema，却把城市写错、选择了危险工具、遗漏业务约束。执行前仍需语义验证、权限判断、幂等策略和人工审批边界。工具返回后，模型看到的通常又只是文本或结构化 token；它没有直接“感受”数据库或浏览器，只看到 runtime 选择暴露的观察结果。

这也解释了为什么 tool result 必须被视为不可信输入。网页、数据库字段或 shell 输出可能含有看似指令的文字；一旦追加进上下文，它会和其他 token 一起影响分布。runtime 需要保留来源和 trust level，隔离数据与指令，必要时截断、转义或让独立 parser 提取字段，而不是假设模型天然知道哪段话有权改变目标。

04

必要数学：分解与采样

语言模型给整段输出 y 的概率，不是一次算出，而是用 chain rule 分解为每个 token 的条件概率乘积：

P(y₁,…,yₜ | x) = ∏ᵢ P(yᵢ | x, y₁,…,yᵢ₋₁)

x 是生成前已有的上下文；yᵢ 是第 i 个输出 token。这个式子解释了两件工程事实。第一，早期一个小错误会进入后续条件，改变整条轨迹；tool name 选错后，参数往往会继续“合理地”为错误工具服务。第二，长轨迹不是一个原子决策，而是一连串局部决策，因此 context management、阶段性验证和可恢复 checkpoint 很重要。

训练时，基础语言模型通常最小化真实下一个 token 的 negative log-likelihood，也就是 cross-entropy。若真实 token 是 y，损失可写作：

L = −log P(y | context)

当模型给真实 token 的概率越低，惩罚越大。对海量序列反复优化后，参数学到哪些 token 在哪些上下文后更可能出现。这个目标没有直接写入“完成用户业务目标”或“永不调用危险工具”；这些行为来自训练数据、后训练反馈、推理时 instructions 以及 runtime 约束的共同作用。也因此，低 training loss 与高 agent task success 不是同一个指标。

每一步的概率来自 logits z 的 softmax。temperature τ 控制分布的尖锐程度：

P(token = j) = exp(zⱼ / τ) ÷ Σₖ exp(zₖ / τ)

τ 较低时，高 logit token 更占优势，输出通常更稳定；τ 较高时，低分候选获得更多概率，探索性增加。但 temperature 不是“正确性旋钮”。如果错误 tool call 本来就是最高分，降低温度只会更稳定地犯错。greedy decoding 取最高概率 token，也不等于得到全序列最高概率，更不等于得到业务上最优动作。

如果一条 100-token 参数序列中每一步平均有 99% 概率选中期望 token，粗略相乘得到整段完全匹配的概率约为 0.99¹⁰⁰ ≈ 36.6%。真实决策并不独立，平均概率也不会固定，但这个例子说明：局部很准不代表长串精确复制可靠。不要要求模型背出 opaque ID；让 runtime 查询、枚举、校验或用短别名映射。

工具 schema 约束可以看作在每一步建立合法集合 A，把不在 A 中的 token 概率设为 0，再归一化。这能消除无效 JSON，却无法表达所有真实约束，例如“退款超过 500 元必须审批”。后者属于 runtime policy，而不是 decoding grammar。

05

对 Agent 设计的影响

1. Tool description 是概率控制面

名称、描述、参数 schema 会进入上下文，影响下一 token 分布。两个语义重叠的工具会竞争概率；含糊描述会增加错误选择。tool design 不只是 API ergonomics，也是模型决策界面。

2. Observation 决定下一轮世界

模型只知道被追加回上下文的结果。把 20 MB 日志原样塞回去，不等于“提供更多信息”；关键错误可能被埋没，还会消耗 context 和 attention。runtime 应把 observation 设计成紧凑、带来源、可验证、保留关键失败细节的对象。

3. 权限不能来自 prompt

“不要删除生产数据”只是一段会影响概率的 token，不是权限边界。真正的边界必须在模型之外：凭据 scope、allowlist、sandbox、审批、dry-run 和资源配额。prompt 可以帮助选择，但不能授予或撤销能力。

4. Verification 要切断错误累积

因为序列概率逐步分解，错误会沿轨迹传播。在高风险节点加入类型检查、状态断言、测试、独立 reviewer 或环境反馈，相当于在外层 loop 建立新的观测与分支，而不是让模型基于错误前提继续流畅生成。

06

取舍与失败模式

结构化输出 vs. 表达能力：严格 schema 能大幅降低解析失败，但 schema 越复杂、动态变化越频繁，越会占用上下文、增加首次处理成本，并可能让模型在错误抽象里稳定输出。先让工具边界简单，再要求模型遵守。

单次大调用 vs. 外层 loop：把整个任务交给一次超长 generation，runtime 简单，但中途不可观测、不可验证、失败重做成本高。细粒度 loop 增加编排开销，却能 checkpoint、重试具体步骤并在副作用前审批。粒度应围绕可验证状态转移，而不是追求调用次数最少。

确定性 vs. 探索：低 temperature、固定 tool choice 和严格 grammar 提高重复性，适合稳定工作流；但复杂研究与 debugging 可能需要探索多个假设。更可靠的做法常是让探索发生在无副作用的候选生成阶段，再由 evaluator 或环境测试收敛，而不是直接提高执行阶段随机性。

看起来会推理 vs. 已完成：自然语言解释很流畅，只说明生成轨迹在语言分布上合理。它不证明文件已写入、交易已提交、测试已通过或目标状态已达到。completion 必须由环境状态和 verifier 定义。模型的“done”只是一个提案。

最值得记住的失败模式：把符合 schema 的 tool call 当成正确决策，把模型自报完成当成环境已完成，把 prompt prohibition 当成权限控制。
07

可复用判断

  1. Agent 不是 LLM 内部的一项单独能力，而是 token generator 与 runtime state machine 的组合系统。
  2. tool call 从模型侧仍是逐 token 生成；结构化约束保证格式，不保证意图、权限或业务正确性。
  3. prompt、tool schema 和 observation 都是概率控制面；credential、sandbox、approval 和 verifier 才是确定性控制面。
  4. 长任务可靠性来自在外层 loop 中不断把环境事实重新引入，而不是让单次生成变得无限长。
  5. 任何“完成”都应由环境状态判定，不能由模型的最后一句话判定。

LLM Internals · Part 1 of 3

How Does the Next Token Become an Agent's Next Action?

An LLM contains no hidden task scheduler. It repeatedly predicts symbols; the agent runtime interprets some of those symbols as actions with side effects. That boundary is the starting point for understanding tool calling, loops, and reliability.

2026-09-0818 min readLLM / Next-token prediction / Tool calling / Agent runtime
01

Today's proposition

A common but dangerous mental model says that an LLM first forms a complete plan internally and then prints that plan word by word. A closer description is this: at every position, the model computes a distribution over candidate tokens from the current context, selects one token, appends it to the context, and repeats. A tool call, a JSON argument, and even the sentence “I should search first” must all pass through this token-by-token generation process.

A token is not the same thing as a word. A tokenizer may assign separate units to a Chinese character, an English stem, whitespace, punctuation, a JSON quote, or a protocol control marker. A tool argument that looks simple at the character level can require many local choices from the model. This helps explain why long identifiers, rare paths, exact quotation, and nested JSON are fragile: many consecutive token decisions must all land correctly. A schema constraint can reduce the legal candidate set at each step, but it cannot make the model understand the intended meaning of an argument.

This does not mean the model is “only autocomplete” and therefore cannot plan. Training compresses patterns from language, code, reasoning traces, and tool use into the parameters; context supplies the current goal, tool definitions, and previous results. Complex computation can emerge through sequential generation, just as a CPU runs large programs from simple instructions. The crucial difference is that a CPU transition is fixed by a program, while an LLM transition is a conditional probability distribution; agent reliability therefore cannot come from the model alone.

A second extreme is equally misleading: saying “it only predicts tokens” does not explain how the distribution is computed. A Transformer performs substantial vector computation at every step. Its hidden states may encode intermediate features, candidate plans, and uncertainty that have not been written out. Those internal representations, however, do not automatically gain system permissions and are not directly executable actions. The engineering boundary still lies at the observable output protocol.

The boundary to establish today: the model proposes the next symbols; the runtime decides whether those symbols are text or an action, whether execution is allowed, how it runs, and how the result enters the next context.
02

Connect it to the loop you know

You already know the typical loop: assemble context → call the model → detect a tool call → execute it → append the result → call the model again. Now expand “call the model.” The runtime sends no abstract intention. It sends tokens representing system and developer instructions, user messages, tool names, descriptions, and parameter schemas. The model does not return a JavaScript function object either. It emits protocol-defined output tokens that a service or SDK parses into a structured item.

An agent loop is therefore a composition of two state machines. The inner machine is the model's autoregressive token loop, ending at an end token, a tool-call boundary, or a length limit. The outer machine is the runtime action loop, which validates, executes, and reassembles context. Many apparent “model problems” occur at this boundary: an ambiguous schema spreads probability across bad arguments, a long tool result contaminates the next context, a retry duplicates a side effect, or a stop condition truncates a trajectory that still needs work.

while (!done) {
  response = model(context, toolSchemas)   // inner: token generation
  if (response.type === "tool_call") {
    call = validate(response)
    result = await executeWithPolicy(call) // outer: real side effect
    context.push(call, result)
  } else {
    done = acceptFinal(response)
  }
}
03

From logits to side effects

Generation begins with tokenization. Text and protocol markers become integer IDs; an embedding table maps those IDs to vectors. After many Transformer layers, the hidden state at the final position is projected into a logits vector as wide as the vocabulary. A logit is not a probability, only an unnormalized score for a candidate token; softmax converts the scores into a probability distribution.

Suppose the context contains the goal “check Beijing weather” and a tool definition get_weather(location). Training has taught the model that, in similar contexts, producing a tool-call marker, a tool name, and valid arguments often fits the objective better than inventing weather. The first special token may therefore enter a tool_call branch. The name and arguments are still generated token by token, but decoding can be constrained by a grammar or JSON Schema: illegal next tokens are masked and the remaining probabilities are renormalized.

In a real API, the protocol layer wraps this token stream into output items. A streaming client may first receive the start of a tool call, then argument deltas, and only later the completed call; the runtime must not execute while the argument object is still incomplete. A call ID pairs the later tool result with the originating request. These items are transport and state-management abstractions. They do not change the underlying autoregressive process, but they determine whether retries, parallel calls, and connection recovery can be implemented correctly.

Schema-constrained decoding improves syntactic conformance, not semantic correctness. Arguments may perfectly match JSON Schema while naming the wrong city, selecting a dangerous tool, or omitting a business constraint. Execution still requires semantic validation, authorization, idempotency policy, and human-approval boundaries. Once a tool returns, the model normally sees only text or structured tokens again. It does not directly “feel” a database or browser; it sees the observation that the runtime chose to expose.

This also explains why a tool result must be treated as untrusted input. A webpage, database field, or shell output can contain language that looks like an instruction. Once appended to context, those tokens influence the distribution alongside everything else. The runtime should preserve provenance and trust level, separate data from instructions, and truncate, escape, or independently parse fields when necessary instead of assuming the model inherently knows which text has authority to change the goal.

04

Essential math: factorization and sampling

A language model does not assign the probability of a complete output sequence y in one indivisible step. By the chain rule, it factorizes that probability into a product of next-token conditionals:

P(y₁,…,yₜ | x) = ∏ᵢ P(yᵢ | x, y₁,…,yᵢ₋₁)

x is the context available before generation and yᵢ is the i-th output token. This equation explains two engineering facts. First, an early error becomes part of every later condition and changes the whole trajectory; after selecting the wrong tool name, the model may continue producing arguments that are locally coherent for that wrong tool. Second, a long trajectory is not an atomic decision but a chain of local decisions, making context management, intermediate verification, and recoverable checkpoints important.

During training, a base language model typically minimizes the negative log-likelihood of the observed next token, equivalently a cross-entropy loss. If the observed token is y, the loss is:

L = −log P(y | context)

The lower the probability assigned to the observed token, the larger the penalty. Repeating this optimization over enormous collections of sequences teaches the parameters which tokens tend to follow which contexts. The objective does not directly say “complete the user's business goal” or “never call a dangerous tool.” Those behaviors emerge from the combined effects of training data, post-training feedback, inference-time instructions, and runtime constraints. Low training loss and high agent task success are therefore different metrics.

At each position, probabilities come from a softmax over logits z. Temperature τ controls the sharpness of the distribution:

P(token = j) = exp(zⱼ / τ) ÷ Σₖ exp(zₖ / τ)

At a lower τ, high-logit tokens dominate and output is usually more stable. At a higher τ, lower-scoring candidates receive more probability and exploration increases. Temperature is not a “correctness knob,” however. If a wrong tool call already has the highest score, lowering temperature merely makes that mistake more repeatable. Greedy decoding takes the highest-probability token at each step; that is not guaranteed to produce the highest-probability complete sequence, much less the best action under a business objective.

If every position in a 100-token argument sequence had an average 99% chance of producing the intended token, a crude product gives only 0.99¹⁰⁰ ≈ 36.6% probability of an exact match. Real token decisions are not independent and their probabilities are not constant, but the example exposes an important design rule: high local accuracy does not make long exact reproduction reliable. Do not ask a model to memorize opaque identifiers when the runtime can query, enumerate, validate, or map a short alias.

A tool schema constraint can be viewed as defining a legal set A at each step, setting the probability of tokens outside A to zero, and renormalizing. This removes invalid JSON but cannot express every real constraint, such as “refunds over $500 require approval.” That belongs in runtime policy, not the decoding grammar.

05

Implications for agent design

1. Tool descriptions are a probabilistic control surface

Names, descriptions, and parameter schemas enter the context and influence the next-token distribution. Semantically overlapping tools compete for probability; ambiguous descriptions increase selection error. Tool design is not merely API ergonomics—it is the model's decision interface.

2. An observation defines the next world

The model knows only the result appended to context. Dumping a 20 MB log does not necessarily “provide more information.” The decisive error can be buried while context and attention are consumed. The runtime should shape observations into compact, attributable, verifiable objects that preserve critical failure detail.

3. Permission cannot come from a prompt

“Do not delete production data” is a sequence of tokens that influences probability, not a permission boundary. The real boundary must live outside the model: credential scope, allowlists, sandboxing, approvals, dry runs, and resource quotas. A prompt can guide selection but cannot grant or revoke capability.

4. Verification must interrupt error accumulation

Because sequence probability factorizes step by step, errors propagate along a trajectory. Type checks, state assertions, tests, an independent reviewer, or environment feedback at high-risk points create a new observation and branch in the outer loop instead of letting the model fluently continue from a false premise.

06

Trade-offs and failure modes

Structured output versus expressiveness: a strict schema can greatly reduce parsing failures, but a complex or frequently changing schema consumes context, can add first-use processing cost, and may cause the model to produce stable output inside the wrong abstraction. Make the tool boundary simple before demanding conformance.

One large call versus an outer loop: delegating the whole task to one long generation simplifies the runtime but makes intermediate work unobservable and unverifiable, while failures are expensive to redo. A fine-grained loop adds orchestration overhead but enables checkpoints, step-level retries, and approval before side effects. Choose granularity around verifiable state transitions, not the fewest possible model calls.

Determinism versus exploration: low temperature, fixed tool choice, and strict grammars improve repeatability for stable workflows. Complex research and debugging may need multiple hypotheses. A more reliable pattern is to explore in a side-effect-free candidate stage and then converge through evaluators or environment tests, rather than making the execution stage more random.

Apparently reasoned versus actually complete: a fluent explanation only shows that the generated trajectory is plausible under the language distribution. It does not prove that a file was written, a transaction committed, a test passed, or a target state reached. Completion must be defined by environment state and a verifier. The model's “done” is only a proposal.

The failure pattern worth remembering: treating a schema-valid call as a correct decision, treating self-reported completion as completed environment state, or treating a prompt prohibition as access control.
07

Reusable judgments

  1. An agent is not a separate capability hidden inside an LLM; it is a system composed of a token generator and a runtime state machine.
  2. From the model's side, a tool call is still generated token by token. Structural constraints guarantee format, not intent, authorization, or business correctness.
  3. Prompts, tool schemas, and observations are probabilistic control surfaces. Credentials, sandboxes, approvals, and verifiers are deterministic control surfaces.
  4. Long-task reliability comes from repeatedly reintroducing environment facts through the outer loop, not from making one generation infinitely long.
  5. Environment state—not the model's final sentence—must define completion.

Primary sources

  • Vaswani et al., Attention Is All You Need — the original Transformer and attention paper. Today we used only the layer of the mental model in which a Transformer maps context to next-token logits; attention itself will receive a later series.
  • Yao et al., ReAct: Synergizing Reasoning and Acting in Language Models — a representative treatment of interleaving reasoning traces, actions, and environment observations.
  • Official OpenAI documentation: Using tools — current protocol examples for function calling, built-in tools, and remote MCP. The documentation exposes tools through the request's tools configuration and defines a function tool through its name, description, and JSON Schema.

Where we continue tomorrow

Established today: an LLM emits a conditional token distribution; an agent runtime interprets some outputs as tool actions; schema constraints, runtime policy, and environment verification occupy different reliability layers.

Still unresolved: we temporarily treated the Transformer as a black box that maps context to logits. The next issue will open that box and follow one token through embeddings, position information, self-attention, and the residual stream, asking what attention can actually “see” and what it cannot.
