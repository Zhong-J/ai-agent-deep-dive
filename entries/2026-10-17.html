MoE 看起来更省，怎样证明 Agent 真的受益？

用 matched quality、任务切片、路由漂移和端到端成本，把 MoE 的活跃参数优势变成可验证的系统判断。

2026-10-17约 20 分钟MoE evaluation / Matched quality / Routing drift / Tail latency / Verified outcome
01

今日命题

一家团队把 Agent 的主模型换成 MoE：每 token 活跃参数更少，离线通用题分数更高，平均 tokens/s 也提高了。上线后却出现两类意外：某些长工具日志让一个 expert 热点拖慢 p99；工具调用 JSON 在罕见错误场景更易坏，导致修复轮次增多。于是每请求账单降低，而每个经验证完成的任务可能更贵。

前两篇解释了为什么这种结果不矛盾：MoE 1/3 的 top-k 只稀疏化 FFN 算术，capacity、overflow、梯度覆盖影响训练；2/3 的 expert parallelism 带来 token permutation、两次 all-to-all、最慢专家同步，以及专家权重和每请求 KV 两笔驻留成本。今天不再重复公式或数据流，而要回答系统决策：怎样公平比较 MoE 与 dense，怎样检测路由漂移而不把 expert ID 拟人化，何时可以安全发布？

核心判断：‘MoE 更省’是一个带质量、负载、硬件、风险和时间范围的条件命题。比较单位不是参数或单次请求，而是在同一任务合同下达到终态、满足安全门的 cost per verified outcome 与尾延迟。
02

从专家路由到 Agent 外层裁决

昨天的课程状态记录了四个已建立事实：expert parallelism 分片权重，token permutation 与两次 all-to-all 连接远端 FFN；最慢 expert 与 batch skew 影响同步尾部，平均负载不保证 p99；prefill 的大批 token/带宽与 decode 的小 GEMM/固定通信开销不同；expert weights、expert cache 与每请求 KV 分开驻留，Agent 多轮重复付费。第 3 篇将它们放在同一张评测表，但不把任何一个微指标误作最终成功。

这里有三个不同的路由层。MoE router 在模型内选 token 的 FFN；serving scheduler 安排设备、batch、cache 和 admission；Agent runtime 根据风险选择模型、工具、审批与 verifier。专家使用率高，只说明某些参数被调用；它不证明引用正确、tool 参数合法、用户有权限，或远端写入成功。与 10 月的 model-routing、SLO 文章相比，今天新增的是 MoE 专属的测量误区：路由分布随 token 内容与模型 checkpoint 改变，专家编号甚至可置换；同一个 E7 名称未必代表相同函数。

因此对照实验应绑定完整版本：权重/checkpoint、tokenizer、router、top-k、overflow/offload 策略、expert placement、attention/KV 配置、采样参数与服务代码。只改一个变量时，才可能把损益归因给它。若同时换了模型训练数据和硬件栈，结论应说‘这两套系统的端到端对比’，不能声称是 MoE 架构本身的因果收益。

03

机制：把性能主张变成可反驳的实验

1. 先设可比较的候选集

最公平的产品问题不是‘同参数谁强’，而是：在相同任务分布、风险约束与可用硬件预算下，哪套系统能以更低全链路成本达到要求的质量？选 dense 与 MoE 候选时，至少记录两种视角：固定质量门槛比较成本/尾延迟；固定成本或 deadline 比较 verified quality。若一方无法通过必要安全/质量门，就不要用低价宣传‘效率优胜’。论文中‘质量相当’的实验是作者在其任务与设备上的报告，不会自动迁移到你的 Agent。

2. 用 Agent 任务切片构造流量

按只读研究、代码修改、结构化 tool call、多语言、长 tool output、罕见错误和高风险外部写入分层。每个 case 保存输入版本、principal、required claims、可用 tools、授权边界、expected effect 和 verifier。复用同一 case 向两套路线发出，保留相同预算、采样与工具环境；生成具有真实到达间隔、上下文长度和并发波动的 load，而不是只跑单用户短 prompt。比较时按 task slice 报 verified success、错误类型、修复轮次与人工介入，避免大量简单 QA 掩盖一小类昂贵的工具失败。

3. MoE trace 只做有边界的诊断

在固定 checkpoint 与路由规则内，记录每层每 expert token counts、router 概率摘要、最大/平均负载、overflow、远端路由比例、all-to-all、expert GEMM shape、expert-cache miss 与 KV occupancy；按 prefill/decode 和 batch size 切片。若 code/JSON 请求的 p99 同时升高且某设备长时间成为 straggler，这些 trace 指向下一步实验：重新 placement、复制热点 expert 或调 admission。它们不证明该 expert‘理解代码’，也不证明它导致了最终 tool-call 错误。诊断需配对复现实验和 outcome 变化。

4. 漂移比较先校验 expert 身份

同一模型权重和 tokenizer 的两段线上流量，expert 使用比例变化可能是任务 mix、工具结果分布或 serving policy 变化。先固定 slice，再比较路由分布与质量。换了 checkpoint 后，专家功能可能旋转或置换；直接比较‘旧 E7 占 12%，新 E7 占 20%’没有稳定语义。可使用固定 probe set、功能响应及必要的对齐分析，但仍以质量和安全回归为主。路由漂移报警是调查入口，不是自动回滚或安全裁决。

5. 终态与成本用同一分母

对每个 accepted task，把模型多轮、共享 GPU 与 expert devices、网络、KV/权重驻留、tool、重试、人工 review 与 verifier 费用记到同一 trace。只有 required claims 有证据、授权满足、远端 effect 已核验时才计 verified success；fail、unknown、超时仍在分母。这样可计算每个经验证结果的总成本，而不是只比每百万 token 单价。延迟从 acceptedAt 到 terminal verdict，另列 TTFT、ITL、queue、collective 与 tool wait；p99 对交互产品尤其重要。

6. 必要的反事实和回归门

固定 prompt/case，仅改变 batch 构成或并发，观察热点和尾延迟；固定负载，仅改变 placement/offload，定位网络或 cache 成本；固定服务条件，仅升级 checkpoint，测质量、路由和 tool format。构造‘禁止发布’与‘允许发布’最小对照、相近 schema 名称、少见语言与长错误日志，确认高风险结论不会因专家热点或 overflow 策略改变。每次 release 预先定义 p95/p99、verified quality、overflow、成本与 hard safety gates；unknown 不能被平均分涂成 pass。

7. 从离线到 shadow/canary

离线评测只能覆盖已知流量。先 shadow 复放脱敏请求，不执行外部写入；再对允许的低风险切片做小流量 canary，监控 route、质量、p99、KV/admission 和成本。若发现长 tool output 导致热点或结构化动作回归，回滚版本/placement，未决外部 effect 另行 reconcile。生产日志应最小化记录原始内容、设置 retention 与权限；专家统计需要的是计数与带版本的摘要，不应复制用户机密。

04

必要数学：同质质量约束下的成本前沿

对路线 r、任务切片 t，设 q(r,t)=N_verified/N_accepted。N_accepted 包含失败、unknown、超时和人工升级；N_verified 仅计独立 verifier 判定 required claims 与业务效果全部满足的任务。若只从‘模型给出答案’的请求里取分母，会把拒绝和修复成本藏起来。matched quality 要求在每个高风险切片上 LCB[q(r,t)]≥τ_t，LCB 是按任务族/来源聚类得到的成功率下置信界，τ_t 是预先确定的最低质量门；还要单独通过安全 hard gates。没有足够样本就标 unknown。

定义 CPVO(r)=C_total(r)/N_verified(r)。C_total 包含 GPU/CPU 时间、网络、内存或 offload、工具、重试、人工和验证。成功数为零时 CPVO 不可用，不能用便宜的失败请求制造‘省钱’。另报告从任务接纳到终态的 p99(L_terminal)；模型单轮 ITL 或平均 tokens/s 不能代替它。只有质量和安全约束同过后，才在 CPVO 与 p99 上讨论 Pareto 改善。

在同一 checkpoint、同一 task slice 内，令第 e 个 expert 的路由份额 P_e=n_e/Σ_j n_j，可计算 R_load=max_e n_e/(Σ_j n_j/E) 来表示本批最热专家相对均值。R_load 大提示 straggler 风险，却不证明任务错误。模型版本改变后，专家 ID 可能置换，P_e 不能逐编号直接相减；先用固定 probes 做功能对齐，或只比较置换不敏感的负载分布与终态结果。

05

对 Agent 系统的影响

能力：MoE 可能用较低活跃 FFN 算术达到高总参数容量，但对 Agent 的价值须体现为更多经验证任务完成，尤其是工具参数、代码修改、引用和多语言切片，而非通用题平均分。

可靠性：router 使用率或均衡不直接证明安全。版本、batch mix、长工具输出引发的负载变化要与结构化输出、越权尝试和终态 effect 联合看；重要权限仍由 runtime broker 与 verifier 保证。

性能：跨设备 all-to-all、expert cache、KV 和最慢专家可能让 MoE 在某些高并发切片上 p99 不如 dense。把 prefill/decode 和多轮 Agent 任务分解，才能找到放置、调度或模型路线的真实瓶颈。

运营：把 matched-quality、CPVO、终态尾延迟和安全 hard gate 变成发布合同。收益只对测试过的流量、硬件和版本成立，新分布需要再校准。

06

取舍与失败模式

  • 用总参数或活跃参数定胜负：二者都不是 quality-matched 的端到端成本；固定任务和门槛再比较。
  • 平均 tokens/s 掩盖 p99：热门 expert、offload miss、长工具结果与排队集中在尾部。
  • 负载均匀当作任务正确：路由可均匀但 tool-call JSON 更差；按业务 slice 看 verified outcome。
  • 跨 checkpoint 逐 expert 比较：ID 可置换/功能漂移；先对齐 probe，最终仍看结果。
  • 只选简单题 matched quality：代码、语言、工具和罕见错误可能反转结论；要求风险切片逐一过门。
  • 失败请求从成本分母消失：repair turns、人工和 unknown 必须计入总费用。
  • 把论文百分比当本地 SLA：硬件、版本、batch 与模型质量都不同；本地 shadow/canary 实测。
  • 内部 expert 充当授权者：它只是计算路径，不能放宽 tool 权限或独立 verifier。
07

可复用的技术判断

  • MoE 与 dense 的公平比较先匹配任务质量与安全门，再比较 CPVO 和终态 p99。
  • 按代码、语言、工具调用、长观察与高风险效果切片；平均题分和 tokens/s 不够。
  • 同版本内 expert 负载与 overflow 可诊断热点；跨 checkpoint 的 expert ID 不能直接赋予稳定语义。
  • 所有失败、unknown、修复与人工介入计入同一个 accepted-task 成本账本。
  • 内部 router 是计算机制；Agent 的权限、完成和发布仍由外部控制面与 verifier 裁决。
08

MoE Looks Cheaper. How Do You Prove an Agent Benefits?

Turn MoE's active-parameter story into a verifiable systems judgment through matched quality, task slices, routing drift, and end-to-end cost.

2026-10-1720 min readMoE evaluation / Matched quality / Routing drift / Tail latency / Verified outcome
01

Today's proposition

A team replaces an agent's primary model with an MoE. Fewer parameters activate per token, a general offline score improves, and average tokens per second rises. After launch, long tool logs create a hot expert that worsens p99. Rare error cases produce more malformed tool-call JSON and require extra repair turns. The per-request bill falls, yet the cost of each verified completed task may rise.

The first two parts make this unsurprising. Part 1 showed that top-k sparsifies FFN arithmetic while capacity, overflow, and gradient exposure constrain training. Part 2 traced expert parallelism through token permutation, two all-to-alls, slowest-expert synchronization, and distinct residency ledgers for expert weights and per-request KV. Today we do not repeat those formulas or data paths. The systems question is how to compare MoE fairly with dense models, detect routing drift without anthropomorphizing expert IDs, and decide whether a release is safe.

Core judgment: 'MoE is cheaper' is conditional on quality, workload, hardware, risk, and time. The comparison unit is not parameters or one request, but tail latency and cost per verified outcome under the same task contract and safety gates.
02

From expert routing to an outer agent verdict

The saved curriculum state established four facts. Expert parallelism shards weights, while token permutation and two all-to-alls reach remote FFNs. The slowest expert and batch skew determine synchronized tails, so average balance cannot guarantee p99. Prefill has many tokens and bandwidth pressure; decode has small GEMMs and fixed communication overhead. Expert weights, expert cache, and per-request KV are separate residency ledgers, repaid over an agent's turns. Part 3 puts them in one evaluation without treating any micro-metric as final success.

Three routing layers remain distinct. The MoE router chooses token FFNs inside the model. The serving scheduler controls devices, batches, caches, and admission. The agent runtime chooses a model, tools, approvals, and verifier by risk. High expert utilization says certain weights were invoked; it proves nothing about citations, valid tool arguments, user permission, or a committed remote write. Compared with the earlier model-routing and SLO lessons, MoE adds a specific measurement trap: route distributions change with token content and checkpoint, and expert IDs can be permuted. A label such as E7 does not necessarily denote the same function after retraining.

Bind a complete version in each comparison: weights and checkpoint, tokenizer, router, top-k, overflow and offload policy, expert placement, attention and KV configuration, sampling, and serving code. When only one variable changes, attribution is more credible. If training data and hardware stack both change with the model, report an end-to-end comparison of two systems, not a causal benefit of MoE architecture itself.

03

Mechanism: make the performance claim falsifiable

1. Select candidates that can be compared

The product question is not 'which model wins at equal total parameters?' It is which system reaches required quality at lower full-chain cost under the same task distribution, risk constraints, and available hardware budget. Keep two views. At a fixed quality gate, compare cost and tail latency. At a fixed cost or deadline, compare verified quality. If one route cannot pass mandatory safety or quality gates, a lower price is not an efficiency win. A paper's quality-matched comparison reports its authors' tasks and devices; it does not automatically transfer to your agent.

2. Construct agent-task traffic slices

Stratify read-only research, code edits, structured tool calls, multilingual work, long tool output, rare errors, and high-risk external writes. Each case stores input version, principal, required claims, available tools, authority boundary, expected effect, and verifier. Replay a paired case through both systems with the same budget, sampling, and tool environment. Reproduce realistic arrival intervals, context lengths, and concurrency spikes, not just single-user short prompts. Report verified success, error types, repair turns, and human interventions by task slice so abundant easy QA does not conceal a small class of expensive tool failures.

3. Bound what an MoE trace can diagnose

Within a fixed checkpoint and router rule, record token counts by layer and expert, summaries of router probabilities, max-to-mean load, overflow, remote-route fraction, all-to-all time, expert GEMM shape, expert-cache misses, and KV occupancy. Slice by prefill or decode and batch size. If code or JSON requests develop high p99 while one device repeatedly becomes the straggler, the traces suggest a next experiment: change placement, replicate a hot expert, or adjust admission. They do not prove the expert 'understands code' or caused the final malformed tool call. Attribution needs a paired reproduction and an outcome change.

4. Check expert identity before measuring drift

Within the same weights and tokenizer, a changed expert-use histogram may reflect a task-mix shift, new tool results, or a serving-policy change. Fix the slice before comparing routes and quality. After changing checkpoint, expert functions can rotate or permute. 'Old E7 handled 12%; new E7 handles 20%' has no stable semantic interpretation on its own. A fixed probe set, functional responses, and careful alignment analysis can help investigation. Outcome and safety regressions remain primary. A routing-drift alert starts a diagnosis; it is not itself an automatic rollback or a safety verdict.

5. Use one denominator for terminal states and cost

For each accepted task, charge model turns, shared and expert GPUs, network, KV and weight residency, tools, retries, human review, and verifier work to the same trace. Count verified success only when required claims have evidence, authorization is satisfied, and the remote effect is confirmed. Failures, unknowns, and timeouts remain in the accepted-task denominator. This yields cost per verified outcome rather than price per million tokens. Measure latency from acceptedAt to terminal verdict, with TTFT, ITL, queue, collective, and tool wait as subcomponents. p99 matters for interactive service.

6. Run counterfactual and regression gates

Hold prompt and case fixed while changing batch mix or concurrency to expose hotspots and tail latency. Hold load fixed while changing placement or offload to isolate network and cache costs. Hold serving fixed while updating checkpoint to test quality, routing, and tool format. Use paired 'must not deploy' versus 'may deploy' cases, near-identical schema names, rare languages, and long error logs. Check that high-risk conclusions do not depend on a hot expert or overflow policy. Define p95 and p99, verified quality, overflow, cost, and hard safety gates before a release. Unknown must not be averaged into pass.

7. Move from offline to shadow and canary

Offline evaluation covers only known traffic. First shadow de-identified requests without external writes. Then canary only approved lower-risk slices at small volume while monitoring routes, quality, p99, KV and admission, and cost. If long tool output creates a hotspot or structured-action regression, roll back model version or placement and separately reconcile unresolved external effects. Production telemetry should minimize raw content and enforce retention and access controls. Expert diagnostics usually need counts and versioned summaries, not copies of user secrets.

04

Essential mathematics: a cost frontier under quality gates

For route r and task slice t, define q(r,t)=N_verified/N_accepted. Accepted tasks include failures, unknowns, timeouts, and human escalations. Verified tasks require an independent verdict that all required claims and business effects hold. Using only cases where the model produced an answer as the denominator hides refusals and repair cost. Matched quality requires LCB[q(r,t)]≥τ_t for each high-risk slice. LCB is a lower confidence bound clustered by source or task family; τ_t is a pre-registered quality floor. Separate hard safety gates must also pass. Insufficient samples imply unknown.

Define CPVO(r)=C_total(r)/N_verified(r). Total cost includes GPU and CPU time, network, memory or offload, tools, retries, humans, and verification. With zero verified successes, CPVO is undefined; cheap failed requests cannot establish savings. Report p99(L_terminal) from task acceptance to terminal verdict. A model's one-turn ITL or average tokens per second cannot replace it. Discuss a Pareto improvement in CPVO and p99 only after both routes meet quality and safety constraints.

Within one checkpoint and one task slice, expert e's route share is P_e=n_e/Σ_j n_j. A batch hotspot ratio is R_load=max_e n_e/(Σ_j n_j/E), comparing the hottest expert with the mean across E experts. High R_load suggests straggler risk but does not prove an outcome error. After a model-version change, expert IDs may permute; P_e cannot be subtracted by ID without alignment. Fixed functional probes may help, or one can compare permutation-invariant load statistics and terminal outcomes.

05

Implications for agent systems

Capability: MoE may offer larger total capacity with less active FFN arithmetic, but agent value appears as more verified task completions, particularly in tool arguments, code edits, citations, and multilingual slices—not just a higher average general benchmark score.

Reliability: balanced router use does not prove safety. Compare version, batch-mix, and long-tool-output load changes with structured-output validity, unauthorized-action attempts, and terminal effects. Runtime brokers and verifiers still own consequential permissions.

Performance: cross-device all-to-all, expert cache, KV, and a hot straggler may make MoE worse than dense at p99 for some concurrent slices. Decompose prefill, decode, and the multi-turn agent task before deciding whether placement, scheduling, or model route is the bottleneck.

Operations: make matched quality, CPVO, terminal tail latency, and hard safety gates a release contract. Any gain is bounded to the tested traffic, hardware, and version; new distributions need recalibration.

06

Trade-offs and failure modes

  • Total or active parameters decide the winner: neither is end-to-end cost at matched quality. Fix tasks and gates first.
  • Average tokens per second hides p99: hot experts, offload misses, long tool results, and queues concentrate in the tail.
  • Balanced load treated as correctness: routes may be even while tool-call JSON worsens. Inspect verified outcomes by business slice.
  • Expert IDs compared across checkpoints: IDs can permute and functions drift. Align with probes if necessary; results still decide.
  • Quality matched only on easy questions: code, languages, tools, and rare errors can reverse the conclusion. Require gates by risk slice.
  • Failed requests disappear from the cost denominator: repair turns, human work, and unknown states belong in total cost.
  • Paper speed percentages used as local SLAs: hardware, versions, batches, and quality differ. Measure through shadow and canary runs.
  • An internal expert becomes an authority: it is a compute path, not permission to weaken tool policy or independent verification.
07

Reusable technical judgments

  • Match task quality and hard safety gates before comparing MoE and dense by CPVO and terminal p99.
  • Slice code, languages, tool calls, long observations, and high-risk effects; aggregate benchmark scores and tokens per second are insufficient.
  • Within one version, expert load and overflow diagnose hotspots. Across checkpoints, expert IDs lack automatic stable semantics.
  • Keep failures, unknowns, repair, and human work in one accepted-task cost ledger.
  • The internal router is compute; external control planes and verifiers still decide agent authority, completion, and release.
08

Primary sources and evidence tiers

  • Mixtral of Experts — the authors describe a decoder-only top-two MoE and task results; those comparisons are not guarantees for every agent.
  • OLMoE — the authors release weights, data, code, and logs and analyze specialization in their model; this does not grant universal semantics to an expert number.
  • DeepSeek-V3 Technical Report — the authors report another load-balancing and architectural choice; training and inference figures belong to their setting.
  • ST-MoE and Expert Choice Routing — the authors study stability, transfer, and alternate routing, illustrating why total parameter count is insufficient.
  • DeepSpeed-MoE — the authors compare training and inference costs against quality-relevant baselines; reported acceleration is not a local replication.
  • τ-bench — the authors judge tool agents by final database state and repeated trials. This article borrows the terminal-state and consistency lens; the benchmark was not built specifically for MoE.

The matched-quality task contract, route-drift interpretation, CPVO and p99 release gates, and authority separation are editorial engineering design built from these primary sources and need validation in a particular service.

09

Series complete; the remaining boundary is empirical

Three-part synthesis: Part 1 built sparse training from token hidden states, top-k, capacity, overflow, and balancing loss. Part 2 traced expert placement, two all-to-alls, hot stragglers, prefill versus decode, and separate weight and KV residency. Part 3 returns those internals to matched-quality agent tasks, comparing verified success, CPVO, terminal p99, and hard safety gates by slice. 'Few active parameters' is now a systems hypothesis to test, not a performance conclusion.

Revalidation remains: model revisions, batch mix, tool output, and hardware change routes and the cost frontier. A stable-looking expert ID is not stable function. MoE Internals Part 3/3 is complete.
