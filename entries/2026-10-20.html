每个 token 都更快了，为什么 Agent 的 p99 反而变差？

从请求队列、continuous batching、KV 驻留和 prefill/decode 冲突出发，完成推理优化三部曲的端到端验收。

01

今日命题

团队上线 speculative decoding 与 4-bit 权重后，离线单请求 benchmark 的每 token 时间显著下降。线上 Agent 的 p99 终态却变差：检索结果一到，大段 prefill 插入 decode 队列；长会话占住 KV；draft 额外占用 GPU；一些请求反复被抢占并重算。单个 kernel 的节省是真的，但等待、排队与资源竞争把收益吃掉了。

今天的问题不是再解释一次 p/q 接受证明或量化尺度，而是：服务系统怎样让多条请求在有限计算与显存上持续前进，并把局部加速兑现为用户可感知的 TTFT、ITL、p99 与任务完成率？最关键的转变是把‘模型速度’当作调度输入，而不是发布结论。推理系统需要知道哪个请求待 prefill、哪个待 decode、谁的 KV 仍驻留、谁已到工具边界，以及哪个服务等级的 deadline 正在逼近。

核心判断：吞吐是单位时间完成的工作量，资源利用率是可用容量的占用比例；goodput 是满足时延与质量条件的完成量；Agent 优化最终要以经验证的终态和尾延迟结账。
02

承接前两篇：算法收益为何会丢在队列里

第 1 篇的 speculative decoding 在 target 的目标采样规则下减少串行 target 步数，但增加 draft 计算、整段核验、候选 KV 和拒绝回滚。第 2 篇把权重、激活和 KV 量化拆成三本账：W4A16 可能减轻低 batch decode 的权重带宽，W8A8 可能改变 prefill GEMM，低位 KV 可能释放并发空间；它们的 kernel 与误差代价各异。把这些组件一起上线，scheduler 看到的任务大小与资源占用会改变，不能把单项 speedup 相乘。

一个 Agent 请求也不是一条连续输出流。它可能经历 prompt prefill、几个 token 的 tool-call JSON、等待外部工具、把长结果拼回上下文、再次 prefill、最后生成答案。工具等待不消耗同样的 GPU 计算，却可能保留 KV 或占住运行时槽位；工具返回又会造成突发 prefill。与其给整条 Agent trace 一个平均 tokens/s，更应把每次模型阶段、工具等待、排队和验证分别计时，并把同一请求的阶段用 trace ID 串起来。

03

机制：从请求入队到终态

1. 准入与迭代级批处理

传统静态 batch 等一组请求同时开始并一起结束；生成长度不同会让短请求等长请求。continuous batching 在每个 decode 迭代重新组批：完成者退出，等待者在资源允许时加入。Orca 论文提出 iteration-level scheduling 与 selective batching，是这一方向的重要一手资料。但‘每步重组’不是免费午餐：调度开销、KV 页面映射、kernel shape 改变以及抢占都要计入。

2. Prefill 与 decode 争用同一设备

Prefill 一次处理许多输入 token，倾向大矩阵乘和高计算占用；decode 每条序列通常每迭代前进少量 token，并反复读取权重与 KV。一个长 prefill 若整块插入共享 GPU，会让已在流式输出的请求停顿，形成 ITL 尖峰。反过来只优待 decode，新请求的 TTFT 会恶化。chunked prefill 把长输入分成可调度小块，与 decode 步交错；它改善干扰的可能性取决于块大小、kernel 效率和额外切分成本。Sarathi 与 Sarathi-Serve 的实验报告了特定设置的吞吐/延迟折中，不构成对所有负载的通用保证。

3. KV 是准入门，不是‘剩余显存’注脚

每个活跃请求保留各层历史 K/V；总容量随请求数和长度上升。按最大输出长度预留会浪费，完全不预留则可能在生成中途耗尽。分页式 KV 管理可减少连续块碎片并按需分配，但还会有 page table、内外部碎片和访存代价。PagedAttention/vLLM 论文报告其服务设计的吞吐收益；编辑性设计判断是：调度器须同时跟踪当前驻留和未来增长，必要时限制准入、抢占或交换/重算，而不是把 OOM 当作正常控制流。任何 KV 回收都必须与输出、位置和工具状态一致。

4. 工具边界打断批处理假设

模型输出一个已确认的工具调用后，Agent runtime 可暂停模型执行；工具可能毫秒返回，也可能很久。持续保留 KV 可加快恢复，却占据别人需要的显存；驱逐 KV 释放容量，恢复时可能要重新 prefill 历史。两种成本应按工具等待时长、会话长度和命中率决定，不能只看缓存命中。工具结果若改变 prompt，先前可复用的前缀仅限真正字节与语义策略一致的部分。draft 的未核验 token 仍不能穿过工具边界。

5. 分离 prefill/decode 是另一种资源配置

若两阶段负载差异很大，可在不同 GPU 池分别执行 prefill 与 decode。DistServe 作者报告它在其测试设置中通过分离干扰提高 goodput；代价是 KV/激活跨设备传输、网络排队、资源闲置风险与更复杂的故障恢复。单机 chunked prefill 与分离部署不是谁‘更先进’的排序，而是对阶段混合、SLO 和硬件拓扑的不同选择。

6. 把公平性写进调度策略

只最大化总 tokens/s，长 prompt 或大客户可能占用资源，短请求长期等候；只按最短作业优先，也可能饿死长任务。可用队列等待上限、租户权重、aging、deadline 与显存预算组合，但预估输出长度不准。超时、抢占和取消必须有清晰语义：已提交 token 不回滚成另一条文本，已发出的外部 action 不可由 GPU scheduler 擅自重试。调度器只决定计算顺序；Agent runtime 才负责外部副作用。

04

必要数学：从吞吐到 goodput 和尾延迟

对一个请求定义 TTFT=T_queue+T_prefill+T_first_decode。T_queue 是首次 token 前的全部调度等待（包括准入、分块间和首次 decode 前），T_prefill 是实际输入计算，T_first_decode 是首次生成计算；再快的低位 kernel 也无法单独消除前两项。若输出 n 个 token，可把相邻已提交 token 的 n−1 个间隔记作 ITL₁…ITLₙ₋₁，报告分位数而不是只报平均。Agent 终态延迟还需加上多次模型调用、工具等待、重试和 verifier，不能由一次请求的 TTFT/ITL 直接推得。

设窗口内完成 N 个请求，其中满足延迟 SLO 的有 N_slo，且通过任务质量/安全门的有 N_verified，则定义一个本文使用的操作性指标 goodput_verified=N_both/Δt：N_both 是同时满足两组条件的请求数，Δt 是观测秒数。论文中的 goodput 定义和 SLO 集可能不同，比较时要写明口径。吞吐 N/Δt 上升而 N_both/Δt 下降，就是‘更多工作、更少可用结果’。

KV 准入可用必要条件 M_weights+Σᵢ M_KV(Tᵢ)+M_temp≤M_device 检查：Σ 覆盖活跃请求，Tᵢ 是各自历史长度，M_temp 包括激活、kernel workspace、draft 与传输 buffer。这个不等式不保证低延迟，只排除明显超配；还要给未来输出与突发 prefill 留余量。Little 定律的稳态近似 并发 L≈到达率 λ×平均在系统时间 W 提醒我们：队列等待变长会让在途请求增多；只有已准入或保留缓存的请求占 KV，若它们与队列争资源才可能形成正反馈。它不替代测量非稳态突发与 p99。

05

Agent 系统验收：把三种优化放进同一实验

建一个固定任务合同和流量重放：保留 prompt、工具返回大小与时间、语言、输出长度、并发曲线、模型版本、sampling policy、硬件和权限；为每条 trace 记录请求入队、prefill 分块、decode、KV 占用、抢占、工具暂停/恢复、终态验证。先以原目标模型加原调度器建基线，再分别启用 speculative、权重/激活/KV 量化、scheduler 策略，最后测组合。量化后的 target 已是新目标分布；即使 speculative 对这个新 target 精确，也不等于保留原 FP16 分布。

切片至少包括短工具 JSON、长检索与大工具日志、代码、多语言、长会话，以及突发并发。读数不止模型 tokens/s：每个切片的 verified success、schema 与权限失败、TTFT、ITL p99、Agent 终态 p99、稳定 goodput、峰值 KV、抢占/重算率、每个正确结果的总成本。若总体均值变好却高风险写操作回归，不能靠平均值放行。外层 runtime 对已提交动作继续做 authorization、幂等与业务 verifier。

上线门槛应是预先声明的：质量与安全不得越线，关键切片的尾延迟不恶化，稳定负载下可用结果/秒和成本达到目标。若 draft 接受率在工具 JSON 上低或低位 KV 损害长距离证据，可按任务类型路由回基线；但路由规则本身也要记 trace、测回退率与成本。所谓‘推理优化成功’，是这些终态条件成立，不是某张 GPU 图漂亮。

06

取舍与失败模式

  • 只测空载吞吐：没有队列和突发，测不到 prefill 干扰与尾延迟；重放真实到达过程。
  • 无限延长 batch：可提高算力利用率，却推迟新请求 TTFT、挤满 KV；同时检查稳定性和公平性。
  • 把工具等待会话永远留在 GPU：恢复快但占容量；驱逐又可能重算，需按等待分布选择。
  • 把 paged KV 当作无限内存：它缓解分配碎片，不取消物理容量、带宽和质量门槛。
  • 混合 prefill/decode 不设预算：大 prefill 阻塞流式 decode；过度 decode 优先则饿死新请求。
  • 把每项加速比相乘：draft、低位 kernel 与 batch 争同一计算/显存，组合必须实测。
  • 把 timeout 当作可重试业务动作：GPU 计算可重调度，外部工具副作用只能按 runtime 的幂等合同处理。

分离部署适合足够稳定且阶段差异明显的负载；单池交错可能在小规模或不稳定流量下更简单。两者都需要以同一质量门和 SLO 比较。

07

可复用的技术判断

  • continuous batching 在迭代边界重组请求；关键资源约束是计算预算和可增长的 KV 驻留。
  • prefill 与 decode 对硬件的需求不同，chunking 或分离部署要用 TTFT、ITL 和 p99 的共同变化判断。
  • 工具暂停/恢复使 Agent 成本跨越多个模型调用；保留 KV 与重算 prefill 是有条件的选择。
  • speculative 对量化 target 的精确性不等于原 FP16 模型的精确性；三项优化的收益不能相乘。
  • 以 verified goodput、关键切片质量、尾延迟、公平性和终态成本决定是否上线。

Inference Optimization Internals · Part 3 of 3

Every Token Is Faster. Why Is the Agent's p99 Worse?

Trace request queues, continuous batching, KV residency, and prefill/decode contention, then close the inference-optimization series with end-to-end agent acceptance.

2026-10-2020 min readLLM serving / Continuous batching / Chunked prefill / KV residency / Goodput / Agent p99
01

Today's proposition

A team ships speculative decoding and four-bit weights. Its single-request offline benchmark shows lower time per token. Production agent p99 nevertheless worsens. Retrieved evidence arrives and creates a large prefill that interrupts an active decode batch; long sessions occupy KV memory; the draft model uses extra GPU resources; and some requests are repeatedly preempted and recomputed. The kernel-level savings are real, but waiting, queues, and resource contention consume them.

Today's question is not another proof of p/q acceptance or another derivation of a quantization scale. It is how a serving system makes many requests progress under finite compute and memory, and converts local acceleration into user-visible time to first token, inter-token latency, p99, and task completion. The conceptual shift is to treat model speed as an input to the scheduler, not as a release conclusion. The server must know which request needs prefill, which needs decode, whose KV remains resident, who is paused at a tool boundary, and whose service deadline is approaching.

Core judgment: throughput counts completed work per unit time, utilization measures occupied capacity; goodput counts completions that meet latency and quality conditions. Agent optimization ultimately settles on verified terminal outcomes and tail latency.
02

How the first two parts meet the queue

Part 1's speculative decoding reduces serial target steps under a specified target sampling rule, but adds drafting, block verification, candidate KV, and rejection rollback. Part 2 separated three quantization ledgers. W4A16 may relieve weight bandwidth in low-batch decode; W8A8 can change the prefill matrix-multiply path; low-bit KV may free concurrency capacity. Their kernels and error costs differ. Shipping them together changes the job sizes and resource footprint seen by the scheduler. Their isolated speedup numbers cannot simply be multiplied.

An agent request is not one uninterrupted stream. It may prefill a prompt, emit a few tokens of tool-call JSON, wait for an external tool, append a long result, prefill again, and finally generate an answer. Tool waiting uses little of the same GPU compute but may retain KV or consume runtime slots. Tool returns create bursty prefills. Instead of assigning the whole trace an average tokens-per-second figure, time every model phase, tool wait, queue, and verification separately. Carry a trace ID across them so the request-level outcome remains attributable.

03

Mechanism: from admission to terminal outcome

1. Admission and iteration-level batching

A static batch begins and ends as a cohort. Unequal generation lengths make short requests wait for long ones. Continuous batching reforms the batch at each decode iteration: completed requests leave and waiting requests enter when resources permit. Orca introduced iteration-level scheduling and selective batching as a key early system design. Rebatching is not free. Scheduling work, KV-page mapping, changing kernel shapes, and preemption all consume time.

2. Prefill and decode contend for a device

Prefill processes many input tokens at once and tends toward large matrix multiplies with high compute occupancy. Decode advances a sequence by a small number of tokens per iteration while repeatedly reading weights and KV. A long prefill inserted as one block on a shared GPU can stall streams already decoding and create an inter-token-latency spike. Giving absolute priority to decode reverses the problem: new requests wait for their first token. Chunked prefill divides long inputs into schedulable pieces that can interleave with decode steps. The benefit depends on chunk size, kernel efficiency, and partition overhead. Sarathi and Sarathi-Serve report throughput–latency trade-offs for their evaluated configurations, not a universal guarantee.

3. KV is an admission gate

Every active request retains historical keys and values for each layer, so total occupancy rises with both sequence length and concurrency. Reserving for maximum possible output wastes memory; reserving nothing risks exhaustion midway through generation. Paged KV management reduces contiguous-allocation fragmentation and allocates on demand, but adds page mapping and access costs. The PagedAttention/vLLM paper reports throughput gains for its design. The editorial system implication is that a scheduler should track resident bytes and plausible future growth, then limit admission, preempt, swap, or recompute when necessary instead of treating an out-of-memory error as normal control flow. KV recovery must stay consistent with emitted tokens, positions, and tool state.

4. Tool boundaries interrupt batching assumptions

After the model emits a confirmed tool call, the agent runtime can pause model execution. A tool may return quickly or after a long delay. Retaining KV accelerates resumption but occupies memory needed by other users; evicting KV frees capacity but may require re-prefilling the history. Choose based on tool-wait distribution, session length, and actual reuse, not hit rate alone. When the tool result changes the prompt, reusable prefix state is limited to the portion that truly matches the prior bytes and policy. Unverified draft tokens still cannot cross the tool boundary.

5. Disaggregating prefill and decode

If the two phases have very different resource profiles, they can run in distinct GPU pools. The DistServe authors report improved goodput from avoiding interference in their tested setting. The trade is KV or activation transfer across devices, network queues, potentially idle capacity, and harder failure recovery. Single-pool chunked prefill and disaggregation are not ranks on a maturity ladder. They are different choices for workload mix, service objectives, and hardware topology.

6. Make fairness explicit

Maximizing aggregate tokens per second can let long prompts or large tenants monopolize resources while small requests wait. Pure shortest-job priority can starve long jobs. Queue-wait caps, tenant weights, aging, deadlines, and memory budgets can be combined, but output lengths are uncertain. Timeout, preemption, and cancellation need clear semantics: already committed text does not silently roll back into another answer, and a GPU scheduler must not retry an external action on its own. The scheduler orders compute; the agent runtime owns side effects.

04

Essential mathematics: throughput, goodput, and tails

For one model request define TTFT=T_queue+T_prefill+T_first_decode. T_queue includes all scheduling waits before the first token (admission, gaps between chunks, and the wait before first decode), T_prefill is actual input computation, and T_first_decode computes the initial token. A faster low-bit kernel cannot by itself remove the first two terms. For n output tokens, record the n−1 inter-token intervals ITL₁ through ITLₙ₋₁ between committed tokens and report their distribution, not only a mean. Agent terminal latency additionally includes several model calls, tool waits, retries, and a verifier; it cannot be inferred directly from one call's TTFT and ITL.

Suppose N requests complete during an observation window, N_slo meet a latency objective, and N_verified pass task-quality and safety gates. Define an operational metric for this article, goodput_verified=N_both/Δt, where N_both satisfies both conditions and Δt is elapsed seconds. Papers may define goodput and their SLO set differently; declare the denominator and thresholds before comparison. An increase in raw throughput N/Δt with a decrease in N_both/Δt means the server did more work but delivered fewer usable results.

A necessary KV admission check is M_weights+Σᵢ M_KV(Tᵢ)+M_temp≤M_device. The sum covers active requests; Tᵢ is each history length. M_temp includes activations, kernel workspace, drafting, and transfer buffers. This inequality excludes obvious overcommit but does not guarantee latency; leave headroom for future output and bursty prefills. Little's law gives the steady-state approximation in-flight L≈arrival rate λ×mean system time W. Longer queue residence increases in-flight requests, but only admitted or cache-retaining requests occupy KV; competition between them can reinforce pressure. It does not replace measurement of non-stationary bursts or p99.

05

Agent acceptance: test all three optimizations together

Build a fixed task contract and a traffic replay that preserves prompts, tool-return sizes and timing, languages, output lengths, concurrency curve, checkpoint, sampling policy, hardware, and permissions. For every trace, record arrival and admission, prefill chunks, decode steps, KV occupancy, preemptions, tool pause and resume, and terminal verification. Start with the original target and scheduler as baseline. Enable speculation, weight/activation/KV quantization, and scheduling changes separately, then measure the combination. A quantized target is a new target distribution. Even exact speculative sampling relative to that new target does not preserve the original FP16 distribution.

Include short tool JSON, long retrieval and large tool logs, code, multiple languages, long sessions, and bursty concurrency. The scorecard extends beyond model tokens per second: verified success by slice, schema and authority failures, TTFT, ITL p99, agent-terminal p99, stable goodput, peak KV, preemption or recomputation rate, and total cost per correct outcome. A better overall average does not excuse a regression on a high-risk write slice. The outer runtime still authorizes committed actions and applies idempotency and business verifiers.

Declare release gates in advance: quality and safety floors must hold, important slices must not regress at the tail, and usable outcomes per second and cost must hit targets under stable load. If draft acceptance is poor for tool JSON or low-bit KV hurts long-range evidence, route those slices back to baseline. Record the routing policy itself in traces, including fallback rate and cost. Inference optimization succeeds when those terminal conditions hold, not when a GPU chart looks attractive.

06

Trade-offs and failure modes

  • Benchmark only an empty server: no queues or bursts means no prefill interference or tail behavior. Replay realistic arrivals.
  • Grow batches without bound: utilization can improve while new-request TTFT and KV pressure worsen. Check stability and fairness together.
  • Keep every tool-waiting session on GPU: resumption is quick but occupancy is costly; eviction may require re-prefill. Use the wait distribution.
  • Treat paged KV as infinite memory: it mitigates allocation fragmentation, not physical capacity, bandwidth, or quality constraints.
  • Mix prefill and decode with no budget: large prefills stall streaming; absolute decode priority can starve arrivals.
  • Multiply isolated speedup ratios: drafting, low-bit kernels, and batching compete for the same compute and memory. Measure the combination.
  • Treat timeout as permission to retry an action: GPU compute can be rescheduled; external side effects obey the runtime's idempotency contract.

Disaggregation can suit sufficiently stable workloads with distinct phase profiles; interleaving in one pool may be simpler at smaller scale or with variable traffic. Compare both under the same quality gates and service objectives.

07

Reusable technical judgments

  • Continuous batching reforms work at iteration boundaries; compute budget and growing resident KV are the central constraints.
  • Prefill and decode stress hardware differently. Judge chunking or disaggregation through TTFT, ITL, and p99 together.
  • Tool pause and resume spread agent cost across several model calls; retaining KV versus re-prefilling is a conditional choice.
  • Exact speculation against a quantized target is not exactness against the original FP16 target. Do not multiply isolated speedups.
  • Release on verified goodput, quality for important slices, tail latency, fairness, and terminal cost.
08

Primary sources and evidence tiers

  • Orca: A Distributed Serving System for Transformer-Based Generative Models — this systems paper introduces iteration-level scheduling and selective batching; measurements are from the authors' setup.
  • Efficient Memory Management for Large Language Model Serving with PagedAttention — the authors present paged KV management and report gains in their serving environment.
  • SARATHI and Sarathi-Serve — the authors study the throughput–latency trade-off from chunked prefill interleaved with decode.
  • DistServe — the authors propose prefill/decode disaggregation and report goodput under their SLO and hardware assumptions.
  • Fast Distributed Inference Serving for Large Language Models — the authors study preemption and scheduling for generation; cited here as systems background for fairness and tails.

The operational goodput_verified metric, agent tool boundaries, authorization, and release gates are this article's editorial engineering framework, not a unified measure or product guarantee established by all these papers.

09

Three-part synthesis and the next path

Series complete: Part 1 showed how drafting, target verification, and positive-residual correction preserve a specified target sampling distribution while keeping unverified tokens away from tools. Part 2 separated weight, activation, and KV quantization, including scales, outliers, kernels, and quality risk. Part 3 put those local optimizations inside admission, prefill/decode contention, KV residency, tool pauses, and fair scheduling, then accepted them through agent verified goodput, p99, and total cost. These layers are not substitutes: algorithmic exactness, numerical approximation quality, and systems behavior need independent evidence.

Next path, not unfinished work: how retrieval candidates, reranking, and evidence attribution form a reliable information ingress outside the model context. A future issue can begin Retrieval/RAG Internals as a new systematic path rather than replaying serving equations.
